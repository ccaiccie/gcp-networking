Lesson 1: Dynamic NICs in the same VPC network

Domain 2 — Implementing a VPC network

Primary source: https://docs.cloud.google.com/vpc/docs/multiple-interfaces-concepts

Problem and architecture

Dynamic NICs are IEEE 802.1Q VLAN subinterfaces under a parent vNIC. They can be added or removed without recreating an instance, can raise total interfaces to 16, and now can coexist in the same VPC as other interfaces. Each interface in the same VPC must use a unique subnet; Dynamic NICs share parent bandwidth and queues. They don't support RDMA-profile VPCs, Windows drivers, GPU instances, firewall endpoints/packet-intercept features, or certain edge-security functions.

flowchart LR
 A[Client / source] --> B[Dynamic NICs in the same VPC network]
 B --> C[Google Cloud control or data plane]
 C --> D[Destination / observed outcome]
 D -. logs / health / policy .-> B

What to notice: separate the object that selects or governs traffic from the actual packet path. For troubleshooting, prove the control-plane configuration first, then verify the data-plane observation at each hop.

Control plane, packet flow, and design choices

The design starts by identifying scope, ownership, and the resource that makes the forwarding or policy decision. Build the expected path from source to destination, including any proxy termination, encapsulation, route exchange, policy evaluation, or logging boundary. Avoid assuming that reachability proves policy correctness: a path can work while bypassing the intended observation or security point.

DecisionPreferred approachRisk to test
Centralized governanceUse project/organization-scoped controls where the feature supports themCross-project IAM and ownership
RolloutStage, observe, then enforceHidden dependencies and asymmetric paths
OperationsCorrelate configuration with logs/metricsSampling, metadata, health, or unsupported combinations

Prerequisites, limits, security, and HA

Verify API enablement, IAM, resource scope, release stage, quotas, supported endpoint types, address families, and regional/global compatibility before deployment. Preview features should be treated as pre-GA. Security design must preserve least privilege and make trust boundaries explicit. For availability, identify whether failure is zonal, regional, per-appliance, per-backend, or control-plane only, and test convergence rather than inferring it from resource health.

Operations and troubleshooting

  1. Describe the relevant resources and confirm scope/project/region.
  2. Verify IAM and API enablement.
  3. Trace the expected route/policy/load-balancer decision.
  4. Inspect product logs and metrics, accounting for sampling.
  5. Test a known-good and known-bad flow.
  6. Check release-stage limitations and quotas before changing architecture.

Scenario

A platform team deploys this capability and reports that traffic is reachable but behavior differs between two clients. Compare client attributes, project/region, address family, selected policy/route/backend, and observation point. The exam-quality answer is usually the one that explains the actual decision point rather than adding an unrelated route or firewall rule.

Exam anchors

  • Know whether the feature proxies, encapsulates, routes, filters, or only observes traffic.
  • Know its scope and the project where logs/policies live.
  • Know at least one unsupported or pre-GA boundary from the primary source.

Lesson 2: App Engine Direct VPC egress visibility with VPC Flow Logs

Domain 5 — Managing, monitoring, and troubleshooting network operations

Primary source: https://docs.cloud.google.com/vpc/docs/flow-logs

Problem and architecture

VPC Flow Logs now includes App Engine resources configured with Direct VPC egress. Sampling is packet-based, aggregated by 5-tuple, then optionally secondary-sampled and filtered. Logs land in the reporting VPC project's Cloud Logging; Shared VPC therefore centralizes these records in the host project. Egress sampling occurs before egress firewall evaluation, while ingress sampling occurs after ingress firewall evaluation.

flowchart LR
 A[App Engine Direct VPC egress] --> B[VPC packet sampling]
 B --> C[5-tuple aggregation]
 C --> D[Cloud Logging]
 D -. filters / metadata .-> B

What to notice: sampling position relative to firewall evaluation explains why denied egress can appear while denied ingress might not.

Control plane, packet flow, and design choices

Choose organization, VPC, or subnet scope based on governance. Aggregation intervals range from seconds to minutes; secondary sampling and metadata selection affect volume and cost. Filtering should be designed around incident and capacity questions rather than used blindly.

ChoiceEffectCaution
Org scopeBroad standardized coverageCost and ownership across projects
MetadataRicher attributionMore storage
FilterReduces log volumeCan hide future forensic evidence

Prerequisites, limits, security, and HA

Direct VPC egress must be configured for the serverless resource and Flow Logs enabled at a supported scope. Flow Logs are sampled telemetry, not packet capture. Default Logging retention is finite and longer forensic retention requires custom retention or export.

Operations and troubleshooting

  1. Confirm Direct VPC egress and the subnet/VPC used.
  2. Confirm the Flow Logs configuration and filter.
  3. Search Logging in the reporting VPC project.
  4. Interpret direction and firewall sampling position correctly.

Scenario

An App Engine service reaches an internal database but operations sees no records. Verify the serverless resource uses Direct VPC egress, the correct network scope is enabled, the filter retains the flow, and the team is querying the host/reporting project.

Exam anchors

  • Flow Logs are sampled and aggregated.
  • Shared VPC logging follows the reporting VPC project.
  • Ingress and egress firewall sampling positions differ.

Lesson 3: Private Service Connect metadata in VPC Flow Logs

Domain 5 — Managing, monitoring, and troubleshooting network operations

Primary source: https://docs.cloud.google.com/vpc/docs/flow-logs

Problem and architecture

New PSC annotations identify source/destination PSC interfaces, consumer connections, endpoints, and service attachments. These fields make it possible to correlate a sampled flow with the PSC control-plane object responsible for the private service path. Metadata can be disabled or selectively included to control logging cost, so incident workflows must verify the active metadata configuration before assuming a field is absent because PSC was not involved.

flowchart LR
 A[Consumer] --> B[PSC endpoint/interface]
 B --> C[Service attachment]
 C --> D[Producer service]
 B -. PSC metadata .-> E[VPC Flow Logs]

What to notice: the log can connect data-plane evidence to named PSC objects without exposing application payload.

Control plane, packet flow, and design choices

PSC abstracts producer addressing behind consumer-side private connectivity. Metadata fields help determine which endpoint or attachment participated when several services share similar address space. Preserve the distinction between connection state and sampled flow state.

EvidenceUseNot proof of
Endpoint nameConsumer-side attributionApplication success
Attachment nameProducer publication pathBackend health
Consumer connectionConnection correlationUnsampled flows

Prerequisites, limits, security, and HA

Metadata is useful only when included by the active Flow Logs configuration. Treat it as operational metadata, not payload inspection. Availability remains determined by the PSC service architecture and producer backends.

Operations and troubleshooting

  1. Confirm the PSC endpoint/interface and attachment.
  2. Confirm metadata annotations are enabled.
  3. Filter on PSC fields and 5-tuple.
  4. Correlate timestamps with producer health and application logs.

Scenario

Two PSC endpoints use similar private ranges. An incident responder can use endpoint and service-attachment annotations to identify which published service handled the sampled flow before examining producer-side health.

Exam anchors

  • Metadata improves attribution, not packet capture.
  • Selective metadata can reduce cost but reduce forensic richness.
  • PSC object identity and application health are separate questions.

Lesson 4: Cloud Network Insights Compute Engine Monitoring Points

Domain 5 — Managing, monitoring, and troubleshooting network operations

Primary source: https://docs.cloud.google.com/network-intelligence-center/docs/cloud-network-insights/deploy-gce-monitoring-points

Problem and architecture

Cloud Network Insights uses Monitoring Points to measure network and web application performance. Compute Engine points can be deployed with Terraform or Marketplace. The Cloud Network Insights Editor role is needed in the enabled project and Compute Admin is needed for Terraform deployment in the target project. Generated download commands use a time-limited token; successful points normally become Active within minutes.

flowchart LR
 A[Compute Engine Monitoring Point] --> B[Measured path]
 B --> C[Application / remote point]
 A --> D[Cloud Network Insights control plane]
 D --> E[Policies and visualization]

What to notice: this is active measurement from strategic vantage points, not passive mirroring.

Control plane, packet flow, and design choices

Place points in representative network segments rather than directly on the workload. The point needs outbound control-plane reachability and must be positioned so the measured path resembles the user or branch path being diagnosed.

DeploymentStrengthOperational need
TerraformRepeatable IaCCompute Admin
MarketplaceGuided deploymentExternal/control-plane connectivity
Multiple pointsPath comparisonStrategic placement

Prerequisites, limits, security, and HA

Use least-privilege roles, protect generated tokens, and verify the point can reach required control-plane endpoints. A point that is Active proves registration, not that every target policy is correctly configured.

Operations and troubleshooting

  1. Confirm roles and target project.
  2. Deploy the bundle using the selected method.
  3. Wait for Active registration.
  4. Create monitoring policies and compare measurements across points.

Scenario

A branch reports intermittent latency while Google Cloud VMs look healthy. Deploy points at a central VPC and representative branch/cloud edge to distinguish application latency from path latency.

Exam anchors

  • Monitoring Points are active vantage points.
  • Role requirements differ between Cloud Network Insights administration and Compute deployment.
  • Placement determines diagnostic value.

Lesson 5: Cloud Network Insights Azure Monitoring Points

Domain 4 — Hybrid and multi-cloud network interconnectivity

Primary source: https://docs.cloud.google.com/network-intelligence-center/docs/cloud-network-insights/deploy-azure-monitoring-points

Problem and architecture

Azure-optimized Monitoring Points extend Cloud Network Insights into a non-Google cloud. The installation bundle is obtained from Google Cloud and deployed in Azure using Bicep following AppNeta instructions. The point must have network reachability to the Cloud Network Insights/AppNeta control plane. This creates an active measurement vantage point rather than a passive packet capture.

flowchart LR
 A[Azure Monitoring Point] --> B[Hybrid / internet path]
 B --> C[Google Cloud service]
 A --> D[Cloud Network Insights]
 D --> E[Cross-cloud performance view]

What to notice: measurements originate inside Azure, helping isolate provider edge, interconnect, internet, and application segments.

Control plane, packet flow, and design choices

Choose Azure regions/subnets that represent important user or workload paths. The generated curl download command is time-limited; bundle transfer and Bicep deployment are distinct from point registration.

ChoiceWhyFailure symptom
RegionRepresentative latencyMisleading baseline
Subnet/egressControl-plane reachabilityPoint never Active
Multiple cloudsSegment isolationSingle-vantage ambiguity

Prerequisites, limits, security, and HA

Cloud Network Insights Editor is required in the Google Cloud project. Azure deployment privileges and egress must be handled in Azure. Treat bundle tokens as temporary credentials.

Operations and troubleshooting

  1. Generate/download the bundle.
  2. Deploy with Bicep.
  3. Verify outbound reachability.
  4. Confirm Active status.
  5. Build policies that compare Azure and Google Cloud vantage points.

Scenario

Only Azure users see elevated response time. A point in Azure and one near the Google Cloud service can reveal whether latency accumulates before or after the cloud boundary.

Exam anchors

  • Multi-cloud monitoring does not imply multi-cloud routing.
  • Active measurements complement Flow Logs.
  • Control-plane reachability is a deployment prerequisite.

Lesson 6: VPC Service Controls service patterns

Domain 6 — Cloud network security

Primary source: https://docs.cloud.google.com/vpc-service-controls/docs/manage-service-perimeters

Problem and architecture

Service patterns provide granular control over Google API host/path access through the private VIP or PSC all-apis bundle. The configuration uses VPC accessible services with GOOGLE_APIS_VIA_PRIVATE_PATH and can allow supported services plus URL patterns for unsupported APIs. Dry-run mode and audit logs are the safest rollout method because a syntactically valid restriction can still break required application API calls.

flowchart LR
 A[Workload inside perimeter] --> B[private.googleapis.com or PSC all-apis]
 B --> C[VPC accessible service patterns]
 C -->|allowed host/path| D[Google API]
 C -->|not allowed| E[Denied]

What to notice: this controls which APIs/paths are reachable through the private path; it is not a replacement for IAM authorization at the API.

Control plane, packet flow, and design choices

Patterns match allowed service identities or URL patterns and can include custom request-header conditions supported by the feature. Design a minimal allow set, validate it in dry-run, then promote to enforced configuration.

LayerQuestionTool
PerimeterMay the private path reach this API?Service patterns
IdentityMay this principal perform the operation?IAM
NetworkCan the workload reach the VIP/endpoint?VPC/PSC/DNS

Prerequisites, limits, security, and HA

Service patterns apply to Google APIs through the configured private path scope. Unsupported or missing patterns can deny dependencies, so dry-run evidence is critical.

Operations and troubleshooting

  1. Model required API hosts and paths.
  2. Create dry-run VPC accessible services YAML.
  3. Observe audit violations.
  4. Correct dependencies.
  5. Enforce only after clean validation.

Scenario

A perimeter allows Storage but an application also calls an auxiliary API. Dry-run logs reveal the blocked hostname/path before enforcement, preventing an outage.

Exam anchors

  • Service patterns complement IAM.
  • Use private-path enforcement scope.
  • Dry-run is the safe migration mechanism.

Lesson 7: Network Security Integration direct internet egress

Domain 6 — Cloud network security

Primary source: https://docs.cloud.google.com/network-security-integration/docs/in-band/in-band-integration-overview

Problem and architecture

Direct internet egress lets an in-band producer appliance inspect consumer traffic and send it directly to the internet through the appliance external interface. GENEVE preserves the original packet to the appliance. Compared with standard reinjection, the path crosses the consumer/producer boundary twice total instead of four times, and consumer VPCs don't need Cloud NAT or external IPs for that inspected path.

flowchart LR
 A[Consumer VM] -->|GENEVE intercepted packet| B[Producer security appliance]
 B -->|external interface| C[Internet]
 C --> B
 B -->|GENEVE return| A

What to notice: direct egress removes the post-inspection return to the consumer VPC before internet access.

Control plane, packet flow, and design choices

Cloud NGFW policy with apply_security_profile_group selects traffic for interception without changing VPC routes. The producer appliance must be configured by its vendor for direct internet egress and must handle inspection and internet-facing behavior.

ModelBoundary crossingsConsumer NAT
Standard reinjectionFourNeeded for private source egress
Direct internet egressTwoNot needed for this path

Prerequisites, limits, security, and HA

Producer and consumer interception resources, security profile groups, supported appliances, and correct GENEVE/MTU handling are prerequisites. Appliance scale and failure handling become part of internet availability.

Operations and troubleshooting

  1. Confirm firewall policy selects the flow.
  2. Confirm GENEVE delivery to a healthy appliance.
  3. Verify appliance inspection/NAT/vendor configuration.
  4. Verify direct external-interface egress and return reinjection.

Scenario

A team removes Cloud NAT from consumer VPCs after enabling direct egress but loses internet access. Check that the appliance itself is configured for direct internet egress; enabling in-band interception alone does not automatically configure vendor appliance behavior.

Exam anchors

  • Packet Intercept avoids route changes.
  • GENEVE preserves the original packet.
  • Direct egress centralizes internet-facing infrastructure in the producer path.

Lesson 8: NCC IPv6 include/exclude filters for hybrid spokes

Domain 4 — Hybrid and multi-cloud network interconnectivity

Primary source: https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/spoke-filters-overview

Problem and architecture

NCC spoke filters constrain route exchange. Export filters control what a spoke contributes to the hub; import filters control what a hybrid spoke receives. IPv6 CIDRs are supported in Preview for VLAN attachment and Cloud VPN hybrid spokes, while Router appliance spokes remain IPv4-only. Include/exclude lists support up to 16 unique nonoverlapping CIDRs and special all-range keywords where supported.

flowchart LR
 A[Hybrid spoke] -->|export filter| B[NCC hub route table]
 B -->|import filter| C[Hybrid spoke]
 D[IPv6 prefixes] --> A

What to notice: export governs contribution to the hub; import governs acceptance from the hub.

Control plane, packet flow, and design choices

Filters operate on route exchange, not packets. A filtered route never becomes a usable forwarding entry through that exchange path. Use include lists for tight allow models and exclude lists to remove exceptions from broader ranges.

SpokeIPv6 filter statusKey caveat
VLAN attachmentPreviewHybrid dynamic routes
Cloud VPNPreviewHybrid dynamic routes
Router applianceIPv4 onlyNo IPv6 filter ranges

Prerequisites, limits, security, and HA

Ranges must be unique and nonoverlapping within the configured list. Route filters can intentionally remove reachability; design both directions and both address families.

Operations and troubleshooting

  1. Inspect spoke filter configuration.
  2. Check whether the prefix is exported to the hub.
  3. Check whether destination spoke imports it.
  4. Verify BGP learned/advertised state on the hybrid edge.

Scenario

IPv4 works across a VPN spoke but IPv6 does not. Confirm the IPv6 range is included in both the relevant export and import logic and that the spoke type supports IPv6 filtering.

Exam anchors

  • Filters change route exchange, not firewall policy.
  • Import and export direction matters.
  • Router appliance has a different IPv6 limitation.

Lesson 9: SNI-based routing for proxy Network Load Balancers

Domain 3 — Configuring managed network services

Primary source: https://docs.cloud.google.com/load-balancing/docs/tcp

Problem and architecture

Regional proxy Network Load Balancers can use TLSRoute resources to inspect the unencrypted SNI in ClientHello and select a backend while preserving TLS passthrough. A target TCP proxy uses either its single default backend or TLS routes, not both. Missing, invalid, or unmatched SNI closes the connection. HTTP connection coalescing can create surprising routing because a connection stays bound to its selected backend.

flowchart LR
 A[TLS client] -->|ClientHello + SNI| B[Target TCP proxy]
 B --> C[TLSRoute match]
 C --> D[Backend service]
 D --> E[Backend terminates TLS]

What to notice: the load balancer reads SNI but passes encrypted TLS through; the backend owns the certificate.

Control plane, packet flow, and design choices

TLSRoute hostnames map connections to backend services. The connection is permanently associated with the selected backend path, so application protocols that reuse TLS connections must be evaluated carefully.

ClientHelloResult
Valid matching SNIRoute to matched backend
No SNIClose
Invalid/unmatched SNIClose

Prerequisites, limits, security, and HA

SNI routing is Preview and limited to supported regional proxy NLB modes. It is not HTTP host routing and does not decrypt the TLS stream.

Operations and troubleshooting

  1. Inspect forwarding rule and target TCP proxy.
  2. Inspect attached TLSRoute hostnames.
  3. Capture/verify client SNI behavior.
  4. Check backend health and certificate independently.

Scenario

A non-SNI legacy TLS client fails while modern clients succeed. This is expected when TLS routes are in use because absent SNI is not sent to a default backend.

Exam anchors

  • SNI is visible in ClientHello.
  • TLS remains end-to-end to the backend.
  • Default backend and TLSRoute modes are mutually exclusive.

Lesson 10: Managed workload identity for backend mTLS

Domain 3 — Configuring managed network services

Primary source: https://docs.cloud.google.com/load-balancing/docs/release-notes

Problem and architecture

On September 18, 2026, managed workload identity for backend mTLS became GA for global/regional external and cross-region/regional internal Application Load Balancers. It integrates Certificate Authority Service and Certificate Manager so backend identity certificates and trust can be automated and rotated, reducing private-key lifecycle toil while retaining authenticated load-balancer-to-backend TLS.

flowchart LR
 A[Client] -->|HTTPS| B[Application Load Balancer]
 B -->|backend mTLS| C[Backend workload identity]
 D[CA Service / Certificate Manager] -. identity + trust lifecycle .-> B
 D -. managed cert lifecycle .-> C

What to notice: frontend client TLS and backend mTLS are separate trust relationships.

Control plane, packet flow, and design choices

The load balancer authenticates the backend connection using managed workload identity material. Centralized trust and automated rotation reduce static key distribution and make workload identity governance easier to audit.

LayerIdentityOwner
FrontendService presented to clientFrontend certificate policy
BackendWorkload identityManaged workload identity/CA trust

Prerequisites, limits, security, and HA

Use only supported Application Load Balancer families and validate CA/trust configuration. Automated rotation reduces operational risk but does not fix unhealthy backends or application authorization.

Operations and troubleshooting

  1. Separate frontend and backend TLS symptoms.
  2. Check trust configuration and workload identity pool.
  3. Check certificate rotation/status.
  4. Check backend health and TLS handshake errors.

Scenario

Frontend HTTPS succeeds but backends return handshake failures. Investigate backend trust/identity and certificate lifecycle rather than replacing the public frontend certificate.

Exam anchors

  • Backend mTLS authenticates the service-to-backend leg.
  • Managed identity reduces manual private-key handling.
  • The capability became GA on September 18, 2026 for listed ALB families.

Lesson 11: Cloud Armor managed rulesets

Domain 6 — Cloud network security

Primary source: https://docs.cloud.google.com/armor/docs/release-notes

Problem and architecture

On September 17, 2026, Cloud Armor managed rulesets entered Preview. They protect backend services and APIs using threat signatures that Google keeps current. Treat managed rules as a security control that still requires staged rollout, logging, false-positive analysis, and policy-order awareness rather than as a substitute for application-specific authorization.

flowchart LR
 A[Internet request] --> B[Cloud Armor policy]
 B --> C[Managed ruleset signatures]
 C -->|allowed| D[Backend service/API]
 C -->|matched threat| E[Enforcement]

What to notice: managed signature maintenance reduces rule-content toil but policy placement and false-positive handling remain customer responsibilities.

Control plane, packet flow, and design choices

Use managed rules as part of layered WAF policy. Observe matches before aggressive enforcement where business traffic is sensitive to false positives. Keep custom application authorization independent.

ControlPurpose
Managed rulesetGoogle-maintained web threat signatures
Custom policyApplication-specific conditions
Application authUser/workload authorization

Prerequisites, limits, security, and HA

The feature is Preview as of the report date. Pre-GA support terms and compatibility must be considered before production dependence.

Operations and troubleshooting

  1. Enable logging/visibility.
  2. Stage rules and inspect matches.
  3. Investigate false positives by signature/request.
  4. Adjust policy without weakening unrelated controls.

Scenario

A new managed rule blocks legitimate API requests. Use match logs to identify the signature and tune the policy rather than bypassing Cloud Armor for the entire backend.

Exam anchors

  • Managed does not mean no monitoring.
  • Release stage matters.
  • WAF threat detection is distinct from application authorization.

Lesson 12: Cross-project SSL policy referencing

Domain 1 — Designing and planning a Google Cloud VPC network

Primary source: https://docs.cloud.google.com/load-balancing/docs/release-notes

Problem and architecture

Cross-project SSL policy referencing, introduced in Preview in August 2026, lets a central administrative project own global or regional SSL policies while supported Application Load Balancers and global external proxy Network Load Balancers in other projects reference them. This separates cryptographic governance from application ownership and is useful when platform teams need consistent TLS posture across projects.

flowchart LR
 A[Admin project] --> B[Central SSL policy]
 B -. cross-project reference .-> C[App project target proxy]
 C --> D[Load balancer frontend]
 D --> E[Backend]

What to notice: policy ownership can be centralized without moving the load balancer itself into the admin project.

Control plane, packet flow, and design choices

Choose global or regional policy scope to match the supported target proxy. Centralization improves consistency but creates an administrative dependency, so change management and IAM must be deliberate.

ModelBenefitRisk
Per-project policyLocal autonomyDrift
Cross-project central policyConsistent TLS postureCentral change blast radius

Prerequisites, limits, security, and HA

The feature is Preview and only supported load-balancer families can reference policies across projects. IAM must permit the reference; central policy changes can affect multiple application teams.

Operations and troubleshooting

  1. Confirm policy scope and owning project.
  2. Confirm target proxy/load balancer support.
  3. Confirm cross-project IAM.
  4. Test client TLS negotiation after policy changes.

Scenario

A security team wants one TLS baseline for dozens of app projects. Cross-project policy referencing reduces duplication while preserving app-project load balancer ownership.

Exam anchors

  • Central policy is governance, not traffic transit.
  • Scope compatibility matters.
  • Preview status should influence production design.
