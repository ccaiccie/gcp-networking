1. Verified Peering Provider: provider-mediated access to Google’s public edge

Domain 1 — Designing and planning a Google Cloud network
Primary: Verified Peering Provider overview · Comparison: Direct Peering overview

Problem, architecture, and trust boundary

Verified Peering Provider (VPP) is for enterprises that want high-quality access to publicly reachable Google services without operating a Direct Peering relationship themselves. The enterprise buys internet or IP-transit service from a provider that already peers with Google. The provider owns the peering mechanics, physical diversity, and operational relationship with Google; the customer remains responsible for its enterprise WAN, route policy, provider contract, and application security.

The important boundary is that VPP is not private RFC1918 connectivity into a VPC. It reaches public Google endpoints, including Google Cloud public IPs, Google Workspace, Cloud VPN public endpoints, and other internet-reachable Google services. If the design requirement is private VPC prefix exchange, use products such as Cloud Interconnect, Cloud VPN, or other private connectivity options instead.

flowchart LR
A[Enterprise WAN] --> B[Verified Peering Provider]
B --> C[Private provider-to-Google peering]
C --> D[Google edge]
D --> E[Public Google APIs and services]
D --> F[Public IPs of Google Cloud workloads]
A -. RFC1918 VPC routes are not created by VPP .-> G[Private VPC prefixes]

What to notice: the provider-to-Google segment can be dedicated private fiber, but the service outcome for the customer is access to publicly reachable Google services, not a Cloud Interconnect-style private VPC attachment.

Availability, operational model, and selection criteria

Google classifies participating providers with silver and gold technical badges based on connectivity diversity. Gold indicates stronger metro-level diversity; silver indicates redundant points of presence. Google periodically validates provider requirements, but Google does not give the end customer an SLA for the VPP service itself; the ISP may offer its own commercial SLA before handoff to Google.

ChoiceBest fitMain responsibility
Verified Peering ProviderYou want managed, provider-mediated reachability to Google public servicesProvider manages peering; customer manages provider service and enterprise edge
Direct PeeringYou meet Google peering requirements and want direct operational controlCustomer manages BGP, physical redundancy, routing policy, and peering operations
Cloud Interconnect / VPNYou need private VPC prefix connectivityCloud Router/BGP, attachments or tunnels, and hybrid route design

Security, routing, and troubleshooting

Do not mistake the provider badge for an application security boundary. TLS, IAM, firewall policy, Cloud Armor, and service-specific authentication still protect workloads. When troubleshooting, separate the enterprise-to-provider segment, provider backbone, provider-to-Google peering, and Google service path. BGP visibility available to the customer depends on the ISP service; some customers can consume the service without operating their own ASN or BGP session.

Scenario: a company needs predictable enterprise internet access to Google Workspace and public Google Cloud APIs in several markets but does not meet Direct Peering requirements. A VPP is appropriate. The same company also needs private access to a database subnet in its VPC; that second requirement still needs private hybrid connectivity.

Exam/interview anchor: VPP simplifies public Google connectivity through a qualified ISP; it does not inject private VPC routes into your WAN.

2. GKE privately used public IP (PUPI) ranges for Pod address conservation

Domain 1 — Designing and planning a Google Cloud network
Primary: Configuring privately used public IP addresses for GKE

Why PUPI exists

Large GKE estates can exhaust RFC1918 space because VPC-native clusters allocate substantial secondary ranges for Pods. PUPI lets you use selected public IPv4 address blocks privately as GKE Pod CIDR space without owning those public addresses. The addresses remain private to your routing design; they are not a claim of ownership on the public internet.

This is an IPAM strategy, not a shortcut around collision analysis. If your enterprise later needs to reach the real public destination represented by a privately reused address, routing becomes ambiguous. The design team must choose ranges that are acceptable to lose as public destinations from networks that treat those addresses as private.

flowchart LR
A[RFC1918 pool] --> B[Nodes and infrastructure]
C[Selected public range reused privately] --> D[GKE secondary Pod range]
D --> E[Pod alias IPs]
E --> F[VPC routing]
E -. not ownership of public internet prefix .-> G[Internet]

What to notice: PUPI is most useful when Pod scale consumes RFC1918 space, while node and infrastructure addressing can stay in conventional private ranges.

Architecture, routing, and design choices

PUPI Pod addresses participate in VPC-native alias IP routing just like other Pod ranges. They can be advertised to connected networks when your hybrid routing policy includes them, which means every connected domain must understand that those prefixes are intentionally private in your environment. NAT policy for internet egress should also be explicit so a Pod source that looks globally routable is not assumed to be legitimately routable on the public internet.

Address strategyAdvantageRisk to plan for
RFC1918 PodsConventional private addressingAddress exhaustion at large scale
PUPI PodsPreserves scarce RFC1918 spaceLoss of reachability to the real public destination for reused prefixes unless carefully segmented/NATed
IPv6 / dual stackLarge address space and future-facing designApplication and dependency readiness

Security, operations, and failure scenario

Firewall and policy engines evaluate the actual Pod source addresses, so rules, SIEM parsing, and allowlists must not assume that every non-RFC1918 source is internet-originated. Keep IPAM documentation authoritative and label these ranges clearly in route inventories. Test DNS destinations and SaaS dependencies against the chosen PUPI space before deployment.

Scenario: an enterprise assigns a public block as PUPI and later buys a SaaS product hosted within the real public block. Pods can route toward the privately reused range instead of the internet destination. The fix is architectural—renumber, segment, or design NAT/route exceptions carefully—not a Kubernetes Service tweak.

Exam anchor: PUPI solves private-address scarcity for Pods, but it creates intentional overlap with the global public address space and therefore demands disciplined IPAM.

3. Regional versus global dynamic routing mode in VPC and Cloud Router

Domain 4 — Implementing hybrid network interconnectivity
Primary: Set routing and best path selection modes · Concepts: Cloud Router overview

Control-plane scope

The VPC dynamic routing mode determines the regional scope of dynamic routes learned and advertised by Cloud Routers. Regional mode is the default: learned dynamic routes are primarily usable in the same region as the Cloud Router, while advertisements reflect the applicable regional scope. Global mode makes dynamic routes available across regions in the VPC and lets Cloud Routers advertise appropriate subnets across the VPC according to configuration.

This setting belongs to the VPC network, not to one BGP session. Changing it therefore has a broad control-plane blast radius. Do not confuse dynamic routing mode with best path selection mode: the former controls route scope; the latter controls how Cloud Router evaluates learned BGP paths.

flowchart TB
ON[On-premises prefix 10.50.0.0/16] --> CR1[Cloud Router us-central1]
CR1 --> VPC[VPC dynamic routing mode]
VPC -->|Regional| R1[Us-central1 resources]
VPC -. not broadly installed .-> R2[Europe-west1 resources]
VPC -->|Global| R3[Us-central1 + other regions]

What to notice: a healthy BGP session can still produce regional reachability asymmetry when the VPC routing mode is regional.

Design implications and route behavior

Regional mode limits failure and advertisement scope and can be appropriate when regions are intentionally independent. Global mode simplifies multi-region hybrid reachability but requires the on-premises network to accept the broader advertisement and failure domains. Route priority, MED, custom advertisements, and best path selection still matter after a route is in scope.

ModeUse whenOperational concern
RegionalHybrid connectivity is intentionally region-localRemote regions might require their own hybrid attachment or explicit design
GlobalAny region should use available hybrid connectivityOutages or route leaks can have a wider blast radius

Troubleshooting and scenario

When one region can reach on-premises but another cannot, verify BGP state, learned routes, and the VPC dynamic routing mode before changing firewall rules. Also verify whether a remote region has a more specific route or policy-based route that wins after the dynamic route becomes visible.

Scenario: a company has a single Interconnect attachment in us-central1 and launches a workload in europe-west1. BGP is established and the on-prem prefix is visible on the router, but the European VM cannot use it. If the VPC remains in regional dynamic routing mode, that symptom is expected; global mode or a region-specific connectivity design is required.

Exam anchor: dynamic routing mode answers “where are dynamic routes usable?”; best path selection answers “which eligible path wins?”

4. Internal passthrough Network Load Balancer as a static-route next hop

Domain 2 — Implementing VPC networks
Primary: Internal passthrough Network Load Balancers as next hops

Service-insertion architecture and packet flow

An internal passthrough Network Load Balancer (ILB) can be the next hop of a VPC static route. This makes a health-checked, scalable set of router, NAT, inspection, or gateway VMs look like one logical next hop. Client VMs need no special guest configuration: VPC routing selects the static route, the ILB chooses a healthy backend, and the packet is delivered without proxy termination.

Because the ILB is passthrough, it preserves source and destination information. The virtual appliance, not the load balancer, performs routing, filtering, proxying, or NAT. For two-arm appliances, two ILBs can front different NICs on the same appliance set, one in each VPC network.

flowchart LR
C[Client VM] --> R[Static route]
R --> ILB[Internal passthrough NLB next hop]
ILB --> A1[Healthy appliance VM nic0]
ILB --> A2[Healthy appliance VM nic0]
A1 --> N[Routing / firewall / NAT]
A2 --> N
N --> D[Destination]

What to notice: route selection happens before backend selection; the load balancer supplies health-aware appliance selection, not Layer-7 proxying.

Requirements and caveats

The route and ILB must belong to the same VPC network. Without global access, the next-hop route is usable only by clients in the ILB’s region; enabling global access makes it usable from other regions. The destination of the static route cannot equal or be more specific than an existing subnet route. A forwarding rule using L3_DEFAULT cannot be used as a static-route next hop; traffic would be silently dropped.

Google also cautions against sending traffic to Google APIs and services through a next-hop VM or next-hop ILB; use the default internet gateway path for those destinations, including Private Google Access flows.

Design pointCorrect model
HealthILB health checks determine eligible appliance backends for new connections
ProtocolsNext-hop processing supports VPC-supported protocol traffic rather than being limited by normal forwarding-rule service ports
Same-subnet routingCannot override subnet routes to hairpin same-VPC subnet traffic through an appliance

HA, observability, and scenario

For symmetric two-ILB designs using the same multi-NIC backend VMs, keep eligible backend sets and failover policy aligned so forward and reverse paths do not diverge unexpectedly. Monitor health checks, backend eligibility, effective routes, appliance interface state, and appliance session tables.

Scenario: a security team wants a default route through a pair of firewall VMs. The static route points to an ILB, allowing health-based failover. If all appliance backends fail health checks, route existence alone does not provide a usable forwarding path; fix backend health rather than changing client routes.

Exam anchor: ILB-as-next-hop gives VPC-native service insertion with health-checked appliances; it does not replace appliance routing/NAT policy.

5. Cloud NGFW FQDN objects: DNS-driven firewall destinations

Domain 2 — Implementing VPC networks
Primary: Fully qualified domain name objects overview

Resolution and policy model

FQDN objects let Cloud NGFW policy rules refer to DNS names instead of manually maintained destination IP lists. Cloud NGFW periodically resolves the names and maps them to IP addresses, following the VPC’s Cloud DNS resolution order. That means the firewall decision is coupled to the DNS view available to the target VPC, including private zones, response policies, Compute Engine internal DNS, and public DNS as applicable.

FQDN objects are not URL filtering. They match resolved destination addresses associated with a hostname; they do not inspect HTTP paths or prove that the application payload uses a particular Host header.

flowchart LR
F[Firewall policy FQDN object] --> D[Cloud DNS resolution order]
D --> P[Private/response/internal/public answer]
P --> I[Resolved IP set]
I --> R[Firewall rule match]
C[Workload packet] --> R
R --> A[Allow or deny]

What to notice: DNS is control-plane input to the firewall object; the data-plane packet match ultimately uses resolved addresses.

Compatibility and limits

A VPC using an outbound DNS server policy with an alternative name server is not compatible with FQDN objects. Google recommends avoiding FQDN objects for records with TTLs shorter than 90 seconds because fast-changing answers can outrun the firewall’s periodic resolution behavior. Wildcards such as *.example.com are not supported; each FQDN must have at least two labels and follow standard DNS label rules. Internationalized names are supported through Unicode/Punycode handling, subject to the documented encoded-length rules.

NeedBest control
Allow traffic to a stable hostname whose IPs changeFQDN object
Allow a whole SaaS domain wildcard or web categoryURL filtering / appropriate Layer-7 control, not a wildcard FQDN object
Allow a fixed infrastructure networkIP range or address group

Security and troubleshooting

Because the DNS answer is authoritative input, protect DNS administration and understand split-horizon behavior. A private zone can intentionally make the same FQDN resolve differently for one VPC, which changes the firewall object’s effective IP set there. Troubleshoot by resolving the FQDN from the affected VPC context, checking the VPC DNS policy, then reviewing effective firewall policy and logs.

Scenario: a policy allows api.partner.example, but the partner rotates addresses with a 30-second TTL. Connections intermittently fail. The lesson is not to increase an unrelated firewall priority; choose a control compatible with rapidly changing destinations or work with a more stable endpoint model.

Exam anchor: FQDN object = periodically resolved DNS name to IPs; no wildcards, and DNS architecture directly affects policy behavior.

6. Governing Cloud NAT with constraints/compute.restrictCloudNATUsage

Domain 3 — Configuring managed network services
Primary: Cloud NAT organization policy constraints

Governance problem and hierarchy

Cloud NAT is easy for project teams to create, but enterprises often need central control over which subnets may use it. The list constraint constraints/compute.restrictCloudNATUsage lets an Organization Policy Administrator express allowed or denied subnet scope at organization, folder, project, or subnetwork hierarchy levels.

The constraint is preventive rather than retroactive. Existing Cloud NAT configurations continue to work even if they would violate a newly introduced policy. This makes rollout planning important: inventory existing gateways first, then enforce policy and separately remediate legacy configurations.

flowchart TB
O[Organization policy] --> F[Folder]
F --> P[Project]
P --> S[Subnet eligibility]
S --> G{New NAT gateway or subnet creation}
G -->|Complies| A[Allowed]
G -->|Violates| D[Creation blocked]
E[Existing NAT configuration] -. not retroactively disabled .-> O

What to notice: enforcement blocks resource changes that would violate policy; it is not a packet-time NAT filter.

Allow/deny semantics and Shared VPC

If allowedValues is configured, unspecified values are denied. If only deniedValues is configured, unspecified values are allowed. If both are present, denied values take precedence in conflicts. In Shared VPC, policy administration must account for the host project because that is where shared network resources live.

Policy shapeEffect
Allowed list onlyOnly listed subnet scope can participate; everything else is denied
Denied list onlyListed scope is blocked; everything else remains allowed
BothDenied wins on conflict
No valuesConstraint does not restrict usage

Failure modes and operations

A subtle failure occurs when a regional NAT gateway is configured for all subnets and policy later allows only one existing subnet: creation of a new subnet in that region can be blocked because that subnet would automatically become eligible for the broad NAT gateway. Likewise, creation of a broad gateway can be blocked when one of the region’s subnets is not permitted.

Scenario: a platform team sees “permission/policy” failure while creating a subnet, even though the subnet itself is valid. Trace effective organization policy and existing all-subnet NAT gateways before treating it as an IAM issue.

Exam anchor: restrictCloudNATUsage governs configuration eligibility, inherits through resource hierarchy, and is not retroactive.

7. Cloud NAT dynamic port allocation and exhaustion behavior

Domain 3 — Configuring managed network services
Primary: Cloud NAT IP addresses and ports

Allocation algorithm

Cloud NAT must translate many private source sockets into finite source-port space on NAT IPs. Static port allocation assigns a fixed number of ports per VM. Dynamic port allocation starts a VM at a configured minimum and doubles the allocation as usage approaches exhaustion, up to a configured maximum. When usage falls substantially, excess ports can be returned to the shared pool.

Public NAT uses static port allocation by default; Private NAT uses dynamic port allocation by default. Dynamic allocation is useful when VM egress demand varies widely because idle VMs do not reserve as much port capacity.

flowchart LR
VM[VM egress connections] --> MIN[Minimum ports]
MIN --> U{Near exhaustion?}
U -->|Yes| D[Double allocation]
D --> M{Below maximum?}
M -->|Yes| U
M -->|No| X[Potential port exhaustion]
U -->|Usage falls| R[Return excess ports]

What to notice: scaling ports is reactive, so a sudden burst can still experience connection latency or timeouts while additional port blocks are allocated.

Compatibility and sizing choices

Endpoint-Independent Mapping is incompatible with dynamic port allocation on Public NAT; if you require endpoint-independent behavior, use static port allocation. Choose minimum ports high enough for normal bursts and maximum ports high enough for peak concurrency without consuming unnecessary address capacity.

ModeStrengthTradeoff
StaticPredictable per-VM reservationCan waste ports when VM usage is uneven
DynamicAdapts per VM and reclaims idle portsScale-up events can introduce transient drops/latency

Monitoring and failure scenario

Watch Cloud NAT metrics and logs for allocation pressure, dropped connections, NAT IP utilization, and affected VMs. Distinguish port exhaustion from DNS failure or firewall denial by correlating timestamps and source VM identity. If many high-connection-rate VMs exhaust their maximum allocations, add NAT capacity and tune min/max settings rather than simply extending TCP timeouts.

Scenario: a fleet of batch workers is quiet most of the day and suddenly opens thousands of outbound connections. Dynamic allocation is efficient overall, but too-low minimums can produce a burst of allocation events. Raising the minimum can trade a little idle capacity for smoother burst handling.

Exam anchor: dynamic allocation conserves port space, but min/max sizing and burst behavior still matter.

8. Cloud Armor rate limiting: throttle versus rate-based ban

Domain 3 — Configuring managed network services
Primary: Rate limiting overview · Configuration: Configure rate limiting

Control model

Cloud Armor rate-based rules protect backend capacity from abusive or erratic request volumes. A throttle rule allows traffic up to a threshold and applies an exceed action only to requests above the threshold. A rate-based ban can temporarily apply the exceed action to all requests from the aggregation key after the client exceeds the configured threshold.

Rate limiting can aggregate on keys such as source IP or selected request attributes. The configured threshold is approximate and is enforced independently in serving regions, so it should be used for abuse mitigation and availability protection—not strict billing, licensing, or globally exact quotas.

flowchart LR
R[Request] --> K[Aggregation key]
K --> C{Rate within threshold?}
C -->|Yes| A[Conform action: allow]
C -->|No throttle| T[Exceed action for excess requests]
C -->|No rate-based ban| B[Temporary ban window]
B --> E[Deny or redirect matching client]

What to notice: throttle sheds only excess requests, while a ban changes subsequent treatment for the client during the ban period.

Thresholds, preview, and design

Current documentation allows rate-limit threshold counts from 1 through 10,000 with supported interval values from 10 seconds through 3,600 seconds. Use preview mode and request logs to estimate normal high-percentile traffic before enforcement. A rule can be changed from throttle to rate-based ban, but a rate-based ban cannot be converted back to throttle in place.

ActionUse whenRisk
ThrottleLegitimate bursts are expected but backend capacity must be protectedToo-low thresholds shed good traffic
Rate-based banRepeated high-rate clients are likely abusiveShared NAT/proxy clients can cause collateral blocking

Troubleshooting and scenario

Choose aggregation keys carefully. If thousands of legitimate users share one proxy IP, per-IP rate limiting can treat them as one client. Inspect Cloud Armor logs, matched rule priority, enforcement key, backend region, and response status. Because thresholds are applied per associated backend and serving region, aggregate traffic can exceed the numeric threshold when viewed globally.

Scenario: a ticketing site sees flash-sale bursts. Start with preview, measure normal per-client peaks, and prefer throttling over immediate bans unless repeated abuse is well identified.

Exam anchor: Cloud Armor rate limits are availability controls with approximate regional enforcement, not exact global quotas.

9. Cloud Armor advanced network DDoS protection for L3/L4 exposed resources

Domain 3 — Configuring managed network services
Primary: Cloud Armor overview · Feature: Advanced network DDoS protection

Protection scope

Google provides always-on infrastructure DDoS defenses, while Cloud Armor Enterprise adds advanced network DDoS capabilities for customers exposing network load balancers, protocol forwarding, or VMs with public IP addresses. The advanced service adds attack monitoring, alerting, targeted mitigations, and mitigation telemetry for network-layer attacks.

This differs from Layer-7 Cloud Armor policies attached to HTTP(S) backends. Application rules, WAF expressions, bot controls, and HTTP rate limiting protect application semantics; advanced network DDoS protects L3/L4-facing resources where there might be no HTTP proxy to evaluate application requests.

flowchart TB
A[Internet attack traffic] --> G[Google network edge]
G --> N[Advanced network DDoS detection and mitigation]
N --> P[Network Load Balancer / protocol forwarding / public VM]
H[HTTP request] --> L[Cloud Armor L7 security policy]
L --> B[HTTP(S) backend]

What to notice: network DDoS mitigation and Layer-7 security policy are complementary controls at different layers.

Subscription, telemetry, and deployment

Advanced network DDoS protection is a Cloud Armor Enterprise capability. Design work therefore includes commercial tier, resource eligibility, telemetry integration, incident workflow, and escalation ownership. For internet-facing architecture, document which resources are proxy-protected at Layer 7 and which expose Layer 3/4 services directly.

ExposurePrimary concernRelevant control
External HTTP(S) applicationWAF, bots, HTTP floodsCloud Armor security policy and Adaptive/rate controls
External network LB / protocol forwardingVolumetric and protocol attacksAdvanced network DDoS protection
Public VMDirect L3/L4 exposureAdvanced network DDoS plus firewall hardening

Operations and incident scenario

During an event, correlate DDoS telemetry with load-balancer metrics, VM/network metrics, firewall logs, and application availability. Do not infer that high packet volume automatically means the backend is receiving the same volume: upstream mitigation can absorb traffic before it reaches the resource.

Scenario: a UDP service behind an external passthrough Network Load Balancer is flooded. HTTP WAF rules cannot help because there is no HTTP request to inspect. Network-layer DDoS protection and backend capacity/health are the relevant layers.

Exam anchor: match the defense to the layer—L3/L4 advanced network DDoS for exposed network services; Layer-7 policy for proxied applications.

10. Split-horizon Cloud DNS with public and private zones

Domain 3 — Configuring managed network services
Primary: General DNS overview · Zone behavior: DNS zones overview

Resolution architecture

Split-horizon DNS serves different answers for the same name depending on the requester’s network context. A common design has a public zone for internet clients and a private managed zone with the same suffix authorized to one or more VPC networks. Queries from those VPCs use the private DNS view; public resolvers see the public zone.

Cloud DNS selects among overlapping private namespaces using longest-suffix matching. Crucially, if a private zone is authoritative for a suffix but lacks a requested record, Cloud DNS can return NXDOMAIN instead of falling through to the public zone for that same name. This makes private-zone completeness a real operational concern.

flowchart LR
I[Internet client] --> PUB[Public authoritative zone example.com]
V[VPC workload via 169.254.169.254] --> PRIV[Private zone example.com]
PUB --> A[Public answer 203.0.113.20]
PRIV --> B[Internal answer 10.20.30.40]
PRIV -->|record missing| N[NXDOMAIN; no automatic public fallback for covered name]

What to notice: the same FQDN can intentionally map to different addresses, but a private zone can also shadow public records.

Design choices and related zone types

Use a private managed zone when you want a complete internal copy of a namespace. Use a response policy when only a small set of names should be overridden while most names continue to resolve publicly. Use a forwarding zone when an on-premises DNS server remains authoritative for the private namespace. Private zones can overlap public zones; private zones authorized to the same VPC must obey Cloud DNS overlap rules.

RequirementRecommended DNS primitive
Full internal view of example.comPrivate managed zone
Override only api.example.comResponse policy
On-prem DNS remains authoritativeForwarding zone

Troubleshooting and security

Verify the querying VM uses the metadata resolver, identify every private/forwarding/peering zone authorized to the VPC, then apply longest-suffix logic. Test both internal and external resolvers. DNS administration is a security boundary because changing the private answer can redirect trusted workloads without changing application configuration.

Scenario: internal users resolve portal.example.com successfully, but status.example.com returns NXDOMAIN even though it exists publicly. An internal example.com private zone shadows the public namespace and lacks the status record. Add the intended private record or redesign the override using a narrower namespace/response policy.

Exam anchor: split horizon depends on DNS view and zone precedence; private-zone authority can intentionally or accidentally shadow public records.

11. GKE 1.36+ kube-dns on CoreDNS: scale, EndpointSlices, and DNS observability

Domain 5 — Managing, monitoring, and troubleshooting network operations
Primary: About kube-dns for GKE

Architecture change and why it matters

In GKE Standard clusters, kube-dns remains the cluster DNS service name, but GKE 1.36 and later uses a CoreDNS-based implementation. The newer implementation uses EndpointSlices and removes the older 1,000-endpoint-per-Service awareness limit, supports up to 15 upstream name servers instead of 3, and raises concurrent outbound TCP connection capacity from 200 to 1,500.

Autopilot is different: Cloud DNS is the default DNS provider there. For Standard clusters, Pods normally point to the kube-dns Service ClusterIP through /etc/resolv.conf, with Kubernetes search domains and ndots:5.

flowchart LR
P[Pod] --> S[kube-dns Service ClusterIP]
S --> C[CoreDNS-based kube-dns Pods in GKE 1.36+]
C --> ES[EndpointSlices for Service discovery]
C --> U[Upstream resolvers for external names]
N[NodeLocal DNSCache optional] --> S

What to notice: the Service-facing contract stays familiar while internal implementation and scaling characteristics improve.

Customization and caveats

Stub domains can direct selected suffixes to custom resolvers. Custom upstream resolvers replace the default external-resolution path except for cluster-local names, so environments using Workload Identity Federation or Google internal names must preserve the required internal resolution path, commonly via the metadata server. A custom kube-dns Deployment is customer-managed and is not automatically managed by the built-in autoscaler.

Characteristic1.35 and earlier1.36+
Service endpoint awarenessUp to 1,000 endpointsEndpointSlices; aware of all endpoints
Upstream name servers315
Outbound TCP connections2001,500

Troubleshooting and observability

For 1.36+, Google provides a GKE DNS Observability dashboard and CoreDNS-style metrics on port 9153. Diagnose latency by separating application lookup behavior, Pod resolver configuration, NodeLocal DNSCache, kube-dns replica capacity, upstream latency, and endpoint discovery. getaddrinfo EAI_AGAIN often points to transient resolver pressure rather than a VPC route failure.

Scenario: a Service grows beyond 1,000 Pods. On older kube-dns, some endpoints might not be represented; after 1.36+, EndpointSlices remove that specific awareness ceiling. If latency remains, examine query volume and upstream behavior rather than assuming endpoint discovery is still the limitation.

Exam/interview anchor: GKE 1.36+ keeps the kube-dns service contract but changes the implementation and observability profile materially.

12. Cloud Network Insights Monitoring Points and synthetic path telemetry

Domain 5 — Managing, monitoring, and troubleshooting network operations
Primary: Cloud Network Insights overview · Deployment: Add Monitoring Points

What Cloud Network Insights adds

Cloud Network Insights uses Monitoring Points—software agents deployed at meaningful network locations—to actively probe network and web paths. This is different from passive flow logs: synthetic probes let you continuously measure a path even when application users are not generating representative traffic.

Monitoring policies bind a source Monitoring Point to a target and define what is tested and how often. Network paths expose Layer-3/4 metrics such as RTT, loss, jitter, and path changes. Web paths can use HTTP probes or a real browser engine to measure application behavior.

flowchart LR
MP1[Monitoring Point: branch] --> POL[Monitoring policy]
POL --> T[Target]
MP2[Monitoring Point: GCP VPC] --> POL
POL --> NP[Network path: RTT/loss/jitter]
POL --> WP[Web path: HTTP/browser experience]
NP --> OBS[Cloud Observability metrics/logs]
WP --> OBS

What to notice: dual-ended monitoring can reveal one-way latency and asymmetric routing more precisely than a single-ended probe.

Deployment architecture and design

Monitoring Points can be deployed in Google Cloud VPCs, remote branches, on-premises data centers, AWS, or Azure. Google recommends placing them in representative network segments rather than directly on the monitored workload. A centralized Google Cloud project manages installation packages, inventory, dashboards, and alert integrations.

Path typeUseKey evidence
Single-ended network pathProbe a third-party or unmanaged targetRTT, loss, jitter, hop changes
Dual-ended network pathYou control agents at both endsOne-way latency and asymmetry
HTTP web pathLightweight API/site reachabilityHTTP/TLS/DNS timing
Browser web pathFull end-user page experienceRendered page and JavaScript behavior

Operations and scenario

Use synthetic alarms to detect persistent deviations, then correlate exported telemetry with Cloud Monitoring and Cloud Logging. Monitoring Points complement Connectivity Tests: Connectivity Tests reasons about configuration and forwarding feasibility, while synthetic probes measure the actual observed path and performance over time.

Scenario: users report intermittent SaaS latency from one branch. A branch Monitoring Point and a cloud-region Monitoring Point show that only the branch path develops loss at an ISP hop. That evidence narrows the fault domain before application teams spend time tuning the service.

Exam anchor: choose configuration-analysis tools for “should this path work?” and synthetic Monitoring Points for “how is this path actually behaving over time?”
