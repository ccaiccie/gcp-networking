1. Regional and multi-regional Google API endpoints through PSC

Domain 1 — Design VPC

Architecture and behavior

Regional API endpoints use hostnames such as SERVICE.REGION.rep.googleapis.com; multi-regional endpoints scope processing to a jurisdictional multi-region. A Private Service Connect regional endpoint is an internal IP from a regular subnet that targets a Google-managed service attachment. By default clients must be in the same region and VPC/Shared VPC; global access expands reach to other regions and connected hybrid networks. Regional endpoints keep request processing and TLS termination in the selected region, making them a design tool for residency and isolation rather than merely private connectivity.

DNS, IAM, and packet flow

Create a private Cloud DNS zone/record for the exact REP hostname pointing at the endpoint IP; otherwise public DNS returns the public service address. Shared VPC service-project creation requires network permissions in the host project plus endpoint permissions in the service project. Hybrid clients require Cloud DNS inbound forwarding in the region of the VPN/VLAN attachment. Peered VPC clients cannot reach these endpoints.

Operations and caveats

IPv4 or /96 IPv6 endpoint addresses are supported as documented. The global-access setting cannot be changed in place: recreate the endpoint. Verify DNS first, then route/firewall reachability, endpoint state, and finally API behavior. A common failure is resolving the public REP address instead of the PSC IP.

flowchart LR; C[Client]-->D[Private DNS];D-->E[PSC regional endpoint];E-->S[Google regional API frontend];S-->R[Regional resource]

Decision: choose REP+PSC when regional processing/isolation matters; ordinary Private Google Access does not support REP endpoints.

2. Cloud DNS forwarding zones and target routing

Domain 3 — Managed services

Architecture

A forwarding zone is a private managed zone that contains forwarding targets instead of DNS records. Targets can be same-VPC internal addresses, on-premises addresses reachable over VPN/Interconnect, internet addresses, or one FQDN target. Longest-suffix private-zone matching determines which overlapping zone handles a query.

Packet flow and routing

For internal/on-prem targets, Cloud DNS originates queries from 35.199.192.0/19. Firewalls must allow TCP/UDP 53. On-premises must return that prefix through the same VPC, normally by advertising it on the relevant Cloud Router BGP session. The target that receives the query must directly send the reply; a different resolver replying causes the response to be ignored. FQDN targets resolve through VPC resolution order and can resolve to at most 50 addresses.

Failure and operations

Cloud DNS ranks targets using successful responses—including NXDOMAIN—and latency. If none reply it synthesizes SERVFAIL. Responses are cached for the shorter of 60 seconds or record TTL while targets are reachable; if all targets become unreachable, previously cached records can persist for their TTL. Troubleshoot suffix selection, route to target, firewall 53, return route for 35.199.192.0/19, and asymmetric resolver replies.

3. Application Load Balancer frontend mutual TLS

Domain 6 — Security

Trust model

Frontend mTLS authenticates the client at the target HTTPS proxy. Certificate Manager trust configs hold trust anchors and optional intermediates. The load balancer proves server identity as usual and requests a client certificate, validates possession of its private key, then validates the chain. Modes can reject invalid clients or allow invalid/missing certificates so identity details can be handled by the backend.

Limits and design

All Application Load Balancer families support mTLS. A trust config has one trust store; documented limits include 200 combined anchors/intermediates, at most 100 intermediates, 500 allowlisted certificates, chain depth 10, received chain up to 16 KB/10 certificates, RSA 2048–4096, and ECDSA P-256/P-384. Revocation checking is not performed by the load balancer. Client certificate presentation is subject to a non-configurable GFE timeout.

Operations

Rotate CAs by adding multiple anchors during overlap. Troubleshoot handshake failures by separating server-certificate negotiation from client-chain validation, checking chain completeness, key algorithms, constraints, and mode. Treat allow-invalid as transport of identity evidence, not equivalent to enforced authentication.

sequenceDiagram;Client->>ALB: TLS ClientHello;ALB-->>Client: Server cert + client-cert request;Client->>ALB: Client cert + proof;ALB->>Trust: Validate chain;ALB->>Backend: HTTP(S) request

Sources: https://docs.cloud.google.com/load-balancing/docs/mtls · https://docs.cloud.google.com/certificate-manager/docs/core-components

4. Backend mTLS: load balancer to workload authentication

Domain 6 — Security

Architecture

Backend mTLS protects the second TLS leg. Here the load balancer is the TLS client and the backend is the server. A trust config validates the backend certificate; a client certificate lets the backend authenticate the load balancer. A BackendAuthenticationConfig references both and is attached to the backend service.

Control plane and identity

Required APIs include Compute, Certificate Manager, Network Security, and Network Services. Supported backends include instance groups, hybrid connectivity NEGs, and zonal NEGs. SNI is set to the configured hostname; the backend selects its certificate using SNI, and the load balancer expects the SNI to match a SAN. Global and regional backend authentication resources must align with the backend service scope.

Failure workflow

Validate four layers: backend reachability/health, TLS protocol, server chain/SAN validation, then client-certificate acceptance by the backend. A key lifecycle caveat is that a client certificate cannot simply be attached after a BackendAuthenticationConfig is created; design certificate lifecycle before rollout.

flowchart LR; C[Client]-->LB[ALB];LB--client cert + SNI-->B[Backend];B--server cert-->LB;LB-->TC[Trust config]

Sources: https://docs.cloud.google.com/load-balancing/docs/backend-mtls-setup

5. Application Load Balancer custom request/response headers

Domain 3 — Managed services

Behavior

Custom headers let an Application Load Balancer add or transform metadata on traffic. Google recommends centralizing transformations in the URL map. Backend-service header configuration can coexist, but when the same header is set in both places, the URL map wins. Custom request headers are added to client requests sent to backends, not to health-check probes.

Design and security

Use headers for controlled metadata propagation, routing context, or backend observability, but never assume a backend will see those headers on health checks. Avoid trusting client-supplied identity headers unless the load-balancer configuration overwrites them and the backend is reachable only through the trusted path.

Troubleshooting

When a backend sees an unexpected value, inspect URL-map transformations before backend-service settings, then distinguish client traffic from health probes. Confirm the effective load-balancer mode supports the intended transformation and test with a backend that logs received headers.

flowchart LR; C[Client headers]-->U[URL map transform];U-->BS[Backend service transform];BS-->B[Backend];HC[Health check]--no custom request header-->B

Source: https://docs.cloud.google.com/load-balancing/docs/https/custom-headers-global

6. GKE Dataplane V2 eBPF service and policy processing

Domain 2 — Implement VPC

Architecture

Dataplane V2 uses eBPF programs in the node kernel to process packets with Kubernetes-aware metadata. It uses Cilium rather than kube-proxy for Kubernetes Services in supported configurations and makes NetworkPolicy enforcement intrinsic. New Autopilot clusters use Dataplane V2 by default.

Scale and constraints

The service map tracks Pod backends and has a documented 260,000-entry ceiling across Services. Published specifications include up to 10,000 Pods behind one Service, 10,000 ClusterIP Services, and 750 LoadBalancer Services for GKE, subject to broader cluster/location limits. Dataplane V2 is selected at cluster creation; existing clusters cannot be upgraded in place to it.

Operations

High rates of short-lived TCP connections can drive anetd CPU consumption; connection pooling and keep-alives can mitigate this. Troubleshooting should correlate Service endpoints, policy verdicts, node anetd health, and eBPF-based telemetry rather than assuming iptables behavior.

flowchart LR; P1[Pod]-->EBPF[eBPF/Cilium on node];EBPF-->SM[Service map];SM-->P2[Backend Pod];NP[NetworkPolicy]-->EBPF

Source: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/dataplane-v2

7. GKE Dataplane V2 observability and Hubble flow semantics

Domain 5 — Operations

Telemetry model

Dataplane V2 observability exposes workload network metrics, topology, policy verdicts, and CLI flow troubleshooting. The anetd Pod exposes Prometheus-format metrics on node port 9965; hubble-relay exposes flows through a ClusterIP service on port 443. Managed Service for Prometheus can ingest metrics through PodMonitoring.

Interpretation

Hubble flow events occur at connection establishment, first observation of a TCP flag, and periodically after at least five seconds. Consequently flow metrics count flow events—not bytes or packets—and should not be mistaken for throughput. Useful metrics include processed flows, drops, port distribution, TCP flags, and ICMP events.

Limits and failure workflow

Observability has a documented 5,000-node cluster-wide limit and requires Dataplane V2 on Google Cloud. Autopilot has metrics enabled by default but observability tools disabled by default; Standard differs. When diagnosing policy denial, correlate topology, verdict table, Hubble CLI, PodMonitoring health, and Cloud Monitoring.

flowchart LR; EBPF[eBPF flows]-->A[anetd :9965];EBPF-->H[hubble-relay :443];A-->P[Managed Prometheus];P-->M[Cloud Monitoring]

Source: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-dpv2-observability

8. NCC hybrid spoke IPv6 import/export filters

Domain 4 — Hybrid

Route policy

NCC export filters determine which routes a spoke sends to the hub; import filters determine which hub routes a hybrid spoke receives. Hybrid-spoke IPv6 dynamic-route include/exclude filtering entered Preview on August 31, 2026. Router appliance spokes remain IPv4-only for these IPv6 filter capabilities.

Design semantics

VPC/producer spokes can filter exported subnet ranges; hybrid VLAN attachment and Cloud VPN spokes can filter exported dynamic routes and imported hub routes. Include import ranges support up to 16 unique non-overlapping CIDRs; overlapping/containing entries are invalid. VPC spokes do not use import filters in the same way hybrid spokes do.

Operations

Use filters to constrain route domains, not as a packet firewall. During troubleshooting, distinguish BGP learning from NCC export acceptance and hub-to-spoke import acceptance. A route can exist at the Cloud Router yet intentionally never enter the NCC exchange domain.

9. NCC propagation of global Google APIs

Domain 4 — Hybrid

New capability

As of September 10, 2026, propagation of global Google APIs through Network Connectivity Center is Preview. This capability introduces a distinct NCC quota for propagated global Google APIs and extends the hub/spoke model beyond ordinary subnet/dynamic route exchange.

Design reasoning

Treat API endpoint propagation as a service-reachability construct controlled by NCC, not as generic transitive internet access. Inventory which API endpoints must be reachable, which spokes should receive them, and how DNS directs clients. Preserve least privilege with route/filter and service-access controls around the propagated reachability.

Troubleshooting

Separate failures into DNS name resolution, endpoint propagation/quota, hub/spoke membership, route acceptance, and application/API authorization. Preview status is itself a production-design caveat: confirm regional availability and current quotas before committing an architecture.

10. Cloud Network Insights active synthetic monitoring

Domain 5 — Operations

Architecture

Cloud Network Insights uses AppNeta-managed Monitoring Points to originate synthetic probes across Google Cloud, branches, on-premises, AWS, Azure, and internet paths. Monitoring policies define source, target, test type, protocol, and frequency. Telemetry is exported into Cloud Monitoring while alarms/events reach Cloud Logging.

Path types

Single-ended network paths provide round-trip measurements to targets without a second Monitoring Point. Dual-ended paths place agents at both ends and add one-way latency and asymmetry visibility. Web paths use either HTTP(S) checks or browser/Selenium execution to separate DNS, TCP/TLS, server, and page-load behavior.

Deployment and operations

Use a dedicated project and place Monitoring Points near the user/application perspective being measured, not on the workload itself. Google Cloud Monitoring Points need outbound HTTPS 443, NTP UDP 123, DNS 53, plus test protocols. Cloud Monitoring has a soft 10,000 MonitoredResources project limit across Monitoring Points and paths.

flowchart LR; MP1[Branch MP]--synthetic probes-->MP2[Cloud MP];MP1-->SAAS[SaaS];MP1-->CP[AppNeta control plane];CP-->MON[Cloud Monitoring/Logging]

11. Cloud Network Insights policy, metrics, and alarm workflow

Domain 5 — Operations

Policy plane

Monitoring policies are configured in AppNeta and continuously generate network or web paths. Network paths measure L3/L4 route characteristics such as RTT, loss, jitter, and path changes; web paths measure application experience including DNS resolution, TLS, HTTP status, and browser rendering.

Metric semantics

Single-ended metrics use a total perspective because they represent round trips; dual-ended paths can expose inbound and outbound one-way measurements. Network errors are categorized so DNS-resolution failure can be separated from connect refusal/unreachable and local Monitoring Point/interface problems.

Operational model

Use multiple alarm severities so early degradation can go to chat while sustained/major degradation pages an operator. Deep hop-by-hop and waterfall diagnosis remains in AppNeta, while Cloud Monitoring/Logging provides unified dashboards and alerting. This complements passive Flow Logs: synthetic probes can reveal degradation before real user traffic exists.

12. Regional API endpoint isolation versus ordinary API access

Domain 1 — Design VPC

Isolation objective

Regional endpoints constrain processing and TLS termination to one region; multi-regional endpoints constrain them to a defined jurisdiction. Public access uses Standard Tier networking, while private access can use PSC regional endpoints. This is materially different from selecting a regional resource while calling a global API hostname.

Design choices

Choose public REP endpoints when regional processing is required but internet-reachable API access is acceptable. Choose PSC REP endpoints when clients need an internal endpoint IP and private VPC/hybrid reachability. Global access on the PSC endpoint controls cross-region client reachability; DNS determines whether clients actually use that endpoint.

Verification

Verify the exact service supports REP, the requested operation/resource scope is compatible, TLS terminates in the intended region, DNS maps the hostname to the intended public or private endpoint, and hybrid clients use inbound DNS forwarding where needed. Do not assume all Google APIs support regional endpoints.
