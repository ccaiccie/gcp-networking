1. VPC firewall statefulness and connection tracking

Domain 6

Architecture and evaluation model

VPC firewall rules are distributed controls applied to VM interfaces, not packets hauled through a central firewall appliance. Their stateful behavior is fundamental: once an initiating flow is allowed and tracked, matching response traffic is automatically allowed while state remains active. The return flow must match the reverse 5-tuple—source/destination IP, source/destination port, and protocol. Google tracks TCP, UDP, SCTP, and ICMP for IPv4 and corresponding IPv6 protocols including ICMPv6.

Fragmentation, lifetime, and scale

The firewall does not reassemble fragmented TCP. The first fragment contains the transport header and can match a TCP rule; later fragments might require separate consideration. Connection tracking similarly guarantees only the first return fragment automatically. Tracked state remains active with traffic within the documented activity window; when the table is full, longest-idle entries are displaced first. Capacity is machine-type dependent: shared-core machines support 130,000 tracked connections; 1–8 vCPU machines support 130,000 per vCPU; larger machines cap at 1,040,000.

Security and troubleshooting

You cannot create a deny rule that cancels the associated response packets of an already tracked allowed connection. When a flow fails after a long idle period, distinguish state expiration from route, policy, or application failure. For very high connection-rate proxies or NVAs, monitor connection churn and size the VM with connection-state capacity in mind.

flowchart LR C[Client] -->|allowed SYN| F[VPC firewall] F --> V[VM service] V -->|reverse 5-tuple| CT[connection tracking] CT -->|state active: response allowed| C

The key observation is that response authorization comes from tracked state, not a mirror-image reverse rule.

SymptomLikely check
Return traffic works without reverse allowExpected stateful behavior
Later fragments failTransport header absent on non-first fragments
Idle sessions drop under heavy scaleTracked-connection pressure/eviction
Remember: stateful does not mean unlimited or fragment-transparent.

2. Private Service Connect service connection policies

Domain 1

Problem and components

A service connection policy lets a consumer network authorize a supported managed-service class to create PSC endpoints automatically. The policy identifies the consumer VPC, a subnet from which endpoint IP addresses can be allocated, and a connection limit. This replaces manual endpoint creation when the managed service supports automated PSC lifecycle.

Control plane and packet path

The policy is an authorization object, not a forwarding hop. The producer service control plane uses the authorization to create a PSC endpoint—an internal consumer-side forwarding rule/address. Application traffic then goes to that endpoint and PSC carries it to the producer service. Subnet address capacity and the policy connection limit therefore govern how far automated service deployment can scale.

Security, operations, and failure analysis

The trust boundary is deliberately narrow: a policy authorizes a specific service class rather than arbitrary producers. Use DNS to abstract endpoint IPs so service lifecycle does not become application configuration. If the service exists but an endpoint was never created, verify policy match, network/subnet, IAM, connection limit, and address capacity before troubleshooting data-plane routing. If the endpoint exists, then move to endpoint status, DNS, firewall, and service health.

flowchart LR A[Consumer admin] --> P[Service connection policy] P -->|service class + subnet + limit| S[Managed service control plane] S -->|creates| E[PSC endpoint] W[Workload] --> E --> D[PSC data plane] --> M[Managed producer service]

Provisioning permission and runtime packet forwarding are separate stages.

SettingEffect
SubnetProvides automated endpoint addresses
Connection limitCaps producer-created connections
Service classConstrains which managed service can use the policy
Remember: service connection policy ≠ route ≠ service attachment; it is consumer authorization for automated PSC connection creation.

Primary: AlloyDB PSC overview — service connection policy.

3. Network Connectivity Center producer VPC spokes

Domain 2

Use case and prerequisite

A producer VPC spoke extends routes for supported Google managed-service producer networks into an NCC hub. You do not attach the inaccessible producer-owned VPC directly. Instead, you identify your consumer VPC spoke and the already-active peering between that VPC and the producer. For many private-services-access products, the peering is servicenetworking-googleapis-com; NetApp Volumes uses its documented sn-netapp-* form.

Propagation and topology

After the producer spoke represents that peering, supported producer subnet routes can be propagated to other VPC spokes through NCC according to hub topology. Include/exclude export ranges let you hide or expose specific producer prefixes. In a star topology, the producer spoke and its corresponding consumer VPC spoke must be in the same group. A producer spoke does not override topology isolation or create general-purpose transitivity.

Supported scope and troubleshooting

Google documents supported services including AlloyDB, Cloud SQL, Filestore, Memorystore, Apigee, Cloud Build, Looker, Managed Lustre, NetApp Volumes, Vertex AI, and others. Third-party producer peerings are not automatically eligible. If a spoke can reach other NCC networks but not a managed-service IP, verify service support, active peering, producer-spoke association, star-group placement, and export filters.

flowchart LR P[Service producer VPC] <-->|existing peering| C[Consumer VPC spoke] C --> H[NCC hub] P -. represented by producer spoke .-> H H --> A[App VPC spoke A] H --> B[App VPC spoke B] A -->|propagated service route| P B -->|propagated service route| P

NCC propagates eligible producer routes; it does not transfer ownership of the producer network.

Remember: producer spokes depend on an existing supported producer peering and preserve NCC topology controls.

Primary: Supported services for producer VPC spokes. CLI: Create producer VPC spoke.

4. Cloud DNS cross-project binding

Domains 1 & 3

Why it exists

Shared VPC often puts network ownership in a host project while application ownership stays in service projects. Cross-project binding lets a service project own and administer a private DNS zone yet bind that zone directly to the Shared VPC network in the host project. It cleanly separates DNS namespace ownership from network ownership.

Resolution and IAM behavior

IAM remains project-scoped: the service team can manage its zone without becoming a host-project network administrator. Because the zone is directly associated with the shared network, workloads in the Shared VPC can resolve it without a placeholder VPC or a chain of DNS peering relationships. Google specifically calls out that this is useful for delegated service-project namespaces and avoids peering hop complexity.

When to choose it

Use cross-project binding when the administrative boundary is project ownership inside a Shared VPC. Use DNS peering when one VPC truly needs to consult another VPC's DNS namespace, and use forwarding when queries must be sent to alternative resolvers. When resolution fails, verify the target network/project association, zone visibility, IAM, and overlapping suffixes—especially a more-specific zone that can shadow the expected answer.

flowchart TB H[Host project: Shared VPC] --- N[Shared network] A[Service project A: owns app-a.internal] -->|bind| N B[Service project B: owns app-b.internal] -->|bind| N V1[VM/Pod A] --> N V2[VM/Pod B] --> N

The host keeps network control while service projects keep their DNS namespace control.

MechanismUse it for
Cross-project bindingSeparate zone and Shared VPC ownership
DNS peeringVPC-to-VPC namespace consultation
Forwarding zoneSend a suffix to alternative DNS servers
Remember: cross-project binding is an ownership/governance solution as much as a DNS solution.

Primary: DNS zones overview.

5. Zonal Cloud DNS zones for GKE

Domain 3

Scope and purpose

A zonal Cloud DNS managed zone can be scoped to specified GKE clusters in a location rather than exposed throughout an entire VPC. It is useful when cluster-oriented names should remain visible only to intended clusters and VPC-wide private-zone visibility would be too broad.

Configuration model

The current gcloud interface combines private visibility with --gkeclusters and --location. Because the zone is location-aware, operational commands can also require location context. Example:

gcloud dns managed-zones create my-zonal-zone \
  --dns-name=cluster.local. \
  --visibility=private \
  --gkeclusters=cluster1 \
  --location=us-east1-b

Resolution and troubleshooting

A query from a bound cluster is evaluated in the zone's intended visibility context; an unrelated VM or unbound cluster should not be assumed to see the same records. If cluster A resolves the suffix and cluster B does not, first inspect bindings and location rather than changing CoreDNS. For wrong answers, inspect overlapping zone suffixes and which authoritative private zone applies to the querying context.

flowchart LR Z[Zonal private DNS zone] -->|bound| A[GKE cluster A] A --> PA[Pods resolve records] B[GKE cluster B] -. not bound .-> Z V[Ordinary VPC VM] -. not automatically VPC-wide .-> Z

Visibility follows cluster bindings, not simply VPC membership.

Design caveat

Do not confuse zonal DNS scope with the zone name's DNS suffix. The suffix can look conventional while the resource visibility is cluster/location scoped. Operational runbooks should record both.

Remember: “private” does not always mean “all workloads in the VPC.”

Primary: gcloud dns managed-zones create.

6. GKE NodeLocal DNSCache

Domain 2

Architecture and benefit

NodeLocal DNSCache places a caching DNS agent on each GKE node. Pods query the local path first; cache hits avoid cross-node DNS traffic, and misses are forwarded to the cluster DNS provider. This lowers lookup latency, reduces pressure on centralized DNS components, and can reduce conntrack pressure for DNS-heavy workloads.

Current behavior and lifecycle

Autopilot enables NodeLocal DNSCache by default and does not let you turn it off. Standard clusters enable it by default starting with version 1.34.1-gke.3720000. Older Standard clusters can enable it through the NodeLocalDNS add-on. Enabling or disabling it on an existing Standard cluster triggers node recreation using the node upgrade strategy; maintenance policies are honored, so the change should be planned as an infrastructure rollout.

gcloud container clusters update CLUSTER_NAME \
  --location=COMPUTE_LOCATION \
  --update-addons=NodeLocalDNS=ENABLED

Failure isolation

If DNS latency affects Pods on one node, inspect that node's local DNS agent before scaling the cluster-wide DNS service. If all nodes fail similarly, move upstream to Cloud DNS/kube-dns, private-zone visibility, forwarding, or authoritative DNS. NodeLocal DNSCache does not become authoritative and cannot repair an incorrect upstream zone.

flowchart LR P[Pod] --> L[NodeLocal DNSCache] L -->|cache hit| P L -->|miss| D[Cluster DNS provider] D --> A[Authoritative DNS] A --> D --> L --> P

Local caching changes where repeated queries are answered, not which service owns the record.

ClusterCurrent behavior
AutopilotEnabled by default, not overridable
Standard ≥ 1.34.1-gke.3720000Enabled by default

7. GKE Ingress BackendConfig and FrontendConfig

Domain 3

Kubernetes-to-load-balancer mapping

GKE Ingress drives Google Cloud Application Load Balancer resources. Each referenced Service/port maps to a backend service. BackendConfig configures supported backend-service features; FrontendConfig configures selected frontend behavior such as SSL policy and HTTP-to-HTTPS redirects.

Health checks

The Google load-balancer health check is an external check and is not the same object as a Pod readiness/liveness probe. GKE can derive health settings from BackendConfig, readiness probe, or defaults, but BackendConfig gives the clearest control. With container-native load balancing, the configured health-check port must match the serving Pod's container port; with instance-group backends, it must match the Service nodePort. Custom Ingress health checks support HTTP, HTTPS, and HTTP2, not gRPC.

Feature composition and reconciliation

BackendConfig can integrate Cloud Armor, IAP, Cloud CDN, custom health checks, timeouts, and draining where supported. One Service/port pair consumes one BackendConfig even if several Ingresses reference it, so those Ingresses share the backend policy. IAP and Cloud CDN cannot be enabled simultaneously on the same backend service. To remove a previously enabled feature, explicitly set its documented disabled/empty value; simply deleting fields can fail to reconcile the underlying resource.

flowchart LR I[Ingress] --> L[Application Load Balancer] S[Service port] --> B[Backend service] BC[BackendConfig] --> B FC[FrontendConfig] --> L B --> N[NEG / instance group] --> P[Pods]

Troubleshoot by mapping the Kubernetes object to the specific Google load-balancer resource it programs.

Failure scenario

If Pods are Ready but the load balancer marks them unhealthy, compare path, protocol, and port used by the Google health checker with what the application actually serves. Readiness alone is not end-to-end proof.

Remember: BackendConfig is backend-service policy; FrontendConfig is frontend policy.

Primary: Ingress configuration. Supporting: Ingress health checks.

8. Internal passthrough Network Load Balancer global access

Domain 3

Regional load balancer, wider client geography

An internal passthrough Network Load Balancer remains regional even when global access is enabled. The forwarding rule and backends remain in one region; allowGlobalAccess widens which client regions can use that regional internal frontend. Without global access, client and connected hybrid paths are region constrained; enabling it removes that client-region restriction but does not create connectivity by itself.

Packet behavior

Because this is passthrough, the backend receives the original client source IP and the forwarding-rule VIP as destination. The guest agent installs a local route so the VM accepts the VIP, and the application must bind to the VIP or an any-address. Responses use direct server return rather than traversing a reverse proxy.

Hybrid connectivity and troubleshooting

VPC peering, Cloud VPN, and Cloud Interconnect clients can use the load balancer when routing and firewall policy permit. If remote clients fail after global access is enabled, verify the forwarding-rule flag, route advertisement/learning, backend ingress rules, return path, and application bind state. Global access does not fix a missing BGP route or a service listening only on the VM's primary address.

flowchart LR R[Remote-region client] -->|global access| V[Regional internal VIP] O[On-prem via VPN/Interconnect] -->|route + global access| V V --> B1[Backend zone A] V --> B2[Backend zone B] B1 -->|direct server return| R B2 -->|direct server return| O

Client eligibility changes; backend geography and passthrough semantics do not.

Remember: global access does not convert a regional internal NLB into a global load balancer.

Primary: Internal passthrough Network Load Balancer overview.

9. Load-balancer SSL policies and post-quantum key exchange

Domain 6

Enforcement point and scope

An SSL policy is attached to a target HTTPS or target SSL proxy and governs the frontend TLS handshake between client and load balancer. It does not configure load-balancer-to-backend TLS. Policies are global or regional to match the load-balancer/target-proxy scope; a target proxy references at most one SSL policy, while one policy can serve multiple compatible proxies.

Profiles and protocol floor

Profiles include COMPATIBLE, MODERN, RESTRICTED, FIPS_202205, and CUSTOM for selected TLS 1.2-and-earlier cipher suites. The minimum TLS version further restricts negotiation. FIPS_202205 requires a minimum of TLS 1.2. Setting the minimum to TLS 1.3 requires RESTRICTED. Without an attached policy, the load balancer behaves like COMPATIBLE with minimum TLS 1.0. Policy changes do not interrupt already-established connections; they affect new handshakes.

Post-quantum key exchange

Current SSL policies also expose post-quantum key exchange using hybrid X25519MLKEM768. ENABLED uses it with compatible TLS 1.3 clients. Google's documented rollout says DEFAULT remains off until October 2026, then becomes enabled by default; DEFERRED postpones the default until October 2027. The feature protects the frontend TLS leg only.

flowchart LR C[Client] -->|TLS leg 1: SSL policy applies| T[Target HTTPS/SSL proxy] P[SSL policy] --> T T -->|leg 2 configured independently| B[Backend]

Do not infer backend TLS posture from the frontend SSL policy.

Failure scenario

If legacy clients fail after hardening while modern clients succeed, inspect offered TLS versions/ciphers against the selected profile and minimum version. A healthy load balancer can still intentionally reject a client whose handshake no longer overlaps.

Remember: SSL policy is a frontend handshake policy, not an end-to-end TLS template.

Primary: SSL policies overview.

10. Dual-stack Cloud Interconnect VLAN attachments

Domain 4

Attachment stack type

Cloud Interconnect VLAN attachments can be IPv4-only or dual-stack. Dual stack enables both IPv4 and IPv6 user traffic. For Dedicated Interconnect, IPv6 routes can be exchanged using an IPv6 BGP session or a supported MP-BGP design. The attachment's traffic-family capability and the BGP session/address-family design are related but separate choices.

Changing an existing attachment

Changing IPv4-only to dual-stack adds IPv6 attachment state and can add a default IPv6 BGP session. If the peer router is already configured, the session can establish and start routing quickly. To stage without immediately accepting IPv6, disable the attachment or the peer's IPv6 BGP configuration first. Downgrading dual-stack to IPv4-only removes IPv6 addressing/session state and drops IPv6 traffic.

End-to-end prerequisites

The VPC must have suitable internal IPv6 subnet addressing and workloads must actually use IPv6. The peer must support the chosen session design and advertise/accept IPv6 routes. Firewall rules must permit IPv6 separately. Therefore an Established BGP session is not proof that IPv6 applications work.

flowchart LR V[VPC dual-stack workloads] --> C[Cloud Router] C <-->|IPv4 BGP + optional MP-BGP| R[On-prem router] C <-->|optional IPv6 BGP| R C --- A[VLAN attachment IPV4_IPV6] --- I[Interconnect] --- R

A single physical attachment can carry both families while route exchange can use different BGP models.

ChangeRisk
IPv4 → dual-stackPeer can begin IPv6 exchange when ready
Dual-stack → IPv4IPv6 session/address removed; IPv6 traffic drops
Remember: plan the VPC, attachment, BGP, routes, and firewall as one IPv6 dependency chain.

11. Internet NEGs for external backends

Domains 3 & 4

Endpoint model

An internet NEG represents an internet-routable backend outside the consumer VPC. Endpoint types include public IP:port and FQDN:port. It lets a Google load balancer provide a Google frontend while forwarding to a third-party/public origin—useful for migration, multi-origin architectures, and Cloud CDN external origins.

Global versus regional behavior

Global internet NEGs are scoped differently from regional internet NEGs and support different endpoint counts and health-check models. Global internet NEGs used with GFE-based load balancers do not use centralized VM-style health checks. Regional internet NEGs on Envoy-based load balancers can use distributed health checks sourced from proxy-only-subnet addresses. Origin firewall rules must account for the actual health-check source model.

Internet NEG versus hybrid NEG

Do not use an internet NEG for a private RFC1918 endpoint reachable only through Interconnect or VPN. That belongs in a hybrid connectivity NEG, which uses NON_GCP_PRIVATE_IP_PORT endpoints reached through Cloud VPN, Cloud Interconnect, or router appliances. Internet NEGs instead represent public internet reachability.

Security and troubleshooting

Protect a public origin against direct bypass. For Application Load Balancers, an origin can validate a high-entropy custom request header inserted by the load balancer in addition to origin-side access controls. Supported Cloud Armor policy can filter client requests before they reach the external origin. If regional health checks fail, inspect proxy-only-subnet source reachability rather than assuming traditional Google health-check ranges.

flowchart LR U[Client] --> L[External Application LB] L --> B[Backend service] --> N[Internet NEG] --> O[Public external origin] A[Cloud Armor] --> L L -. custom origin-auth header .-> O

The client-facing edge is Google; the backend can remain outside Google Cloud.

Remember: choose the NEG type based on how the load balancer reaches the backend, not where the application team sits.

12. Cloud Armor edge policies and network-edge protection

Domain 6

Policy types and enforcement

Cloud Armor has multiple enforcement patterns. Backend security policies are commonly attached to supported backend services for application-aware protection; edge security policies enforce earlier in the edge path and are the only Cloud Armor policy type that can attach to backend buckets. A backend service can have supported policy types attached according to product rules, so policy type and target must be designed together.

IAM and rule evaluation

Creating and modifying security-policy rules requires Compute Security Admin-class permissions; attaching a policy to a backend service uses policy-use and backend-service permissions associated with network administration. Rules are priority ordered: the highest-priority matching rule applies, followed by the default rule if no earlier rule matches. Preview is valuable before enforcing a restrictive rule.

Beyond WAF: network DDoS

Cloud Armor is not only a Layer 7 WAF. Cloud Armor Enterprise advanced network DDoS protection covers supported network load-balancer, protocol-forwarding, and public-IP VM scenarios with monitoring, mitigation, and telemetry for Layer 3/4 attacks. That is distinct from HTTP WAF signatures, rate limiting, and Adaptive Protection.

Operations

When legitimate traffic is denied, identify the exact policy type, attached target, rule priority, expression, and default action. Normalize paths in custom expressions to reduce encoding/case bypasses. For GKE Ingress, use BackendConfig as the controller-owned Cloud Armor integration point so reconciliation does not overwrite out-of-band changes.

flowchart LR C[Client/attacker] --> E[Google edge] E --> EP[Edge policy / network DDoS] EP --> L[Supported load balancer] L --> BP[Backend policy where supported] BP --> A[Application] E --> N[Network LB / protocol forwarding / public-IP protection]

Select enforcement according to traffic layer and protected resource; “Cloud Armor = WAF” is incomplete.

Remember: correct policy type + correct attachment point + correct layer are all exam-worthy design choices.

Primary: Create and manage security policies. Supporting: Advanced network DDoS protection.
