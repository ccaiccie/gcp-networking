1. External IPv4 governance with constraints/compute.vmExternalIpAccess

Domain 1 — Design and planningDomain 6 — Network security
Primary authoritative source: Compute Engine — Configure static external IP addresses
Supporting operational source: GKE — Troubleshoot cluster creation

Problem and policy boundary

Giving a VM an external IPv4 address creates a direct internet-reachable network edge and increases the number of resources that must be hardened and monitored. The list constraint constraints/compute.vmExternalIpAccess lets an organization, folder, or project restrict which Compute Engine VM instances may have external IP addresses. The control is resource-governance rather than packet filtering: it prevents a disallowed VM configuration from being created or expanded; it is not a substitute for firewall policy, Cloud Armor, identity controls, or egress inspection.

The constraint can use an allowlist of fully qualified VM resource paths, a denylist, or deny-all. An allowlist is useful for an exception-driven design such as explicitly approved bastions. Google documents the constraint as non-retroactive, so policy rollout must include an inventory and remediation plan for existing external addresses rather than assuming the policy removes them.

flowchart LR
O[Organization policy] --> E{VM permitted?}
E -->|Allowlisted| V[VM may receive external IPv4]
E -->|Not allowlisted| X[Provision/update denied]
V --> F[VPC firewall + host hardening]
V --> I[Internet]
P[Private VM] --> N[Cloud NAT or controlled proxy for egress]

What to notice: the organization policy is evaluated at configuration time. A private VM can still reach the internet through a governed egress service such as Cloud NAT without owning a public address.

Hierarchy, exceptions, and managed-workload impact

Policy can be set at different Resource Manager levels, so troubleshooting starts with the effective policy, not merely the project-local setting. The allowlist value identifies a VM by project, zone, and instance name. In Shared VPC designs, remember that worker VMs belong to service projects even though their NICs use subnets from a host project.

A major operational caveat is autoscaling. If a managed instance group or a public GKE cluster is designed to create VMs with external addresses, a restrictive policy can stop new members from being created. Google specifically documents public GKE cluster creation failures when the policy blocks node external addresses; the remedy can require changing the effective policy and recreating the failed cluster rather than repairing the incomplete cluster.

DesignBenefitFailure mode to anticipate
Deny all VM external IPsSmallest direct internet attack surfacePublic-node or legacy VM workflows fail unless redesigned
Allowlist approved VMsExplicit exception modelAutoscaled instances have dynamic names and do not fit a static exception model well
Private VM + Cloud NATInternet egress without public VM addressingRequires NAT sizing, logging, route, and firewall design

Verified configuration pattern and troubleshooting

Google documents a policy file containing the constraint and listPolicy.allowedValues, followed by gcloud resource-manager org-policies set-policy. A deny-all policy uses listPolicy.allValues: DENY. Before rollout, inventory public VM interfaces and identify managed services that expect public nodes. After rollout, validate effective policy at each exception project and test both a permitted and a denied deployment.

Scenario: a security team applies deny-all at the organization and the next GKE public cluster creation fails. Firewall debugging is a distraction: the node VM never receives the required external address. Either use an architecture compatible with private nodes or change the effective organization policy where that public-node design is intentionally allowed.

Exam/interview anchor: organization policy controls whether the resource may have the address; firewall policy controls traffic to and from an address that exists.

2. Cross-project Application Load Balancer service referencing

Domain 1 — Design and planningDomain 3 — Managed network services
Primary authoritative source: Set up a global external Application Load Balancer with Shared VPC
Supporting architecture source: External Application Load Balancer overview

Why separate frontend ownership from service ownership?

Cross-project service referencing allows a load balancer's forwarding rule, target proxy, and URL map to live in a central project while a URL map references backend services owned by other projects. This creates a useful operating model: the platform or network team owns the public entry point, certificates, and routing policy, while application teams own backend services and the workloads behind them.

The backend service remains coupled to its own backend resources and health checks. Google requires a backend service and its referenced backends to be defined in the same project, and health checks associated with that backend service are also kept with it. The cross-project boundary is therefore between the URL-map/frontend side and the backend-service side, not arbitrarily between every load-balancing resource.

flowchart LR
C[Client] --> F[Frontend + target proxy\nProject A]
F --> U[URL map\nProject A]
U -->|cross-project reference| B[Backend service\nProject B]
B --> H[Health check\nProject B]
B --> W[Backends\nProject B]
IAM[roles/compute.loadBalancerServiceUser] -. authorizes use .-> B

What to notice: IAM authorization to use the backend service is the bridge across project ownership; moving the backend itself to the frontend project is not required.

IAM, organization policy, and naming

The project that owns a backend service must authorize the load-balancer administrator to reference it, typically with roles/compute.loadBalancerServiceUser, which includes the relevant use permission. This can be granted narrowly at the resource level when governance requires it. Organization policy can further restrict cross-project service references. Classic Application Load Balancers do not support this deployment model.

Because same-named backend services can exist in different projects, Google recommends unique backend service names across an organization when cross-project references are used. This reduces operator ambiguity during incident response and URL-map review.

ResourceCentral/project AService/project B
Forwarding rule / target proxyYesNo
URL mapYesNo
Backend serviceReference onlyOwned here
Backend + health checkNoStay with backend service

Packet flow and troubleshooting

The data plane is still normal proxy load balancing: a client session terminates at Google's load-balancing infrastructure, the URL map selects the backend service, and the load balancer establishes a backend connection according to the backend service protocol. Project ownership changes control-plane authorization, not the fundamental proxy path.

Scenario: a URL-map update in Project A fails with a “cross-project references ... not allowed” style error even though the backend is healthy. Check IAM on the backend service and organization-policy restrictions before checking health-check firewall rules; this is a control-plane authorization failure, not a data-plane health failure.

Memory anchor: frontend and routing can be centralized; backend service, backends, and health check remain an application-owned unit.

3. Cross-project SSL policy referencing as centralized TLS governance

Domain 3 — Managed network servicesDomain 6 — Network security
Primary authoritative source: Use SSL policies

Control-plane model

Cross-project SSL policy referencing separates TLS policy ownership from load-balancer ownership. A central security or platform project can own approved SSL policies while target HTTPS or SSL proxies in service projects reference them. The target proxy must use the full resource URI of the central policy, which removes ambiguity about project scope.

This mechanism centralizes policy but does not merge resource scope. Global target proxies reference global policies. Regional target HTTPS proxies reference regional SSL policies in the same region. IAM is deliberately split: administrators in the central project need permissions to manage the policy, and the actor attaching it needs compute.sslPolicies.use; in the service project the actor also needs the target-proxy create or update permissions.

flowchart LR
SEC[Central security project] --> P[SSL policy]
APP[Service project] --> T[Target HTTPS/SSL proxy]
T -->|full resource URI + use permission| P
CL[Client TLS handshake] --> T
T --> B[Backend connection\nseparate protocol/security choice]

What to notice: the SSL policy governs client-to-proxy TLS. It does not automatically configure or validate encryption on the proxy-to-backend leg.

Supported attachment logic and IAM

Google documents cross-project attachment for target HTTPS proxies and target SSL proxies with scope-appropriate policy resources. The central policy project can delegate only the use permission instead of broad edit rights. This supports a strong separation-of-duties model: service teams can deploy load balancers but cannot silently weaken the organization's approved TLS baseline.

ConcernCentral policy projectService project
Create/change SSL policySecurity/network/load-balancer admin roleNot required
Attach central policycompute.sslPolicies.useTarget proxy create/update
ScopeGlobal or regional policyProxy scope must be compatible

Validated CLI pattern and failure analysis

gcloud compute target-https-proxies update TARGET_PROXY_NAME \
  --ssl-policy=projects/POLICY_PROJECT_ID/global/sslPolicies/CENTRAL_SSL_POLICY_NAME \
  --project=SERVICE_PROJECT_ID

For a regional target HTTPS proxy, Google documents the regional policy URI and the --region flag. If attachment fails, verify policy scope, project IDs, compute.sslPolicies.use, and target-proxy permissions independently. A successful attachment followed by backend TLS errors points elsewhere: backend protocol, certificates, or backend mTLS configuration.

Scenario: a service owner can update a URL map but receives permission denied when attaching the approved central policy. Granting broad project Editor would work but violates least privilege; grant the explicit policy-use permission plus the required proxy update role instead.

Exam anchor: centralized TLS governance is a resource-reference and IAM problem; frontend SSL policy and backend encryption are separate security planes.

4. HTTP/3 over IETF QUIC at the external Application Load Balancer edge

Domain 3 — Managed network servicesDomain 5 — Operations
Primary authoritative source: External Application Load Balancer overview — HTTP/3
Supporting source: External Application Load Balancer performance best practices

Where HTTP/3 exists in the proxy path

HTTP/3 uses HTTP semantics over QUIC, which uses UDP and integrates TLS 1.3. For Google external Application Load Balancers, HTTP/3 is a client-to-load-balancer protocol. It is not the protocol used from the load balancer to an application backend. Treat the two proxy legs independently: a client can use HTTP/3 while the backend service uses HTTP, HTTPS, HTTP/2, or another supported backend protocol.

sequenceDiagram
participant C as Client
participant G as Google load-balancing edge
participant B as Backend
C->>G: HTTPS discovery / HTTP/3 advertisement
C->>G: QUIC over UDP + TLS 1.3
G->>B: New proxy connection using configured backend protocol
B-->>G: Response
G-->>C: HTTP/3 response
Note over C,G: If QUIC/UDP cannot establish, a compliant client falls back to HTTPS/HTTP/2

What to notice: HTTP/3 does not make the application server an HTTP/3 server when a proxy load balancer is in between.

Why QUIC helps and why it can fail silently

QUIC can reduce transport head-of-line blocking and handles connection migration better than a TCP connection identified by a fixed 5-tuple. Google also documents BBR congestion control for HTTP/3 connections. These properties can improve latency and throughput, especially on mobile or lossy networks.

The operational caveat is UDP reachability. Enterprise firewalls, client networks, or middleboxes can block or rate-limit UDP. Proper clients fall back to HTTPS/HTTP/2, so an application may appear healthy while the expected HTTP/3 performance benefit is absent. Troubleshooting therefore needs protocol-aware client tests and edge telemetry rather than only checking HTTP status codes.

LegPossible protocolWho controls it?
Client → load balancerHTTP/1.1, HTTP/2, HTTP/3 as supportedClient capability, LB mode/config, network path
Load balancer → backendConfigured backend service protocolBackend service setting and backend capability

Design and troubleshooting scenario

For supported global external deployments, the QUIC override controls whether the load balancer advertises HTTP/3. When users on one corporate network show higher latency while home users negotiate HTTP/3, test whether UDP to the load-balancer edge is blocked. Do not “fix” the backend to speak HTTP/3; that misunderstands the proxy boundary.

Memory anchor: HTTP/3 is an edge protocol optimization; backend protocol selection remains an independent design choice.

5. Application Load Balancer backend protocol selection and HTTP/2 connection economics

Domain 3 — Managed network servicesDomain 5 — Operations
Primary authoritative source: External Application Load Balancer performance best practices
Supporting source: Encryption from the load balancer to backends

Backend protocol is explicit, not negotiated as a fallback chain

The backend service protocol tells the proxy how to communicate with its backend. For Application Load Balancers, common choices include HTTP, HTTPS, HTTP/2 over TLS, and where supported H2C for cleartext HTTP/2. Google documents that the load balancer uses the protocol configured on the backend service and does not fall back to a different backend protocol when communication fails.

This is independent from the client-facing protocol. A client can negotiate HTTP/2 with the HTTPS frontend while the load balancer uses HTTP/1.1 HTTPS to a backend, or the frontend can receive HTTP/3 while the backend connection uses HTTP/2. Proxy termination is the decoupling point.

flowchart LR
C[Client protocol\nHTTP/1.1, HTTP/2, or HTTP/3] --> P[Application LB proxy]
P -->|backend service = HTTP| H1[HTTP/1.1 backend]
P -->|backend service = HTTPS| H2[HTTP/1.1 + TLS backend]
P -->|backend service = HTTP2| H3[HTTP/2 + TLS backend]
P -->|where supported: H2C| H4[HTTP/2 cleartext backend]

Connection pooling and latency

A counterintuitive Google-documented behavior is that HTTP/2 from the load balancer to backend instances can require more TCP connections than HTTP or HTTPS. The connection-pooling optimization used for HTTP/1.1 HTTP(S) backends is not available in the same way for HTTP/2 backends, so frequent backend connection creation can raise backend latency. Protocol choice should therefore be driven by application requirements such as gRPC or end-to-end HTTP/2 semantics, not by the assumption that HTTP/2 always reduces every connection count.

For HTTP/2 over TLS, backends must serve TLS and the backend service protocol must be HTTP2. For H2C, TLS is not used on that leg. Google also distinguishes network-level encryption inside supported Google Cloud backend cases from application-layer TLS; hybrid or internet NEG backends deserve explicit secure protocol choices.

ProtocolBackend TLSOperational point
HTTPNo application TLSSimple HTTP/1.1; evaluate trust boundary
HTTPSYesHTTP/1.1 with TLS; connection pooling available
HTTP2YesRequired for some gRPC designs; may create more backend TCP connections
H2CNoHTTP/2 over cleartext where the LB mode supports it

Failure scenario

An application team changes the backend service to HTTP2 because clients use HTTP/2, but backend servers only listen for HTTP/1.1 TLS. The load balancer will not automatically downgrade to HTTPS. The correct repair is to align backend capability with the configured backend protocol, or choose HTTPS if end-to-end HTTP/2 is not required.

Exam anchor: client protocol and backend protocol are independent; troubleshoot each proxy leg separately.

6. Cloud Router explicit BGP identifier ranges for stable router IDs

Domain 2 — Implementing VPC networksDomain 4 — Hybrid connectivity
Primary authoritative source: Configure the BGP identifier range for a Cloud Router

Router ID behavior and why stability matters

A BGP identifier (router ID) is a 4-octet unsigned value represented in IPv4 notation. Cloud Router can derive a router ID automatically from its IPv4 BGP interfaces, but that convenience has an operational side effect: without an explicit BGP identifier range, adding or removing BGP sessions or periodic maintenance can change the automatically selected identifier. A router-ID change can restart BGP adjacency and therefore cause avoidable control-plane churn.

Assigning an explicit identifier range gives Cloud Router a stable identifier. It is required for IPv6 BGP. If an IPv6 interface is added to a router that lacks the explicit setting, Google can automatically populate a random range from link-local IPv4 space.

flowchart TB
R[Cloud Router] --> I{Explicit identifier range?}
I -->|Yes| S[Stable router ID selected from range]
I -->|No, IPv4 only| A[Auto ID from lexicographically-last IPv4 interface]
I -->|IPv6 added| G[Identifier range required / populated]
A --> C[Interface/session changes can alter ID]
C --> X[BGP restart risk]

Range rules and change impact

Google requires the explicit identifier range to come from 169.254.0.0/16 with a prefix length of at most /30. It must not overlap IPv4 ranges used by BGP sessions on the router or custom BGP identifier ranges of another Cloud Router in the same VPC network and region. This is control-plane address planning; it does not become an advertised workload prefix.

Changing an existing explicit BGP identifier range is disruptive: Google warns that all existing BGP sessions for all peers on the Cloud Router restart. Treat a retrofit like a routing maintenance event, verify redundant paths, and avoid simultaneous maintenance on parallel connectivity.

CaseRouter-ID behaviorDesign action
IPv4 BGP, no explicit rangeDerived automatically and can changeAccept churn risk or configure a stable range
IPv6 BGPExplicit identifier range requiredPlan nonoverlapping 169.254/16 space
Modify existing rangeAll router BGP sessions restartUse a maintenance/failover plan

Validated CLI and troubleshooting

gcloud compute routers create ROUTER_NAME \
  --bgp-identifier-range=BGP_IDENTIFIER_RANGE

gcloud compute routers update ROUTER_NAME \
  --bgp-identifier-range=BGP_IDENTIFIER_RANGE

If creation fails, verify that the range is link-local, appropriately sized, and nonoverlapping. If a network experiences BGP resets after routine interface changes and no explicit identifier is configured, compare router IDs before and after the event.

Memory anchor: BGP peer addresses establish the session; the BGP identifier identifies the router. Do not conflate the two.

7. Partner Interconnect ASN 16550 and Cloud Router sharing constraints

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary authoritative source: Create Partner Interconnect VLAN attachments
Supporting source: Cloud Router BGP identifier and ASN guidance

The Partner Interconnect ASN exception

Normal Cloud Router creation uses a private Google-side ASN from documented private ranges. Partner Interconnect is a notable exception: the Cloud Router associated with Partner Interconnect VLAN attachments must use Google's public ASN 16550. This constraint is easy to miss when a design standard assumes every Cloud Router should use an enterprise-selected private ASN.

A Cloud Router uses one local ASN across all BGP sessions it manages. Therefore, choosing 16550 for Partner Interconnect affects what else that router can manage. It naturally fits other Partner Interconnect sessions and can be shared with a Dedicated Interconnect attachment only if using 16550 is acceptable for that routing design. Do not plan to attach a different local ASN to another session on the same Cloud Router.

flowchart LR
CR[Cloud Router\nlocal ASN 16550] --> P1[Partner VLAN attachment A]
CR --> P2[Partner VLAN attachment B]
CR --> D[Dedicated attachment\npossible only if same local ASN design works]
CR -. cannot use a second local ASN .-> X[Session requiring a different Cloud Router ASN]

Attachment creation and provider handoff

A Partner Interconnect VLAN attachment is created with type PARTNER and an existing Cloud Router in the network and region to be reached. Google automatically creates the router interface and BGP peer elements associated with the attachment, and the attachment produces a pairing key that is shared with the service provider. The provider completes its side of provisioning before the attachment reaches a usable state.

The attachment MTU is another contract across the path. Google currently documents valid Partner attachment MTUs of 1440 (default), 1460, 1500, and 8896; using a larger value requires compatible VPC, on-premises VM, router, and provider-path configuration.

Design checkPartner Interconnect implication
Cloud Router local ASNMust be 16550
BGP session creationGoogle/provider workflow creates session components for the attachment
Pairing keyShare with the connectivity provider
Router reuseAll sessions share the same local ASN; separate routers when ASN requirements conflict

Failure scenario and verification

A team tries to reuse a Cloud Router created with private ASN 64514 for a new Partner Interconnect attachment and treats the failure as a provider issue. The correct first check is the Cloud Router ASN. Conversely, if 16550 is correct but the attachment is awaiting provider activation, changing BGP timers is premature.

Exam anchor: Partner Interconnect changes the local-AS assumption: remember 16550 and the one-ASN-per-Cloud-Router consequence.

8. Dedicated Interconnect single-region 99.99% Critical production topology

Domain 1 — Design and planningDomain 4 — Hybrid connectivity
Primary authoritative source: Establish 99.99% availability for Dedicated Interconnect
Comparison source: Establish 99.9% availability for Dedicated Interconnect

SLA is a topology property, not a connection count

Google recommends the 99.99% configuration for production and mission-critical workloads. The important design principle is failure-domain diversity: merely ordering several Interconnect circuits does not create the intended SLA if they share the wrong metro or edge availability domain. In the traditional multi-metro critical topology, at least four connections are distributed across two metros and both edge availability domains in each metro. Google also supports qualifying single-region 99.99% topologies in supported metros, introduced as a production-critical option.

For comparison, the 99.9% design uses at least two Dedicated Interconnect connections distributed across a valid pair of facility/edge-availability-domain combinations in one metro and is positioned for noncritical workloads that can tolerate some downtime.

flowchart TB
ON[On-premises routers] --> M1A[Metro A / EAD 1]
ON --> M1B[Metro A / EAD 2]
ON --> M2A[Metro B / EAD 1]
ON --> M2B[Metro B / EAD 2]
M1A --> VA[VLAN attachments]
M1B --> VA
M2A --> VA
M2B --> VA
VA --> CR[Cloud Router BGP tasks]
CR --> VPC[VPC]

VLAN attachments, Cloud Router tasks, and maintenance

For the documented multi-region 99.99% topology, each VPC uses at least four VLAN attachments, each dependent on a unique Interconnect connection. Google points out that simply creating more Cloud Router resources does not increase the SLA: Cloud Router distributes VLAN-attachment BGP sessions across redundant BGP software tasks based on edge availability domain. Reliability comes from the complete connectivity topology, not from counting router objects.

Maintenance is coordinated between edge availability domains within a metro, but not necessarily among different metros. That is why metro diversity matters. On-premises routers should advertise the same destination prefixes across the redundant BGP sessions; MED or other routing policy can influence preferred paths without removing failover reachability.

TargetTopology ideaUse case
99.9%At least 2 connections across paired facility/EAD combinations in one metroNoncritical, downtime-tolerant
99.99%Production-critical qualifying topology; multi-metro design uses at least 4 connections across both EADs in two metrosMission-critical / low downtime tolerance

Capacity and failure testing

An SLA-shaped topology can still fail operationally if surviving links cannot carry the failed link's traffic. Capacity planning therefore includes N-1/N-N failure bandwidth, BGP preference, VLAN attachment quotas, and on-prem router redundancy. Test withdrawal of preferred paths and verify that failover does not overload remaining circuits.

Scenario: four circuits are ordered, but all terminate in one metro. The circuit count looks impressive, yet the design does not meet the documented multi-metro 99.99% failure-domain pattern. Fix placement before tuning BGP.

Memory anchor: for Interconnect, availability is built from metro + edge-domain diversity + attachment design + failover capacity.

9. Connectivity Tests analysis of Google Threat Intelligence firewall rules

Domain 5 — Operations and troubleshootingDomain 6 — Network security
Primary authoritative source: Network Intelligence Center release notes — September 22, 2026
Supporting source: Connectivity Tests overview

What changed on September 22, 2026

Google announced that Connectivity Tests now analyzes firewall policy rules that use Google Threat Intelligence data. That matters because configuration analysis can now incorporate a policy decision whose source match is maintained by Google's threat-intelligence data rather than only static address constructs. For network operations, this closes a visibility gap between “the route exists” and “the effective security policy allows the simulated flow.”

Connectivity Tests is fundamentally a configuration-analysis system. It builds a model of the path and evaluates relevant Google Cloud network configuration. In selected scenarios it can also perform live data-plane probing, but a successful or failed configuration analysis should not be confused with synthetic application transaction testing.

flowchart LR
S[Source endpoint] --> CT[Connectivity Tests model]
CT --> R[Route / LB / NAT evaluation]
R --> FP[Firewall policy evaluation]
GTI[Google Threat Intelligence lists] --> FP
FP -->|allow path| D[Destination modeled reachable]
FP -->|deny match| X[Trace identifies policy decision]

Operational workflow

When investigating a suspected firewall issue, define the source, destination, protocol, and port accurately. Read the trace in order rather than jumping directly to the final verdict. A GTI-backed firewall rule can be the decisive step even if route selection, peering, or load-balancer configuration is correct. Conversely, a GTI-enabled rule being present does not prove that a particular IP is currently in the relevant intelligence category; evaluate the trace output.

Tool/outputQuestion it answers
Connectivity Tests configuration analysisGiven current modeled configuration, should this flow be reachable and which control decides?
Live data-plane analysis where supportedCan active probes corroborate modeled connectivity?
Firewall/security logsWhat happened to real traffic and which policy/rule matched?

Scenario and troubleshooting boundary

A VM loses access to a destination after a security team introduces a GTI-based deny rule. Routing tables are unchanged. Run a Connectivity Test with the exact tuple and inspect the firewall-policy step; if the modeled policy now denies it, changing routes is counterproductive. Then use logging and security-team context to determine whether the destination belongs in an intelligence-driven block category or the application should use a different destination.

Freshness anchor: GTI firewall-rule analysis in Connectivity Tests is a September 22, 2026 capability, so older troubleshooting runbooks may omit it.

10. Cloud Armor managed rules: stable/canary signature operations

Domain 6 — Cloud network security
Primary authoritative source: Cloud Armor managed rules overview
Configuration source: Set up managed rules
Release source: Cloud Armor release notes — September 17, 2026 Preview

Managed rules versus static hand-maintained signatures

Cloud Armor managed rules are Google-maintained threat-detection groups that are integrated directly into Cloud Armor security policies. Google curates and validates signatures against threat intelligence, automatically rolls signature updates, and can expedite emergency coverage for time-sensitive or zero-day vulnerabilities. The feature entered Preview on September 17, 2026.

The managed-rules model differs from merely enabling an OWASP CRS version and leaving it unchanged. The category is a living signature stream. Current documented categories include SQL injection, cross-site scripting, local/remote file inclusion, automated threats, authentication bypass, account takeover, SSRF, file upload, data leakage, backdoor/trojan, spam/abuse, and miscellaneous threats.

flowchart LR
REQ[Incoming request] --> C[Cloud Armor security policy]
C --> CAN[Managed rules canary\npreview / early signatures]
CAN --> LOG[Logs for impact review]
C --> ST[Managed rules stable\nenforced production baseline]
ST -->|match| D[Deny/action]
ST -->|no match| B[Backend service]

Stable/canary deployment strategy

Google recommends stable for production-validated behavior and canary for earlier signature exposure. A strong rollout pattern places canary at a higher priority in preview mode and stable at a lower priority in enforced mode. Preview lets operators observe what canary would have blocked before it can impact users, while stable continues enforcement.

Security-policy rule priority still matters. Cloud Armor executes the action of the highest-priority matching terminal rule. Treat managed rules as part of the overall policy graph, not as a separate appliance inserted after every custom rule.

Version strategyUseOperational treatment
stableProduction-validated signaturesEnforced baseline; automatically updated
canaryEarly-access signaturesPrefer preview first; analyze logs before enforcement

Validated configuration pattern

gcloud compute security-policies rules create 100 \
  --security-policy POLICY_NAME \
  --action deny-403 \
  --expression "evaluateManagedRules('xss:canary')" \
  --preview

gcloud compute security-policies rules create 200 \
  --security-policy POLICY_NAME \
  --action deny-403 \
  --expression "evaluateManagedRules('xss:stable')"

The policy does not protect a workload until attached to a supported backend service. Logs expose managed-rules metadata such as ruleset ID/version and preview matches, which should be part of the promotion decision.

Exam/interview anchor: canary preview is the safety valve for automatically evolving signatures; stable is the enforced baseline.

11. Cloud Armor CEL matching on raw request bodies and structured parameters

Domain 6 — Cloud network security
Primary authoritative source: Configure custom rules language attributes
Supporting source: Request body content parsing
Release source: Cloud Armor release notes — August 27, 2026 Preview

New application-aware custom-rule inputs

On August 27, 2026 Google announced Preview support for advanced match conditions that inspect request body content and parameters. The custom CEL language exposes request.body as the raw request body string and request.params as a map of parsed parameters. Parameter sources can include URL query parameters and supported structured request bodies such as JSON, form data, and GraphQL.

This is different from preconfigured WAF parsing. The goal here is to build an explicit custom policy condition around an application-specific field or body pattern. The language still follows normal Cloud Armor rule priority semantics: once the highest-priority matching rule with a terminal action is selected, lower-priority rules are not evaluated.

flowchart TB
R[HTTP request] --> A[Cloud Armor]
A --> RAW[request.body\nraw string]
A --> PAR[request.params\nparsed map]
RAW --> CEL[CEL advanced condition]
PAR --> CEL
CEL -->|match| ACT[allow / deny / other supported action]
CEL -->|no match| NEXT[Continue policy evaluation]

Examples and parsing boundaries

Google's documented examples include matching a POST body that contains a value and testing a parameter by name. For example, request.method == 'POST' && request.body.contains('malicious-value') examines the raw body, while request.params.category == 'electronics' evaluates a parsed parameter. Use raw-body inspection when literal content is important; use parameters when application structure is the policy contract.

Body inspection is bounded. Cloud Armor documents request-body inspection sizes up to the first 64 kB, configurable among supported sizes. JSON parsing should be enabled appropriately for workloads that rely on REST, JSON, or GraphQL. Oversized or malformed content can change what is visible to a rule, so security design should not assume arbitrary request bodies are fully inspected.

request.bodyRaw stringLiteral markers, prefixes, regex over body text
request.paramsKey/value mapQuery, JSON/form/GraphQL parameter policy

Security and troubleshooting scenario

A rule is meant to block a dangerous JSON field but never matches. First verify Content-Type and parsing behavior, then inspection-size limits, then the CEL expression and rule priority. If a higher-priority terminal rule already matches, the body rule will not run. Preview mode and request logging are safer ways to validate custom conditions before enforcing them.

Memory anchor: request.body is raw content; request.params is structured data. Select the representation that matches the application contract.

12. GKE Gateway Policy model: HealthCheckPolicy and GCPBackendPolicy

Primary authoritative source: Configure Gateway resources
Supporting source: GKE Gateway controller concepts

Policy attachment replaces Ingress-specific configuration habits

GKE Gateway uses Gateway API resources plus Google policy custom resources instead of treating older Ingress annotations or BackendConfig/FrontendConfig as interchangeable configuration. The selected GatewayClass determines which Google Cloud load-balancer implementation is created. Routes attach to Gateways, while policies attach to specific Kubernetes resources to shape generated Google Cloud infrastructure.

HealthCheckPolicy configures health checks for a backend target. GCPBackendPolicy configures backend-service behavior. For single-cluster Gateways, the target is typically a Service; for multi-cluster patterns, policy can target a ServiceImport as documented. Policy and target must satisfy scope/namespace requirements.

Health checks are not Pod readiness probes

A key troubleshooting distinction is that the Google Cloud load balancer health check is not automatically equivalent to a Kubernetes Pod readiness probe. If the application does not return a healthy response on the default health-check behavior, define a HealthCheckPolicy that matches the actual application endpoint and protocol. A Pod can be Kubernetes-ready yet remain unhealthy to the load balancer, or the reverse, if these contracts are misaligned.

Policy conflicts are deterministic rather than merged arbitrarily. Google documents that only one GCPBackendPolicy can attach to a target; when conflicting policies attempt to target the same resource, the controller reports policy status and uses its documented precedence behavior. Always inspect resource status conditions instead of inferring that the newest YAML won.

Prerequisites and scenario

Gateway deployment prerequisites depend on GatewayClass but include a compatible GKE version/configuration, VPC-native networking, and for regional/cross-region proxy-based load balancers an appropriate proxy-only subnet. The cluster's HTTP load-balancing capability must not be disabled when the controller depends on it.

Scenario: a service returns 200 on /ready but 404 on /. Pods are Ready, yet the Gateway backend stays unhealthy. Rather than changing firewall rules first, inspect the Google Cloud health check and attach a HealthCheckPolicy that probes the application's real health endpoint.

Exam/interview anchor: Kubernetes readiness and load-balancer health are related operationally but are distinct control planes.
