1. External IPv4 governance with constraints/compute.vmExternalIpAccess

Domain 1 — Design and planningDomain 6 — Network security
Primary: Compute Engine — Configure static external IP addresses
Supporting: GKE — Troubleshoot cluster creation

Problem, scope, and trust boundary

A VM external IPv4 address creates a directly reachable internet edge. The list constraint constraints/compute.vmExternalIpAccess lets an organization, folder, or project restrict which Compute Engine VM instances may have external IPs. This is a resource-governance control evaluated when a VM configuration is created or changed; it is not a packet filter and does not replace VPC firewall policy, host hardening, identity controls, or application-layer protection.

The constraint can use allowed values, denied values, or deny-all. Allowlisted values identify individual VM resources by project, zone, and instance name. Google documents the control as non-retroactive, so a rollout needs an inventory and remediation plan for existing external addresses rather than assuming the policy removes them.

flowchart LR
O[Org / folder / project policy] --> E{VM allowed external IP?}
E -->|yes| V[VM external IPv4 may be configured]
E -->|no| X[Provision or update denied]
V --> FW[VPC firewall + host controls]
P[Private VM] --> N[Cloud NAT / controlled egress]
N --> I[Internet]

Notice: private workloads can still use controlled egress without each VM owning a public address.

Hierarchy, managed services, and failure modes

Always inspect the effective policy across the Resource Manager hierarchy. In Shared VPC, worker VMs are resources of service projects even though they consume host-project subnets. A restrictive policy can also surprise managed systems that create VMs dynamically. Google specifically warns that managed instance groups and public GKE clusters that need external addresses can fail to scale or create nodes under an incompatible policy. For a failed public GKE creation caused by the constraint, changing the effective policy can require recreating the failed cluster.

PatternBenefitMain caveat
Deny allSmallest direct VM internet exposureBreaks designs that require public VM addresses
Per-VM allowlistExplicit exceptions such as approved bastionsPoor fit for dynamic autoscaled names/resources
Private VM + Cloud NATInternet egress without public VM IPRequires NAT capacity, logging, routing, and firewall design

Validated configuration and troubleshooting

Google documents a policy file containing constraint: constraints/compute.vmExternalIpAccess and listPolicy.allowedValues, applied with gcloud resource-manager org-policies set-policy. A deny-all policy uses listPolicy.allValues: DENY. Validate both a permitted and denied test deployment and monitor managed-workload creation after rollout.

Scenario: a public GKE cluster creation fails before nodes become usable. If audit logs show this organization-policy violation, firewall debugging is premature: the resource configuration was denied before normal network reachability could exist.

Anchor: organization policy decides whether the external address may exist; firewall policy decides what traffic an existing interface can exchange.

2. Cross-project Application Load Balancer service referencing

Domain 1 — Design and planningDomain 3 — Managed services
Primary: Global external Application Load Balancer with Shared VPC
Supporting: External Application Load Balancer overview

Architecture and ownership split

Cross-project service referencing lets a load balancer's frontend resources and URL map live in one project while the URL map references backend services owned by other projects. It supports a platform model in which the network team owns the public entry point, certificates, target proxy, and routing policy while application teams retain their backend-service configuration and workloads.

The backend service remains coupled to its backends and associated health checks; these stay in the backend-service project. The cross-project boundary is therefore intentional rather than arbitrary.

flowchart LR
C[Client] --> F[Forwarding rule + target proxy\nProject A]
F --> U[URL map\nProject A]
U -->|cross-project use| B[Backend service\nProject B]
B --> H[Health check\nProject B]
B --> W[Backends\nProject B]
IAM[Load Balancer Services User] -. authorizes reference .-> B

IAM, organization policy, and data plane

The backend-owning project must authorize use of the referenced service, commonly with roles/compute.loadBalancerServiceUser or the equivalent narrow use permission. Organization policy can further limit cross-project references. Classic Application Load Balancers do not support this model. Google also recommends unique backend-service names across projects to reduce operator ambiguity.

Project ownership changes the control plane, not the proxy packet path. The client connection terminates at Google's load-balancing infrastructure; the URL map chooses a backend service; the proxy creates a backend connection according to that service's protocol and health.

ResourceCentral projectService project
Forwarding rule / target proxy / URL mapOwnedNot required
Backend serviceReferencedOwned
Backends + health checksNoOwned with backend service

Failure scenario

If a URL-map update fails with a cross-project reference permission error while the backend itself is healthy, check the backend-service use permission and organization policy first. Health-check firewall changes cannot repair a control-plane authorization failure.

Anchor: central routing, decentralized services; IAM is the explicit bridge across ownership.

3. Cross-project SSL policy referencing for centralized TLS governance

Domain 3 — Managed servicesDomain 6 — Security
Primary: Use SSL policies — cross-project SSL policy referencing

Why this is different from ordinary SSL-policy tuning

The design problem here is ownership, not cipher selection. A central security project can own approved SSL policies while target HTTPS or SSL proxies in service projects reference them. The service team can therefore operate a load balancer without receiving the ability to weaken centrally governed TLS policy.

The target proxy references the central policy by full resource URI. Scope still matters: global proxies use global policy resources, and regional HTTPS proxies use compatible regional policy resources. Cross-project reference does not convert regional resources into global ones.

flowchart LR
SEC[Central security project] --> P[Approved SSL policy]
APP[Service project] --> T[Target HTTPS/SSL proxy]
T -->|full URI + sslPolicies.use| P
CL[Client TLS] --> T
T --> BK[Backend connection\nseparately configured]

IAM and security planes

Google lists central-project roles such as Compute Security Admin, Network Admin, or Load Balancer Admin for policy management, while attachment can be delegated with compute.sslPolicies.use. The service project still requires target-proxy create/update permissions. This separation supports least privilege and change control.

The SSL policy governs the client-to-proxy TLS leg. Backend encryption is a separate decision involving the backend service protocol, backend certificates, and optional backend mTLS. Successful frontend policy attachment does not prove backend TLS is healthy.

ActionControl
Create/change central policyCentral security/network role
Attach central policycompute.sslPolicies.use plus target-proxy update permission
Secure backend legBackend protocol/certificate/mTLS configuration

Validated CLI pattern

gcloud compute target-https-proxies update TARGET_PROXY_NAME \
  --ssl-policy=projects/POLICY_PROJECT_ID/global/sslPolicies/CENTRAL_SSL_POLICY_NAME \
  --project=SERVICE_PROJECT_ID

Regional target HTTPS proxies use a regional policy URI and region flag. If attachment fails, isolate policy scope, resource URI, central use permission, and service-project proxy permissions before touching application backends.

Anchor: cross-project SSL policies centralize governance of client-side TLS; they do not collapse frontend and backend security into one setting.

4. HTTP/3 over IETF QUIC at the external Application Load Balancer edge

Domain 3 — Managed servicesDomain 5 — Operations
Primary: External Application Load Balancer overview — HTTP/3
Supporting: Performance best practices

Two proxy legs, two protocol choices

HTTP/3 carries HTTP over QUIC, which uses UDP with integrated TLS 1.3. In Google external Application Load Balancers, HTTP/3 is a client-to-load-balancer capability. It is not used on the proxy-to-backend connection. A client can therefore use HTTP/3 while the backend service is HTTP, HTTPS, HTTP/2, or another supported protocol.

sequenceDiagram
participant C as Client
participant G as Google edge
participant B as Backend
C->>G: HTTP/3 over QUIC/UDP
G->>B: Configured backend protocol
B-->>G: Backend response
G-->>C: HTTP/3 response
Note over C,G: If QUIC cannot establish, compliant clients fall back to HTTPS/HTTP/2

Performance and middlebox behavior

QUIC reduces transport head-of-line blocking and supports connection migration, which can help mobile and higher-latency clients. Google documents BBR congestion control for HTTP/3 connections. The main operational dependency is UDP reachability: enterprise networks or middleboxes that block or rate-limit UDP can prevent QUIC while leaving ordinary TCP/443 healthy.

Because clients normally fall back, the application might appear healthy while silently losing the expected HTTP/3 performance benefit. Use protocol-aware tests and edge telemetry rather than treating a successful HTTP status alone as proof that HTTP/3 is operating.

LegProtocol authorityTypical failure clue
Client → LBClient capability + LB support + network pathQUIC fails but HTTP/2 fallback works
LB → backendBackend service protocolBackend protocol/TLS mismatch

Scenario

Home users negotiate HTTP/3 but corporate users do not, while both receive valid pages. Investigate UDP/QUIC policy on the corporate path; changing the backend to “HTTP/3” is the wrong layer because the load balancer terminates the client protocol.

Anchor: HTTP/3 is an edge transport optimization; backend protocol remains an independent proxy-leg decision.

5. Application Load Balancer backend protocol selection and HTTP/2 connection economics

Domain 3 — Managed servicesDomain 5 — Operations
Primary: External Application Load Balancer performance best practices
Supporting: Encryption from the load balancer to backends

Protocol is explicit

The backend service protocol tells the proxy how to talk to its backends. Common Application Load Balancer choices include HTTP, HTTPS, HTTP/2 over TLS, and H2C where supported. Google states that the load balancer uses the configured backend protocol and does not fall back to a different one if that protocol cannot communicate with the backend.

Frontend and backend protocols are independent. A client can negotiate HTTP/2 or HTTP/3 while the backend connection uses HTTP/1.1 HTTPS, or an HTTP/1.1 client can be proxied to an HTTP/2 backend.

flowchart LR
C[Client HTTP/1.1, 2, or 3] --> P[Application LB proxy]
P -->|HTTP| H1[HTTP/1.1 cleartext backend]
P -->|HTTPS| H2[HTTP/1.1 + TLS]
P -->|HTTP2| H3[HTTP/2 + TLS]
P -->|H2C where supported| H4[HTTP/2 cleartext]

Connection pooling, encryption, and gRPC

A counterintuitive behavior documented by Google is that HTTP/2 between the load balancer and backend instances can require significantly more TCP connections than HTTP or HTTPS because the HTTP(S) connection-pooling optimization is not available in the same way. Frequent connection setup can increase backend latency. Choose HTTP/2 because the application semantics require it, not because “HTTP/2 always means fewer connections.”

For the HTTP2 backend protocol, backends must use TLS. H2C is HTTP/2 over cleartext TCP where supported. For backends outside the Google Cloud VPC trust boundary, explicitly secure the backend leg rather than assuming network-level encryption.

Backend protocolTLS on backend legKey point
HTTPNo application TLSHTTP/1.1
HTTPSYesHTTP/1.1 over TLS, pooling optimization
HTTP2YesNeeded for some gRPC designs; potentially more TCP connections
H2CNoHTTP/2 cleartext where supported

Scenario

A team changes a backend service from HTTPS to HTTP2 only because clients use HTTP/2. Backends still speak HTTP/1.1 TLS and begin failing. The load balancer will not “downgrade” its backend protocol; align the backend capability or restore HTTPS.

Anchor: troubleshoot the client leg and backend leg independently, and include connection-count behavior in HTTP/2 capacity analysis.

6. Cloud Router explicit BGP identifier ranges for stable router IDs

Domain 2 — VPC implementationDomain 4 — Hybrid connectivity
Primary: Configure the BGP identifier range for a Cloud Router

Router ID versus peer addressing

A BGP identifier (router ID) is a 4-octet unsigned value represented in IPv4 notation. Without an explicit range, an IPv4 Cloud Router derives its ID from the lexicographically last IPv4 interface address. Adding or removing BGP sessions, or some maintenance events, can therefore change the automatically selected ID and restart adjacencies.

An explicit identifier range gives Cloud Router a stable ID and is required for IPv6 BGP. If the first IPv6 interface is added to a router without one, Cloud Router can populate a random range from link-local IPv4 space.

flowchart TB
R[Cloud Router] --> Q{Explicit identifier range?}
Q -->|yes| S[Stable router ID]
Q -->|no IPv4-only| A[Auto ID from interface addresses]
A --> C[Interface/session change]
C --> X[Possible router-ID change + BGP restart]
Q -->|IPv6 BGP| V[Explicit range required]

Range and change constraints

Google requires the range to come from 169.254.0.0/16 with a prefix length at most /30. It must not overlap IPv4 addresses used by BGP sessions on that Cloud Router or another custom BGP identifier range in the same VPC network and region. This is control-plane address planning, not a workload prefix.

Changing an existing explicit identifier range restarts all BGP sessions on the Cloud Router. Treat it as planned routing maintenance and preserve an alternate path.

SituationBehaviorDesign action
IPv4, no explicit rangeAuto-derived ID can changeAccept churn risk or configure stable range
IPv6 BGPIdentifier range requiredReserve nonoverlapping link-local range
Change rangeAll BGP sessions restartUse redundancy and maintenance window

Validated CLI

gcloud compute routers create ROUTER_NAME \
  --bgp-identifier-range=BGP_IDENTIFIER_RANGE

gcloud compute routers update ROUTER_NAME \
  --bgp-identifier-range=BGP_IDENTIFIER_RANGE

Anchor: peer IPs form the adjacency; the router ID identifies the BGP speaker. Stability of the latter matters to convergence.

7. Cloud VPN cipher determinism, IKEv2, and fragmentation

Domain 4 — Hybrid connectivityDomain 6 — Security
Primary: Supported IKE ciphers
Supporting: Create HA VPN to a peer gateway

Negotiation can change with initiator direction

Cloud VPN uses IPsec ESP tunnel mode and supports IKEv1 and IKEv2 for supported configurations. IKEv2 is required for IPv6 traffic and for custom cipher configuration. When Cloud VPN initiates a security association, it proposes algorithms in configured/default order and the peer selects. When the peer initiates, Cloud VPN selects from the peer proposal using its own preference. With multiple acceptable algorithms, the resulting cipher can therefore differ depending on which side initiated a rekey.

That variability is operationally important because different algorithms can affect performance and effective packet overhead/MTU. Google recommends a stable cipher selection: configure both sides to propose and accept a single mutually supported algorithm for each cipher role. For HA VPN tunnel pairs, use consistent ciphers and Phase 2 lifetime values on both paths.

sequenceDiagram
participant G as Cloud VPN
participant P as Peer VPN
G->>P: IKE proposal ordered by G
P-->>G: Select supported cipher
Note over G,P: Later SA may be peer-initiated
P->>G: Peer proposal order
G-->>P: Select by Cloud VPN preference
Note over G,P: Single agreed cipher per role makes result deterministic

IKE fragmentation and packet-loss symptoms

Cloud VPN supports IKEv2 fragmentation per RFC 7383 and Google recommends enabling it on the peer device when supported. If fragmentation is disabled, IKE messages from Google that exceed the gateway MTU can be dropped. Some IKE messages, including IKE_SA_INIT and IKE_SESSION_RESUME, cannot use this fragmentation mechanism.

Separate IKE control-plane packet sizing from user-data MTU. A tunnel can fail during negotiation even before encrypted application traffic exists. Conversely, an established tunnel can still have data-plane PMTUD or MSS problems.

ChoiceImplication
IKEv2Recommended default; required for IPv6 and custom cipher configuration
Multiple cipher choicesNegotiated result can vary by initiator/rekey
Single mutually supported cipher per roleMore deterministic performance/overhead
IKE fragmentationHelps oversized fragmentable IKEv2 messages traverse constrained paths

Troubleshooting scenario

A VPN works after some rekeys but changes performance after others. Instead of treating the tunnel as randomly unstable, compare the negotiated algorithms and initiator direction. A tightly constrained, mutually supported cipher set removes one variable. If IKE negotiation itself fails on a path with small MTU, verify peer-side IKE fragmentation and packet captures.

Anchor: deterministic crypto configuration is an availability and performance control, not only a compliance preference.

8. Flow Analyzer latency mode: RTT analysis from VPC Flow Logs

Domain 5 — Operations and troubleshooting
Primary: Flow Analyzer overview
Supporting: Analyze traffic flows

What Flow Analyzer adds to raw logs

Flow Analyzer provides an interactive analysis layer over VPC Flow Logs stored in a log bucket. It uses 5-tuple flow identity and an Observability Analytics/BigQuery-backed workflow so operators can ask traffic questions without hand-writing SQL. Its default presentation emphasizes bytes and packets; latency mode instead analyzes round-trip time for TCP flows.

flowchart LR
V[VPC resources] --> FL[VPC Flow Logs]
FL --> LB[Log bucket]
LB --> FA[Flow Analyzer]
FA --> VOL[Data-volume mode\nbytes / packets]
FA --> LAT[Latency mode\nTCP RTT]
LAT --> R[Average / Max / Median / P95 / P99 / StdDev rankings]

Ranking versus aggregation

Latency mode can rank flows by average, maximum, median, P95, P99, or standard deviation. Ranking decides which flows make the “highest latency” set; chart aggregation decides how the selected flows are plotted. Those choices can deliberately differ—for example, rank by median to find persistently slow flows but plot maximum to expose spikes within that set.

Latency is reported for source and destination sampling points when the log data contains those observations. Low-volume flows can be excluded to prevent sparse samples from dominating the view. Alignment period and flow grouping affect how records are combined, so comparisons should use consistent settings.

MetricBest for
AverageOverall mean behavior, including influence from spikes
MedianTypical latency while resisting isolated spikes
MaxWorst observed spike
P95/P99Tail latency and user-experience risk
StdDevInconsistency/jitter-like variability in RTT

Operational caveats and scenario

Flow Analyzer is only as complete as the VPC Flow Logs being collected and retained. It is not an application tracing system and RTT is a network-flow metric rather than an HTTP transaction latency metric. Confirm logging coverage, aggregation/sampling, endpoint direction, and time window before drawing conclusions.

Scenario: users report intermittent slowness. Ranking by average hides the issue, but P99 and Max isolate one destination with severe tail latency. Compare source/destination observations and correlate the time window with route, backend, and infrastructure events.

Anchor: use median for “typical,” P95/P99 for tail experience, Max for spikes, and standard deviation for instability.

Configuration model versus live traffic

10. Cloud Armor managed rules: stable/canary signature operations

Domain 6 — Security
Primary: Managed rules overview
Configuration: Set up managed rules
Release: September 17, 2026 Preview

Managed signature lifecycle

Cloud Armor managed rules are Google-maintained threat-detection categories integrated into security policies. Google curates signatures from threat intelligence, automatically updates them, and can expedite emergency zero-day coverage. The feature entered Preview on September 17, 2026. Categories include SQL injection, XSS, account takeover, authentication bypass, automated threats, SSRF, file upload, leakage, backdoor/trojan, and other attack families.

flowchart LR
R[Request] --> P[Cloud Armor policy]
P --> C[canary managed rules\npreview]
C --> L[Logs for evaluation]
P --> S[stable managed rules\nenforced]
S -->|match| X[Deny/action]
S -->|no match| B[Backend]

Stable versus canary

stable is the production-validated stream and Google recommends it as the production baseline. canary receives earlier signature changes. A safe operating pattern is canary at higher priority in preview mode and stable at lower priority in enforced mode; this records what the newer signatures would block without immediately impacting users.

Normal Cloud Armor rule priority still applies. Managed rules do not bypass higher-priority terminal policy decisions, and a security policy protects traffic only after it is attached to a supported backend service.

VersionRoleOperational posture
stableProduction-validated signaturesEnforce baseline
canaryEarly signature exposurePreview, measure, then decide

Validated pattern

gcloud compute security-policies rules create 100 \
  --security-policy POLICY_NAME --action deny-403 \
  --expression "evaluateManagedRules('xss:canary')" --preview

gcloud compute security-policies rules create 200 \
  --security-policy POLICY_NAME --action deny-403 \
  --expression "evaluateManagedRules('xss:stable')"

Managed-rules logging includes ruleset identity/version and preview matches, providing evidence for canary promotion or exception tuning.

Anchor: automatic signatures require an operational safety loop; preview canary and enforce stable.

11. Cloud Armor CEL matching on raw request bodies and structured parameters

Domain 6 — Security
Primary: Custom rules language attributes
Supporting: Request body content parsing
Release: August 27, 2026 Preview

Raw versus structured matching

On August 27, 2026 Google announced Preview support for advanced match attributes that inspect request body content and parameters. request.body exposes the raw request body as a string. request.params exposes a key/value map for supported query/body parameters, including structured content such as JSON, form data, and GraphQL when parsing applies.

flowchart TB
R[HTTP request] --> A[Cloud Armor]
A --> RAW[request.body raw string]
A --> PAR[request.params parsed map]
RAW --> CEL[CEL advanced condition]
PAR --> CEL
CEL -->|match| ACT[Policy action]
CEL -->|no match| NEXT[Continue evaluation]

Parsing boundaries and priority

Google examples include request.method == 'POST' && request.body.contains('malicious-value') and comparisons such as request.params.category == 'electronics'. Choose raw-body matching when literal content matters and structured parameters when the application field is the policy contract.

Inspection is bounded. Cloud Armor documents configurable request-body inspection sizes through the first 64 kB. JSON/GraphQL parsing depends on content type and parsing configuration; malformed or oversized bodies can change what is visible. Rule priority also matters because lower-priority rules are not evaluated after a higher-priority terminal match.

InputRepresentationBest fit
request.bodyRaw stringLiteral/prefix/regex content
request.paramsMapNamed query/JSON/form/GraphQL fields
Preconfigured WAF parsingSignature orientedGeneric attack signatures

Scenario

A JSON-field deny rule never triggers. Verify Content-Type and parsing, body inspection size, CEL syntax, and whether a higher-priority rule terminates evaluation. Use preview mode and logging before enforcement because application payloads can generate false positives.

Anchor: raw bytes and structured parameters are different security abstractions; choose deliberately.

12. Hybrid connectivity NEGs: centralized versus distributed Envoy health checks

Domain 2 — VPC implementationDomain 3 — Managed servicesDomain 4 — Hybrid connectivityDomain 5 — Operations
Primary: Hybrid connectivity NEG overview
Supporting: Health checks overview

Hybrid NEG data plane

A hybrid connectivity NEG uses NON_GCP_PRIVATE_IP_PORT endpoints to represent routable application endpoints outside Compute Engine, such as on-premises or another cloud reached through supported hybrid connectivity. The load balancer proxies requests to these endpoints, but the health-check source depends on the load-balancer architecture.

Global external/classic Application Load Balancers and comparable global/classic proxy NLBs use Google's centralized health-check system. On-premises security must allow the documented Google probe ranges 35.191.0.0/16 and 130.211.0.0/22, and hybrid routing must return those probes correctly.

flowchart TB
G[Global/classic proxy LB] --> CH[Centralized Google health checks]
CH -->|35.191/16 + 130.211/22| ON[Hybrid NEG endpoints]
R[Regional/cross-region Envoy LB] --> DE[Distributed Envoy health checks]
DE -->|source: proxy-only subnet| ON
CR[Cloud Router] --> ADV[Advertise return routes for required probe source ranges]
ADV --> ON

Distributed Envoy model

Envoy-based regional and cross-region load balancers use distributed Envoy health checks for hybrid NEGs. Probes originate from Envoy proxies in the regional proxy-only subnet, so external firewalls must allow that subnet and Cloud Router must advertise the proxy-only subnet range toward the external environment. This is a frequent asymmetry failure: client traffic may be routable while health-check return traffic is not.

Google documents important limitations: gRPC health checks and health checks using PROXY protocol v1 are not supported for distributed Envoy health checking. The console/API/gcloud backend health status for external hybrid endpoints can appear as N/A; this is expected, so troubleshooting must use load-balancer logs and external endpoint/firewall evidence. Every Envoy proxy can health-check endpoints independently, so probe traffic can scale significantly—in the worst case approximately quadratically with proxy/endpoints relationships.

LB familyHealth-check sourceExternal routing/firewall need
Global/classic proxy LBsCentral Google probe rangesAllow/return 35.191/16 and 130.211/22
Regional/cross-region Envoy LBsRegional proxy-only subnetAdvertise and allow proxy-only subnet

Scenario

An on-prem hybrid NEG works behind a global external ALB but is unhealthy after migration to a regional external ALB. Reusing only the old centralized-probe firewall rules is insufficient: the regional Envoy design needs reachability from the proxy-only subnet. Verify Cloud Router advertisement, on-prem route acceptance, and firewall permits for that subnet.

Anchor: “hybrid NEG” does not imply one universal health-check source. Identify the load-balancer data plane first.
