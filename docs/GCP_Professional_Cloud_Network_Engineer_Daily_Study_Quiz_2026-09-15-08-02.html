1. IPv6-only VPC subnets and stack transitions

Domain 1 — Design

Problem, architecture, and behavior

IPv6-only subnets remove IPv4 addressing from workload interfaces and are useful where an application and all dependencies are IPv6-ready. A VPC is global while each subnet is regional. Google assigns the subnet IPv6 range unless BYOIP is deliberately used. An IPv6-only interface must be created that way; unlike a dual-stack interface, it cannot later be converted to another stack type. Existing IPv4-only subnets can be converted to dual-stack, with either internal or external IPv6 access.

Design choices, caveats, operations

Choose internal IPv6 for private reachability and external IPv6 when globally routable addresses are required. Validate DNS dependencies, firewall policy coverage, client dual-stack behavior, and every middlebox before migration. A common failure is enabling IPv6 on the subnet while an application still resolves or calls an IPv4-only dependency. Verify subnet stack type and interface addressing before blaming routing.

2. Alias IP ranges for service addressing

Domain 2 — Implement VPC

Architecture and packet behavior

Alias IP ranges let one VM interface own additional internal addresses or ranges drawn from the subnet primary range or a secondary range. The VPC routes packets for those aliases to the owning VM without requiring the VM to advertise routes. This is a foundational mechanism behind scalable service and container addressing patterns.

Security, configuration, troubleshooting

Alias ranges must be unique in the VPC. Firewall rules must permit the alias traffic; an important nuance is that source service accounts and source tags expand only to primary interface IP addresses, so an alias-source flow can behave differently than expected. On supported Linux images, the guest agent installs aliases as local routes. A service that starts before the guest agent can fail to bind; order it after google-guest-agent.service. Troubleshoot by describing the subnet secondary ranges, checking firewall policy, and inspecting ip route show table local.

flowchart LR A[Client] -->|dst alias 10.20.1.8| V[VPC fabric] --> N[VM NIC primary 10.20.0.5] --> L[Local alias route] --> APP[Service bound to 10.20.1.8]

Scenario: a daemon works after manual restart but fails after boot; verify guest-agent/service startup ordering rather than changing VPC routes.

Primary: https://docs.cloud.google.com/vpc/docs/configure-alias-ip-ranges
Supporting: https://docs.cloud.google.com/vpc/docs/alias-ip

3. Cloud Router custom learned routes

Domain 4 — Hybrid

Why and control plane

Custom learned routes let a BGP session inject manually specified prefixes as if they were learned from its peer. They are useful when you want route liveness tied to the BGP session but cannot or do not want the peer to advertise every destination. Unlike an ordinary static route, the route can disappear when the associated BGP path becomes unavailable.

Selection, limits, failure behavior

The custom learned prefix participates in dynamic route processing and should be designed with the VPC dynamic routing mode and competing prefixes in mind. It is not equivalent to teaching the external peer a route; it affects what Google Cloud considers learned. A critical NCC caveat is that site-to-site data transfer does not propagate Cloud Router custom learned routes to external sites. If a route appears in one VPC but not across NCC site-to-site transfer, verify feature support before debugging BGP advertisements.

flowchart LR P[On-prem BGP peer] <-->|BGP session/liveness| CR[Cloud Router] -->|custom learned prefix| R[VPC dynamic route] --> W[Workload]

Takeaway: custom learned routes combine manual prefix intent with BGP-session fate sharing; they are not universal route redistribution.

Primary: https://docs.cloud.google.com/network-connectivity/docs/router/how-to/custom-learned-routes
Supporting: https://docs.cloud.google.com/network-connectivity/docs/router/release-notes

4. Cloud DNS peering zones and resolution direction

Domain 3 — Managed services

Architecture and resolution

A DNS peering zone lets a consumer VPC forward matching DNS queries into the name-resolution order of a producer VPC. DNS peering is directional: granting the consumer access to the producer resolver does not create network connectivity or reverse DNS sharing by itself. The producer network's applicable private zones, forwarding zones, and policies determine the eventual answer.

Design and troubleshooting

Use peering when DNS authority/resolution should remain centralized while workloads live in another VPC. Do not confuse DNS peering with VPC Network Peering. When a consumer cannot resolve a producer-private name, inspect the peering-zone suffix, producer network binding, overlapping private zones, and forwarding targets. If resolution works but TCP fails, move to routing/firewall troubleshooting because DNS peering does not provide a data path.

flowchart LR C[Consumer VM] --> CZ[Consumer peering zone] --> PR[Producer resolver order] --> Z[Private/forwarding zone] --> A[DNS answer] C -. data traffic requires separate connectivity .-> S[Service]

5. GKE mixed-protocol LoadBalancer Services

Domain 3 — Managed services

Architecture and data plane

A mixed-protocol GKE LoadBalancer Service exposes TCP and UDP through one Service and one VIP instead of coordinating separate Services. It is supported with regional external and internal passthrough Network Load Balancers, including IPv4, IPv6, and dual-stack configurations. The implementation uses Layer-3 forwarding rules that send traffic arriving on the VIP to cluster nodes.

Security and failure modes

GKE creates priority-999 firewall rules permitting only the TCP/UDP traffic declared by the Service, while priority-1000 managed rules block other traffic to the VIP. Higher-priority user rules can unintentionally override this protection. If UDP works but TCP does not, compare the Service ports/protocols, forwarding rules, and higher-priority firewall policy before splitting the Service.

flowchart LR C[Client] --> VIP[One LB VIP] -->|TCP| N1[GKE nodes] VIP -->|UDP| N2[GKE nodes] FW[Priority 999 allow declared protocols] --> VIP

Primary: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/mixed-protocol-lb
Supporting: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer

6. GKE automatically created firewall rules

Domain 6 — Security

Policy layers and behavior

GKE automatically creates ingress allow rules needed by clusters, Services, Gateways/HTTPRoutes, and Ingress resources. These rules coexist with hierarchical firewall policies, global and regional network firewall policies, and classic VPC rules. Most GKE-created rules use priority 1000 unless documented otherwise. Administrators should not manually edit or delete controller-managed rules because reconciliation can revert changes.

Egress isolation and troubleshooting

If you intentionally deny egress, preserve node-to-control-plane connectivity on TCP 443; environments using Konnectivity and deny-all egress also need the required TCP 8132 path. Connectivity Tests and firewall logging help identify the actual effective rule. A classic failure is adding an organization-level deny that takes precedence over a GKE-created VPC allow and then assuming the generated rule is broken.

flowchart TD H[Hierarchical policy] --> N[Network firewall policy] --> V[VPC/GKE managed rules] --> NODE[GKE node/Pod path]

Primary: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/firewall-rules
Supporting: https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order

7. Network Analyzer insights and log-based alerting

Domain 5 — Operations

What it does

Network Analyzer continuously discovers invalid or suboptimal network and service configurations and surfaces insights. Results are precalculated; after a change, allow roughly 10–20 minutes for refreshed information or explicitly request an update. Insights can be Active, Dismissed, or Fixed, and historical views are based on first-reported time.

Operationalization

Network Analyzer writes platform logs under networkanalyzer.googleapis.com/analyzer_reports. Teams can query report groups such as hybrid connectivity, route the logs through sinks, and create log-based alerts for high-priority or category-specific findings. Access requires relevant Compute network/instance list permissions; Recommender API access is separate. If an insight disappears, check status and time filters before assuming the analyzer stopped.

flowchart LR CFG[Network config] --> NA[Network Analyzer] --> I[Insight] --> LOG[Cloud Logging] --> ALERT[Log-based alert]

Primary: https://docs.cloud.google.com/network-intelligence-center/docs/network-analyzer/use-network-analyzer
Supporting: https://docs.cloud.google.com/network-intelligence-center/docs/network-analyzer/setup-log-based-alerts

8. Connectivity Tests: configuration analysis versus live data plane

Domain 5 — Operations

Two complementary analyses

Connectivity Tests models expected packet forwarding from configuration and, for supported paths, can also send live probes. Configuration analysis can identify route, firewall, VPN, VLAN attachment, and service-path issues; it does not guarantee the production data plane is healthy. Live analysis reports reachability plus median and p95 one-way latency and packet loss.

Limits and interpretation

Live probes can randomly sample ECMP paths or load-balancer backends, so not every path is guaranteed to be exercised. Live analysis does not support every endpoint or feature, including GKE Pods and several load-balancer types. It is diagnostic, not continuous monitoring. A configuration result saying a packet could be delivered plus a failing application should trigger live/path and endpoint investigation, not a conclusion that the network is healthy.

flowchart LR S[Source] --> CT[Connectivity Test] CT --> CA[Config state-machine trace] CT --> LP[Live probes when supported] CA --> R[Combined diagnosis] LP --> R

Primary: https://docs.cloud.google.com/network-intelligence-center/docs/connectivity-tests/concepts/overview
Supporting: https://docs.cloud.google.com/network-intelligence-center/docs/connectivity-tests/concepts/common-use-cases

9. External proxy Network Load Balancer session affinity

Domain 3 — Managed services

Hashing and persistence

External proxy Network Load Balancers always hash to choose a backend. The default NONE affinity is not absence of hashing; it uses a 5-tuple. CLIENT_IP uses source and destination IPs to improve stickiness across connections from a client. Affinity is best-effort and depends on backend health, capacity, and membership.

Design caveats

Affinity can break when autoscaling or autohealing changes membership, a NEG endpoint is removed, a backend becomes unhealthy/full, or the configured backend count changes. For global/classic proxy NLBs, a changed internet path can land on a different first-layer GFE and alter affinity. RATE or CONNECTION balancing is generally more predictable for affinity than UTILIZATION when fullness changes.

flowchart LR C[Client] --> G[GFE/proxy] --> H{Affinity hash} --> B1[Healthy backend] H --> B2[Other backend]

Primary: https://docs.cloud.google.com/load-balancing/docs/tcp
Supporting: https://docs.cloud.google.com/load-balancing/docs/backend-service

10. Cloud NGFW firewall policy evaluation order

Domain 6 — Security

Hierarchy and enforcement order

Cloud NGFW evaluates hierarchical firewall policies and regional system policies before other applicable firewall rules. For network firewall policies versus classic VPC firewall rules, the VPC can use AFTER_CLASSIC_FIREWALL (default) or BEFORE_CLASSIC_FIREWALL. Within a policy, lower numeric priority is evaluated first and evaluation stops on an applicable terminal match.

Actions and troubleshooting

Hierarchical policy actions include allow, deny, apply_security_profile_group, and goto_next. The latter deliberately delegates evaluation down the hierarchy rather than allowing traffic. When a classic allow appears ineffective, inspect organization/folder policies and the configured network-policy enforcement order. Do not troubleshoot only the rule collection closest to the VM.

flowchart TD ORG[Org hierarchical policy] --> FOLDER[Folder policy] --> ORDER{Network policy order} ORDER --> CLASSIC[Classic VPC rules] ORDER --> NFP[Global/regional network policy]

Primary: https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order
Supporting: https://docs.cloud.google.com/firewall/docs/firewall-policies

11. GKE network isolation troubleshooting

Domain 2 — Implement VPC

Private-node dependency chain

Private nodes use internal addresses and still need paths to required Google APIs and artifacts. In non-Shared-VPC clusters, GKE can automatically enable Private Google Access when private nodes are enabled; in Shared VPC, administrators must ensure the host subnet is configured appropriately. Internet-dependent workloads additionally need Cloud NAT or another deliberate egress path.

Failure workflow

If nodes fail registration, check access to Cloud Storage/Artifact Registry, egress firewall policy, Shared VPC IAM, Private Google Access, and required DNS. A subtle case occurs when common public images pull successfully from mirror.gcr.io but uncached images fail: the successful cached pull proves access to Google's mirror, not general internet egress. Host required images in Artifact Registry or provide deliberate egress.

flowchart LR N[Private GKE node] --> PGA[Private Google Access] --> API[Google APIs/Artifact Registry] N --> NAT[Cloud NAT if internet needed] --> I[Internet]

Primary: https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/network-isolation
Supporting: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/network-isolation

12. Service Extensions callouts to user-managed services

Domain 3 — Managed services

Programmable data path

Service Extensions callouts let supported Application Load Balancers invoke Envoy gRPC services during request/response processing. Unlike sandboxed Wasm plugins, user-managed callouts can run on VMs, GKE, multi-cloud, or on-premises infrastructure and can maintain state or call external systems. Uses include custom authentication, authorization, routing, header manipulation, security integrations, and cache-influencing logic.

Availability and trust boundary

The flexibility moves scalability and availability responsibility to the callout service. Treat it as part of the request critical path: size it for load, bound latency, secure gRPC connectivity, and define failure behavior. A callout that is correct functionally but undersized can become an application-wide bottleneck. Observe both load-balancer and extension-service latency/error metrics during incidents.

flowchart LR C[Client] --> LB[Application Load Balancer] -->|gRPC callout| EXT[User-managed extension] EXT -->|decision/mutation| LB --> B[Backend]

Primary: https://docs.cloud.google.com/service-extensions/docs/overview
Supporting: https://docs.cloud.google.com/service-extensions/docs
