1. VPC custom organization policies: enforce network guardrails before resources are created

Domain 1 — Design and planningDomain 2 — VPC implementationDomain 6 — Security
Primary authoritative source: Manage VPC resources by using custom organization policies

Problem, scope, and policy inheritance

Enterprise VPC standards fail when they exist only in diagrams or deployment checklists. Google Cloud Organization Policy lets a platform team turn selected VPC design requirements into centrally enforced constraints. VPC custom constraints can target supported fields on resources such as networks, subnetworks, routes, addresses, network attachments, service attachments, internal ranges, and service networking connections. Policies can be enforced at the organization, folder, or project level and are inherited by descendants unless the hierarchy rules are deliberately changed.

For a VPC network, supported fields include resource.autoCreateSubnetworks, MTU, IPv6-related settings, network firewall policy enforcement order, peering controls, and routing configuration fields. This makes policy useful for preventing an invalid resource from being created rather than detecting drift after deployment.

A["Organization / folder / project"] --> P["Organization policy"]

resource type + CEL condition"]
C --> R{"CREATE / UPDATE request"}
R -->|Complies| OK["Resource operation allowed"]
R -->|Violates| DENY["Operation rejected"]
DRY["Dry-run policy / Policy Simulator"] --> P

What to notice: the enforcement point is the resource operation. A policy is not a packet filter and does not sit in the data plane; it prevents or constrains control-plane changes before a noncompliant network resource exists.

Constraint construction, IAM, and safe rollout

A custom constraint defines the resource type, the method types on which it applies, a CEL condition, and an action type. The VPC documentation provides an example that allows network creation only when resource.autoCreateSubnetworks == false, which prevents creation of auto-mode VPC networks. Most supported VPC resources can be constrained on CREATE and, where supported, UPDATE. A notable limitation is that custom constraints for route resources are enforced only on CREATE.

Managing custom organization policies normally requires the Organization Policy Administrator role, roles/orgpolicy.policyAdmin, at the organization resource. Roll out cautiously: create the custom constraint, verify it is available, apply a dry-run policy, inspect the predicted violations, and then promote the live policy. If an UPDATE constraint applies to an already noncompliant resource, later changes can be blocked unless the change resolves the violation, so brownfield environments need staged testing.

name: organizations/ORGANIZATION_ID/customConstraints/custom.createOnlyCustomNetwork
resourceTypes:
- compute.googleapis.com/Network
condition: "resource.autoCreateSubnetworks == false"
actionType: ALLOW
methodTypes:
- CREATE
displayName: Restrict creation of networks to custom mode networks
description: Only custom mode networks allowed.

Design scenario, troubleshooting, and decision table

Assume a landing-zone team requires every new VPC to use explicit subnet creation. A project automation pipeline attempts to create an auto-mode network and receives an organization-policy violation. Do not weaken the policy as the first response. Confirm the constraint name and inherited policy, inspect whether the request sets autoCreateSubnetworks to true, and correct the deployment to create a custom-mode network. If an exception is legitimate, use the organization-policy hierarchy or conditional rules intentionally rather than silently bypassing the standard.

Exam anchor: Organization Policy is a control-plane governance guardrail. For VPC custom constraints, know the hierarchy, supported resource fields, CREATE/UPDATE enforcement, dry-run testing, and the route-resource CREATE-only limitation.

2. GKE multi-cluster Gateway: config cluster, ServiceImport, and fleet-wide backends

Domain 1 — Design and planningDomain 2 — ImplementationDomain 3 — Managed services
Primary authoritative source: About multi-cluster Gateways
Supporting authoritative sources: Deploy an external multi-cluster Gateway · Configure multi-cluster Services

Control plane and data plane

A multi-cluster Gateway (MCG) is not “a Gateway object copied everywhere.” Participating GKE clusters register to a fleet, and one cluster is designated as the config cluster. Gateway and HTTPRoute resources for the multi-cluster entry point live there. The GKE Gateway controller watches that API and provisions the corresponding Google Cloud Application Load Balancer resources.

Backend discovery uses Multi-cluster Services (MCS). Each exporting cluster has a normal Service plus a same-name, same-namespace ServiceExport. The MCS controller creates a ServiceImport representation across fleet clusters. For an MCG HTTPRoute, the backend reference is a ServiceImport, not a normal Service. The load balancer can then send traffic directly to healthy Pods in multiple clusters as one logical backend pool.

Service + ServiceExport"] --> MCS
MCS --> SI["ServiceImport"]

ALB --> P2["Healthy Pods B"]

Availability, scope, and hard limits

Choose a regional or otherwise highly available config cluster because losing its Kubernetes API does not instantly erase the existing load balancer, but it prevents desired-state reconciliation and configuration updates. Google documents MCG as a global service; if the fleet control plane has a regional failure, it fails statically and makes no further load-balancer changes until recovery.

All clusters attached to one multi-cluster Gateway must use the same VPC, and cross-project load balancing is not supported for the MCG itself. MCS has its own scaling guidance: a namespaced Service is safely exported from up to five clusters; keeping a Service below 250 Pods is the documented safe guideline; and Google recommends no more than 250 unique exported Service ports. MCS supports ClusterSetIP and headless Services, not NodePort or LoadBalancer Services. Each MCS consumes backend-service quota, and each zone of each exporting cluster creates a NEG.

Failure scenario and verification

If an HTTPRoute is accepted but no backends appear, first verify that the route references group: net.gke.io, kind: ServiceImport, and the correct port. Then inspect the corresponding ServiceImport and its derived EndpointSlice to see whether MCS propagated endpoints. If one cluster’s Pods are unhealthy, the Google load balancer can use remaining healthy capacity in the other cluster without changing the route object.

3. Kubernetes ExternalDNS with Cloud DNS: record automation, ownership, and safe reconciliation

Domain 2 — ImplementationDomain 3 — Managed servicesDomain 5 — Operations
Primary standards/implementation source: Kubernetes SIG Network ExternalDNS
Authoritative Google Cloud context: Cloud DNS records overview
Source-role note: ExternalDNS behavior comes from the Kubernetes SIG project; Cloud DNS behavior comes from Google Cloud documentation.

What problem it solves — and what it is not

ExternalDNS is a Kubernetes controller that watches selected Kubernetes resources and reconciles desired DNS records into an external DNS provider such as Cloud DNS. It is not the in-cluster DNS server and does not replace kube-dns or Cloud DNS for GKE service discovery. Its job is to convert objects such as LoadBalancer Services, Ingresses, or supported Gateway API sources into provider-side DNS records.

A common pattern is to annotate a Service with the hostname that should be published. ExternalDNS compares Kubernetes desired state with provider records and submits changes. This is especially useful when a load balancer IP changes during service recreation: the controller updates the DNS record automatically rather than relying on a ticket or manual gcloud command.

flowchart LR
K8S["Kubernetes Service / Ingress / Route"] --> ED["ExternalDNS controller"]
ED --> DES["Desired DNS record set"]
ED --> OWN["TXT ownership registry"]
DES --> API["Cloud DNS API"]
API --> Z["Managed public/private zone"]
R["Recursive resolver"] --> Z

Ownership and blast-radius controls

Use --domain-filter to constrain which DNS suffixes the controller can manage. ExternalDNS strongly recommends a stable, unique --txt-owner-id; TXT registry records let a controller distinguish records it owns from unrelated records already in the zone. Changing TXT ownership settings after deployment can orphan ownership state, so treat the owner ID as durable infrastructure metadata.

Before granting write access, run with --dry-run and inspect proposed changes. Deletion semantics are also deliberate: with a sync policy, removing the Kubernetes source can delete the owned DNS record; with upsert-only behavior, deleted Kubernetes objects do not automatically remove records. That difference matters during blue/green migrations and accidental object deletions.

Validated controller pattern and troubleshooting

kubectl annotate service web   "external-dns.kubernetes.io/hostname=web.example.org."

external-dns   --provider=google   --google-project=DNS_PROJECT_ID   --source=service   --domain-filter=example.org   --txt-owner-id=gke-prod-01   --dry-run

When a record does not appear, separate the pipeline into stages: (1) is the source object watched, (2) does its hostname pass the domain filter, (3) does ExternalDNS produce a desired endpoint, (4) does controller identity have Cloud DNS write access, and (5) does ownership policy permit the change? Only after the Cloud DNS record exists should you debug recursive caching and TTL behavior.

4. Global external Application Load Balancer custom headers: precedence, metadata, and limits

Domain 3 — Managed servicesDomain 5 — OperationsDomain 6 — Security
Primary authoritative source: Create custom headers in backend services — global external ALB

Where transformation occurs

Custom request headers are added by the load balancer when it forwards a client request to the backend. Custom response headers are set before the proxy returns a response to the client. Header values can include load-balancer-provided variables such as estimated client RTT, geographic information derived from the client source IP, TLS parameters, and CDN state where applicable.

For global external Application Load Balancers, Google recommends centralizing transformations in the URL map when practical. If the same header is configured in both the backend service and URL map, the URL-map value wins and the backend-service value is ignored for that name. This precedence rule matters during migrations because two teams can otherwise think they own the same header.

sequenceDiagram
participant C as Client
participant U as URL map
participant B as Backend service
participant A as App backend
C->>U: HTTP request
U->>B: Apply URL-map header transforms
B->>A: Apply backend-service headers unless same name is already set by URL map
A-->>B: Response
B-->>C: Response headers set before delivery

Security and health-check caveats

Custom request headers are not added to health-check probes. If an application refuses requests unless a custom authorization header is present, real client traffic can succeed while health checks fail. Solve that by designing a health endpoint that does not depend on a header the probe never receives, rather than trying to “fix” the health check with a header feature that does not apply.

Cloud Armor can also insert a header. If Cloud Armor and the load balancer insert the same header name, the load balancer’s value overwrites the Cloud Armor value. Use separate names for security signals that must survive to the backend.

Limits, validation, and troubleshooting

Do not use prohibited hop-by-hop headers or reserved prefixes such as Google-managed header namespaces. Header names are case-insensitive; HTTP/2 encodes header names in lower case. For a missing value, capture a backend request and determine whether the URL map or backend service owns the transformation, whether the variable has a value for that request type, and whether another system overwrote the header.

Anchor: header transforms are proxy-plane metadata tools, not health-check headers or an identity system. Know precedence and hard limits.

5. Protocol forwarding: single-VM target instances with destination-IP preservation

Domain 1 — DesignDomain 2 — ImplementationDomain 5 — Troubleshooting
Primary authoritative source: Protocol forwarding overview

Architecture and packet flow

Protocol forwarding uses a regional forwarding rule that points to a zonal target instance, which in turn references exactly one VM. It preserves the forwarding rule’s destination IP instead of translating it to the VM’s interface address. That makes it useful for appliances or protocols where software needs to bind to the published address, and for special IP mobility patterns where the target VM can be changed behind a stable rule.

It is not a passthrough load balancer. There is no backend service, no distribution across a pool, and no health check. The target instance and referenced VM must be in a zone belonging to the forwarding rule’s region.

C["Client"] --> F["Regional forwarding rule
VIP + protocol + ports"]
F --> T["Zonal target instance"]
T --> V["Single VM"]
V -->|"Direct return
TCP source = VIP"| C
M["Operator / automation"] -. "Moves target to replacement VM" .-> T

Protocol and address semantics

External protocol forwarding supports AH, ESP, GRE, ICMP, ICMPv6, SCTP, TCP, UDP, and an L3-default option for broad protocol handling; internal protocol forwarding supports a corresponding Layer-3 model with regional internal addresses. For TCP, the target VM must reply using the forwarding-rule IP as the source so the client can associate the response with its established connection. Connectionless protocols have more source flexibility, but clients generally still expect replies from the destination they contacted.

Software on the target VM should listen on the forwarding-rule IP or a wildcard address and the selected port. A target-instance VM can also use an associated external forwarding-rule IP as the source of outbound internet connections in specialized designs.

Operations and failure design

CharacteristicProtocol forwardingPassthrough load balancer
TargetsOne target instance → one VMBackend service → backend pool
Health checksNot supportedSupported

Because there is no health check, build an external synthetic check or appliance-specific heartbeat and automation if you require recovery. Internal protocol forwarding can switch a forwarding rule between a target instance and a compatible passthrough load-balancer backend service without recreating the rule; the external transition requires recreation. For fragmented UDP, Google recommends an all-ports UDP rule or L3-default rule so non-initial fragments without port fields still match.

Anchor: protocol forwarding is a stable regional IP/protocol selector for one VM, not a health-aware load balancer.

6. Cloud Router maintenance-event diagnosis: BGP restarts, route preservation, and evidence correlation

Domain 4 — Hybrid and multi-cloudDomain 5 — Operations
Primary authoritative source: Identify router maintenance events

Why this matters

Cloud Router maintenance can look alarming on an external peer because the BGP session can restart even when the maintenance event is expected. Google exposes a specific maintenance signal indicating that router-task maintenance is occurring, BGP sessions will restart, and routes are preserved for the duration of the configured timers. The operational skill is to distinguish a routine control-plane event from a routing failure that actually changes reachability.

That distinction prevents a common escalation mistake: treating every peer-side BGP reset as proof of packet loss. The maintenance event is evidence about the routing control plane. You still need to correlate it with route presence, connectivity telemetry, and peer behavior before deciding whether user traffic was affected.

sequenceDiagram
participant P as Peer router
participant C as Cloud Router
participant L as Cloud Logging
participant W as Workload path
C->>P: Maintenance causes BGP restart
C->>L: Router maintenance event
Note over C,P: Routes preserved for configured timer period
P-->>C: BGP session re-establishes
W-->>L: Correlate reachability / packet-loss evidence

Verification workflow and log-based evidence

Start with time correlation. Record the exact peer-router reset time, then inspect the Cloud Router page and logs for the matching maintenance message. Google documents using Cloud Logging and a log-based metric to identify completed maintenance events. If the timestamps align, next check whether expected routes stayed installed during the timer window and whether the data path showed loss or latency.

A healthy outcome is a brief BGP restart with routes retained and no workload impact. A suspicious outcome is different: routes disappear, the session does not recover after the expected window, repeated resets continue without a corresponding maintenance event, or connectivity tests show real path failure. In that case, continue into BGP configuration, underlying HA VPN or Interconnect state, peer-router logs, and timer behavior.

Failure scenario and decision table

Suppose an on-premises router logs a BGP reset at 02:14 and the NOC opens a severity-one incident. Cloud Router shows a maintenance event at 02:14, routes remain present, and application telemetry shows no packet loss. The right response is to record the expected maintenance event and verify peer recovery, not to force a failover. If instead the session remains down and routes age out, escalate because the evidence now shows a reachability risk rather than a benign maintenance restart.

Observed conditionEvidence to collectAction
BGP restart + maintenance event + routes retainedRouter event log, peer log, route tableVerify recovery; avoid unnecessary failover
BGP restart with no matching maintenance eventPeer diagnostics, Cloud Router logs, VPN/Interconnect statusTroubleshoot configuration or transport causes
Routes disappear after restartHold timers, route tables, peer advertisementsInvestigate control-plane failure affecting reachability
Session recovers but users report lossPath telemetry and connectivity testsCorrelate control plane with actual forwarding symptoms

Anchor: A Cloud Router maintenance message is a diagnosis aid, not an outage verdict. Correlate the BGP event, route retention, peer recovery, and real connectivity evidence.

7. Dedicated Interconnect VLAN attachment BGP-address governance and immutable fields

Domain 2 — ImplementationDomain 4 — Hybrid connectivity
Primary authoritative source: Create Dedicated Interconnect VLAN attachments
Supporting authoritative source: Modify Dedicated Interconnect VLAN attachments

Attachment-to-router relationship

A Dedicated Interconnect VLAN attachment allocates a VLAN on a physical Interconnect connection and associates that logical attachment with a Cloud Router in the VPC/region being connected. Google can auto-assign the VLAN ID and BGP peering addresses, but enterprises with address-management constraints can control those values at creation time.

For normal link-local IPv4 BGP addressing, Google allocates from 169.254.0.0/16. You can supply up to 16 candidate prefixes, each /29 or shorter, and Google selects an unused /29. The candidate space must be unique across all Cloud Routers in all regions of that VPC. Google assigns one address to Cloud Router, one to the customer router, and reserves the remaining addresses in the selected /29.

Candidate subnets versus custom addresses

Dedicated Interconnect also supports explicitly supplied custom BGP IPs for both Cloud Router and the customer router under documented constraints. You cannot combine custom IPv4 addresses with candidate IPv4 subnets for the same address allocation. Candidate subnets are an IPv4 mechanism; IPv6 uses different automatic/custom options.

Failure scenarios and lifecycle planning

If an IPAM team later discovers that a selected BGP link subnet conflicts with an enterprise convention, you cannot simply edit the VLAN attachment’s BGP IPs. Create a replacement attachment, establish the new BGP session, validate route exchange, shift traffic, and then remove the old attachment. The same recreate rule applies to the VLAN ID. This is why BGP peering space and VLAN-ID governance belong in the design review before provisioning.

8. HA VPN packet-rate capacity planning and horizontal tunnel scale-out

Domain 1 — DesignDomain 4 — Hybrid connectivityDomain 5 — Operations
Primary authoritative source: HA VPN topologies to increase bandwidth
Supporting authoritative source: Cloud VPN overview — network bandwidth

The real unit: packets per second, both directions combined

Each Cloud VPN tunnel supports up to 250,000 packets per second for the sum of ingress and egress. Depending on average packet size, that corresponds to roughly 1–3 Gbps. Capacity planning based only on “3 Gbps per tunnel” is therefore unsafe: small packets reach the pps ceiling earlier, and bidirectional traffic shares the same pps budget.

Scale out by adding more tunnels. For example, Google’s guidance for a 600,000 pps requirement uses three pairs of HA VPN tunnels (six tunnels) to provide the required aggregate capacity while retaining failover capacity.

IP addressing and topology choices

If multiple tunnels can share the same HA VPN interface public IP, a gateway interface can support multiple peer tunnels in applicable topologies. If every tunnel needs a distinct pair of public IPs, use additional HA VPN gateways. Project tunnel quotas still apply even when a gateway interface can logically support many tunnels.

RequirementDesign implication
More aggregate ppsAdd tunnels and distribute routes/flows across them

Monitoring and troubleshooting

Google’s byte-based VPN metrics need unit discipline: 3 Gbps is 375 MB/s, and the documented tunnel ceiling is still fundamentally pps-based. Monitor both sent and received volume and, where possible, packet rate and packet-size distribution. A tunnel can be pps-bound without showing 3 Gbps.

Scenario: a design averages 2.2 Gbps but consists mostly of small transactional packets and experiences loss under bursts. Before blaming encryption algorithms or BGP convergence, check whether the combined packet rate approaches the tunnel’s 250k pps limit. If so, horizontal tunnel scale-out is the appropriate lever.

Anchor: Cloud VPN capacity is 250k pps per tunnel, ingress plus egress. Engineer tunnel count for packet rate and failure headroom.

9. VPC firewall blind spots: metadata-server exposure and external SMTP restrictions

Domain 2 — ImplementationDomain 5 — OperationsDomain 6 — Security
Primary authoritative source: About VM metadata
Supporting authoritative source: Sending email from an instance

Two controls that are easy to misdiagnose as ordinary VPC firewall behavior

Not every connectivity or security issue around a Compute Engine VM is explained by an allow or deny VPC firewall rule. Two high-value examples are the host-local metadata service and Google's anti-abuse treatment of external SMTP. The metadata service is reached through metadata.google.internal or link-local addresses such as 169.254.169.254; requests and responses stay on the physical host running the VM. External SMTP on TCP port 25 can be restricted by Google Cloud even when your egress policy otherwise permits the flow.

flowchart LR

host-local endpoint"]

Metadata security boundary and SMTP behavior

Metadata is powerful because it can expose instance data and, depending on the workload identity configuration, credentials usable by software on the VM. Google warns that any process able to query the metadata URL can access metadata values available to that instance, so untrusted or third-party processes should be sandboxed. HTTPS metadata endpoints add transport protections for supported Shielded VM scenarios, but application isolation and least privilege still matter.

For outbound email, Google does not place the same platform restriction on external destination TCP ports 465 and 587. Destination TCP port 25 is commonly blocked when the destination is external to the VPC because of spam-abuse risk, although some projects can be permitted. Port 25 to destinations reachable internally—such as the same VPC, a peered VPC, or on-premises through VPN/Interconnect—is treated differently and remains subject to routing and firewall policy.

Troubleshooting workflow and decision table

If a VM cannot reach an external SMTP server on port 25, first separate platform restriction from your own firewall policy. Confirm the destination really is external, inspect project-level SMTP restriction status, verify the egress firewall path and default internet route, and prefer authenticated TLS submission on 465 or 587 when supported. If the problem is metadata exposure rather than mail, inventory which local processes can access the metadata endpoint, remove sensitive custom metadata, sandbox untrusted code, and review service-account privilege.

10. Cloud Armor hierarchical security policies: inheritance, evaluation order, and goto_next

Domain 1 — DesignDomain 6 — Network security
Primary authoritative source: Hierarchical security policies overview

Ownership, association, and inheritance

Cloud Armor hierarchical security policies extend WAF and DDoS controls beyond a single project/backend. A policy can be owned by an organization or folder and associated with an organization, folder, or project node. Once associated, protected resources under that node inherit the policy. Creation alone does not enforce anything; association is the step that places the policy into the effective chain.

This design separates central controls such as enterprise-wide deny conditions from application-specific service-level policy. Operators can inspect the effective Cloud Armor rules that apply to a protected resource across all hierarchical and service-level policies.

flowchart TD
O["Organization hierarchical policy"] --> F["Parent folder policy"]
F --> SF["Subfolder policy"]
SF --> P["Project hierarchical policy"]
P --> S["Service-level policy"]
O -. "allow/deny = terminal" .-> X["Stop evaluation"]
O -. "goto_next" .-> F

Evaluation order and terminal actions

Evaluation order is fixed by hierarchy: organization-level policy first, then folder policies from parent to child, then project-level hierarchical policy, then the service-level security policy. This ordering is separate from numeric rule priority inside an individual policy. A low-priority-number service rule cannot “jump ahead” of a matched terminal organization rule.

Hierarchical policies add the goto_next action. A matching goto_next stops evaluating the remaining rules in the current policy and continues with the next policy in the hierarchy. By contrast, a matching allow or deny is terminal for the request; later policies do not get to re-decide it.

ActionEffectUse case
denyTerminal blockOrganization-wide forbidden source/pattern
allowTerminal allowExplicit enterprise exception when intended
goto_nextSkip remainder of current policy; evaluate next policyDelegate decision to child/service policy for selected traffic

Design failure scenario

A central team creates an organization-level allow for a trusted source expecting the application’s service-level WAF to continue evaluating SQL injection. Because allow is terminal, the request can bypass later service-policy rules. If the intent is merely “do not apply the rest of this central policy; let the application policy decide,” use goto_next instead.

Propagation after organizational changes can take time, so rollout plans should include staged association, preview/log analysis where available, and effective-policy inspection. Policy owners should document which decisions are terminal and which are delegated.

Anchor: hierarchy defines policy order; priority orders rules inside a policy; goto_next is the delegation primitive.

11. Cloud DNS ALIAS records: zone-apex synthesis versus ordinary CNAME resolution

Domain 2 — ImplementationDomain 3 — Managed services
Primary authoritative source: Cloud DNS records overview — ALIAS records

The zone-apex problem

A traditional CNAME cannot be placed at a zone apex because the apex must also contain records such as SOA and NS, and CNAME semantics do not allow coexisting record types at the same owner name. Cloud DNS provides an ALIAS record type, currently documented as Preview, to provide CNAME-like indirection at a public-zone apex while answering clients with ordinary A or AAAA data.

ALIAS is Cloud DNS-specific and is not exposed to clients as an ALIAS RR. When a resolver asks for an address, Cloud DNS resolves the configured target using Google recursive resolvers and synthesizes A/AAAA records whose owner name is the ALIAS name.

TTL, failures, and DNSSEC

The TTL of a synthesized address is the smallest of the ALIAS record’s configured TTL and TTLs encountered during target resolution. If target resolution fails with an error response, Cloud DNS returns SERVFAIL; a successful response with no address data results in NODATA. Intermediary CNAMEs found while resolving the ALIAS target are not exposed in the final synthesized answer.

ALIAS records are available only in Cloud DNS public zones and are not compatible with DNSSEC. That is a decisive architecture tradeoff: if DNSSEC at the zone is mandatory, an ALIAS-based apex design is not appropriate.

Scenario and troubleshooting

If example.com must point indirectly at a changing SaaS hostname, ALIAS can provide apex flattening. If clients receive SERVFAIL, test the target name independently from a public recursive resolver; an ALIAS cannot synthesize a valid address if its target chain fails. If enabling DNSSEC is a hard compliance requirement, redesign the apex target rather than trying to enable DNSSEC on a zone containing ALIAS records.

Architecture and policy scope

Global external Application Load Balancers can replace selected backend- or load-balancer-generated 4xx/5xx responses with content from an error service. Policies can vary by status code and by URL-map context such as hosts, paths, request headers, or parameters. The error service can be a backend bucket or backend service; Cloud Storage-backed error content is a common design.

The feature can also customize errors generated when Cloud Armor denies a request, as long as the custom error policy matches the status code used by the security rule. This lets a platform team return user-friendly HTML to browsers and structured JSON to API clients while keeping the original application/backend isolated from error-content delivery.

Status overrides, logging, and caching

A custom policy can override the response status sent to the client, even returning 200 for a maintenance page when that behavior is intentionally desired. Logging preserves the original server/load-balancer status in httpRequest.status; when an override is applied, the load-balancer log adds overrideResponseCodeServed. That distinction is essential when dashboards show client success while the backend is actually returning failures.

When Cloud CDN and negative caching are involved, the caching policy belongs to the backend that generated the error, not simply to the error-service object. An override code changes which negative-caching rule is considered. A 200 override does not use negative caching as an error status.

Scenario: an outage dashboard shows a sudden rise in HTTP 200 while backend logs show 503. If a maintenance policy overrides 503 to 200, both observations can be correct. Query overrideResponseCodeServed together with the original httpRequest.status to preserve incident visibility.

Anchor: custom error responses are a second fetch path with independent content/security concerns. Never let a friendly 200 override hide the original failure signal.
