1. PSC propagation through NCC: centralize endpoints across VPC spokes

Domain 1

Architecture and use case

Private Service Connect endpoints are normally local to the consumer VPC that owns them. NCC connection propagation lets a common-services VPC host accepted PSC endpoints and makes those services reachable from other VPC spokes attached to the same hub. NCC creates propagated connections; administrators do not create a duplicate endpoint in every spoke.

Propagation is triggered when PSC export is enabled on the hub, when a VPC spoke joins, when a new eligible endpoint is created, or when a producer raises a service attachment's propagated-connection limit. The process is asynchronous, so endpoint creation and end-to-end availability are separate events.

Scope, route export, and limits

Spoke export filters control which endpoint subnets participate. If an endpoint subnet is excluded, other spokes do not receive propagated connections for those endpoints. Global access on the original endpoint controls whether workloads in other regions can consume the propagated service.

IPv6 PSC propagation is not supported. Endpoints using privately used public IP ranges are not propagated. For on-premises reachability through hybrid spokes, the hub must use a single routing VPC containing the hybrid spokes and that routing VPC must itself also be a VPC spoke. Broad Private NAT configuration can break access to propagated PSC services.

Troubleshooting

Start with propagation state and quotas before packet analysis. Producer propagated-connection limits, producer forwarding-rule quota, producer NAT-IP exhaustion, and consumer propagated-connection quota create distinct failure states. Once propagation is healthy, move to DNS, endpoint regional/global scope, firewall policy, and producer service health.

flowchart LR P[Producer service]-->SA[Service attachment] SA-->EP[PSC endpoint in common-services VPC] EP-->H[NCC hub - PSC export] H-->A[VPC spoke A - propagated connection] H-->B[VPC spoke B - propagated connection] ONP[On-prem]-->RV[Single routing VPC + hybrid spokes] RV-->H

Official figure/reference: PSC propagation through NCC.

Remember: PSC supplies service connectivity; NCC propagation solves endpoint sprawl but is constrained by export filters, quotas, routing-VPC design, and IPv4-only support.

2. Cloud NGFW firewall endpoints: packet intercept, capacity, and MTU

Domain 6

How insertion works

A Cloud NGFW firewall endpoint is a Google-managed zonal Layer 7 inspection resource. It is not a route next hop. A firewall policy rule that applies a security profile group selects traffic, and Google packet intercept transparently redirects that traffic to the endpoint while preserving the original routing intent.

Endpoint associations bind an endpoint to VPC networks. Redirected packets carry a VPC network identifier, allowing Cloud NGFW to distinguish flows from VPCs with overlapping CIDRs.

Performance and packet size

Google documents per-connection throughput of about 250 Mbps with TLS inspection and 1.25 Gbps without TLS inspection. Overloaded endpoints can drop legitimate traffic, so utilization is an availability metric.

Jumbo-frame support is selected at creation. Inspection adds GENEVE overhead; VPC MTU must remain within the endpoint's supported size or advanced inspection services can fail. Changing jumbo support later requires endpoint recreation.

Failure workflow

If traffic routes correctly but inspection is absent, verify endpoint association, zone coverage, rule priority, security-profile group, and policy enforcement. If small traffic works but large or TLS-inspected transfers fail, check MTU and endpoint throughput before changing routes.

flowchart LR W[Workload]-->F[Firewall policy] F-->|apply security profile group|PI[Packet intercept] PI-->E[Firewall endpoint] E-->|allow after inspection|D[Original destination] E-->|deny|X[Drop] F-.no match.->D

Official figure/reference: Firewall endpoint overview.

Remember: Cloud NGFW Enterprise insertion is policy-driven packet intercept, not route-to-NVA insertion.

3. Network Security Integration in-band: third-party inspection without route steering

Domain 6

Producer-consumer architecture

NSI in-band lets a security producer publish a packet-inspection service and a consumer steer selected VPC flows through it. The producer places appliances behind an internal passthrough Network Load Balancer and creates an intercept deployment group plus zonal deployments. The consumer creates an intercept endpoint group and association to bind that service to a VPC.

A hierarchical or global network firewall policy rule uses APPLY_SECURITY_PROFILE_GROUP. Matching traffic is redirected through packet intercept to the producer service and returned to the original path when allowed.

Enforcement order

Google recommends BEFORE_CLASSIC_FIREWALL. If classic VPC firewall rules are evaluated first, they can drop traffic before interception occurs, making a healthy inspection service appear unused.

Operations

Validate the chain in order: policy match, endpoint-group association, producer deployment group, internal passthrough NLB, appliance health, then return to the intended destination. Route tables alone do not reveal the insertion path.

flowchart LR C[Consumer VM]-->R[Firewall rule] R-->IEG[Intercept endpoint group] IEG-->IDG[Producer deployment group] IDG-->ILB[Internal passthrough NLB] ILB-->A1[Inspection appliance A] ILB-->A2[Inspection appliance B] A1-->D[Original destination] A2-->D

Official figure/reference: NSI in-band tutorial.

Remember: NSI separates consumer selection resources from producer inspection resources and depends heavily on firewall policy order.

4. Regional internal Application Load Balancer with Cloud Run

Domain 3

Architecture

A regional internal Application Load Balancer can publish a Cloud Run service privately through a serverless NEG. Clients connect to an internal VIP; Google-managed Envoy proxies use a proxy-only subnet, apply URL-map/backend policy, and create a new connection toward the serverless backend.

The serverless NEG identifies the Cloud Run service rather than holding fixed endpoint IP addresses. The load-balancer resources and Cloud Run service must satisfy regional placement requirements.

Security and request flow

Setting Cloud Run ingress to internal can prevent direct public ingress while allowing the internal ALB path. Because this is a proxy load balancer, client source-IP semantics differ from a passthrough NLB.

Troubleshooting

Verify the forwarding rule/VIP, proxy-only subnet, URL map, backend service, serverless NEG target, Cloud Run region, ingress setting, and revision health. Direct VPC egress is an outbound Cloud Run feature and is not the inbound publication mechanism.

flowchart LR C[VPC client]-->VIP[Regional internal ALB] VIP-->E[Envoy proxy] E-->U[URL map/backend service] U-->N[Serverless NEG] N-->R[Cloud Run - internal ingress]

Official figure/reference: Internal ALB with Cloud Run.

Remember: The serverless NEG is the integration object between the ALB and Cloud Run.

5. Regional internal Application Load Balancer with Cloud Storage backend buckets

Domain 3

Use case

This pattern lets internal clients retrieve Cloud Storage content through a regional internal Layer 7 VIP and backend buckets. It is useful for controlled internal read access but has backend-specific constraints that make it very different from a generic private object-storage gateway.

Important limitations

The Cloud Storage bucket must be publicly accessible. Private bucket access is not supported. Signed URLs are not supported. Cloud CDN is not supported. Only HTTP GET is supported through this integration, and the bucket must be in the same region as the load balancer; dual-region and multi-region buckets are unsupported.

Data path and decision guidance

Envoy proxies in the proxy-only subnet apply the URL map and retrieve content from the selected regional backend bucket. Choose this only when the public-bucket and read-only constraints are acceptable. If private storage semantics, uploads, signed URLs, multi-region storage, or CDN are required, use a different pattern.

6. Cloud Router BGP route policies: programmable import/export control

Domain 4

Purpose and policy direction

BGP route policies add programmable processing to routes imported from or exported toward Cloud Router peers. Terms have priorities, match expressions, and actions. Google examples include destination/community matching and actions such as setting MED.

Import policies affect routes received from the peer. Export policies affect advertisements sent to the peer. A BGP session can be Established while a policy removes or modifies the desired routes, so adjacency health alone is not sufficient evidence.

Verified CLI and troubleshooting

gcloud compute routers list-route-policies ROUTER_NAME \
  --region=REGION

Use the output to confirm policy names and direction. Then inspect term ordering, match conditions, actions, advertisements, accepted routes, quotas, and final best-path selection.

flowchart LR P[Peer]-->|BGP updates|I[Import policy] I-->CR[Cloud Router] CR-->V[VPC dynamic routes] V-->CR CR-->E[Export policy] E-->|BGP advertisements|P

Official reference: List BGP route policies.

Remember: Established BGP proves adjacency, not that a route survived policy.

7. MACsec for Dedicated Interconnect: MKA and fail-open risk

Domain 1

Where MACsec fits

MACsec protects supported Dedicated Interconnect physical links at Layer 2. It is distinct from HA VPN over Interconnect, which adds IPsec at Layer 3. MACsec must be selected when the Dedicated Interconnect connection is ordered.

The customer and Google edge routers establish a MACsec Key Agreement session before encrypted Layer-2 traffic is carried. Google documents broad support for 100-Gbps and 400-Gbps connections; 10-Gbps availability is location dependent.

Fail-closed versus fail-open

The default behavior drops traffic when MKA cannot be established. Fail-open can keep the connection operating with unencrypted traffic and is intended for testing/troubleshooting, not normal production.

Operational impact

Changing fail-open requires temporarily disabling MACsec and causes packet loss, so production traffic should be drained from the affected VLAN attachments first.

gcloud compute interconnects macsec update INTERCONNECT_CONNECTION_NAME \
  --no-enabled --fail-open
gcloud compute interconnects macsec update INTERCONNECT_CONNECTION_NAME \
  --enabled
flowchart LR CE[Customer router]<-->|MKA + MACsec|GE[Google edge] GE-->I[Dedicated Interconnect] I-->V[VLAN attachment] V-->CR[Cloud Router] F[MKA failure]-->C[Default: drop] F-->O[Fail-open: unencrypted]

Official reference: MACsec fail-open behavior.

Remember: Fail-open trades confidentiality for availability; it is not a free HA feature.

8. HA VPN with IPv6: gateway IP version, stack type, and BGP IPv6

Domain 4

Three independent choices

IPv6 HA VPN requires engineers to separate the external gateway interface IP version, gateway stack type, and BGP route families. Google and peer gateway external IP versions must match. The stack can be IPv4-only, dual-stack, or IPv6-only only in supported combinations.

Stack type cannot be changed after gateway creation; moving to a different stack requires recreation.

IPv6 route exchange

IPv6 workload routes require IPv6 route exchange or a corresponding IPv6 BGP session. IPv6 can be disabled temporarily without deleting the gateway by disabling route exchange/session configuration.

gcloud compute vpn-gateways create GW_NAME \
  --network=NETWORK --region=REGION \
  --gateway-ip-version=IPV6 --stack-type=IPV4_IPV6

Availability

IPv6 does not eliminate HA topology requirements. The 99.99% SLA still depends on the supported redundant tunnel design using both HA VPN interfaces.

flowchart LR G[HA VPN IF0/IF1]<-->|IPsec outer IPv4/IPv6|P[Peer VPN] G<-->|BGP IPv4|CR[Cloud Router] G<-->|BGP IPv6 when enabled|CR CR-->V4[IPv4 routes] CR-->V6[IPv6 routes]

Official reference: Create HA VPN.

Remember: Outer address family, gateway stack type, and BGP route family are related but different settings.

9. Cloud IDS: managed detection using private services access and Packet Mirroring

Domain 5

Architecture

Cloud IDS is out-of-band threat detection. Production traffic stays on its normal path while Packet Mirroring copies selected VPC traffic to a managed IDS endpoint. Monitoring failure therefore does not necessarily create an application forwarding outage.

Prerequisites

Cloud IDS requires Service Networking private services access. The allocated range must be RFC 1918. If private services access already exists for another service, Cloud IDS requires a separate unique allocated range. IAM separates endpoint administration, packet-mirroring attachment, and log viewing.

gcloud services enable servicenetworking.googleapis.com --project=PROJECT_ID

gcloud ids endpoints create ENDPOINT_NAME \
  --network=VPC_NETWORK --zone=ZONE --severity=SEVERITY

Operations

Google recommends IDS endpoints in regions containing monitored workloads. If findings disappear, verify Packet Mirroring policy scope/filter first, then IDS endpoint state, private services access, and log permissions.

flowchart LR A[Workload A]-->B[Destination] A-.mirrored copy.->PM[Packet Mirroring] B-.mirrored copy.->PM PM-->IDS[Cloud IDS] IDS-->L[Threat findings/logs] A-->|original flow|B

Official reference: Configure Cloud IDS.

Remember: Cloud IDS observes copies; Cloud NGFW Enterprise enforces inline.

10. Firewall logging: proving rule matches without overclaiming

Domain 5

Logging families

Google provides logs for classic VPC firewall rules and Cloud NGFW policy rules. Records include connection information and rule identity, and optional metadata can add workload/policy context at additional cost.

What a log proves

A firewall log proves a logged rule matched the connection. It does not prove the application succeeded. Routing, NAT, DNS, load-balancer health, return paths, or application policy can still fail after a firewall allow.

No firewall log also does not automatically prove a deny; logging may be disabled or the traffic may never have reached the evaluation point.

11. Internal passthrough NLB with Service Directory registration

Domain 3

Discovery layer

Service Directory registration adds managed discovery to an internal passthrough Network Load Balancer. Clients can use Service Directory APIs or DNS and administrator-selected names instead of hard-coded VIPs or only generated internal names.

Multiple load balancers can be represented in a common namespace, and IAM can be applied at namespace or service scope.

Data-plane semantics

Registration does not turn the load balancer into a proxy. The internal passthrough NLB retains passthrough forwarding behavior. Service Directory answers how clients discover the service; the NLB answers how packets are distributed.

Compatibility

Support differs by load-balancer family. Cross-region internal Application Load Balancers do not support the same Service Directory registration model, so engineers must identify the exact LB type before assuming feature parity.

flowchart LR C[Client]-->SD[Service Directory/DNS] SD-->VIP[Internal passthrough NLB VIP] VIP-->B1[Backend A] VIP-->B2[Backend B]

Official reference: Internal NLB + Service Directory.

Remember: Discovery plane and forwarding plane are separate concerns.

12. NCC dynamic route exchange: workload VPC versus routing VPC

Domain 2

Two VPC roles

A workload VPC contains application resources and is attached as a VPC spoke. A routing VPC contains hybrid connectivity resources such as HA VPN tunnels, VLAN attachments, or Router appliance VMs. Routing VPCs and their hybrid spokes must be in the same project as the NCC hub.

The routing VPC itself does not always need to be a VPC spoke, although PSC propagation to on-premises networks is one case where it must also join as a VPC spoke.

Dynamic routing and best path

NCC hybrid spokes support Cloud Router legacy best-path selection. The routing VPC's regional or global dynamic-routing mode determines where NCC dynamic routes from hybrid spokes are programmed into workload VPC spokes. Regional mode limits programming by region; global mode can distribute those routes across regions.

Longest-prefix match remains fundamental. For equal prefixes, MED and the legacy best-path process influence installed paths.

Troubleshooting

Verify the prefix at Cloud Router, confirm export from the hybrid spoke to the hub, confirm import into the VPC spoke, then check regional/global route programming and firewall policy. Same-hub membership is not equivalent to unrestricted transit.

flowchart LR O[On-prem]-->HSP[Hybrid spoke] HSP-->RV[Routing VPC + Cloud Router] HSP-->H[NCC hub] H-->W1[Workload VPC spoke A] H-->W2[Workload VPC spoke B] M[Regional/global routing mode]-.controls programming.->W1 M-.->W2

Official reference: NCC dynamic route exchange.

Remember: Identify routing VPC, workload VPC, spoke type, routing mode, and path-selection behavior separately.
