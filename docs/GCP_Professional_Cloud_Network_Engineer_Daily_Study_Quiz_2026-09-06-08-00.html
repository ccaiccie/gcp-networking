1. Direct VPC egress versus Serverless VPC Access connectors

Domain 1

What problem it solves

Cloud Run and other serverless workloads often need private access to resources in a VPC. Historically, Serverless VPC Access connectors supplied a managed pool of connector instances. Direct VPC egress removes that connector hop for supported Cloud Run workloads and attaches the revision directly to a selected VPC network and subnet. Google explicitly recommends understanding Direct VPC egress prerequisites, IP allocation, IAM, firewall rules, and limitations before migration.

Data-plane behavior

With a connector, outbound traffic traverses the serverless platform and then connector instances before entering the VPC. With Direct VPC egress, Cloud Run uses a direct network path. Google states that this path is faster, supports more traffic, and generally has lower latency and higher throughput. The revision can route only private ranges through the VPC or route all egress through the VPC. Network tags can be associated at revision scope, which lets VPC firewall rules distinguish revisions.

flowchart LR R[Cloud Run revision] -->|Direct VPC egress| S[Selected subnet] S --> V[VPC resources] R -.legacy path.-> C[Serverless VPC Access connector] C --> V R -->|all-traffic option| E[VPC-controlled egress path]

Notice: the migration removes connector instances from the forwarding chain; it does not remove firewall policy or subnet address planning.

Migration and operations

Google recommends gradual migration: update a new revision for Direct VPC egress, initially route no production traffic to it, validate the network/subnet/egress state, then move a small percentage of traffic before completing the cutover. Connector resources continue to incur charges even when disconnected, so delete unused connectors after migration. The migration guide also warns that clearing a connector can reset the egress setting to the default private-ranges behavior unless you explicitly configure all-traffic afterward.

Design pitfalls

DecisionMeaning
private-ranges-onlyOnly private destinations use the VPC path; other traffic follows normal serverless egress behavior.
all-trafficAll outbound traffic enters the VPC, enabling centralized NAT, inspection, or policy.
Network tagsRevision-level identity that can be targeted by firewall rules.
Keep connector after cutoverUnnecessary cost and operational clutter once no workloads depend on it.
Exam takeaway: Direct VPC egress changes the forwarding architecture, not the security model. Always revalidate routes, firewall policy, NAT/egress controls, and source-address expectations.

Primary: Migrate Serverless VPC Access to Direct VPC egress. Supporting: Send Cloud Run traffic to a VPC network.

2. Private services access: allocated ranges, producer VPCs, and hidden peering constraints

Domain 1

Architecture

Private services access connects a consumer VPC to a service producer VPC by using VPC Network Peering. The consumer first reserves one or more allocated IPv4 ranges that cannot be reused for subnets or static-route destinations. A private connection is then created to the producer, and the managed service allocates producer-side subnets from the consumer-provided range. Google documents services such as Cloud SQL, AlloyDB, Filestore, Vertex AI, and others that use this model.

flowchart LR VM[Consumer VM] -->|internal IPv4| P[Peering/private connection] AR[Allocated range 10.240.0.0/16] --> P P --> PV[Producer VPC dedicated to consumer] PV --> PS[Producer subnet e.g. /24] PS --> DB[Managed service instance]

Notice: the allocated range belongs to the consumer address plan, but producer subnets are created in the producer VPC and selected by the service producer.

Routing and reachability

When the connection becomes active, subnet routes are exchanged across peering so consumer VMs can reach the service instance by internal IPv4. Peering is not transitive. A VPC that is merely peered to the consumer cannot automatically reach the producer service. Hybrid reachability is also not automatic because producer networks do not initially learn the consumer's custom on-premises routes. Where supported, custom route export and explicit return-path design are required; a producer-side default route can prevent an exported default route from doing what you expect, so Google recommends a more-specific route when needed.

Limits and security

IPv6 ranges are not supported for private services access. Only one consumer VPC can create the private connection to a given managed service instance, though Shared VPC, supported NCC producer spokes, or hybrid designs can extend reachability. The allocated range itself cannot be resized in-place by changing its CIDR; you can instead modify which allocated ranges are associated with the connection. The consumer remains responsible for securing its network and access to the service.

SymptomLikely causeCheck
New managed instance fails to provisionAllocated range exhaustedFree space and additional allocated ranges
Peered VPC cannot reach servicePeering is not transitiveUse supported NCC/Shared VPC/PSC design
On-prem can send but replies failProducer lacks return routeCustom route export and more-specific return path
Remember: private services access is peering-backed managed-service connectivity, not Private Service Connect. Its address allocation and non-transitivity behavior are fundamental design constraints.

Primary: Private services access.

3. BYOIP v2: PAP, PDP, ROA validation, scope, and safe route announcement

Domain 1

Resource hierarchy and ownership

Bring your own IP (BYOIP) lets an organization use its own public address space for supported Google Cloud resources. A public advertised prefix (PAP) represents the aggregate route Google can advertise. From the PAP, the customer creates one or more public delegated prefixes (PDPs) that delegate portions of the space to a project and either regional or global scope. Google validates ownership for externally advertised prefixes using ROA and reverse-DNS checks.

Provisioning and announcement

External IPv4 and external-access IPv6 PAPs require an internet-announcement provisioning process that takes on the order of weeks; Google documents approximately two to four weeks depending on configuration. Internal-access IPv6 prefixes are not advertised to the internet and become usable after validation without the same announcement delay. For recommended v2 regional configurations, announcement can be controlled after provisioning rather than automatically started.

flowchart LR RIR[RIR / ROA ownership] --> PAP[Public Advertised Prefix] PAP --> PDP1[Regional PDP] PAP --> PDP2[Sub-prefix] PDP1 --> IP[Static external IP resources] PDP2 --> FR[Supported forwarding rules/subnets] PAP -->|BGP announcement when enabled| INET[Internet]

Notice: PAP is the advertisement unit; PDPs are delegation/allocation units.

Important constraints

Google warns against overlapping external announcements. If the same prefix or a more-specific portion is advertised simultaneously outside Google, unpredictable routing and packet loss can result. New PAPs cannot mix global and regional PDP use. IPv6 BYOIP has additional delegation modes and only regional address support; global IPv6 BYOIP addresses are not supported. BYOIP addresses cannot be moved between projects, and not every resource type supports them.

Operational checklist

CheckWhy
ROA and reverse DNSRequired to prove control of externally used address space.
PAP statusDetermines whether the prefix is ready to announce or currently announced.
PDP scopeControls where child addresses can be used.
Existing BGP announcementsMust not overlap the Google announcement.
Resource support matrixBYOIP support differs by resource and IP version.
Remember: BYOIP is an address-ownership and routing-lifecycle project, not merely reserving a static IP. Plan validation, delegation, project scope, and BGP cutover as one change.

Primary: Bring your own IP addresses; Create public delegated prefixes.

4. Direct Peering and Verified Peering Provider: Google edge access is not VPC private routing

Domain 1

What these products connect

Direct Peering establishes BGP peering between an organization's network and Google's edge network. Verified Peering Provider gives organizations access to Google's edge through a provider that maintains the peering relationship. Both are fundamentally different from Cloud Interconnect: they improve paths to publicly reachable Google services and Google public IPs, but they do not create private VPC route exchange to internal-only workload addresses.

flowchart LR ON[Enterprise network] -->|Direct Peering BGP or provider| EDGE[Google edge] EDGE --> PUB[Google public services / public IPs] ON -.no VPC custom dynamic routes.-> VPC[Private VPC resources] ON -->|Interconnect instead| CR[Cloud Router] CR --> VPC

Notice: routes learned through Direct/Verified Peering do not appear as VPC custom dynamic routes.

Design comparison

Direct Peering uses no Google Cloud resources and is opaque to individual projects. Google does not provide an SLA for Direct Peering. A Verified Peering Provider removes the requirement for the customer to meet Google's Direct Peering criteria and requires the provider to maintain diverse redundant connectivity. Cloud Interconnect, in contrast, creates VLAN attachments and Cloud Router relationships, can reach internal-only VPC resources, and has Google-defined SLA topologies.

NeedFit
High-throughput private access to RFC1918/internal VPC resourcesCloud Interconnect
Better direct path to Google's public edge and customer meets peering requirementsDirect Peering
Better path to Google edge without meeting Direct Peering requirementsVerified Peering Provider
Project-visible dynamic routes from on-premCloud Interconnect + Cloud Router

Troubleshooting perspective

If a Direct Peering link is up but an internal-only VM remains unreachable, that is an architecture mismatch rather than a routing bug. Conversely, public Google service reachability issues should be investigated at the external BGP/edge path, not in VPC route tables.

Remember: peering to Google's edge is not the same as peering or interconnecting with your VPC.

Primary: Direct Peering overview. Supporting comparison: Choose a Network Connectivity product.

5. VPC Network Peering: subnet exchange, custom-route controls, and non-transitivity

Domain 2

Core model

VPC Network Peering creates private connectivity between two VPC networks. Peered networks can belong to different projects or organizations. The networks remain administratively independent: firewall rules and IAM are not merged. Subnet routes are exchanged so resources can communicate using internal addresses, provided CIDR ranges do not conflict.

Custom routes and dynamic routes

Custom static and dynamic routes are not automatically shared in every direction. Import/export controls on each peering relationship determine whether eligible custom routes cross the boundary. This is especially important for reaching on-premises networks through one VPC's Cloud VPN or Interconnect. Even with custom-route exchange, VPC Peering remains non-transitive: VPC A cannot use VPC B as a transit hop to VPC C merely because B is peered with both.

flowchart LR A[VPC A] <-->|subnet routes + eligible exported custom routes| B[VPC B] B <-->|peering| C[VPC C] A -.not transitive.-> C ON[On-prem] -->|VPN/Interconnect| B B -->|export custom route if enabled| A

Notice: exporting B's custom route toward A can expose B's on-prem prefix, but it does not create A-to-C peering transit.

Route and security boundaries

Peering does not exchange firewall rules. Each VPC must independently allow the traffic. Overlapping subnet ranges prevent useful route exchange and should be caught during address planning. Internal load balancers can be reachable from peers when product-specific regional/global-access requirements are met, but backend firewall policy still lives in the load balancer's VPC.

Troubleshooting workflow

  1. Confirm both peering sides are active.
  2. Check that source and destination subnet ranges do not overlap.
  3. Inspect effective routes on each side.
  4. If the destination is a custom route, verify import/export on both relevant peering configurations.
  5. Validate return routing.
  6. Check firewall rules independently in each VPC.
  7. Do not expect transit to a third peered VPC.
Exam trap: "Export custom routes" does not turn VPC Network Peering into a transit network.

Primary: VPC Network Peering.

6. Application Load Balancer URL-map traffic management: routes, rewrites, redirects, and ordered rules

Domain 3

Two-stage decision model

An Application Load Balancer is a Layer-7 proxy. The URL map first selects a backend service or redirect action using host/path/request matching; the chosen backend service then selects a backend according to its balancing configuration. Advanced routeRules can match path, HTTP headers, and query parameters. Unlike simple pathRules, ordered route rules are evaluated by priority.

Rewrite versus redirect

A rewrite changes the request that the load balancer forwards to a backend; the client does not need to know the internal origin URL. A redirect tells the client to make a new request to a different URL and can be used for HTTP-to-HTTPS migration, hostname consolidation, path changes, and URL shortening. These are fundamentally different packet/application behaviors even though both are configured in a URL map.

flowchart LR C[Client request] --> LB[Application Load Balancer proxy] LB --> UM[URL map] UM -->|routeRule match| RW[Rewrite host/path] RW --> B1[Backend service] UM -->|redirect action| C2[Client receives 3xx and reconnects] UM -->|default| B2[Default backend]

Notice: redirect creates a second client request; rewrite modifies the proxied request internally.

Failure modes

Misordered routeRules can shadow a more specific match. A hostname rule must use an FQDN rather than an IP address. A rule may successfully choose the intended backend service while health checks or backend capacity still prevent successful serving. Troubleshooting therefore separates URL-map selection from backend-service health.

FeatureUseCommon mistake
pathRulesSimple host/path mappingAssuming rule order matters like routeRules
routeRulesAdvanced ordered matchingWrong priority shadows desired rule
RewriteTransform host/path before backendExpecting browser URL to change
RedirectTell client to request another URLExpecting transparent backend rewrite
Remember: URL-map troubleshooting is a control decision problem first, a backend-health problem second.

Primary: Application Load Balancer traffic management; Use URL maps.

7. Cloud DNS routing policies: geolocation, weighted answers, failover, and health checks

Domain 3

Why DNS routing policy exists

Cloud DNS routing policies let a managed DNS record choose from multiple answer sets based on policy rather than always returning one static RRset. Common models include weighted round robin for controlled distribution, geolocation for location-sensitive answers, and failover behavior tied to health signals. The control point is DNS resolution, so effects are governed by resolver caching and record TTL—not instantaneous per-packet steering.

flowchart LR CL[Client resolver] --> DNS[Cloud DNS routing policy] DNS -->|geo: us-east| A[Regional endpoint A] DNS -->|geo: europe| B[Regional endpoint B] DNS -->|weighted bucket| C[Canary/secondary target] DNS -->|failover + health| F[Backup target]

Notice: Cloud DNS returns an answer; it is not in the subsequent application traffic path.

Policy behavior

Weighted policies allow operators to assign relative weights to answer groups, useful for gradual migrations and controlled distribution. Geolocation maps query origin geography to answer sets. Health-aware failover can stop returning an unhealthy target and use backup data according to policy. These mechanisms can be combined with regional internal load balancers or service endpoints to build DNS-level resilience.

Operational caveats

DNS is eventually observed by clients through recursive resolvers and caches. A failover decision at the authoritative service does not erase answers already cached elsewhere. A low TTL can speed convergence but increases query rate and is not a substitute for application retries. Health-check scope and the actual service endpoint being measured must match the failure you are trying to mask.

RequirementPolicy
Gradually send a small share to a new endpointWeighted round robin
Prefer regionally appropriate endpointsGeolocation
Return backup only when primary is unhealthyFailover/health-aware policy
Per-request Layer-7 header routingApplication Load Balancer, not DNS
Remember: DNS routing is answer selection, not connection proxying. TTL and recursive caching are part of the failover time.

Primary: DNS routing policies and health checks. Supporting: Google Cloud DNS routing policies article.

8. Partner Interconnect: Layer-2 versus Layer-3 providers and the SLA boundary

Domain 4

Connectivity model

Partner Interconnect connects customer networks to Google through a supported provider rather than requiring the customer to install physical circuits directly at Google's colocation facilities. Google and the provider maintain underlying interconnect capacity; the customer provisions VLAN attachments in Google Cloud and a corresponding service with the partner.

Layer-2 versus Layer-3 handoff

With a Layer-2 partner, the customer establishes BGP directly between its router and Cloud Router across the provider's Layer-2 transport. With a Layer-3 partner, the provider participates in the routing relationship and performs the BGP integration on the customer's behalf. That difference changes who owns BGP configuration, troubleshooting visibility, and some operational responsibilities.

flowchart LR ON[Customer router] --> P[Partner network] P --> G[Google edge] G --> VA[VLAN attachment] VA --> CR[Cloud Router] CR --> VPC[VPC] ON -.L2 partner: BGP reaches Cloud Router.-> CR ON -.L3 partner: provider handles BGP integration.-> P

Notice: Partner Interconnect introduces a provider fault and support domain in addition to Google and the customer.

Availability and responsibility

Production designs need redundant VLAN attachments and partner connectivity according to Google's recommended topologies. The Partner Interconnect SLA covers the defined Google-to-partner service boundary for qualifying topology; the partner may have separate commitments for its access network. Capacity, metro diversity, partner redundancy, and Cloud Router design should therefore be reviewed independently.

Troubleshooting workflow

  1. Check VLAN attachment state and activation.
  2. Determine whether the provider service is Layer 2 or Layer 3.
  3. For Layer 2, inspect customer-to-Cloud-Router BGP state and addressing.
  4. For Layer 3, confirm provider routing handoff and advertised prefixes.
  5. Validate route installation in the VPC and return advertisements.
  6. Separate provider access-circuit faults from Google attachment faults.
Remember: Partner Interconnect does not eliminate BGP; it changes which party owns portions of the BGP and transport responsibility.

Primary: Partner Interconnect overview.

9. Classic VPN in 2026: static/policy routing survives, dynamic BGP is deprecated

Domain 4

Current lifecycle state

Classic VPN is a legacy Cloud VPN architecture. Google's current deprecation page states that Classic VPN dynamic routing with BGP is no longer a supported creation model: since August 1, 2025, new Classic VPN tunnels using BGP cannot be created, and existing BGP-based Classic tunnels continue without an availability SLA. HA VPN is the supported Cloud VPN architecture for BGP connectivity.

What remains relevant

The certification guide still lists Classic VPN route-based and policy-based configurations because static/policy VPN behavior remains operational knowledge. Classic VPN can still be encountered in existing networks and can be created using supported static routing paths where permitted. Engineers must distinguish the tunnel's IPsec health from the route mechanism—static selectors/routes versus Cloud Router BGP.

flowchart LR ON[Peer gateway] <-->|IPsec| CV[Classic VPN gateway] CV -->|static/policy routes| VPC[VPC] CV -.BGP dynamic routing deprecated.-> CR[Cloud Router] ON <-->|supported dynamic BGP path| HA[HA VPN] HA --> CR

Notice: "Classic VPN exists" does not imply "Classic VPN BGP is a supported new design."

Migration logic

If an existing Classic BGP tunnel must be recreated or materially changed, plan a migration to HA VPN rather than assuming the old dynamic topology can be rebuilt. Migration should verify peer compatibility, HA gateway interface mapping, BGP sessions, route priorities, firewall rules, and the desired SLA topology.

Operational trap: deleting an old Classic BGP tunnel can turn a repair into a migration because the same unsupported dynamic configuration might not be recreatable.
Remember: use HA VPN for new dynamic-routing designs; treat Classic VPN as legacy/static knowledge and migration inventory.

Primary: Classic VPN deprecation; Classic VPN static-routing tutorial.

10. Cloud Router standard versus legacy best-path selection

Domain 4

Two separate VPC controls

A VPC has both a dynamic routing mode (regional or global) and a BGP best-path selection mode (legacy or standard). They solve different problems. Dynamic routing mode controls where learned routes are available; best-path mode controls how competing learned BGP paths are ranked before VPC routes are programmed.

Standard mode controls

Google exposes standard-mode controls including bgpAlwaysCompareMed and bgpInterRegionCost. Standard mode was made generally available in late 2024. Legacy remains the default, and Google's current configuration guide recommends legacy best-path mode for critical workloads unless the operator has deliberately validated standard-mode behavior.

flowchart LR P1[Peer A routes] --> CR1[Cloud Router] P2[Peer B routes] --> CR2[Cloud Router] CR1 --> BPM[VPC best-path selection: LEGACY or STANDARD] CR2 --> BPM BPM --> DRM[Regional/global dynamic routing scope] DRM --> RT[VPC dynamic routes] RT --> W[Workloads]

Notice: best-path comparison and route propagation scope are different stages.

Change and validation

Use gcloud compute networks describe NETWORK --format="get(routingConfig)" to verify routingMode, bgpBestPathSelectionMode, and standard-mode options. A mode change is network-wide, so the safe procedure is to model all competing prefixes, MED/AS-path relationships, inter-region behavior, and failover outcomes before changing production.

SettingQuestion it answers
REGIONAL/GLOBALWhere can learned dynamic routes be used?
LEGACY/STANDARDHow are competing BGP paths ranked?
always compare MEDShould MED be compared across otherwise different paths under standard behavior?
inter-region costHow should region-to-region cost influence best-path decisions?
Remember: never describe global dynamic routing as a best-path algorithm; it is propagation scope.

Primary: Set routing and best path selection modes; Cloud Router release notes.

11. Cloud VPN observability: gateway logs, tunnel metrics, and SLA-health signals

Domain 5

Logs versus metrics

Cloud VPN gateways send diagnostic events to Cloud Logging while VPN tunnels expose time-series metrics through Cloud Monitoring. Logs answer event/configuration questions; metrics answer health, throughput, and trend questions. Production monitoring should use both rather than treating an "up" tunnel as proof of healthy end-to-end connectivity.

HA health telemetry

Google exposes HA VPN health concepts including configured_for_sla, gcp_service_health, and end_to_end_health. The first indicates whether the connection is configured with the required topology for the 99.99% SLA; Google-side health reports service allocation/state; end-to-end health indicates whether traffic is actually passing through the HA connection.

flowchart LR GW[Cloud VPN gateway] --> LOG[Cloud Logging events] T[VPN tunnel] --> MET[Cloud Monitoring metrics] MET --> SLA[configured_for_sla] MET --> GCP[gcp_service_health] MET --> E2E[end_to_end_health] MET --> BW[Bandwidth utilization alert]

Notice: topology compliance, Google service health, and true end-to-end health are separate signals.

Retention and alerting

Cloud VPN logs are stored in Cloud Logging for 30 days by default on the documented VPN resource path; longer retention requires routing logs to another destination such as BigQuery or Pub/Sub according to your logging design. Google recommends tunnel-bandwidth alerts for production utilization monitoring. HA VPN metrics are viewed through Metrics Explorer and can feed dashboards and alert policies.

Incident workflow

ObservationNext step
configured_for_sla=falseReview HA topology and required tunnel/Cloud Router configuration
gcp_service_health=falseInvestigate Google-side allocation/service state and incidents
end_to_end_health=false but service health trueCheck peer device, IPsec, routing, firewall, and return path
Bandwidth near ceilingCapacity plan before congestion becomes packet loss
Remember: tunnel state, SLA topology, Google service health, and application-path health are different layers of evidence.

Primary: View Cloud VPN logs and metrics.

12. Cloud Armor bot management: reCAPTCHA challenges, token signals, IAM, and edge enforcement

Domain 6

Problem and enforcement point

Cloud Armor bot management combines security-policy enforcement with reCAPTCHA signals to distinguish likely humans from automated abuse. Enforcement occurs at Google's edge in front of supported protected workloads, so malicious automation can be challenged or denied before it consumes backend application capacity.

Manual and frictionless assessment

A policy can associate a reCAPTCHA CHALLENGEPAGE site key and redirect matching requests to a Google reCAPTCHA challenge. Rules can also evaluate reCAPTCHA action-token or session-token attributes for lower-friction decisions. Action tokens can originate from web, iOS, or Android applications, while session tokens are web-oriented. Google recommends key association to reduce token theft and distinguish applications/platforms.

flowchart LR C[Client/bot] --> A[Cloud Armor security policy] A -->|match suspicious request| RC[reCAPTCHA challenge or token evaluation] RC -->|acceptable| LB[Protected load balancer/backend] RC -->|bad/automated| DENY[Deny or rate-control] A --> LOG[Security policy logs]

Notice: bot decisions are policy actions at the edge; application authentication is still a separate control.

IAM separation

Creating and modifying Cloud Armor security policies requires Compute Security Admin capabilities such as compute.securityPolicies.create and compute.securityPolicies.update. Attaching a security policy to a backend service can be performed by Compute Network Admin permissions. This separation matters in organizations where security authors and network/application operators are different teams.

Configuration example

gcloud compute security-policies update SECURITY_POLICY \
  --recaptcha-redirect-site-key SITE_KEY

gcloud compute security-policies rules create 1000 \
  --security-policy SECURITY_POLICY \
  --expression 'request.path.matches("/login.html")' \
  --action redirect \
  --redirect-type google-recaptcha

Operational pitfalls

Do not challenge every request indiscriminately. Start with high-risk paths, automation indicators, or token-based signals and monitor false positives. Bot management complements WAF, rate limiting, Adaptive Protection, and application authentication rather than replacing them.

Remember: Cloud Armor can turn reCAPTCHA intelligence into an edge policy action; the key design question is where to add friction without harming legitimate clients.

Primary: Configure bot management.
