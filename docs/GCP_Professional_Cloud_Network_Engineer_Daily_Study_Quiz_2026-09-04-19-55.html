Executive summary

1. Shared VPC and Private Service Connect

Domain 1

Use Shared VPC when multiple service projects need centrally governed subnets, routes, and firewall posture while workload ownership remains distributed. Private Service Connect (PSC) gives consumers private endpoints for producer services without extending a flat routed domain. In Shared VPC, PSC endpoints can be placed in host or service projects using host-project subnet addresses. Connectivity scope and project governance are separate decisions: project placement still affects IAM, visibility, administration, and billing. Prefer PSC for service-oriented private access and reduced address coupling; use peering when you genuinely need network-to-network reachability and understand its propagation limits.

Source: PSC deployment patterns

2. IP architecture, private access, and route-domain planning

Domain 1

Treat IP planning as architecture. Reserve non-overlapping space for primary subnet ranges, GKE secondary ranges, hybrid networks, managed-services ranges, and future acquisitions or multi-cloud connectivity. Private Google Access lets internal-only resources reach supported Google APIs and services; private services access and PSC solve different managed-service connectivity problems. Regional versus global dynamic routing affects where learned routes are available. MTU must be considered end to end across VPC, VPN, Interconnect, appliances, and workloads, because encapsulation overhead can produce application failures that look unrelated to routing.

Source: VPC documentation

3. Cloud Router BGP, MED, advertisements, and BFD

Domain 2

Cloud Router is a managed BGP control-plane function; it does not forward user packets. Use it with HA VPN and Interconnect to exchange dynamic routes. Custom advertised routes control what Google advertises to peers, while route priority maps to MED semantics in hybrid decisions. BFD provides faster forwarding-failure detection on supported VLAN-attachment BGP sessions, but support is deliberately limited: Cloud Router BFD is single-hop and is not supported for HA VPN BGP sessions or Router appliance sessions. Build convergence around the actual transport rather than assuming every BGP adjacency can use the same timers.

Source: Cloud Router BFD

4. Network Connectivity Center topology

Domain 2

NCC provides a hub-and-spoke control model for VPC and hybrid connectivity. VPC spokes connect VPC networks; hybrid spokes represent HA VPN tunnels, VLAN attachments, or Router appliance connectivity; producer spokes expose supported producer services. Site-to-site data transfer can let external sites use Google's network as WAN transport. Do not assume unrestricted transitivity. Topology, spoke type, route exchange, route filters, Private NAT, and PSC propagation determine what can actually communicate. A strong design treats segmentation and propagation as explicit architecture decisions rather than consequences of attaching everything to one hub.

Source: NCC site-to-site data transfer

5. GKE networking

Domain 2

VPC-native GKE uses alias IP ranges so Pods consume addresses from secondary subnet ranges and participate naturally in VPC routing. Capacity planning must include node ranges, Pod ranges, Service ranges, and future additional Pod ranges. Private nodes reduce direct internet exposure; controlled egress can use Cloud NAT, while Google API access can use Private Google Access. Control-plane exposure is a separate choice from node exposure. Dataplane V2 adds an eBPF-based data plane and integrated network-policy capabilities. In Shared VPC, coordinate subnet ownership, IAM, and secondary ranges between host and service projects before cluster creation.

Source: GKE networking best practices

6. Cloud Load Balancing: proxy versus passthrough

Domain 3

Start load-balancer selection with protocol and packet semantics. Proxy load balancers terminate the client connection and create a new backend connection, enabling Layer 7 traffic management such as URL maps and richer request processing. Passthrough Network Load Balancers preserve source and destination packet information to the backend and use direct server return behavior. That distinction matters for appliances and applications that require original client IP information. Also validate regional versus global scope, backend type, health checks, session affinity, Network Tier, and TLS termination point. Newer global external passthrough features can have different release stages, so verify current status before production design.

Source: Passthrough Network Load Balancing

7. Cloud DNS hybrid resolution

Domain 3

Hybrid DNS is a forwarding-path problem. Inbound server policies help on-premises systems query Cloud DNS private data through hybrid connectivity. Forwarding zones or outbound policies let Cloud DNS send selected queries to external resolvers. DNS peering exposes another VPC's name-resolution order without creating general routed transit. Cross-project binding separates zone administration from network attachment. Split-horizon DNS intentionally returns different answers to different views, while routing policies support patterns such as geolocation and failover. When troubleshooting, draw the exact resolver chain first; otherwise firewall and routing changes can mask the actual authority or forwarding mistake.

Source: Cloud DNS overview

8. Interconnect availability and HA VPN over Interconnect

Domain 4

Dedicated and Partner Interconnect provide private high-capacity connectivity, but availability is topology-dependent. Google documents distinct connection counts and placement requirements for 99.9% and 99.99% SLA designs. If traffic over Interconnect must be encrypted, HA VPN over Cloud Interconnect overlays IPsec on VLAN attachments and uses separate Cloud Routers for the Interconnect tier and HA VPN tier. Encryption must be selected when the VLAN attachment is created. MTU and payload overhead must also be planned. The key lesson is that physical redundancy, routing redundancy, and encryption are separate design dimensions that must all be validated.

Source: HA VPN over Cloud Interconnect

9. Hybrid convergence and failure detection

Domain 4

For fast failover, identify what failure you actually need to detect: BGP adjacency loss, forwarding-path loss, attachment failure, device failure, or metro failure. BFD is useful where supported, but HA VPN BGP sessions do not support Cloud Router BFD. Interconnect designs can use BFD on supported VLAN attachments. Redundant attachments, tunnels, edge availability domains, regions, route priorities, and advertisements determine the real failover path. A healthy BGP adjacency does not prove the complete application path is healthy, so combine control-plane monitoring with data-plane tests and deliberate failover exercises.

Source: Cloud Router BFD

10. Network Intelligence Center troubleshooting

Domain 5

Use the tool that answers the right question. Connectivity Tests models the expected forwarding path and can add live data-plane analysis in supported cases. Flow Analyzer works from VPC Flow Logs to show observed traffic patterns. Network Topology visualizes relationships and throughput. Firewall Insights highlights rule usage and optimization opportunities. Network Analyzer detects failures and suboptimal configuration, while Performance Dashboard helps isolate loss and latency. A critical nuance is time: a Connectivity Test launched from historical Flow Analyzer data evaluates the current network configuration, not the exact historical configuration that existed when the flow was logged.

Source: Connectivity Tests overview

11. Cloud NGFW, hierarchy, and secure tags

Domain 6

Google Cloud firewall design can combine VPC firewall rules, hierarchical firewall policies, and network firewall policies. Hierarchical policies provide organization or folder guardrails, while network policies centralize VPC-scoped controls. Secure tags provide identity-like targeting that scales better than relying only on IP addresses. The hierarchical action goto_next delegates evaluation to the next level. Before migrating policies, understand effective evaluation order so organization controls do not unintentionally override project assumptions. Cloud NGFW tiers add capabilities up through advanced inspection, while logging and Firewall Insights support operations.

Source: Cloud NGFW secure tags

12. Google Cloud Armor

Domain 6

Cloud Armor protects supported load-balanced applications from volumetric and application-layer attacks. Preconfigured WAF rules address common patterns such as SQL injection and XSS; rate limiting addresses abusive request rates; Adaptive Protection adds behavioral detection. Policy attachment point matters because edge and backend security policies protect different traffic paths. Cloud Armor benefits from Google's distributed edge but is not a replacement for VPC firewall policy, IAM, or application authentication. Treat DDoS defense, WAF, east-west segmentation, identity, and service authorization as complementary layers.

Source: Cloud Armor overview

Expert memory anchors

  • Cloud Router exchanges routes; it does not forward user packets.
  • Cloud Router BFD is transport-specific and is not supported on HA VPN BGP sessions.
  • PSC is service connectivity; peering is network connectivity; Shared VPC is centralized network governance across projects.
  • VPC-native GKE scale depends on primary and secondary IP range planning.
  • Passthrough load balancers preserve packet headers; proxy load balancers terminate connections.
  • Hybrid DNS troubleshooting starts by drawing the query path.
  • Connectivity Tests evaluates current configuration even when launched from historical Flow Analyzer data.
  • Cloud Armor and Cloud NGFW or VPC firewall policy protect different layers.
