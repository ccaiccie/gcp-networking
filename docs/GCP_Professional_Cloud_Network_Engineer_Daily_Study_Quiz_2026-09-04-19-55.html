1. Shared VPC + Private Service Connect: governance without flat-network coupling

Domain 1

Problem and architecture

Shared VPC and Private Service Connect solve different layers of the enterprise-network problem. Shared VPC centralizes ownership of VPC networks, subnets, routes, and much of the network security posture in a host project while workloads live in attached service projects. This lets a platform or networking team own the network boundary without forcing application teams to place all resources in one project. Private Service Connect (PSC), by contrast, is service-oriented connectivity: a consumer reaches a producer service through a private endpoint or backend without creating broad routed connectivity between the two VPCs.

In a Shared VPC, PSC endpoints, backends, and service attachments can be deployed in host or service projects. An endpoint uses an address from a host-project subnet; clients throughout the Shared VPC can reach it. Project placement still matters for IAM visibility, administration, and hourly resource billing. That distinction is easy to miss: reachability may be shared while lifecycle ownership is not.

Data plane and packet flow

For a published PSC service, the producer places a load-balanced service behind a service attachment. The consumer creates an endpoint that points at the service attachment. Client VMs send traffic to an internal IP local to the consumer VPC. Google’s Andromeda SDN maps that logical endpoint to the producer service. Google documents that PSC is implemented in the distributed Andromeda data plane rather than by a centralized middlebox; client-side load balancing and translation are applied on the participating hosts. That design avoids inserting an extra user-managed proxy hop.

Official visual: Google’s PSC architecture article contains physical/logical traffic-path figures. A stable Google-hosted historical PSC animation is embedded below as a supplemental visual.

Security, operations, and failure analysis

Producer-side service attachments can use connection preferences and consumer accept lists. The consumer controls the endpoint and its local IP. This creates an explicit trust boundary: the producer does not need the consumer’s entire route domain, and the consumer does not need to import producer subnets. When troubleshooting, separate endpoint state, service-attachment acceptance, producer load-balancer health, DNS-to-endpoint mapping, firewall policy, and application health. A PSC endpoint that resolves correctly does not prove the producer backend is healthy.

Remember: Shared VPC answers “who governs the network?” PSC answers “how do I privately consume or publish a service?” They can be used together.

2. VPC IP architecture, Private Google Access, dynamic-routing scope, and MTU

Domain 1

Plan address space as a long-lived dependency

A production VPC design needs more than “a subnet for each region.” Reserve non-overlapping address space for VM subnets, GKE node ranges, Pod and Service secondary ranges, load-balancer proxy-only subnets where applicable, hybrid connectivity, managed-service ranges, appliance networks, and future mergers or multi-cloud attachments. Google VPCs are global resources but subnets are regional. Overlap is particularly damaging once you introduce peering, NCC, Interconnect, VPN, or service networking because the same destination can no longer be unambiguously routed.

Private access patterns are not interchangeable

Private Google Access lets VMs that have only internal addresses reach supported Google APIs and services. Private services access uses allocated ranges and peering for certain producer services. PSC uses consumer-side private endpoints and a service-centric model. These mechanisms solve adjacent but different problems, so an architecture should name exactly which one is being used rather than saying only “private access.”

Regional versus global dynamic routing

With regional dynamic routing, learned dynamic routes are made available only in the region associated with the relevant Cloud Router path. With global dynamic routing, the best dynamic path for a prefix can be propagated into other regions of the same VPC. Global dynamic routing can simplify multi-region hybrid designs, but it also means a failure or preference change in one region can influence forwarding elsewhere. The dynamic routing mode therefore belongs in the failure-domain discussion, not merely in initial provisioning.

MTU as a hidden application dependency

Google Cloud supports configurable VPC MTU, but the effective end-to-end payload size is constrained by the smallest segment and any encapsulation overhead from IPsec, GRE, GENEVE-like appliances, or overlay networking. Symptoms can include large TLS transfers stalling while pings and small packets succeed. Troubleshooting should compare VPC MTU, guest NIC MTU, tunnel overhead, appliance behavior, and path-MTU discovery rather than treating the problem as “the route is present, therefore networking is fine.”

Visual teaching model:

flowchart LR ONP[On-prem CIDRs] --> HYB[VPN / Interconnect] HYB --> VPC[Global VPC] VPC --> R1[Regional subnet A] VPC --> R2[Regional subnet B] R1 --> PGA[Private Google Access -> Google APIs] R2 --> PSC[PSC endpoint -> managed service] VPC -. MTU must survive every hop .-> HYB

Troubleshooting checklist

  1. Confirm destination classification: Google API, producer service, peer VPC, on-prem prefix, or internet.
  2. Check effective routes and dynamic-routing mode.
  3. Check overlap and more-specific routes.
  4. Check firewall and policy controls independently from routing.
  5. For size-sensitive failures, test MTU/fragmentation rather than only reachability.
Remember: IP allocation, route scope, private-access mechanism, and MTU are architecture decisions that become expensive to change after workloads scale.

3. Cloud Router: BGP tasks, learned routes, MED, advertisements, and BFD

Domain 2

Cloud Router is control plane, not packet forwarding

Cloud Router is an API abstraction implemented through redundant BGP tasks, regional dynamic route control planes, and the VPC control/data planes. BGP tasks establish sessions and exchange prefixes; they do not sit in the forwarding path. This is a critical mental model: packets are forwarded by Google’s VPC data plane after routes are programmed, not through a virtual router appliance named “Cloud Router.”

Learned-route processing

Routes can arrive from a physical router, another Cloud Router, a router in another cloud, or a Router appliance. Google also supports custom learned routes that are configured on a BGP peer to simulate remotely learned prefixes. Custom learned routes track the BGP session lifecycle, so they are withdrawn if that BGP next hop goes down. Google applies dynamic-route quotas, AS-path and origin processing, MED/priority comparisons, and regional/global dynamic-routing behavior before the VPC control plane creates usable dynamic routes.

Custom learned routes are useful when you cannot modify the remote router but need prefixes associated with an HA VPN tunnel, VLAN attachment, or supported appliance path. A subnet route takes precedence when custom learned routes overlap a local VPC subnet; more-specific BGP/custom learned routes do not override the local subnet route in that conflict.

Advertisements and MED

Cloud Router advertises prefixes with MED derived from route priority. Lower MED is preferred by neighbors that honor it. Custom advertisements control which prefixes leave Google toward a peer. Google recommends advertising the same prefixes across redundant links when designing for high availability, optionally with different priorities to influence primary/backup behavior. Modern designs can also use BGP route policies for finer control.

BFD and convergence

BFD provides rapid forwarding-failure detection on supported Cloud Router sessions, notably supported VLAN-attachment BGP sessions. It is single-hop. Google does not support Cloud Router BFD for HA VPN BGP sessions or Router appliance sessions. Therefore “enable BFD everywhere” is not a valid design. Where BFD is unavailable, hold timers and the transport’s own failure signals determine withdrawal speed.

flowchart LR PEER[Peer router] <-->|BGP prefixes / MED| BGP[Cloud Router BGP task] BGP --> DRC[Regional dynamic route control plane] DRC -->|regional/global processing| VC[VPC control plane] VC --> DP[VPC data plane] DP --> VM[Workload] PEER -. packets do NOT traverse Cloud Router .-> VM

Official Google Cloud Router software-components figure.

Operational workflow

When a route is missing, determine whether the BGP session is established, whether the peer advertised the prefix, whether Cloud Router accepted it, whether quotas caused deterministic dropping, whether best-path processing selected another route, and whether the VPC control plane installed a usable dynamic route. This layered workflow prevents the common mistake of stopping at “BGP is Established.”

Remember: Cloud Router exchanges control-plane information. The VPC data plane forwards packets. MED/priority influences path choice; BFD support depends on the transport.

4. Network Connectivity Center: VPC spokes, hybrid spokes, mesh, star, and inspection

Domain 2

What NCC changes

NCC is an orchestration framework built around a global hub and attached spokes. VPC spokes let multiple VPCs exchange subnet reachability without building pairwise peering meshes. Hybrid spokes represent HA VPN tunnels, VLAN attachments, or Router appliance connectivity. Producer VPC spokes and NCC Gateway spokes extend the model to additional service and branch connectivity patterns.

A VPC spoke can attach to one hub at a time. VPC spokes can be in different projects and even different organizations relative to the hub, subject to permissions and supported attachment workflow. Traffic between VPC spokes stays on Google’s network. With hybrid spokes, NCC can support site-to-cloud and, when configured appropriately, site-to-site data transfer across Google’s backbone.

Preset topologies

Current NCC supports preset mesh, star, and hybrid-inspection topologies. The topology is selected when the hub is created and cannot later be changed in place. Mesh places spokes into one routing domain and is the simplest any-to-any model. Star separates center and edge spoke groups so edge-to-edge communication can be controlled through the center. Hybrid-inspection topologies are designed for centralized inspection patterns. Each spoke group has its own route table, and route exchange is affected by spoke type and import/export filtering.

flowchart TB subgraph Mesh H1[NCC Hub] --- A[VPC A] H1 --- B[VPC B] H1 --- C[Hybrid spoke] end subgraph Star HC[Center group] --- E1[Edge VPC 1] HC --- E2[Edge VPC 2] HC --- SEC[Inspection / services] end

Official Google NCC mesh/star/hybrid-inspection topology figures.

Transitivity is designed, not assumed

NCC can provide transitive-looking outcomes that VPC Peering does not, but engineers still need to reason about route import/export, hybrid-spoke advertisement, site-to-site data transfer settings, and spoke-group topology. In mixed VPC/hybrid designs, route exchange toward on-premises depends on Cloud Router advertisement behavior. A hub is not a magic “route everything everywhere” switch.

Failure and troubleshooting

When one spoke cannot reach another, verify the spoke is active and accepted, topology/spoke-group placement is correct, route export and import filters permit the prefix, dynamic routes are being advertised where required, and firewall policy permits traffic. For hybrid spokes, separately validate VPN/Interconnect resource health and Cloud Router BGP state.

Remember: NCC centralizes connectivity management, but topology and propagation are explicit design controls. Know mesh versus star versus inspection before you build.

Primary: NCC overview; VPC spokes; Preset topologies.

5. GKE networking: VPC-native addressing, private nodes, control plane, and Dataplane V2

Domain 2

Address-plan before cluster creation

VPC-native GKE uses alias IP addresses. The node subnet’s primary range provides node addresses; secondary ranges provide Pod and Service addresses. Google’s best-practice guidance emphasizes sizing these ranges for the maximum expected scale, not current cluster size. The Service secondary range is especially important because it cannot simply be expanded or changed over the lifetime of the cluster. Pod capacity can be extended with additional Pod ranges and additional node-pool ranges, but bad initial planning still creates migration pressure.

The control plane has its own address relationship to the cluster and, for architectures that use control-plane peering, requires non-overlapping space. Any overlap with the broader peering group can cause route ambiguity. Shared VPC adds another administrative dimension: the host project owns the subnet and secondary ranges, while the service project owns the cluster resources.

Private nodes and egress

Private nodes do not have external IP addresses. Google APIs can be reached through Private Google Access; general internet egress can be provided through Cloud NAT. Inbound application access is deliberately separate and is typically exposed through an appropriate load balancer, Gateway, Ingress, or internal service. A “private cluster” should be decomposed into node exposure, control-plane endpoint exposure, authorized access, and egress behavior rather than treated as one binary setting.

Dataplane V2 and policy

GKE Dataplane V2 uses an eBPF-based data plane and integrates Kubernetes NetworkPolicy enforcement. Google recommends it for built-in capabilities such as network-policy logging. This does not remove the need for VPC firewall policy: Kubernetes policy and VPC policy protect different enforcement domains. Engineers should know where a packet can be dropped—Pod policy, node/VPC firewall, load-balancer health, route, Cloud NAT, or upstream destination.

flowchart LR ONP[On-prem admin] --> CP[GKE control plane] subgraph VPC[VPC-native cluster subnet] NODE[Private node] --> POD[Pod alias IP] SVC[Service range] --> POD end POD --> PGA[Private Google Access -> Google APIs] POD --> NAT[Cloud NAT -> Internet] LB[Load balancer] --> POD

Official Google “Private nodes communication” diagram.

Troubleshooting pattern

Start with the packet’s identity: source Pod IP, node IP if SNAT is involved, destination, service VIP, and policy domain. Then check Service/EndpointSlice health, Pod readiness, network policy, VPC route/firewall, NAT/PGA configuration, and return path. This layered approach is faster than toggling firewall rules until traffic works.

Remember: GKE networking is mostly address planning plus layered enforcement. Know node, Pod, Service, control-plane, and load-balancer addresses separately.

Primary: GKE networking best practices.

6. Cloud Load Balancing: proxy versus passthrough and why source IP changes

Domain 3

The first decision is packet semantics

Google Cloud load balancers are not one product with cosmetic variants. Proxy load balancers terminate the client connection and create a second connection to the backend. This enables Layer 7 functions, TLS termination, advanced traffic management, and globally distributed proxy infrastructure. Passthrough Network Load Balancers forward packets without proxy termination: backends receive packets with source and destination addresses and transport headers preserved, and responses can use direct server return.

Proxy flow

For proxy Network Load Balancers, there are two connections. The client connects to the load-balancer frontend; a Google proxy then connects to the backend. The backend therefore sees a proxy-source address rather than the original client’s packet source address at Layer 3. Applications that require the true client identity generally use proxy-aware mechanisms rather than expecting unchanged packets.

Passthrough flow

A passthrough NLB preserves original packet headers and supports protocols beyond ordinary proxied TCP/HTTP use cases, including UDP and other IP protocols depending on the product mode. TLS is terminated by the backend because the load balancer is not a TLS proxy. This is attractive for appliances, legacy services, and source-IP-sensitive applications, but it shifts certificate and connection handling to backends.

Troubleshooting

Always identify frontend type, scope, backend type, health check, firewall source ranges, session affinity, and whether the backend expects original client IP. A backend that rejects health-check source ranges can make a perfectly routed service appear unavailable.

Remember: “Proxy versus passthrough” determines connection ownership, source-IP visibility, TLS termination, supported protocols, and return path.

7. Cloud DNS hybrid resolution: inbound, forwarding, peering, and split horizon

Domain 3

DNS is a query path, not just a zone

Hybrid DNS designs fail when engineers think only about zone records and ignore which resolver receives the query, which rule or policy applies, and where the next resolver lives. Cloud DNS private zones provide private authoritative data to associated VPC networks. Inbound server policies make selected Cloud DNS resolution reachable from connected external networks. Forwarding zones and outbound policies send specified queries to external DNS servers. DNS peering lets one VPC use another VPC’s name-resolution order without creating general IP transit.

Split horizon and project boundaries

Split-horizon DNS intentionally returns different answers depending on the querying environment. Cross-project binding can separate DNS-zone administration from the networks that consume the zone. This is useful in platform organizations but can confuse troubleshooting because the project containing the zone is not necessarily the project containing the client VPC.

Hybrid query example

Suppose an on-premises workstation queries db.corp.example. The query reaches a Cloud DNS inbound endpoint over VPN/Interconnect. Cloud DNS evaluates its private-zone and forwarding configuration. If the name belongs to an on-premises authoritative namespace, a forwarding zone can send it back to designated on-premises resolvers. The answer must then return through the same reachable hybrid path. Firewall and route rules must permit DNS to the relevant forwarder addresses.

sequenceDiagram participant O as On-prem client participant I as Cloud DNS inbound participant C as Cloud DNS resolver participant F as On-prem forwarder autonumber O->>I: Query cloud.internal I->>C: Resolve private namespace C-->>O: Private-zone answer O->>I: Query legacy.corp I->>C: Evaluate forwarding zone C->>F: Forward query F-->>C: Authoritative answer C-->>O: Return answer

Official Cloud DNS documentation and topology figures.

Operations and troubleshooting

Draw the resolver chain first. Then verify zone visibility, overlapping private zones, forwarding targets, peering relationships, inbound/outbound policy, route reachability to external resolvers, firewall UDP/TCP 53 behavior, and caching/TTL. A packet capture showing DNS requests leaving a client does not establish that the intended authoritative server was consulted.

Remember: DNS peering is resolution behavior, not VPC route transit. Inbound enables external clients to query Cloud DNS; forwarding/outbound sends selected Cloud DNS queries elsewhere.

Primary: Cloud DNS overview and linked hybrid-DNS guides.

8. Cloud Interconnect + HA VPN over Interconnect: SLA, encryption, and routing tiers

Domain 4

Why overlay HA VPN on Interconnect?

Dedicated or Partner Interconnect provides private high-capacity connectivity, but organizations can have compliance requirements for IPsec encryption in transit. HA VPN over Cloud Interconnect builds HA VPN tunnels over VLAN attachments so traffic traversing the Interconnect path is encrypted. This is not the same as ordinary internet-based HA VPN: the underlay is Interconnect and the VPN is an overlay.

SLA is topology-dependent

Google documents no SLA for an HA VPN over Interconnect gateway with only one VLAN attachment. A single-region production design with appropriate redundant Interconnect connections can qualify for 99.9%, while a multi-region topology built to Google’s redundancy requirements can qualify for 99.99%. For Dedicated Interconnect, the 99.99% deployment process uses four Interconnect connections arranged as two redundant pairs across two regions, with each pair placed across separate edge availability domains in the metropolitan area.

Separate routing layers

The Interconnect transport and HA VPN overlay have separate Cloud Router responsibilities. This is an important operational boundary: the underlay must first provide reachability between VPN endpoints, and then the overlay BGP sessions exchange application prefixes. A design can therefore fail at physical/Interconnect, VLAN/BGP, VPN tunnel, overlay BGP, or VPC route installation layers.

flowchart LR ONP[On-prem router] --> IC1[Interconnect pair / VLAN attachments] IC1 --> CRU[Underlay Cloud Router] CRU --> HVPN[HA VPN gateway over Interconnect] HVPN --> CRO[Overlay Cloud Router / BGP] CRO --> VPC[VPC workloads] ONP -. IPsec encrypted payload over private underlay .-> HVPN

Official HA VPN over Cloud Interconnect deployment architecture.

MTU, failover, and validation

Encryption adds encapsulation overhead, so MTU must be validated across the complete path. During failover tests, verify not only tunnel status but learned/advertised prefixes and application forwarding. Maintenance and metro failures are different failure domains; the topology must match the SLA target.

Remember: HA VPN over Interconnect adds encryption, not a shortcut around Interconnect redundancy. Overall SLA follows the chosen Interconnect topology.

Primary: HA VPN over Interconnect overview; Deployment process.

9. Hybrid convergence: detect the right failure, then withdraw the right route

Domain 4

Control-plane health is not data-plane health

A BGP session can remain established while traffic is blackholed deeper in the path. Conversely, an interface failure can drop BGP immediately even though an alternate forwarding path is available. Hybrid convergence engineering starts by defining the failure you need to detect: peer process failure, local link failure, Interconnect attachment failure, VPN tunnel failure, metro failure, remote application failure, or path degradation.

Detection mechanisms

On supported Interconnect VLAN attachment BGP sessions, BFD can detect forwarding failure faster than relying on BGP hold time alone. On HA VPN BGP sessions, Cloud Router BFD is not supported, so convergence depends on VPN/tunnel state and BGP timers or other platform behavior. Graceful restart can intentionally retain routes during some control-plane restarts, while CEASE or expired hold timers remove routes under different conditions.

Preference and redundant advertisements

Advertise the same required prefixes over redundant paths if you want those paths to be usable during failure. Use MED/priority deliberately if you want active/standby behavior; avoid accidental asymmetry that stateful appliances cannot tolerate. In global dynamic routing, a regional path can become relevant to workloads elsewhere, which broadens the blast radius of preference errors.

flowchart TD F[Failure occurs] --> Q{What failed?} Q -->|VLAN forwarding| BFD[BFD if supported] Q -->|VPN tunnel| VPN[HA VPN state] Q -->|BGP peer| HOLD[BGP notification/hold timer] BFD --> W[Withdraw dynamic route] VPN --> W HOLD --> W W --> BEST[Re-run best-path selection] BEST --> ALT[Install alternate route] ALT --> TEST[Validate application data plane]

Operational test plan

Record baseline BGP peers, learned routes, installed VPC routes, expected MEDs, and application path. Trigger one failure domain at a time. Measure detection, withdrawal, best-path selection, route installation, and application recovery separately. This produces actionable convergence data instead of a single “it failed over in 20 seconds” number.

Remember: Fast BGP timers are not a substitute for understanding the actual failed layer. Test the complete chain from detection to restored application traffic.

Primary: Cloud Router BFD; Learned-route state changes.

10. Network Intelligence Center: choose the tool that answers the question

Domain 5

One console, different evidence types

Network Intelligence Center groups tools that answer different questions. Connectivity Tests evaluates whether the current configuration should allow a path and can incorporate live data-plane analysis for supported scenarios. Flow Analyzer analyzes observed traffic from VPC Flow Logs. Network Topology visualizes resource relationships and traffic metrics. Performance Dashboard highlights packet loss and latency. Firewall Insights analyzes rule configuration and logging-derived usage. Network Analyzer continuously identifies misconfigurations and suboptimal configurations and correlates some issues with recent changes.

Historical evidence versus current configuration

A particularly important nuance: when Connectivity Tests is launched from historical Flow Analyzer data, it uses the flow tuple as input but evaluates the current network configuration. If the network changed after the logged flow occurred, the resulting test does not reconstruct the historical topology. This distinction matters during incident review.

Firewall Insights specifics

Firewall Insights can identify shadowed rules, allow rules with no hits, obsolete rules based on adaptive analysis, unused attributes, overly permissive IP/port ranges, and deny-rule activity. Many metrics depend on Firewall Rules Logging, so “no metric” can mean “not logged,” not “never happened.”

flowchart LR SYM[Symptom] --> CT[Connectivity Tests: should path work now?] SYM --> FA[Flow Analyzer: what traffic was observed?] SYM --> NT[Network Topology: how resources relate] SYM --> PD[Performance Dashboard: loss/latency] SYM --> FI[Firewall Insights: rule use/optimization] SYM --> NA[Network Analyzer: config issues/root causes]

Official Network Intelligence Center module overview.

Troubleshooting workflow

Use Flow Analyzer/Logs to establish that traffic existed; Connectivity Tests to validate current expected forwarding; Firewall Insights and Network Analyzer to find policy/configuration problems; Performance Dashboard to distinguish reachability from performance; and resource-specific logs such as Cloud Router, VPN, Interconnect, or NAT logs for the affected control plane.

Remember: Do not ask one telemetry source to answer a question it was not designed to answer. Configuration analysis, observed flow, and performance telemetry are complementary.

Primary: NIC overview; Flow Analyzer → Connectivity Tests; Firewall Insights; Network Analyzer.

11. Cloud NGFW: hierarchy, goto_next, secure tags, and Layer 7 inspection

Domain 6

Policy layers and governance

Hierarchical firewall policies are organization- or folder-level containers that let central teams enforce security rules across many projects. A higher-level allow or deny cannot be overridden by a lower-level rule. The special goto_next action delegates evaluation to the next folder level or network policy/rules instead of forcing a final decision at the current hierarchy level. This creates a useful governance model: central admins define non-negotiable controls and intentionally delegate application-specific decisions.

Targets and secure tags

Hierarchical policies can target networks and service accounts. Secure tags add centrally governed identity-like selectors that reduce dependence on IP ranges. Network firewall policies can use secure tag source/target values to express segmentation policy that follows tagged resources more cleanly than address-only rules. Tags do not replace IAM; they are policy selectors used by supported network security controls.

Layer 7 inspection

Current hierarchical firewall policy capabilities can direct matched traffic to a security profile group for Layer 7 inspection, such as URL filtering and intrusion prevention. That changes the packet path from simple distributed allow/deny evaluation into transparent interception through firewall endpoints. Engineers must therefore understand not only the rule match but the service chain and availability of the inspection infrastructure.

flowchart TD P[Packet] --> ORG[Organization hierarchical policy] ORG -->|allow/deny| END[Decision] ORG -->|goto_next| FOLDER[Folder policy] FOLDER -->|goto_next| NET[Network firewall policy / VPC rules] NET --> DEC[Final allow/deny] ORG -->|apply security profile group| L7[Firewall endpoint / L7 inspection] L7 --> DEC

Official hierarchical firewall policy documentation and evaluation diagrams.

Operations and migration

Before moving project rules into hierarchy, calculate effective policy for representative VMs. Validate rule priority, direction, source/target identity, logging, and whether goto_next is required. Firewall Insights and effective-policy views help identify shadowing and unexpected delegation.

Remember: Hierarchy is about authority. goto_next is explicit delegation. Secure tags are scalable policy selectors. L7 inspection changes the forwarding chain.

Primary: Hierarchical firewall policies; Secure tags.

12. Google Cloud Armor: DDoS, WAF, Adaptive Protection, and rate limiting

Domain 6

Where Cloud Armor fits

Cloud Armor protects supported load-balanced applications at the edge/backend-policy layer. It complements rather than replaces VPC firewall policy. VPC/Cloud NGFW controls govern network flows to resources; Cloud Armor focuses on internet-facing/application traffic patterns such as volumetric attacks, malicious HTTP requests, abusive clients, and application-layer attack signatures.

WAF and policy tuning

Preconfigured WAF rules provide managed signatures for common classes such as SQL injection and cross-site scripting. Production deployment requires tuning sensitivity and exclusions because applications often contain inputs that resemble attack signatures. A safe rollout typically begins with preview/observation, review of matches, and controlled enforcement rather than blindly enabling the strictest rule set.

Rate limiting and Adaptive Protection

Rate-based rules can throttle clients to a configured threshold or apply other rate-enforcement behavior depending on policy design. This protects scarce backend capacity from a small number of abusive sources and from spikes that would otherwise crowd out legitimate users. Adaptive Protection adds behavior-based detection to help identify anomalous Layer 7 attack patterns. These features should be combined with application authentication, backend capacity planning, and network-layer controls.

flowchart LR USER[Internet clients] --> EDGE[Google edge] EDGE --> ARMOR[Cloud Armor policy] ARMOR -->|WAF / rate limit / threat controls| LB[Supported load balancer] LB --> APP[Backend application] NGFW[Cloud NGFW / VPC firewall] -. complementary network controls .-> APP

Official Cloud Armor overview and architecture references.

Failure and troubleshooting

When legitimate traffic is blocked, identify the exact security policy, rule priority, expression/signature, source attribute, and enforcement point. Correlate load-balancer logs and Cloud Armor request outcomes. For rate limiting, distinguish application latency caused by backend saturation from deliberate throttling. For WAF, tune exclusions narrowly; disabling the entire rule family removes protection beyond the false-positive field.

Remember: Cloud Armor is application/edge protection. Cloud NGFW/VPC firewall is network policy. WAF, rate limiting, and Adaptive Protection solve different abuse patterns and should be layered.

Primary: Cloud Armor overview; Rate limiting; Preconfigured WAF rules.
