1. Compute Engine network bandwidth, gVNIC, and Tier_1 performance

Domain 1

Why this matters

Google Cloud network performance is governed primarily at the compute-instance level, not per IP address or ordinary vNIC. The machine series, vCPU count, physical-NIC architecture, packet size, flow count, guest driver, and whether Tier_1 networking is enabled determine the practical ceiling. Adding extra vNICs to a single-pNIC VM does not multiply its total egress entitlement.

Architecture and behavior

gVNIC is Google's optimized virtual NIC. Third-generation and later machine series generally use gVNIC, and some configurations require it. Tier_1 networking raises the per-VM bandwidth ceiling on supported second- and third-generation series. Newer network-optimized families can instead expose multiple physical NICs and much larger aggregate throughput. Traffic routed within a VPC follows different limits from traffic whose route exits the VPC through the default internet gateway; external-destination traffic also has per-flow and aggregate ceilings.

Design questionWhat to verify
Need more throughput?Machine-series ceiling, gVNIC support, Tier_1 support, pNIC count, packet rate and flow count.
Multiple vNICs?Do not assume each vNIC receives a fresh bandwidth budget on single-pNIC VMs.
Internet path slow?Check the separate outside-VPC aggregate and per-flow limits, not only the VM's internal-VPC ceiling.
Benchmark below spec?Validate guest offloads, queue count, MTU, packet size, competing disk I/O, and number of parallel flows.

Failure scenario and troubleshooting

A VM with two vNICs reaches only the same throughput it had with one vNIC. That can be expected when both vNICs share one physical NIC and one per-instance egress budget. Check machine-series architecture first, then gVNIC, Tier_1, queue allocation, and whether the test is single-flow. A single flow can hit a lower ceiling than aggregate throughput across many flows.

Exam anchor: bandwidth is primarily per instance and path class; more logical interfaces do not automatically mean more bandwidth.

Teaching diagram

flowchart LR A[Application] --> V[gVNIC] V --> P[Physical NIC / host] P --> G[Google VPC fabric] G --> I[In-VPC destination] G --> E[Outside-VPC destination] T[Tier_1] -. raises supported per-VM ceiling .-> V

What to notice: logical vNIC count and instance bandwidth are not the same thing; the destination path class also changes applicable ceilings.

Primary source: https://docs.cloud.google.com/compute/docs/network-bandwidth

2. Private Service Connect published services: NAT, scaling, and connection lifecycle

Domain 1

Producer model

A producer publishes a service with a service attachment and one or more dedicated Private Service Connect NAT subnets. Consumers connect through PSC endpoints or PSC backends. The producer does not expose its routed VPC to the consumer; PSC translates consumer traffic into producer-side source addresses drawn from the service attachment's NAT subnets.

NAT and scale

PSC service attachments perform source NAT before traffic reaches producer backends. NAT subnets are dedicated to PSC and cannot simultaneously host ordinary VMs or forwarding rules. Capacity planning must consider producer backend count, source-port availability, application connection churn, and PSC's connection-mapping behavior. Long-lived flows need keepalives if they would otherwise exceed idle timeouts.

Trust boundary

Connection preference controls whether consumers are accepted automatically or explicitly. Because PSC is service-oriented, it reduces the blast radius compared with full network peering. Troubleshooting should separately confirm consumer endpoint state, producer acceptance, NAT-subnet capacity, load-balancer/backend health, and application response.

SymptomLikely layer
Endpoint PENDINGProducer connection preference / consumer approval.
Accepted but no app responseProducer load balancer, backend health, firewall, or app.
High connection churnEphemeral ports / PSC NAT mapping scale / backend count.
Idle flows resetApplication keepalive versus PSC idle timeout behavior.
Exam anchor: PSC service publication is private service connectivity with producer-side SNAT, not routed network merger.

Teaching diagram

flowchart LR C[Consumer] --> EP[PSC endpoint/backend] EP --> SA[Service attachment] SA --> NAT[PSC NAT subnet SNAT] NAT --> B[Producer backend] B --> NAT --> EP --> C

What to notice: the producer sees translated source addresses from the PSC NAT subnet rather than a merged consumer route domain.

Primary source: https://docs.cloud.google.com/vpc/docs/about-vpc-hosted-services

3. GKE service discovery with Cloud DNS scopes

Domain 2

DNS choices

GKE service discovery can use kube-dns or Cloud DNS. Cloud DNS is the default DNS provider for Autopilot and supports scopes that change who can resolve Kubernetes service names. Cluster scope behaves like traditional cluster-local DNS. Additive VPC scope exposes headless-service records to clients in the VPC while retaining cluster scope. VPC scope makes cluster Service DNS records resolvable across the VPC and connected hybrid networks.

Resolution path

Pods resolve stable Service names rather than ephemeral Pod IP addresses. NodeLocal DNSCache can cache queries on each node and reduce latency/load on the upstream cluster DNS system. Multi-cluster Services extend naming across participating clusters with clusterset.local records.

Design caveats

Broader scope is not automatically better. VPC-wide visibility changes naming and security assumptions and can create collisions if teams use inconsistent service names or custom cluster domains. Hybrid clients also require network reachability to the resolved endpoints, not merely successful DNS.

Exam anchor: DNS visibility and packet reachability are separate questions; resolving a Service name does not guarantee routability to its endpoints.

Teaching diagram

flowchart LR P[Pod] --> N[NodeLocal DNSCache optional] N --> D[Cloud DNS or kube-dns] D --> CS[Cluster-scope records] D --> VS[VPC-scope records] VS --> H[VM / hybrid client]

What to notice: DNS scope controls who can resolve records; routing and firewall policy still decide who can reach the returned addresses.

Primary source: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-service-discovery

4. GKE pod egress: ip-masq-agent, source preservation, and Cloud NAT

Domain 2

Two translation layers

For Pod traffic leaving a VPC-native cluster, GKE can translate at the node with ip-masq-agent and again at the VPC edge with Cloud NAT. If a destination is not in nonMasqueradeCIDRs, the node rewrites the Pod source to the node IP. Cloud NAT can then translate the node IP for internet egress.

Preserving Pod IPs

If a destination matches nonMasqueradeCIDRs, or default SNAT is disabled, the Pod IP can remain visible outside the node. For internet egress in that design, Cloud NAT must be configured to translate the Pod secondary ranges. For on-premises networks, preserving Pod IPs requires the hybrid network to know return routes for the Pod CIDRs.

Operational failure pattern

If on-premises firewalls expect node IPs but you preserve Pod IPs, return traffic or policy can fail. Conversely, if security tooling needs Pod identity but the node masquerades, visibility is lost. Inspect the destination against nonMasqueradeCIDRs, confirm the actual source on the wire, then check Cloud NAT scope and hybrid route advertisements.

Exam anchor: node SNAT and Cloud NAT are distinct stages; reason about the source address after each stage.

Teaching diagram

flowchart LR P[Pod IP] --> M{Destination in nonMasqueradeCIDRs?} M -->|No| SNAT[Node SNAT to node IP] M -->|Yes| KEEP[Preserve Pod IP] SNAT --> NAT[Cloud NAT if internet] KEEP --> NAT2[Cloud NAT must cover Pod secondary range if internet]

What to notice: the packet can be translated once at the node and again by Cloud NAT, or preserve the Pod source until the VPC edge.

Primary source: https://docs.cloud.google.com/kubernetes-engine/docs/how-to/pod-to-external-endpoint-connectivity

5. GKE LoadBalancer Services, subsetting, and backend models

Domain 3

Controller decisions

A GKE LoadBalancer Service causes the GKE controller to create Google Cloud load-balancing resources. Internal Services create internal passthrough Network Load Balancers; external Services create regional external passthrough load balancers. Modern GKE versions and clusters with subsetting use GCE_VM_IP NEGs rather than node instance-group backends.

Why subsetting matters

Subsetting limits which nodes are programmed as backends for a Service, improving scalability and reducing dataplane churn. Newer GKE versions automatically enable it in more cases. Some modern loadBalancerClass values require subsetting and are immutable after Service creation.

Dual stack and traffic policy

Dual-stack LoadBalancer Services create separate IPv4 and IPv6 forwarding rules and require compatible cluster and load-balancer modes. Source preservation depends on load-balancer type and Kubernetes traffic policy; do not assume every Service preserves the client address the same way.

Exam anchor: know whether the Service is instance-group or NEG backed, whether subsetting is enabled, and which forwarding rules are created.

Teaching diagram

flowchart LR S[Kubernetes Service] --> C[GKE controller] C --> FR[Forwarding rule] C --> BS[Backend service] BS --> NEG[GCE_VM_IP NEGs with subsetting] FR --> NEG

What to notice: the Kubernetes object is translated into Google Cloud forwarding and backend resources; subsetting changes how node backends are represented.

Primary source: https://docs.cloud.google.com/kubernetes-engine/docs/concepts/service-load-balancer-parameters

6. Internal passthrough Network Load Balancer failover policy

Domain 3

Primary and failover groups

Internal passthrough Network Load Balancers can classify backend instance groups or zonal NEGs as primary or failover. Failover behavior is driven by backend health, the failover ratio, and the configured last-resort behavior. Merely adding a failover backend does not mean it is always eligible.

Failover ratio

The ratio sets the health threshold that triggers a switch of the eligible set from primary to failover backends. Operators can also choose whether to drop traffic when all eligible backends are unhealthy and whether existing connections are drained when the active set changes.

Packet semantics

Because the load balancer is passthrough, backends see packets addressed to the forwarding-rule IP. Server software must listen appropriately, and return routing must support direct server return semantics. Failover is therefore both a health-policy problem and a host networking problem.

Exam anchor: distinguish backend health, failover eligibility, and connection-draining behavior; each answers a different availability question.

Teaching diagram

flowchart LR CL[Client] --> VIP[Internal passthrough VIP] VIP --> H{Primary healthy ratio} H -->|Above threshold| P[Primary backends] H -->|Below threshold| F[Failover backends] P --> CL F --> CL

What to notice: health and the failover ratio decide the eligible backend set; connection behavior during the switch is a separate setting.

Primary source: https://docs.cloud.google.com/load-balancing/docs/internal/int-netlb-traffic-distribution

7. Internal Application Load Balancer logging and monitoring

Domain 5

Per-backend-service logging

Internal Application Load Balancer request logging is enabled on backend services. If a URL map references multiple backend services, logging must be considered separately for each. Sampling controls the fraction of requests emitted to Cloud Logging; optional fields can add TLS and ORCA load-report context.

Use logs with metrics

Request logs answer who/what/when for sampled requests, while metrics answer aggregate behavior such as request volume, latency and backend health trends. A 100% sample rate maximizes visibility but also increases log volume and cost. Lower sampling can be sufficient for baselining but may miss rare failures.

Troubleshooting workflow

Start with frontend symptoms, correlate load-balancer response details and backend latency, then compare backend health and application logs. If only one URL path fails, inspect URL-map selection and the specific backend service. If all paths fail simultaneously, proxy subnet, firewall, health checks or regional dependencies become stronger suspects.

Exam anchor: logging is configured per backend service, not once for an entire logical URL map.

Teaching diagram

flowchart LR CL[Client] --> LB[Internal ALB] LB --> B1[Backend service A] LB --> B2[Backend service B] B1 --> LOG[Cloud Logging sampled requests] B2 --> LOG LB --> MET[Monitoring metrics]

What to notice: log enablement follows the backend service, while metrics and application telemetry should be correlated for incident analysis.

Primary source: https://cloud.google.com/load-balancing/docs/l7-internal/monitoring

8. Cloud Router MP-BGP and IPv6 route exchange

Domain 4

Multiple BGP models

Cloud Router supports IPv4-only and IPv6-only BGP sessions, plus multiprotocol BGP where one transport session can exchange both IPv4 and IPv6 NLRI. Dedicated Interconnect and HA VPN can use dual-stack designs, but support varies by connectivity product.

Control-plane separation

Cloud Router exchanges routes; Andromeda forwards packets. An established BGP session only proves the control session is up. You must still confirm that the desired IPv6 prefixes are advertised, learned, selected, installed, and usable by the VPC dataplane.

Compatibility

IPv6 BGP peering and route exchange are not universally available for every Cloud Router consumer. Product-specific support matters: for example, Router appliance and Cross-Cloud Interconnect have restrictions that differ from Dedicated Interconnect and HA VPN.

Exam anchor: separate BGP transport family from address families exchanged; MP-BGP can carry IPv6 NLRI over an IPv4 BGP session where supported.

Teaching diagram

flowchart LR PEER[Peer router] <-->|IPv4 BGP + MP-BGP| CR[Cloud Router] CR -->|IPv4 and IPv6 routes| VPC[VPC control plane] VPC --> DP[Andromeda dataplane] DP --> W[Dual-stack workloads]

What to notice: BGP transport and advertised address family can differ; packet forwarding still happens in the VPC dataplane.

Primary source: https://docs.cloud.google.com/network-connectivity/docs/router/concepts/overview

9. NCC Router appliance spokes and site-to-site data transfer

Domain 4

Use case

Router appliance spokes let third-party SD-WAN routers, firewalls, and other BGP-capable NVAs participate in Network Connectivity Center. Customer sites commonly reach Router appliance VMs through SD-WAN overlays or IPsec, while the appliances peer with Cloud Router inside Google Cloud.

Route propagation

When site-to-site data transfer is enabled, routes learned from one site can be exchanged through the NCC hub to another eligible spoke. In multi-region designs, the VPC's dynamic routing mode matters. Google documents global dynamic routing for topologies where Cloud Routers in different regions need to exchange learned routes.

Failure analysis

A tunnel from the branch to the appliance can be healthy while BGP to Cloud Router is down, or BGP can be healthy while the SD-WAN overlay is broken. Troubleshoot the overlay, appliance forwarding, Cloud Router session, learned routes, NCC spoke status, and return path independently.

Exam anchor: Router appliance adds a vendor NVA into NCC; Cloud Router remains the BGP control-plane integration point.

Teaching diagram

flowchart LR S1[Branch A] --> RA1[Router appliance A] RA1 <-->|BGP| CR1[Cloud Router A] CR1 --> HUB[NCC hub] HUB --> CR2[Cloud Router B] CR2 <-->|BGP| RA2[Router appliance B] RA2 --> S2[Branch B]

What to notice: branch overlay health, appliance forwarding, Cloud Router BGP, and NCC participation are separate failure domains.

Primary source: https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/concepts/data-transfer-topology

10. Network Connectivity Center logs and metrics

Domain 5

What to observe

NCC operations should distinguish hub/spoke control state from the health of underlying connectivity resources. Logs record administrative and service events; metrics help track traffic and resource behavior. For Router appliance designs, the underlying VM, Cloud Router/BGP and overlay telemetry remain equally important.

Troubleshooting method

When a branch-to-branch flow fails, first check spoke status and whether the resource is associated with the expected hub. Then check the underlying VPN, VLAN attachment or Router appliance resource and finally verify routes. Use timestamps to correlate topology changes with BGP resets or traffic drops.

Design for observability

Operational maturity requires labels, consistent resource naming, baseline dashboards and alert thresholds before an outage. A hub showing ACTIVE does not prove each application path is healthy; pair NCC telemetry with path tests and application-level monitoring.

Exam anchor: NCC is orchestration. Always correlate NCC state with telemetry from the underlying spoke resource and dataplane path.

Teaching diagram

flowchart LR U[User symptom] --> NCC[NCC hub/spoke state] NCC --> R[Underlying VPN / Interconnect / Router appliance] R --> B[BGP and routes] B --> P[Path test] P --> A[Application telemetry]

What to notice: effective troubleshooting moves from orchestration state down through the actual connectivity resource, routes, and application path.

Primary source: https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/how-to/viewing-logs-metrics

11. Cloud NGFW intrusion detection and prevention service

Domain 6

Architecture

Cloud NGFW Enterprise IDPS uses Google-managed zonal firewall endpoints and packet-intercept technology to inspect selected workload traffic. Threat prevention capabilities are powered by Palo Alto Networks signatures and include anti-spyware, vulnerability protection and antivirus categories.

Policy objects

Threat-prevention security profiles define signature behavior. A security profile group references the profile and is then applied by a firewall policy rule whose action sends matching traffic through the inspection endpoint. This separates traffic selection from threat-policy behavior.

TLS and operations

Encrypted traffic requires a compatible TLS-inspection design if content inspection is required. Troubleshooting should verify endpoint health, policy association, rule priority, security profile group, TLS inspection where used, threat logs, and whether the application protocol is supported.

Exam anchor: IDPS requires both traffic steering to a firewall endpoint and a threat-prevention policy; one without the other is incomplete.

Teaching diagram

flowchart LR W[Workload traffic] --> R[Firewall policy rule] R -->|apply security profile group| EP[Firewall endpoint] EP --> TP[Threat-prevention profile] TP -->|allow/block| D[Destination]

What to notice: policy selects traffic, the endpoint performs inspection, and the threat-prevention profile determines signature handling.

Primary source: https://docs.cloud.google.com/firewall/docs/about-intrusion-prevention

12. Cloud NGFW policy objects: Threat Intelligence, geolocation, and network context

Domain 6

Dynamic match objects

Modern firewall policies can match more than static CIDRs. Rules can reference Google Threat Intelligence lists, geolocation objects, FQDN/domain objects, address groups, secure tags and network context. Support depends on firewall policy type, direction and target type.

Why it changes operations

Google-managed Threat Intelligence lists reduce the need to manually curate known-malicious addresses. Geolocation expresses country/region policy without hand-maintained IP blocks. Network context can constrain a rule based on security boundary semantics such as INTERNET versus NON_INTERNET.

Policy evaluation

Rule priority still matters. Dynamic objects do not remove the need to understand evaluation order, targets, protocol/port scope and actions. A broad allow at a higher priority can make a lower-priority threat-intelligence deny ineffective.

Exam anchor: dynamic objects simplify matching, but firewall-rule priority and policy scope still decide what action is enforced.

Teaching diagram

flowchart TD PKT[Packet] --> PRI[Highest-priority matching rule] PRI --> OBJ{Match object} OBJ --> TI[Threat Intelligence] OBJ --> GEO[Geolocation] OBJ --> NC[Network context] OBJ --> TAG[Secure tags / FQDN / address groups] TI --> ACT[Rule action] GEO --> ACT NC --> ACT TAG --> ACT

What to notice: dynamic match objects enrich policy expression but do not change first-match priority semantics.

Primary source: https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-details

  • Compute network ceilings are primarily per instance/path class; multiple logical vNICs do not automatically multiply bandwidth.
  • PSC published services use dedicated producer-side NAT subnets and explicit producer/consumer connection state.
  • GKE DNS visibility scope and dataplane reachability are separate questions.
  • ip-masq-agent and Cloud NAT can perform two distinct source-NAT stages.
  • GKE subsetting changes the backend representation and scale behavior of LoadBalancer Services.
  • Passthrough NLB failover depends on health, failover ratio, and connection handling—not simply the existence of standby VMs.
  • Cloud Router is control plane; Andromeda forwards the packets.
  • NCC Router appliances join third-party BGP-capable NVAs to the hub-and-spoke control model.
  • Load-balancer logging is backend-service scoped and should be correlated with metrics.
  • Cloud NGFW IDPS needs both inspection steering and threat-prevention policy.
