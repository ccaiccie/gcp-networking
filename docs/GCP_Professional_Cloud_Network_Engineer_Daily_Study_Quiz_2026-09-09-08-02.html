1. Compute Engine multi-NIC and Dynamic NICs

Domain 1

Problem and architecture

Multiple vNICs attach one Compute Engine VM directly to multiple subnets or VPC networks. Common uses are network/security appliances, migration systems, and management-plane versus data-plane separation. A regular vNIC is a distinct VM interface. Dynamic NICs extend the model with VLAN-tagged subinterfaces beneath a parent vNIC, increasing logical network attachments without consuming another full exposed vNIC for each one.

Routing behavior

The guest normally receives its default route on nic0. Traffic that enters a secondary interface can therefore leave through nic0 unless the guest OS has deliberate source/interface policy routing. Linux designs commonly use multiple routing tables plus ip rule and ip route. This is separate from Google VPC routing: the VPC can deliver a packet correctly to nic1 while the guest chooses the wrong return interface.

Constraints and security

Regular additional vNICs are generally defined when the VM is created. Dynamic NICs use VLAN IDs that must be unique under the same parent and can be added or removed later. Each attached VPC needs correct firewall policy. A multi-homed VM also creates a potential transit path between trust zones, so IP forwarding, host firewalling, service binding, and route policy must be explicitly controlled.

Troubleshooting

Verify vNIC-to-subnet attachment, guest addresses, guest policy routes, return-path symmetry, firewall rules in every VPC, and VLAN configuration for Dynamic NICs. Do not stop when the Google route table looks correct.

flowchart LR A[VPC A]-->N0[nic0] B[VPC B]-->N1[nic1] N0-->VM[VM] N1-->VM VM-->R[Guest policy routing]

Notice: the guest routing decision happens after the VPC has delivered traffic to an interface.

Anchor: Correct VPC routing does not guarantee correct guest policy routing.

Primary: Create VMs with multiple network interfaces

2. Proxy-only subnets for regional managed load balancers

Domain 1

Purpose

Regional Envoy-based load balancers require a proxy-only subnet with purpose REGIONAL_MANAGED_PROXY in each region/VPC where they operate. Google allocates addresses from this subnet to the managed Envoy proxy fleet. Ordinary workloads are not placed there.

Packet flow

Clients connect to the forwarding-rule VIP. The managed proxy terminates that connection, evaluates the applicable proxy/L7 policy, and opens a new backend connection. The VIP itself is not an address from the proxy-only subnet. Backend VMs or endpoints therefore see the managed-proxy side of the connection rather than the original client socket.

Design and firewall impact

Regional managed-proxy load balancers in the same region and VPC share the proxy pool, so address capacity must account for future scale. Backend firewall rules must allow the proxy-only subnet where required. Historical proxy-only subnet purposes might need migration before newer regional Envoy products can coexist.

Failure analysis

A common failure is a reachable VIP with unreachable backends because firewall rules allow client CIDRs but not the proxy subnet. Another is proxy address exhaustion. Validate the forwarding rule, proxy-only subnet purpose/capacity, backend service, health checks, and backend firewall policy.

flowchart LR C[Client]-->VIP[Forwarding rule VIP] VIP-->E[Managed Envoy] P[Proxy-only subnet]-.address pool.->E E-->B[Backend]

Notice: frontend addressing and proxy source addressing are different resources.

Anchor: The LB VIP is not in the proxy-only subnet.

Primary: External Application Load Balancer overview

3. Cloud Service Mesh advanced traffic management

Domain 3

Control model

Cloud Service Mesh controls east-west service traffic without requiring application code changes. A Mesh identifies the service mesh, Route resources define request matching and service selection, and backend services determine distribution among endpoints. HTTPRoute, GRPCRoute, TCPRoute, and TLSRoute have different feature coverage.

Weighted routing and mirroring

Weighted routing supports canary deployment by sending a controlled percentage of traffic to a new service version. Traffic mirroring copies requests to a shadow/debug service while the original request still receives its response from the production destination. Mirroring is observation, not failover.

Endpoint behavior

After a Route chooses a destination backend service, load-balancing policy chooses endpoints. Outlier detection can temporarily eject endpoints that repeatedly fail. This distinction matters: a route can select the correct service while a bad endpoint still creates user-visible errors.

Troubleshooting

Check route match, backend service selection, Envoy/proxyless capability, endpoint health or ejection state, and application response. A mirrored backend's response is not returned to the original client.

flowchart LR C[Client service]-->R[HTTPRoute] R--90%-->P[Production] R--10%-->K[Canary] R-.mirror.->D[Debug] P-->E1[Endpoint 1] P-->E2[Endpoint 2]

Notice: service selection and endpoint selection are two different decisions.

Anchor: Routes choose services; backend services choose endpoints.

Primary: Advanced traffic management

4. GKE Gateway API and ownership boundaries

Domain 3

Why Gateway API

Gateway API is a more expressive successor to Ingress and deliberately separates shared infrastructure ownership from application routing. The GKE Gateway controller watches Kubernetes Gateway resources and reconciles Google Cloud load-balancing resources.

Resource roles

GatewayClass identifies the implementation and feature set. Gateway represents traffic-handling infrastructure and listeners. HTTPRoute or related Route resources contain host/path routing and attach to the Gateway. Kubernetes Services provide backend destinations, frequently through NEGs.

Requirements and design

GKE Gateway requires VPC-native clusters and the HTTP load-balancing add-on. Regional and cross-region GatewayClasses require a proxy-only subnet. The role separation allows a platform team to own the shared listener while application teams own routes within allowed namespaces.

Troubleshooting

Inspect GatewayClass availability, Gateway conditions, Route acceptance/attachment, Service and NEG readiness, health checks, and backend firewall rules. A syntactically valid HTTPRoute that the Gateway does not accept will not create the intended Google Cloud routing.

flowchart TD GC[GatewayClass]-->G[Gateway] G-->R1[HTTPRoute team A] G-->R2[HTTPRoute team B] R1-->S1[Service A] R2-->S2[Service B]

Notice: infrastructure ownership and application routing ownership are intentionally split.

Anchor: Gateway is infrastructure; HTTPRoute is application routing policy.

Primary: Deploying Gateways

5. Cloud DNS response policies

Domain 3

Purpose

Cloud DNS response policies provide targeted answer overrides or bypass behavior for selected names without creating a full authoritative zone for an entire parent domain. This is useful for controlled development redirection, policy overrides, and selective patching of names learned through other private DNS mechanisms.

Evaluation order

Response-policy matching occurs before ordinary private-zone processing. A local-data rule can therefore return an alternate answer even when a private or peering zone would normally answer the query. Bypass behavior can send selected names onward to normal resolution logic.

Scope and limitations

Policies attach to networks and supported GKE scopes. Because they are targeted response controls, they do not have identical semantics to an authoritative zone and should not be used as a universal replacement for zone ownership.

Troubleshooting

When an answer differs from the private zone, inspect response-policy rules first, then private zones, forwarding zones, peering zones, and upstream servers. An early response-policy match can make later DNS resources look broken even though they were never evaluated.

flowchart TD Q[DNS query]-->M{Response policy match?} M--local data-->A[Override answer] M--bypass/no-->N[Normal private/forwarding/peering resolution]

Notice: response policy sits before normal private DNS resolution.

Anchor: Response policy is an early override layer, not another ordinary zone.

Primary: gcloud DNS response policies

6. Private Google Access for on-premises hosts

Domain 4

Use case

On-premises systems can reach supported Google APIs over Cloud VPN or Cloud Interconnect without using normal public internet egress. This is distinct from subnet-level Private Google Access for Google Cloud VMs because the source resides outside the VPC.

DNS steering

Private DNS commonly maps *.googleapis.com to private.googleapis.com or restricted.googleapis.com. Google documents IPv4 VIPs 199.36.153.8/30 for private access and 199.36.153.4/30 for restricted access. Additional Google service domains can require their own private DNS records.

Routing and security

DNS is only half the design. On-premises routing must send the selected VIPs over VPN or Interconnect. If the router still prefers an ISP path, the private access design fails despite correct DNS. Restricted access is commonly used with VPC Service Controls for a tighter service set.

Troubleshooting

Resolve the API name, confirm the intended VIP, trace the route through the hybrid connection, confirm required route advertisements, then separately validate service support, VPC Service Controls, IAM, and API authorization.

flowchart LR O[On-prem host]-->D[Private DNS] D-->V[private/restricted Google API VIP] O-->R[Router] R-->H[VPN or Interconnect] H-->G[Google APIs]

Notice: name resolution and routing must both select the private path.

Anchor: Private API access needs both DNS steering and hybrid routing.

Primary: Configure Private Google Access for on-premises hosts

7. VPC firewall targeting: service accounts versus network tags

Domain 6

Selectors

VPC firewall rules can select traffic and workloads with IP ranges, network tags, and service accounts. Network tags are mutable instance metadata. Service-account targeting binds policy to the identity assigned to the VM.

Security model

If application operators can freely add a network tag, they can potentially make a VM eligible for an allow rule that targets that tag. A centrally governed service account can be a stronger selector when IAM prevents unauthorized assignment of that identity. Service accounts bring their own IAM and lifecycle dependencies, so the choice is a trust-model decision rather than a universal preference.

Rule behavior and caveats

Source selectors, target selectors, direction, action, priority, protocol, and ports all participate in matching. Google documents restrictions on mixing tag and service-account forms and propagation delay for some source-tag changes.

Troubleshooting

Inspect the effective VM tag or service account, rule source/target, direction, action, priority, protocol/port, and implied default behavior. During tag changes, allow for documented propagation delay before concluding the rule is wrong.

flowchart LR S[Source VM]-->F{Firewall rule} T[Network tag]-.selector.->F A[Service account]-.identity selector.->F F-->D[Target VM]

Notice: the selector is part of the workload trust model.

Anchor: Tags are convenient; service accounts can encode stronger identity when IAM is controlled.

Primary: VPC firewall rules

8. GKE FQDN network policies

Domain 6

Problem solved

External SaaS destinations often change IP addresses, making static CIDR allowlists fragile. GKE FQDN network policies allow selected Pods to express egress permissions using names or patterns while GKE follows DNS resolution to enforce the resulting destinations.

Prerequisites

The feature depends on GKE Dataplane V2 and must be enabled on the cluster. Standard clusters may require restarting the anetd DaemonSet after enablement; Autopilot handles node lifecycle through the managed service.

Enforcement semantics

A selected workload receives allowlist-style egress behavior. Enforcement is based on resolved IP address and port, not HTTP URI or other Layer 7 fields. FQDN policy also interacts with Kubernetes NetworkPolicy, so both policy layers must be evaluated when traffic is denied. Existing connections can persist until normal conntrack/session closure.

Troubleshooting

Check exact or wildcard name matching, DNS answers, permitted ports, Dataplane V2 state, node rollout state, and Kubernetes NetworkPolicy interactions. Successful DNS resolution alone does not prove the connection is allowed.

flowchart LR P[Pod]-->D[DNS] D-->I[Resolved IPs] F[FQDN policy]-->E[Dataplane V2] I-->E E--allowed-->X[External service] E--other-->N[Deny]

Notice: DNS informs the policy, but the data-plane check is IP/port based.

Anchor: DNS-aware policy is not an HTTP WAF.

Primary: Control Pod egress with FQDN policies

9. Cloud Interconnect infrastructure maintenance and HA

Domain 4

Event types

Interconnect infrastructure maintenance can be planned, urgent, or unplanned. Depending on the event, part or all capacity of an affected connection can be unavailable. Planned events are normally announced in advance; urgent events can arrive with shorter notice; emergency events can occur without warning.

Topology consequence

A single link in one edge availability domain has no SLA by itself. Production topology should use redundant edge availability domains and must size the surviving path for critical load. Two healthy BGP sessions are not true HA if one link saturates as soon as the other is withdrawn.

Operations

Planned outage information can appear in the Interconnect resource, including expectedOutages, and can be inspected with gcloud compute interconnects describe. Maintenance notifications and Unified Maintenance can feed operational runbooks for supported connection types.

Runbook

Before maintenance, validate route preference and surviving bandwidth. During the event, watch connection, attachment, BGP, loss, and application metrics. After restoration, confirm traffic rebalances and that degraded members are fully healthy.

flowchart LR O[On-prem]-->A[EAD1 Interconnect] O-->B[EAD2 Interconnect] A-->V[VPC] B-->V M[Maintenance]-.removes capacity.->A

Notice: the second path must carry the workload, not merely exist.

Anchor: HA requires redundant capacity, not only redundant BGP.

Primary: Infrastructure maintenance events

10. Load-balancer health checks and backend firewall paths

Domain 3

Separate traffic classes

A load-balancer frontend can be reachable while all backends are unhealthy. Health-check probes, proxy-to-backend requests, and original client traffic are separate flows with different source addresses and enforcement points.

Firewall requirements

Backend firewall rules must allow the documented health-check probe sources and the correct backend request source for the selected load-balancer mode. Global proxy products commonly use Google-controlled source ranges, while regional Envoy-based products use the regional proxy-only subnet for backend requests.

Security boundary

VPC firewall rules are enforced on backend instances or endpoints, not on the public Google Front End itself. Blocking a backend port therefore does not mean the frontend is unreachable. Supported edge restrictions use the corresponding load-balancer security layer such as Cloud Armor.

Troubleshooting

Start with backend health, probe port, named-port or NEG endpoint mapping, firewall source ranges, application bind address, TLS behavior, and HTTP expectations. A TCP health check can succeed while the real application request fails at Layer 7.

flowchart LR C[Client]-->F[LB frontend] H[Health checker]-->B[Backend] F-->P[Proxy or GFE] P-->B W[Backend firewall]-.allow probe/request path.->B

Notice: three paths can have different source identities and failure modes.

Anchor: A working VIP does not prove a working backend path.

Primary: Application Load Balancer overview

11. Standalone zonal NEGs for GKE and custom load-balancer ownership

Domain 2

Endpoint model

A network endpoint group represents endpoints rather than entire VMs. A zonal GCE_VM_IP_PORT NEG identifies exact IP:port application endpoints and is supported by proxy load balancers and Cloud Service Mesh.

Standalone ownership model

With standalone GKE NEGs, Kubernetes can maintain Pod endpoint membership while a separate platform team manages backend services, URL maps, proxies, or service-mesh resources. This separates endpoint lifecycle from the full load-balancer control plane.

Data path and lifecycle

Supported load balancers can reach Pod IP:port endpoints directly, avoiding an extra NodePort/instance-group hop. Pod readiness, NEG membership, backend-service association, and health-check status remain distinct states that must all converge.

Troubleshooting

Inspect the Kubernetes Service annotation/status, NEG existence, endpoint membership, backend service association, health check, firewall rules, and Pod readiness/listening port. A Service object existing is not proof that the cloud NEG contains usable endpoints.

flowchart LR S[Kubernetes Service]-->C[GKE NEG controller] C-->N[Standalone NEG] N-->P1[Pod IP:port] N-->P2[Pod IP:port] B[Backend service]-->N

Notice: GKE can own endpoint population while another team owns the LB.

Anchor: Standalone NEG decouples endpoint membership from load-balancer ownership.

Primary: Backend services and NEGs

12. Internal DNS migration with Cloud DNS query logging

Domain 5

Why baseline first

Changing Compute Engine internal DNS naming behavior can break workloads that rely on old name-scope assumptions. Google recommends collecting query logs before migration so successful and failed lookups can be compared quantitatively.

Evidence

NXDOMAIN identifies non-existent-name responses; NOERROR commonly identifies successful responses. In Shared VPC, the host project owns the network and therefore the network DNS query logs.

Interpretation

Some NXDOMAIN responses are benign because operating-system resolvers try search-suffix variants. Operators should evaluate query name, client identity, and before/after trends rather than interpreting every NXDOMAIN as an outage.

Migration workflow

Enable DNS policy logging, establish a representative pre-change baseline, perform the migration, compare success/failure rates, and identify applications that depend on the old naming behavior. DNS logging can be high volume, so Cloud Logging cost and retention need deliberate planning.

flowchart LR V[VM or Pod]-->D[Cloud DNS] D-->L[Query logs] L-->N[NXDOMAIN trend] L-->O[NOERROR trend] B[Pre-change baseline]-->C[Compare] N-->C O-->C

Notice: the migration decision is backed by measurable pre/post evidence.

Anchor: DNS migration should be evidence-driven, not a blind cutover.

Primary: Monitor DNS failure rates
