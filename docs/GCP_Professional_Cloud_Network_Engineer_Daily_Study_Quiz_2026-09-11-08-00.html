1. Cloud WAN: Google's managed global enterprise backbone

Domain 1

Problem and architecture

Cloud WAN is Google's managed WAN approach for connecting geographically distributed branches, campuses, data centers, users, SaaS access paths, and cloud applications over Google's private backbone rather than building a customer-operated global transit network. Google positions Cloud WAN as a Cross-Cloud Network use case built from existing networking primitives such as Premium Tier, Network Connectivity Center, Cloud VPN, Cloud Interconnect, NCC Gateway, and partner SD-WAN/SSE integrations.

The design goal is not simply “put traffic on Google.” The value is centralizing WAN transport and security insertion while reducing the number of colocation transit stacks and carrier-specific routing domains an enterprise has to manage. Premium Tier brings traffic onto Google's edge and keeps it on the backbone for as much of the path as possible; Verified Peering Providers improve the quality of the last-mile internet handoff to Google.

Control/data plane and design choices

Cloud WAN is an architectural solution, not one single forwarding object. NCC supplies hub/spoke orchestration, Cloud Interconnect or VPN provides private site attachment, and NCC Gateway can connect branches to third-party Security Service Edge providers. For internet-heavy branches, Premium Tier plus a validated peering provider can be used rather than carrying all traffic through a traditional headquarters or colo firewall stack.

Official Google-hosted Cloud WAN visual. Notice that the backbone is the common transport while branch, data-center, cloud, and security edges remain distinct policy domains.

flowchart LR BR[Branches / campuses] --> EDGE[Google edge / Premium Tier] DC[Data centers] --> INT[Cloud Interconnect / VPN] EDGE --> WAN[Google global backbone / Cloud WAN] INT --> WAN WAN --> NCC[NCC orchestration] NCC --> APP[Google Cloud apps] NCC --> SSE[SSE / security partner] WAN --> SAAS[SaaS / internet destinations]

Failure and troubleshooting model

Separate access-edge failure, Google backbone failure, routing-policy failure, and security-service failure. A branch can have internet reachability while its intended Cloud WAN route or SSE service path is broken. Verify attachment health, route exchange, NCC state, security insertion state, and partner edge reachability independently.

Encrypted site attachmentCloud VPN or HA VPN overlay

Exam takeaway: Cloud WAN is an architecture composed from managed Google networking and partner integrations, not a replacement name for a single VPC or router.

Primary: Cloud WAN announcement and architecture. Supporting: Cross-Cloud Network solution.

2. Cloud RDMA and RoCE VPC design for AI/HPC

Domain 1

Why RDMA changes network design

Remote Direct Memory Access allows high-throughput, low-latency data transfer with reduced CPU involvement. Google Cloud supports RDMA-capable networking for specific accelerator and HPC workloads. A VM that uses Cloud RDMA needs a dedicated RDMA-capable interface attached to a VPC using the required RDMA network profile, plus a conventional GVNIC interface for ordinary management and service connectivity.

The important architectural consequence is that the RDMA fabric is not “just another subnet.” It has profile, machine-family, topology, firewall-policy, and workload-placement requirements. Treat the management/control network and the high-performance data network as distinct failure and security domains.

Network profiles and firewalling

RoCE VPC networks use a specialized network profile. Google documents regional network firewall policies and secure-tag targeting for RoCE VPCs. The profile controls capabilities that ordinary VPC networks do not expose. Because traffic patterns are east-west and high-volume, overly broad firewall rules can create large blast radii while overly restrictive rules can silently degrade distributed training jobs.

flowchart LR MGMT[GVNIC management NIC] --> VPC[Regular VPC] VM[AI/HPC VM] --- MGMT VM --- RDMA[IRDMA NIC] RDMA --> ROCE[RoCE VPC + Falcon RDMA profile] ROCE <--> PEER[Peer accelerator VM] POL[Regional firewall policy + secure tags] -. governs .-> ROCE

Notice the two-interface model: conventional VPC connectivity and RDMA data-plane connectivity are intentionally separated.

Operations and troubleshooting

When RDMA performance is poor, verify that the workload is on supported machine types, the RDMA NIC is attached to the correct network profile, peer placement satisfies the documented topology constraints, and firewall policy permits the required flows. Do not start by tuning TCP settings; the application may be using an RDMA transport that bypasses ordinary socket behavior.

Common misconception: enabling high bandwidth on a normal NIC is not equivalent to provisioning an RDMA network path.

Primary: Create a VM with Cloud RDMA. Supporting: Firewall rules for RoCE VPC networks.

3. Compute Engine IP forwarding for router/firewall VMs

Domain 2

Two independent requirements

A Compute Engine VM that forwards packets not addressed to itself requires Google-side IP forwarding to be enabled with the instance canIpForward property, and the guest operating system must also be configured to route packets. Enabling only one side is insufficient. This is fundamental for self-managed routers, firewalls, VPN appliances, and packet-processing middleboxes.

The Google setting permits the virtual NIC to send/receive transit traffic. The guest setting controls whether Linux, BSD, Windows, or the appliance OS actually forwards that traffic. You still need routes that select the VM as a next hop and firewall rules/policies that allow the flow.

flowchart LR SRC[Source VM] -->|route selects appliance| NVA[Router / firewall VM] NVA -->|canIpForward=true| GUEST[Guest forwarding / policy] GUEST --> DST[Destination] FW[VPC firewall / NGFW] -. still applies .-> NVA

Validated configuration

gcloud compute instances create ROUTER_VM \
  --zone=ZONE \
  --machine-type=e2-medium \
  --can-ip-forward

Google also exposes canIpForward: true in the Compute Engine API and can_ip_forward = true in Terraform. For Linux, the guest must separately enable kernel forwarding and any appliance-specific route or security policy.

Troubleshooting workflow

  1. Confirm the source's effective route selects the appliance.
  2. Confirm canIpForward is true.
  3. Confirm the guest OS forwards the relevant IP family.
  4. Confirm the appliance has a return route and state/policy permits the flow.
  5. Check VPC firewall policy on both directions and interfaces.
Exam takeaway: canIpForward is permission to forward; it is not a routing configuration and it does not automatically enable guest forwarding.

Primary: Google example showing IP forwarding configuration.

4. GKE managed DRANET: requesting high-performance network resources from Pods

Domain 2

What DRANET solves

GKE DRANET is Google's managed implementation built on the Kubernetes Dynamic Resource Allocation networking model. Instead of treating a Pod network interface as an implicit side effect of scheduling, workloads can request specialized networking resources through a Kubernetes-native resource API. This is especially important for AI/HPC workloads that need RDMA-capable interfaces.

DRANET is different from ordinary VPC-native Pod addressing and from Multus/IPVLAN. It is intended for allocating high-performance network resources in a portable, upstream-aligned way.

flowchart LR POD[Pod spec] --> CLAIM[Network resource claim] CLAIM --> DRA[Kubernetes DRA / GKE DRANET] DRA --> NIC[High-performance NIC / RDMA resource] NIC --> RDMAVPC[RDMA-capable network] SCHED[Scheduler] -->|places Pod where resource exists| POD

Design implications

Resource availability becomes part of scheduling. A Pod can be perfectly valid from a CPU/memory perspective but remain unschedulable if the required network resource is unavailable on candidate nodes. Capacity planning must therefore include NIC/resource inventory, node-pool placement, network profile constraints, and workload topology.

Troubleshooting

If a Pod is Pending, inspect DRA claims and allocation status before assuming a CNI fault. If the Pod starts but cannot achieve expected throughput, verify the claimed resource was attached, the node type supports the feature, the RDMA network is reachable, and firewall policy permits the peer traffic.

Remember: DRANET moves specialized network attachment into the Kubernetes resource-allocation lifecycle.

Primary: Allocate network resources with GKE managed DRANET.

5. GKE DNS-based control-plane endpoints

Domain 2

Why use a DNS endpoint

GKE control planes can expose DNS-based and IP-based endpoints. Google's current networking best practice recommends DNS-based control-plane access because it simplifies network-path dependencies and supports identity/policy-based access without requiring clients to reach a specific control-plane IP range. The DNS endpoint is reachable from networks that can reach Google Cloud APIs, including hybrid or other-cloud environments.

You can use organization policy to require DNS-only access. When IP access is disabled, gcloud container clusters get-credentials can be directed to the DNS endpoint with --dns-endpoint.

flowchart LR ADMIN[Admin / CI / kubectl] --> GFE[Google Front End] GFE --> DNS[GKE DNS-based endpoint] DNS --> CP[Kubernetes API server] IAM[IAM / access policy] -. authorizes .-> DNS IP[Public/private IP endpoint] -. can be disabled .-> CP

Certificates and kubeconfig

The DNS endpoint is hosted by Google Front End infrastructure and presents a certificate signed by a public CA, so the generated kubeconfig differs from IP-based endpoint kubeconfig. IP-based access uses the cluster CA data; the DNS endpoint does not require the same embedded CA field.

Failure analysis

If kubectl reports that DNS endpoint external traffic is disabled, verify the control-plane endpoint configuration rather than changing VPC routes. If name resolution works but authorization fails, investigate identity and access policy. If API access from a corporate network fails, verify reachability to Google APIs and any proxy restrictions.

Exam takeaway: endpoint selection changes both network reachability assumptions and certificate/access behavior; it is not just a different hostname.

Primary: GKE networking best practices. Supporting: Configure kubectl endpoint access.

6. Cross-region internal Application Load Balancer with Cloud Run

Domain 3

Architecture

A cross-region internal Application Load Balancer provides private Layer 7 access with global service resources and regional forwarding points. With Cloud Run backends, each deployment is represented by a serverless NEG. Proxy-only subnets are required in each region where cross-region internal load-balancer proxies run; backend connections originate from those proxy address ranges.

Cloud Run should normally restrict ingress to internal traffic when the load balancer is the intended entry point. Multi-region Cloud Run deployments let the load balancer continue serving when one region is unavailable.

flowchart LR C[Internal client] --> VIPA[Regional internal VIP A] VIPA --> PA[Envoy proxy A] PA --> NEGA[Serverless NEG A -> Cloud Run A] PA --> NEGB[Serverless NEG B -> Cloud Run B] VIPB[Regional internal VIP B] --> PB[Envoy proxy B] PB --> NEGA PB --> NEGB DNS[Optional GEO DNS] --> VIPA DNS --> VIPB

Traffic preference and caveats

Google documents locality behavior for multi-region Cloud Run. When a Cloud Run NEG exists in the Envoy's region, that local NEG is preferred and a failover region is used when outlier detection identifies a problem. If no Cloud Run service is local to the Envoy region, traffic can be distributed across the available NEGs rather than simply choosing the geographically closest one. A notable limitation is that enabling IAP on this pattern supports only one serverless NEG.

Troubleshooting

Check DNS/VIP selection, proxy-only subnet existence, forwarding rule, URL map, serverless NEG, Cloud Run ingress policy, and outlier-detection state in that order. “Cloud Run is healthy” does not prove the load-balancer-to-NEG path is correct.

Remember: cross-region internal ALB combines global service configuration with regional proxy/data-plane presence.

Primary: Cross-region internal ALB with Cloud Run.

7. Cross-region internal Application Load Balancer with Cloud Storage backend buckets

Domain 3

What makes this backend unusual

Google supports Cloud Storage backend buckets behind a cross-region internal Application Load Balancer. This creates private client access to an internal load-balancer VIP while the backend bucket itself has specific restrictions. Google currently documents that private bucket access is not supported for this pattern: the Cloud Storage bucket must be publicly accessible. Signed URLs are not supported, Cloud CDN cannot be enabled on these internal-managed backend buckets, and only HTTP GET is supported through this architecture.

flowchart LR C[Internal client] --> VIP[Cross-region internal ALB VIP] VIP --> PROXY[Envoy proxy] PROXY --> BB[Backend bucket INTERNAL_MANAGED] BB --> GCS[Publicly accessible Cloud Storage bucket] X[No signed URLs / no Cloud CDN / GET only] -. constraints .-> BB

High availability and Shared VPC

You can deploy regional frontend resources in multiple regions and use DNS routing policy to direct clients to a regional VIP. In Shared VPC, network resources such as subnets and proxy-only subnets live in the host project while load-balancer and backend-bucket components can be placed in service projects according to supported patterns and IAM.

Operational pitfalls

A 403 from the bucket might be a storage permission/public-access issue rather than an ALB routing failure. A forwarding-rule creation failure can result from attempting to assign an address from the proxy-only subnet. Cloud CDN flags that work for external backend buckets are invalid here.

FeatureCross-region internal ALB + backend bucket
Private Cloud Storage bucketNot supported
Signed URLNot supported
Cloud CDNNot supported
HTTP methodGET only
Exam takeaway: internal frontend does not automatically imply private backend-bucket semantics.

Primary: Cross-region internal ALB with Cloud Storage buckets.

8. Cloud Router BGP MD5 authentication and vendor interoperability

Domain 4

What MD5 protects

Cloud Router supports TCP MD5 authentication for BGP sessions. Both BGP peers must use the same secret; if the keys differ, the TCP/BGP session does not establish. The mechanism authenticates BGP TCP segments and helps prevent unauthorized peers from injecting a session, but it does not encrypt route advertisements or user traffic.

Google provides interoperability guidance for Cisco IOS/IOS-XE, Arista EOS, Juniper Junos, Palo Alto Networks VM-Series, and other routing stacks. The syntax differs, but the design principle is identical: configure the same secret on the Cloud Router peer and the remote peer.

sequenceDiagram participant G as Cloud Router participant P as Peer router G->>P: TCP/BGP segment + MD5 digest P->>P: Verify using shared secret P-->>G: BGP response + MD5 digest Note over G,P: Mismatched key => session cannot establish

Operational handling

Treat the key as a secret with a controlled rotation procedure. A unilateral key change is an outage. During migration, coordinate both ends and expect the session to reset. After configuration, verify BGP neighbor state and then verify learned routes; an Established session proves authentication and BGP transport, not that desired prefixes are accepted or selected.

Example peer configuration concept

router bgp ASN
 neighbor CLOUD_ROUTER_IP password SECRET_KEY

The exact syntax varies by vendor and platform version; use the vendor configuration referenced by Google's interop guide.

Common misconception: BGP MD5 authenticates the peering session; it is not payload encryption and is unrelated to MACsec/IPsec.

Primary: Cloud Router MD5 interoperability.

9. Connection draining: protecting existing flows during backend removal

Domain 5

Purpose

Connection draining gives existing connections time to finish when a VM or endpoint is removed from a backend. Google load balancer backend services accept a connection-draining timeout from 0 through 3600 seconds; zero disables the feature. This matters during rolling updates, scale-down, maintenance, and planned backend replacement.

The timeout is configured on the backend service and therefore applies to all referenced backend groups. Draining does not mean “send new traffic to the draining endpoint.” The goal is to stop selecting it for new work while avoiding needless resets for connections already mapped to it.

sequenceDiagram participant C as Client participant LB as Load balancer participant B as Backend being removed C->>LB: Existing connection LB->>B: Existing flow Note over LB,B: Backend enters draining C->>LB: New connection LB->>LB: Select another healthy backend C->>LB: Existing connection packets LB->>B: Continue until drain timeout / close

Configuration and troubleshooting

gcloud compute backend-services update BACKEND_SERVICE \
  --global \
  --connection-draining-timeout=300

Use --region for a regional backend service. If clients still see resets during rolling updates, confirm the application itself is not closing sockets, the drain timeout is long enough for the protocol, and the automation is not deleting resources in a way that bypasses the intended lifecycle.

Nuance: passthrough load-balancer failover has additional connection-tracking and failover-draining behavior. Do not assume the generic backend-service drain timeout describes every failover event.
Exam takeaway: draining protects existing sessions during backend lifecycle changes; health checks and backend eligibility govern new connections.

Primary: Connection draining.

10. Firewall Insights: shadowed and overly permissive rules

Domain 5

Configuration analysis versus traffic-history analysis

Firewall Insights identifies opportunities to simplify and tighten firewall configuration. Shadowed-rule insights are configuration-derived: a rule is effectively covered by another rule of higher or equal priority. Overly permissive insights use observed rule usage and can identify allow rules with no hits, unused attributes, or excessively broad address/port ranges. Deny-rule insights can similarly expose rules with no observed hits.

This distinction matters operationally. Shadowing can be detected without waiting for traffic history, while “unused” depends on an observation period and therefore cannot prove that a rule will never be needed.

flowchart TD RULES[Firewall configuration] --> SHADOW[Shadowed-rule analysis] LOGS[Firewall usage/log data] --> PERM[Overly permissive / no-hit analysis] SHADOW --> REVIEW[Human review] PERM --> REVIEW REVIEW --> TIGHTEN[Remove / narrow / reprioritize rule]

Observation period and refresh

The default observation window for applicable insights is six weeks and can be configured from seven days to one year. Shadowed-rule insights do not use an observation window; Google evaluates existing configuration on a refresh cycle. Traffic data from the most recent period can lag, so a fresh rule may not immediately appear accurately in usage analysis.

Safe remediation workflow

Never delete a no-hit rule solely because it is labeled unused. Check business calendars, disaster-recovery flows, batch jobs, and seasonal traffic. For a shadowed rule, compare all match attributes and actions to ensure the higher-priority rule truly makes the lower rule redundant.

Remember: Firewall Insights is evidence for optimization, not an autonomous permission to delete policy.

Primary: Firewall Insights overview. Supporting: Observation periods and refresh cycles.

11. Identity-Aware Proxy TCP forwarding for administrative access

Domain 6

Security model

IAP TCP forwarding lets administrators reach VMs by internal IP without exposing SSH or RDP directly to the internet. The client creates an authenticated tunnel to IAP; IAP wraps the forwarded connection in HTTPS, checks IAM authorization, and then connects toward the VM. This is a zero-trust-style administrative access path because user identity and authorization are evaluated rather than granting broad network-level VPN access.

flowchart LR ADMIN[Administrator] -->|HTTPS tunnel| IAP[Identity-Aware Proxy] IAM[IAM / context policy] -. authorizes .-> IAP IAP -->|TCP forwarding| VM[VM internal IP: SSH/RDP/etc] FW[Firewall allow from IAP range] -. required .-> VM PUB[External IP] -. not required .-> VM

Prerequisites and policy

The VM needs a firewall rule permitting the IAP TCP-forwarding source range to the destination port. Users need the appropriate IAP tunnel IAM permission as well as whatever OS/login permission the VM requires. IAP authorization and guest authentication solve different layers of access.

Troubleshooting

If the tunnel cannot establish, verify IAM first, then the firewall path from IAP to the VM, then guest service availability. If the IAP tunnel succeeds but SSH authentication fails, do not change VPC routing; investigate OS Login, SSH keys, or guest policy. Corporate proxies may also need to allow IAP domains.

Exam takeaway: IAP TCP forwarding removes the need for a public management IP but does not remove the need for firewall policy or guest-level authentication.

Primary: SSH to VMs using IAP. Supporting: Securing VMs with IAP TCP forwarding.

12. Cloud NGFW Advanced malware sandbox (WildFire) with TLS inspection

Domain 6

Security-service chain

Cloud NGFW Enterprise can submit eligible files to Advanced malware sandbox (WildFire) for analysis. The feature is currently documented as Preview. Configuration involves an Advanced malware sandbox security profile of type WILDFIRE_ANALYSIS, a required threat-prevention security profile, a security profile group, firewall endpoint support, endpoint association with the VPC, and firewall-policy rules that apply the security profile group.

For encrypted traffic, TLS inspection must be added so the security service can see file content. That introduces Certificate Authority Service dependencies: a CA pool/root CA hierarchy and permissions for the Network Security service agent to issue the intermediate certificates used for interception.

flowchart LR VM[Workload] --> EP[Cloud NGFW firewall endpoint] EP --> TLS[TLS inspection policy] TLS --> TP[Threat prevention profile] TP --> WF[WildFire analysis profile] WF --> DEC[Allow / detect / block outcome] CA[CA Service pool + root/intermediate CA] -. enables decryption .-> TLS

Packet-size and endpoint constraints

Google warns that firewall endpoint packet-size support matters. An endpoint with jumbo-frame support accepts packets only up to its documented maximum; without jumbo support the limit is lower. If the associated VPC MTU exceeds the endpoint's supported packet size, malware sandbox inspection is not performed for that VPC. This is a classic example where security architecture and MTU design intersect.

Operations and logs

Submission logs record files sent for analysis and sandbox outcomes. Troubleshooting should verify EULA acceptance, endpoint capability, profile-group composition, policy action, TLS CA configuration, MTU, and whether the file type/direction is included by the WildFire profile.

Release stage: Advanced malware sandbox is Preview; design production dependencies accordingly.
Exam/interview takeaway: Layer 7 security is a chain of endpoint association, policy selection, security profiles, and optional TLS decryption—not a single checkbox.

Primary: Configure Advanced malware sandbox. Supporting: Advanced malware sandbox logs.
