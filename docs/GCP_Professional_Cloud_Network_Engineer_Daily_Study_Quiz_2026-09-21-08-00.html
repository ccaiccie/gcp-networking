1. Managed workload identity for backend mTLS

Domain 6 — Network security

Problem and architecture

Backend mTLS protects the proxy-to-backend hop of supported Application Load Balancers while managed workload identity removes the need to treat long-lived private keys as application configuration. As of September 18, 2026, Google lists the capability as GA for global external, regional external, cross-region internal, and regional internal Application Load Balancers. Keep frontend TLS and backend mTLS conceptually separate: the client authenticates the load balancer at the frontend, while the load balancer and backend establish a distinct authenticated TLS session.

Control/data plane, choices, security

The control plane associates the backend authentication configuration and workload identity with the load-balancing resources. On each backend connection the proxy terminates the client-side connection, initiates a new TLS connection, validates the backend trust configuration, and presents the configured identity when mutual authentication is required. This creates a trust boundary at the proxy. Design certificate authority scope, identity authorization and backend hostname/identity checks deliberately; do not assume frontend certificates secure the backend hop.

Operations, failure scenario, takeaways

If clients receive 5xx responses after enabling backend mTLS, isolate frontend health from backend TLS health: verify backend health, identity/certificate issuance, trust anchors, name/identity matching, and load-balancer logs. A healthy TCP port is not proof that TLS authentication succeeds. Memory anchor: two TLS sessions, two trust decisions.

2. Global Front End as an integrated edge design

Domain 1 — Design and planning

Problem and components

Global Front End, Preview in the August 19, 2026 load-balancing release notes, combines global external Application Load Balancing, Cloud Armor, Cloud CDN and Service Extensions into an integrated internet-facing solution. The architectural value is not a new packet primitive; it is a coordinated edge design and commercial/operational surface for delivery, protection, caching and extensibility.

Packet flow and design choices

Traffic reaches Google's global edge through the external Application Load Balancer. Edge security policy can evaluate requests, CDN can satisfy cacheable content without reaching the origin, and Service Extensions can insert supported programmable processing. Cache hits and blocked requests therefore terminate before backend selection. Keep policy order and cache behavior explicit when troubleshooting because an origin can be healthy while a request never reaches it.

Caveats, operations, scenario

Preview status matters for production governance. Verify feature support and regional/backend compatibility rather than assuming every individual product feature is exposed identically through the integrated offering. For a global retail site, use the edge to reject abusive traffic and serve cacheable objects close to users while forwarding dynamic misses to healthy backends. Observe Armor decisions, cache status, load-balancer request logs and extension behavior separately.

3. Application Load Balancer regex URL rewrites

Domain 3 — Managed network services

Problem and behavior

Preview regular-expression URL rewrites let Application Load Balancer URL-map route rules transform path components before forwarding to a backend. This solves migrations where the public URL contract must remain stable while backend path layout changes. Matching and rewriting are separate concepts: route conditions decide which rule applies; the rewrite changes what the selected backend receives.

Design and packet flow

A request enters the proxy, the URL map evaluates host/path/route rules, the matching rule applies its regex rewrite, and the transformed request is sent to the chosen backend service. Treat this as proxy behavior, not DNS or client redirection: the client need not receive a 3xx and can remain unaware of the internal path transformation.

Operations and failure scenario

Test anchors, capture groups, escaping and rule precedence before migration. A broad expression can silently rewrite unrelated paths. When the frontend returns a backend-generated 404, compare the original request with the path seen by the backend and inspect URL-map configuration. Use narrow route matches and staged testing. Preview status should be considered in production change control.

4. Global external passthrough Network Load Balancer

Domain 3 — Managed network services

Architecture

The global external passthrough Network Load Balancer, Preview since July 31, 2026, is a Layer-4 global variant using Google's anycast edge to steer supported protocol traffic to healthy backends across supported regions. Unlike proxy load balancers, it preserves passthrough semantics and supports TCP, UDP, ESP, GRE, ICMP and ICMPv6. Google documents two external IP addresses backed by disjoint availability groups.

Selection, HA and caveats

Anycast brings a client toward Google's edge; the service selects an eligible region based on proximity, health and capacity, enabling cross-region failover. Backends can be instance groups or NEGs in supported regions. The release note explicitly says GKE backends are not supported in this release. That caveat is an exam-quality discriminator: global scope does not imply universal backend support.

Operations/scenario

For globally distributed UDP or real-time services that need source-preserving Layer-4 delivery, this can fit better than an HTTP proxy. Validate both frontend IPs, backend health, firewall reachability and protocol support. During a regional failure, confirm traffic shifts to healthy capacity rather than debugging application DNS first.

5. Network Security Integration direct internet egress

Domain 6 — Network security

Problem and architecture

Since August 20, 2026, Network Security Integration in-band integration supports a direct internet egress deployment model. A network security appliance in the producer VPC inspects consumer outbound traffic and then sends it directly to the internet through its external network interface. This avoids forcing inspected egress back through the consumer path solely to reach an internet gateway.

Data plane and MTU

Consumer traffic is steered into the in-band integration, encapsulated/transported to the producer security appliance, inspected, and emitted through the appliance's external interface. Preserve return-path symmetry through the inspection design. NSI documentation also calls out GENEVE overhead; consumer and producer MTU planning must leave encapsulation headroom rather than assuming a workload's original MTU survives unchanged.

Security and troubleshooting

The producer appliance becomes both a policy enforcement point and an internet egress dependency. Harden management separately, size throughput and failure domains, and verify routes, interception policy, appliance health, NAT behavior and return routing. If outbound SYNs reach the appliance but replies never return, inspect external-interface routing/NAT and symmetry before changing consumer firewall rules.

6. NCC IPv6 dynamic-route include/exclude filters

Domain 4 — Hybrid/multi-cloud

Problem and control plane

Network Connectivity Center added Preview support on August 31, 2026 for IPv6 dynamic routes in include/exclude spoke filters for hybrid spokes. Export filters determine which subnets or routes a spoke can advertise into the hub; import filters determine which hub routes the spoke can accept. This gives route-policy segmentation without requiring every attached router to carry the full reachable set.

Design choices and convergence

Filter direction is from the spoke's perspective: export controls spoke→hub propagation, import controls hub→spoke acceptance. Apply least-route principles and plan IPv4 and IPv6 policy independently. A filter change can alter reachability even while BGP sessions remain established, so session state alone is insufficient evidence of successful routing.

Troubleshooting scenario

If an IPv6 prefix is learned on a hybrid router but absent from another spoke, inspect the exporting spoke filter, hub propagation, receiving spoke import filter, and resulting route table. Compare intended prefix ranges to filter semantics. Preview status should be considered for critical production use.

7. Cloud NAT TCP TIME_WAIT default transition

Domain 5 — Operations

Change and impact

Google announced a staged change to the default Cloud NAT TCP TIME_WAIT timeout for new gateways from 120 seconds to 30 seconds. During June 30–September 29, 2026, the default for a newly created gateway can depend on whether the regional rollout has occurred; on or after September 30, new gateways use 30 seconds. Existing pre-update gateways retain 120 seconds unless explicitly changed, and custom values are unaffected.

Why it matters

TIME_WAIT retention influences how quickly NAT source ports can be reused after TCP closure. A shorter default can reduce port pressure for high-connection-rate workloads, but operationally the critical lesson is configuration drift: two otherwise similar gateways created at different times can have different defaults during rollout.

Troubleshooting and change control

Never infer the timeout solely from creation templates during the transition. Describe the gateway, verify the effective timeout, correlate NAT logs/metrics with port allocation and connection behavior, and explicitly configure the value when deterministic behavior is required. Recreating an older gateway after rollout can change its default.

8. Public NAT source-based NAT rules

Domain 2 — Implementing VPC

Problem and architecture

Source-based NAT rules for IPv4 Public NAT reached GA on April 13, 2026. They allow egress translation behavior to vary according to source criteria rather than forcing every eligible workload behind one undifferentiated address-selection policy. This is useful when partners allowlist different egress addresses or business zones require separate external identities.

Design and behavior

Cloud NAT remains a managed distributed NAT function associated with Cloud Router configuration; it does not turn Cloud Router into a packet-forwarding hop. Rules influence translation selection for matching sources. Plan rule coverage and fallback deliberately so a workload does not unexpectedly use an address pool intended for another trust or partner domain.

Operations/scenario

For two application tiers that must appear from distinct public IP pools, map their source ranges to appropriate NAT behavior and verify translated addresses from each tier. Troubleshoot by checking source range, NAT rule evaluation, allocated addresses, NAT logging and port metrics. Do not add static routes toward Cloud Router to 'reach' NAT; that confuses control plane with data plane.

9. Cloud Interconnect managed traffic classification

Domain 4 — Hybrid/multi-cloud

Problem and control plane

Managed traffic classification for Cloud Interconnect entered Preview on April 30, 2026. It automates assignment of DSCP values to outgoing packets so differentiated traffic treatment can be expressed without requiring every workload to mark traffic correctly. Classification is a QoS concern, not a routing preference mechanism.

Design and packet behavior

Define which traffic classes deserve differentiated treatment, map classification policy to expected DSCP markings, and ensure the on-premises network honors compatible markings. DSCP does not create bandwidth or override a congested downstream network that ignores QoS. Keep classification policy aligned across the Interconnect boundary.

Operations/scenario

For voice/control traffic sharing an attachment with bulk replication, classification can help preserve service quality when paired with consistent downstream queuing. Verify policy, packet markings and interface/transport metrics. If BGP is healthy but latency rises under load, inspect congestion and QoS rather than changing route advertisements reflexively.

10. 400-Gbps Interconnect connections and VLAN attachments

Domain 4 — Hybrid/multi-cloud

Scale and architecture

As of March 3, 2026, Google lists 400-Gbps connections and VLAN attachment maximum capacities as GA for Dedicated Interconnect and Cross-Cloud Interconnect. Capacity planning still requires topology and redundancy design: one very large circuit is not a substitute for independent failure domains.

Design choices

Separate physical connection capacity, VLAN attachment capacity, BGP sessions and workload throughput requirements. Build redundant connections in supported topology, distribute attachments appropriately, and consider maintenance and device failures. Validate location and platform support before assuming a 400-Gbps option is available everywhere.

Operations/scenario

For an AI/data-transfer environment approaching 100-Gbps ceilings, 400-Gbps capability can reduce the number of parallel constructs, but migration should preserve redundancy. Monitor attachment utilization, dropped traffic, BGP state and physical connection health. If throughput plateaus, identify whether the bottleneck is VM bandwidth, attachment capacity, physical circuit, on-premises interface or application behavior.

11. GKE Gateway session affinity with GCPTrafficDistributionPolicy

Domain 3 — Managed network services

Problem and support

Session affinity using GCPTrafficDistributionPolicy became GA for supported single-cluster GKE Gateway load balancers on August 31, 2026. Supported GatewayClasses listed in the release note include gke-l7-rilb, gke-l7-regional-external-managed and gke-l7-global-external-managed. STRONG_COOKIE_AFFINITY provides the most persistent stickiness among the documented Application Load Balancer affinity modes.

Version and design caveats

Affinity types have minimum GKE versions. CLIENT_IP, HEADER_FIELD, GENERATED_COOKIE and HTTP_COOKIE require 1.35.2-gke.1269001 or later; STRONG_COOKIE_AFFINITY requires 1.36.3-gke.1767000 or later. Affinity improves continuity but can reduce load distribution efficiency and should not replace application state design.

Troubleshooting

If sessions bounce between backends, verify GatewayClass, cluster version, policy attachment, chosen affinity type and backend health. A failed/unhealthy backend can legitimately break stickiness. For stateful legacy applications, prefer explicit policy with a tested failover experience rather than relying on incidental connection reuse.

12. GKE NEG pre-provisioning

Domain 2 — Implementing VPC

Problem and architecture

NEG pre-provisioning entered Preview on August 27, 2026. It lets a GKE Service request empty zonal GCE_VM_IP_PORT NEGs in specified zones, or all zones in a region, even when the cluster currently has no nodes there. This decouples infrastructure dependency creation from workload placement.

Deployment behavior and choices

The cloud.google.com/neg Service annotation is extended with a custom zones parameter. Infrastructure automation can therefore attach known NEG resources to backend services before pods/nodes appear. Empty NEGs are not healthy serving capacity: health and endpoint population remain separate from resource existence.

Operations/scenario

This is valuable for staged deployments where Terraform or another pipeline must create load-balancer backends before a GKE rollout. Verify NEG existence by zone, endpoint population after scheduling, backend health and firewall/health-check paths. If the backend exists but serves no traffic, inspect whether the NEG is still empty before debugging the load balancer itself.
