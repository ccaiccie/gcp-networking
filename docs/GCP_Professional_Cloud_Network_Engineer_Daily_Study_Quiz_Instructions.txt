# Google Cloud Professional Cloud Network Engineer Daily Interactive Study Report Instructions

## Purpose
Create a daily, self-contained, advanced Google Cloud networking study report aligned primarily to the current Google Cloud Professional Cloud Network Engineer certification blueprint and to real-world cloud network engineering practice.

The report must be useful even if the reader never opens the source articles. A source URL is not permission to summarize it into a paragraph: the report must reconstruct the useful technical substance of every selected article in original words so the reader can study the subject from the report alone.

## Source of Truth and Blueprint
1. At the start of every run, verify the current official Google Cloud Professional Cloud Network Engineer certification page and current official exam guide.
2. If Google publishes a newer exam guide, use the newer guide and adapt topic coverage and question weighting accordingly.
3. Prefer official Google Cloud documentation, Architecture Center material, product documentation, release notes, Google Cloud blogs written by product teams, and official training/certification resources.
4. Use authoritative community or expert sources only when they add meaningful operational detail not clearly explained in official documentation.
5. Do not claim an exam, feature, product tier, release stage, limit, or behavior is current unless verified from a current authoritative source.

## Current Blueprint Baseline
Unless the official exam guide changes, use the current six-domain baseline verified in September 2026:
1. Designing and planning a Google Cloud VPC network — approximately 21%.
2. Implementing a VPC network — approximately 20%.
3. Configuring managed network services — approximately 16%.
4. Configuring and implementing hybrid and multi-cloud network interconnectivity — approximately 16%.
5. Managing, monitoring, and troubleshooting network operations — approximately 14%.
6. Configuring, implementing, and managing a cloud network security solution — approximately 13%.

For exactly 50 questions, use 11/10/8/8/7/6 unless the current official blueprint changes.

## Daily Topic Selection
Create exactly 12 substantive target lessons per report. Collectively they must span the current certification blueprint and emphasize advanced practical networking knowledge. Potential lesson families include VPC design, Shared VPC, Private Service Connect, routing, Cloud Router, BGP, NCC, load balancing, Cloud DNS, Cloud NAT, Interconnect, HA VPN, GKE networking, Cloud NGFW, Cloud Armor, VPC Service Controls, Secure Web Proxy, Network Intelligence Center, Flow Logs, troubleshooting, and network observability.

Do not mechanically rotate through a fixed list. Choose 12 high-value lessons that are meaningfully different from the previous 30 calendar days according to the uniqueness ledger.

## 30-Day Uniqueness Ledger
Before researching, fetch `docs/gcp-study-uniqueness-ledger.json`.

Treat the previous 30 calendar days as a hard blocklist. Do not reuse any blocked primary article URL, scenario article URL, canonical URL, title/topic fingerprint, feature lesson, source case, substantially equivalent scenario, or substantially equivalent troubleshooting story. A changed tracking parameter or superficial title variation does not make a source unique.

A same-day correction or replacement explicitly requested by the user may replace that day's ledger entry rather than being treated as a second independent daily run. Preserve the original date but update the filename, source set, fingerprints, and validation metadata to describe the replacement report.

Only update the ledger after the report has been fully generated, committed, fetched back, and successfully validated. If validation fails, do not advance the ledger.

## Comprehensive Article Coverage — REQUIRED
For every primary or scenario article referenced by the report, cover the article comprehensively enough that a learner does not need to open the source to understand its technical content.

Each of the 12 lessons must normally include all applicable elements below:
1. What problem the feature or architecture solves and when to use it.
2. Architecture and named components, including resource scope (global/regional/zonal/project/organization) when material.
3. Control-plane behavior and data-plane or packet flow, step by step where meaningful.
4. Route advertisement, route selection, address translation, DNS resolution, load-balancing, or policy evaluation behavior as applicable.
5. Prerequisites, dependencies, IAM considerations, required companion services, and deployment assumptions.
6. Important configuration choices and what each choice changes.
7. Limits, quotas, unsupported combinations, release-stage considerations, SLA/topology requirements, and compatibility caveats that materially affect design.
8. Security implications and trust boundaries.
9. High availability, failure-domain, convergence, scaling, and performance considerations.
10. Monitoring, logging, verification, and troubleshooting workflow.
11. At least one realistic design or failure scenario with explanation.
12. A concise decision table or comparison table when alternatives can be confused.
13. Validated `gcloud`, Terraform, API, or configuration examples when they materially improve the lesson. Never invent syntax, flags, fields, defaults, or output.
14. Key exam/interview takeaways and common misconceptions.

Do not write one-paragraph article summaries, short snippets, or link lists in place of the above. Several substantial subsections are expected per lesson. If a source page is broad, follow useful supporting links, normally up to two levels deep, and merge the relevant material into one coherent lesson.

## Images and Teaching Diagrams — REQUIRED
Every lesson must contain at least one meaningful visual aid or visual reference that directly explains the topic.

Priority order:
1. Embed an official Google-hosted figure from the referenced article when a stable direct image URL is verified.
2. If the article contains an architecture figure but its direct image URL cannot be safely verified, include a clearly labeled `Official figure` link to the exact Google source page/figure and place an original Mermaid reconstruction immediately beside or below it.
3. If no useful official figure exists, create an original Mermaid architecture, packet-flow, route-flow, DNS-flow, policy-evaluation, failure-domain, or troubleshooting diagram based on verified facts.

Visual requirements:
- Never fabricate image URLs.
- Keep the original article URL and figure description/caption next to every externally hosted image.
- Use descriptive `alt` text.
- Prefer architecture and flow diagrams over decorative images.
- Explain what the reader should notice in each visual; do not drop an image into the report without interpretation.
- Mermaid must be syntactically valid and render in the final HTML.
- For multi-step packet/control-plane topics, diagrams should show arrows, direction, and important transformations such as NAT, proxy termination, route advertisement, tunnel encapsulation, or policy evaluation.

## Source-Role Separation
Maintain clear separation between primary authoritative sources used for facts, supporting/scenario sources used for implementation or troubleshooting, and community/expert commentary used only for supplemental perspective. Do not allow a weak community source to override official Google Cloud documentation.

Requirements:
- Exactly 50 questions.
