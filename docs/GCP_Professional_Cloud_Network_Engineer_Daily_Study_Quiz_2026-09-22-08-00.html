1. Network Connectivity internal ranges: reserve address space before a resource owns it

Domain 1 — Designing and planning a VPC
Primary: Internal ranges overview · Implementation: Create and use internal ranges

Problem, architecture, and control plane

An internal range is a Network Connectivity resource that reserves an IPv4 or IPv6 CIDR for future or specialized use in a VPC without immediately creating a subnet. It is an IPAM/governance primitive: architects can reserve space centrally, communicate intended ownership, and reduce accidental overlap before a workload team creates a consuming resource. The resource is associated with one VPC and carries a usage intent such as FOR_VPC, EXTERNAL_TO_VPC, or FOR_MIGRATION, plus a peering disposition such as FOR_SELF, FOR_PEER, or NOT_SHARED.

flowchart LR
A[Address plan]-->B[Internal range reservation]
B-->C{Usage intent}
C-->D[FOR_VPC]
C-->E[EXTERNAL_TO_VPC]
C-->F[FOR_MIGRATION]
B-->G[VPC overlap checks]
G-->H[Future subnet/service]

Notice: the reservation participates in overlap governance before the eventual subnet or service is created; it is not itself a routed subnet.

Design choices, caveats, and security

ChoiceOperational meaning
Explicit CIDRBest when enterprise IPAM has already assigned a deterministic block.
Automatic allocationGoogle selects from the requested target space after honoring exclusions; validate the chosen block before dependent automation assumes it.
FOR_MIGRATIONProtects address space during subnet migration workflows where temporary overlap semantics are deliberate.
IPv6 internal rangeUse the combinations supported by the internal-range model; current docs describe IPv6 internal ranges with EXTERNAL_TO_VPC and FOR_SELF.

Most semantic properties are intentionally hard to change after creation; treat the resource as part of the address-allocation contract, not an ad-hoc tag. A CIDR can be expanded only where the documented rules allow it; narrowing an allocated range is not a safe rollback mechanism. Resource creation can still fail if its address choice conflicts with existing subnets, routes, peering, or other reservations.

Operations, failure scenario, and memory anchor

List reservations with gcloud network-connectivity internal-ranges list and compare them with subnet inventories before approving new CIDRs. Scenario: a platform team pre-reserves a block for a migration, but an application team independently tries to create a subnet inside it. The reservation makes the conflict visible early rather than after hybrid advertisements or firewall objects have been built around the duplicate range.

Takeaway: an internal range is a control-plane reservation and overlap-governance object. It does not create forwarding by itself.

2. Expanding a subnet primary IPv4 range without creating an outage—or a routing mess

Domain 2 — Implementing a VPC network
Primary: Create and modify VPC networks · Supporting: VPC subnets

Behavior and packet-plane impact

Google Cloud lets you expand a subnet's primary IPv4 range by moving to a shorter prefix, for example /24 to /23. Existing VM addresses and flows are retained; the operation changes the subnet route and address pool rather than renumbering existing interfaces. The change is one-way: you cannot shrink the primary range back to the old prefix, so address planning and overlap checks must happen before the update.

flowchart LR
A[/24 subnet]-->B[Check adjacent CIDR is free]
B-->C[Expand prefix]
C-->D[/23 subnet route]
D-->E[Existing IPs remain]
D-->F[New addresses become allocatable]
F-->G[Update ACLs / hybrid policy / GKE allowlists]

Prerequisites and design checks

Confirm that the enlarged CIDR does not collide with subnets, static/dynamic routes, peered networks, internal ranges, or hybrid prefixes. Auto-mode networks have documented expansion boundaries; proxy-only subnets cannot simply be treated like workload subnets. The data plane is designed to keep forwarding during expansion, but propagation and dependent policy updates can take time.

DependencyWhy it matters after expansion
Firewall and hierarchical policyRules written against the old CIDR do not automatically broaden just because the subnet did.
On-prem route filtersThe larger prefix may be rejected or may overlap an enterprise route.
GKE authorized networksControl-plane allowlists can still contain only the old subnet range.
Monitoring/IPAMCapacity reports and ownership records must reflect the new prefix.

Implementation and troubleshooting

Verified CLI pattern: gcloud compute networks subnets expand-ip-range SUBNET --region=REGION --prefix-length=PREFIX_LENGTH. Afterward inspect the subnet, effective routes, firewall rules, and hybrid advertisements. Scenario: a subnet expands successfully, but newly assigned addresses cannot reach a private control plane because an authorized-network CIDR still reflects the /24. The fix is policy alignment, not a second subnet resize.

Takeaway: subnet expansion is operationally non-disruptive to existing addresses but architecturally irreversible. Treat every CIDR-dependent policy as part of the change plan.

3. GKE control-plane authorized networks for IP-based endpoints

Domain 2 — Implementing a VPC network
Primary: GKE network isolation · Configuration: Configure network isolation

Endpoint model and trust boundary

GKE can expose control-plane access through DNS-based and IP-based endpoints. Google recommends the DNS-based endpoint for many modern deployments because identity and authorization can be handled without maintaining IP allowlists. When IP endpoints are enabled, authorized networks form an IP-based admission boundary for the Kubernetes API server: only configured source CIDRs can reach the enabled IP endpoint path, subject to the rest of the cluster's access configuration.

flowchart LR
A[Admin / automation]-->B{Control-plane access}
B-->C[DNS-based endpoint]
B-->D[IP endpoint]
D-->E[Authorized-network CIDR check]
E--allowed-->F[Kubernetes API]
E--not allowed-->G[Denied before API auth]

Configuration choices and caveats

For an IP path, decide whether public and/or internal IP access is enabled, whether master authorized networks are enforced, and whether global access is required. An internal-only design substantially reduces exposure, but routing to the private endpoint must still exist. Authorized-network limits and release behavior vary by cluster version, so use the current GKE documentation rather than copying an old cluster's assumptions. Expanding a client subnet does not automatically enlarge the control-plane allowlist.

PatternWhen it fits
DNS endpointPreferred where identity-centric access is desired and supported.
Internal IP + authorized networksStrong private-network control where operators arrive from known routed ranges.
Public IP + narrow allowlistUseful for controlled external administration, but internet reachability increases exposure.

Verified example and troubleshooting

A documented creation pattern includes --enable-dns-access, --enable-ip-access, --enable-master-authorized-networks, and --master-authorized-networks CIDR1,CIDR2. For failures, separate routing from filtering: test whether a path exists to the chosen endpoint, confirm the observed source IP, compare it to the allowed CIDRs, then validate IAM/Kubernetes authentication. Scenario: a VPN user reaches the VPC but cannot access the API because NAT changes the user's source to a prefix not on the allowlist.

Takeaway: authorized networks are an IP reachability gate, not a substitute for API authentication and authorization.

4. GKE Dataplane V2: eBPF service forwarding, policy enforcement, and scale

Domain 2 — Implementing a VPC network
Primary: GKE Dataplane V2

Architecture and data path

GKE Dataplane V2 uses eBPF with Cilium technology for Kubernetes service forwarding and network-policy enforcement. The anetd DaemonSet programs the node dataplane. Network policy is always enabled in this mode, and policy logging is integrated. This removes reliance on several legacy iptables-style paths and gives GKE a consistent programmable dataplane, but it does not mean customers can load arbitrary eBPF programs into Google's managed networking stack.

flowchart LR
A[Pod packet]-->B[eBPF hooks on node]
B-->C{Network policy}
C--deny-->D[Drop + optional policy log]
C--allow-->E[Service/backend map]
E-->F[Selected endpoint]
G[anetd]-.programs maps.->B

Scale, compatibility, and performance

Service forwarding depends on finite eBPF map capacity; current documentation calls out a service-endpoint scale limit of roughly 260,000 entries across services. Very high endpoint churn can increase anetd CPU. Connection reuse and sensible service design matter. Dataplane V2 must be selected when the cluster is created; it is not an in-place toggle for an existing cluster. Certain manually assembled load-balancing patterns and custom eBPF assumptions are unsupported. Fragmentation and ICMP behavior can also differ from what operators expect on a traditional Linux dataplane.

SignalInterpretation
anetd CPU spikeInvestigate endpoint churn, policy scale, and service updates before blaming the application.
Policy log denyConfirms enforcement path; correlate namespace/pod selectors and direction.
Only fragmented traffic failsCheck documented fragmentation/ICMP constraints and path MTU.

Operations and scenario

Inspect anetd health, policy logs, service endpoint counts, node networking, and GKE release notes. Modern releases add consistent-hashing options such as Maglev for supported service behavior; evaluate memory and update-cost tradeoffs before treating a hashing algorithm as a free optimization. Scenario: a cluster with thousands of rapidly changing endpoints sees node-network CPU growth. The network engineer should quantify service-map size and churn first, not blindly add firewall exceptions.

Takeaway: Dataplane V2 is a managed eBPF dataplane with explicit scale/compatibility rules; troubleshoot the programmed node dataplane and policy layer together.

5. Cloud DNS forwarding zones: target selection and the hybrid return path

Domain 3 — Configuring managed network services
Primary: Cloud DNS forwarding zones · Supporting: Cloud DNS best practices

Resolution architecture

A forwarding zone owns a DNS suffix in Cloud DNS but forwards matching queries to external name servers instead of storing the authoritative records itself. Targets can be expressed as IP addresses or, for supported configurations, as a forwarding target name; follow the documented target rules rather than mixing forms arbitrarily. This is the normal hybrid pattern when a specific corporate zone remains authoritative on-premises.

sequenceDiagram
participant VM as GCP VM
participant CD as Cloud DNS
participant ON as On-prem DNS
VM->>CD: query app.corp.example
CD->>ON: forward query
ON-->>CD: answer on hybrid return path
CD-->>VM: cached/returned answer

Routing and firewall behavior

For targets reachable through the VPC or hybrid connectivity, Cloud DNS forwarding traffic uses documented source behavior that includes the 35.199.192.0/19 range. On-premises firewalls must permit UDP and TCP port 53 as required, and the return route must come back through the correct VPC/hybrid path. A common failure is allowing the query toward the resolver while forgetting the response route or ACL. Cloud DNS expects the configured forwarding target path to answer; delegated behavior that sends replies from an unexpected server can fail the transaction.

DesignRecommendation
Only corp.example is on-premCreate a forwarding zone for that suffix.
All DNS must be processed on-premEvaluate server policy/alternative name server patterns rather than many broad forwarding zones.
Intermittent failuresCheck both UDP/TCP 53, route symmetry, target health, and cache effects.

Configuration and troubleshooting

The documented gcloud dns managed-zones create workflow uses a private forwarding zone, associated VPC networks, and forwarding targets. Troubleshoot in order: suffix match, VPC association, target address resolution, route to target, firewall, return path, then DNS application behavior. Forwarded answers can be cached, so a fixed resolver may not appear fixed until TTL/cache behavior is understood.

Takeaway: hybrid DNS is a two-way routed application. If queries leave Google Cloud but answers cannot return to Cloud DNS through the expected network, the zone is correctly configured but resolution still fails.

6. Application Load Balancer LONG traffic duration and IN_FLIGHT balancing

Domain 3 — Configuring managed network services
Primary: Backend services overview

Why request duration changes the balancing signal

Request-rate balancing works best when requests are relatively short and homogeneous. For streams, long-running API calls, uploads, or workloads where concurrency is the meaningful pressure signal, Google Cloud supports a trafficDuration model and the IN_FLIGHT balancing mode on supported modern Application Load Balancers and backend types. SHORT is the default traffic duration; LONG tells the system that requests are expected to remain active longer than a typical short transaction.

flowchart LR
A[Client requests]-->B[Application LB proxy]
B-->C{Balancing mode}
C-->D[RATE: requests/sec]
C-->E[IN_FLIGHT: active requests]
E-->F[Backend with concurrency headroom]

Backend compatibility and capacity

Balancing mode and target capacity are properties of supported backends such as instance groups and appropriate zonal NEGs; serverless, internet, and PSC NEGs do not expose the same capacity knobs. Target capacity is a distribution input, not a hard circuit breaker. If every eligible location is above target, the load balancer can still distribute traffic rather than simply refusing all excess work. A capacity scaler of zero is useful for draining where supported, but availability rules matter if it is the only backend.

WorkloadSignal to consider
Fast, similar HTTP callsRATE can align naturally with backend throughput.
Long streaming/API callsIN_FLIGHT better reflects concurrent occupancy.
Serverless NEGUse the backend model's supported controls rather than forcing VM-style balancing modes.

Configuration, operations, scenario

A documented backend-add workflow supports --traffic-duration=LONG for compatible backend services. Correlate backend utilization, request latency, in-flight counts, health checks, and application queue depth. Scenario: two zones have equal RPS, but one has many long-lived requests. RATE alone makes them look equal; IN_FLIGHT exposes the actual concurrency difference and can improve placement.

Takeaway: choose a balancing signal that models the scarce backend resource. Long-lived traffic is fundamentally about occupancy, not merely arrival rate.

7. HA VPN between two Google Cloud VPC networks

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Create HA VPN between Google Cloud networks · Topology: HA VPN topologies

Failure-domain architecture

Two Google Cloud VPCs can be connected with HA VPN by deploying an HA VPN gateway in each VPC, Cloud Routers, and redundant tunnels. For the 99.99% HA topology, each gateway's interface 0 connects to the peer's interface 0 and interface 1 connects to interface 1. Each tunnel runs BGP through Cloud Router. The gateways should be in the same region for this documented VPC-to-VPC pattern, while the routed prefixes themselves can represent broader VPC reachability.

flowchart LR
subgraph VPC-A
GA0[HA GW A if0]
GA1[HA GW A if1]
RA[Cloud Router A]
end
subgraph VPC-B
GB0[HA GW B if0]
GB1[HA GW B if1]
RB[Cloud Router B]
end
GA0==IPsec/BGP==>GB0
GA1==IPsec/BGP==>GB1
RA-.routes.->GA0
RB-.routes.->GB0

Prerequisites and routing

Subnet ranges should not overlap. Each BGP session uses link-local addressing and exchanges routes according to Cloud Router configuration and dynamic-routing scope. Gateway IP stack type is a design-time choice with documented IPv4/dual-stack/IPv6 constraints and is not something to assume can be freely changed later. Avoid reusing a Cloud Router whose ASN or connectivity role conflicts with other attached hybrid services; the VPN documentation specifically calls out interactions that can matter when routers also manage Interconnect constructs.

TopologyResult
Two tunnels, one per gateway interfaceMeets the intended redundant HA design when all other SLA conditions are met.
One tunnel onlyConnectivity can work, but it is not the 99.99% HA topology.

Operations and failure scenario

Verify both tunnel states, both BGP sessions, learned/advertised prefixes, effective VPC routes, and traffic counters. During testing, fail one tunnel/interface and confirm the alternate BGP path carries traffic. Scenario: both IPsec tunnels are up, but one VPC route is missing because its BGP advertisement policy omits the prefix; tunnel health alone does not prove end-to-end routing.

Takeaway: HA VPN redundancy is gateway-interface redundancy plus BGP route redundancy. Validate both planes.

8. Cloud VPN MTU, IPsec overhead, prefragmentation, and TCP MSS

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Cloud VPN MTU considerations · Supporting: Advanced Cloud VPN configuration

Packet transformation

Cloud VPN presents a 1460-byte MTU for the inner path. IPsec adds outer IP and ESP-related overhead, so a peer that accepts an oversized inner packet must fragment it before encryption when fragmentation is needed. Cloud VPN does not rely on fragmenting an already encapsulated ESP packet as a general recovery mechanism. The practical objective is to keep endpoint packet size below the effective tunnel payload or make Path MTU Discovery/TCP MSS behavior reduce it before encapsulation.

flowchart LR
A[Inner packet]-->B{Fits tunnel payload?}
B--yes-->C[IPsec/ESP encapsulate]
B--no-->D[Peer prefragments or endpoint lowers size]
D-->C
C-->E[Internet / Interconnect underlay]
E-->F[Decrypt + reassemble as applicable]

Design interactions

ICMP handling matters because PMTUD depends on useful packet-too-big signaling. TCP MSS clamping on customer equipment can prevent black-hole behavior for TCP, but it does nothing for all UDP applications. HA VPN over Cloud Interconnect still follows encrypted-path MTU constraints; do not assume a jumbo-capable VLAN attachment automatically turns the VPN payload into a jumbo path.

SymptomLikely direction
Ping small succeeds, large failsInvestigate MTU, ICMP filtering, and encapsulation overhead.
TCP works after MSS clampOriginal path likely exceeded effective TCP payload size.
UDP application still failsMSS affects TCP only; fix application/path MTU or fragmentation behavior.

Troubleshooting workflow

Compare endpoint MTU, peer interface/tunnel MTU, DF/PMTUD behavior, firewall treatment of ICMP, and packet captures before and after encryption. Use controlled packet-size tests rather than interpreting “tunnel up” as proof of payload health. Scenario: routing and BGP are perfect, small SSH packets work, but a database replication stream stalls on larger frames. The failure is a data-plane size problem, not a route-selection problem.

Takeaway: tunnel availability and payload viability are separate. MTU is a packet-transformation constraint imposed before encrypted transport.

9. Modern Load Balancing operations: component inventory, topology, and audit history

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Cloud Load Balancing release notes · Architecture reference: Load balancing overview

Why the component view matters

Google Cloud's modern Load Balancing console experience exposes the resource chain rather than treating a load balancer as one opaque object. The component-centric view inventories resources such as forwarding rules, target proxies, URL maps/backend services, and related routing objects; topology visualization helps operators trace how a frontend resolves into a backend path. Integrated audit-log access then answers a different question: what changed in the control plane?

flowchart LR
A[Forwarding rule]-->B[Target proxy]
B-->C[URL map / service selection]
C-->D[Backend service]
D-->E[Backend]
F[Audit logs]-.who changed config?.->A
F-.change history.->D

Control-plane versus data-plane troubleshooting

Start with topology to confirm the intended resource linkage. Then use health/traffic metrics for runtime behavior and audit logs for configuration mutation history. This prevents a common mistake: searching backend health when a recent URL map or forwarding-rule edit disconnected the desired backend entirely.

EvidenceBest question answered
Resource topologyHow are frontend, proxy/routing, backend service, and backend linked?
Health/traffic metricsAre requests reaching a healthy serving path?
Audit logsWho changed which configuration and when?

Scenario and operational discipline

Scenario: a deployment begins returning 404s after a maintenance window. The backends are healthy. The topology shows the forwarding rule and proxy are correct, but the URL map points the host rule to the wrong matcher. Audit history identifies the configuration update that introduced the change. This is faster and safer than recreating backend resources.

Takeaway: troubleshoot a proxy load balancer as a graph of control-plane components plus a separate runtime health path. Audit history explains drift; metrics explain serving behavior.

10. Cloud Network Insights Monitoring Points: active path measurement across clouds and sites

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Cloud Network Insights overview · Setup: Add Monitoring Points · Metrics: Metrics

Architecture and measurement model

Cloud Network Insights uses Monitoring Points deployed as containers or virtual appliances in locations such as VPCs, branches, on-premises sites, AWS, and Azure. Monitoring policies define targets and test behavior. Unlike passive flow telemetry, these probes actively measure path quality. Network-path tests can expose latency, loss, jitter, route/path changes, and—when both ends participate—one-way behavior and asymmetry that a single-ended test cannot prove.

flowchart LR
A[Monitoring Point: GCP]--synthetic probes-->B[Target / remote MP]
C[Monitoring Point: branch]--synthetic probes-->A
D[Monitoring Point: AWS/Azure]--synthetic probes-->A
A-->E[Cloud Monitoring metrics]
A-->F[Cloud Logging]
E-->G[Alert / dashboard / correlation]

Single-ended versus dual-ended design

ModeUse
Single-endedMeasure reachability/round-trip characteristics when you cannot deploy a probe at the destination.
Dual-endedMeasure richer directional characteristics and identify asymmetric degradation between controlled endpoints.
Web-path monitoringMeasure application/web experience separately from generic L3/L4 reachability.

Current 2026 updates simplify deployment: Google added optimized Monitoring Point support for AWS/Azure and console-generated gcloud commands for downloading installer bundles. Those changes reduce friction but do not remove the need to place probes where they represent the user and service path you actually care about.

Operations and failure scenario

Exported metrics integrate with Cloud Monitoring and logs with Cloud Logging, enabling alerting and correlation with infrastructure changes. Scenario: users report intermittent slowness between a branch and GCP while VPN tunnels stay up. A single-ended test shows RTT spikes; a dual-ended path shows loss primarily in one direction after a carrier route change. That evidence narrows escalation far better than tunnel state alone.

Takeaway: active probes answer “what experience is the path delivering now?”—a different question from passive configuration and flow logs.

11. Migrating classic VPC firewall rules to global network firewall policies

Domain 6 — Cloud network security
Primary: Migration overview · No dependencies: Migration workflow · Dependencies: Migrate rules with dependencies

What the migration tool does—and deliberately does not do

The migration workflow converts eligible VPC firewall rules into rules in a global network firewall policy. It does not silently attach the new policy and delete the old rules. That separation is a safety feature: engineers can review converted priorities, targets, logging, tags/service-account dependencies, and effective policy before moving enforcement.

flowchart LR
A[VPC firewall rules]-->B[gcloud migration]
B-->C[Global network firewall policy]
C-->D[Review priorities / targets / logs]
D-->E[Associate policy]
E-->F[Test effective firewalls + logs]
F-->G[Disable old rules]
G-->H[Delete after rollback window]

Priority and dependency translation

If source rules share a priority, migration must create unique policy priorities while preserving relative behavior. The documented conversion gives deny precedence over allow where source priorities collide. Logging settings are preserved where supported. Rules that rely on network tags or service accounts can require secure-tag/IAM-aware handling rather than a mechanical copy. GKE-created firewall rules are a special operational case and should not be assumed to migrate like administrator-owned rules.

PhaseSafe action
ConvertCreate policy/rules; do not change traffic yet.
ValidateInspect translated priorities, targets, logging, dependencies.
AssociateAttach the policy and choose enforcement order deliberately.
CutoverUse effective-firewall views/logs; disable legacy rules before deleting them.

Verified commands and troubleshooting

The documented migration pattern uses gcloud beta compute firewall-rules migrate --source-network=NETWORK_NAME --target-firewall-policy=POLICY_NAME. Association uses gcloud compute network-firewall-policies associations create. When required, enforcement can be changed with gcloud compute networks update NETWORK_NAME --network-firewall-policy-enforcement-order=BEFORE_CLASSIC_FIREWALL. Verify with gcloud compute networks get-effective-firewalls NETWORK_NAME.

Scenario: converted rules look correct, but a workload is denied after cutover because a secure-tag target was not bound as expected. Roll back by restoring the previous enforcement/association state, then fix the IAM/tag dependency instead of changing unrelated CIDRs.

Takeaway: migration is a staged policy refactor. The safe unit of testing is effective behavior, not merely successful rule creation.

12. Application Load Balancer configuration-size quota and URL map quota units

Domain 3 — Configuring managed network services
Primary: Load Balancing quotas and limits · Change history: Cloud Load Balancing release notes

Why configuration size is now a design dimension

Large Application Load Balancer URL maps can contain many host rules, path matchers, route rules, header actions, and advanced policies. Google introduced a newer configuration-size quota model for supported Application Load Balancers. Under that model, an individual URL map can be much larger—up to the documented 1 MB class for applicable modern ALBs—while classic Application Load Balancer limits remain smaller. Projects not using the newer quota model retain the legacy size constraints documented for their load-balancer type.

flowchart LR
A[Forwarding rules]-->B[Target proxy]
B-->C[URL map]
C-->D[Host/path/route rules]
D-->E[Backend services]
A-.more references can raise active config usage.->F[Configuration-size quota]

Quota units and scope

Active configuration usage is not only the raw byte size of one URL map. Complexity contributes quota units, and a configuration referenced through target proxies/forwarding rules can consume capacity according to how many active frontends use it. Quota scope also differs by load-balancer family—for example, global external designs are evaluated at a different scope than regional external or internal designs. This matters in platform projects that centralize many frontends onto a few reusable maps.

QuestionDesign implication
Is this classic or modern ALB?Different size limits/models can apply.
How many frontends activate the configuration?Shared maps can multiply active quota usage.
Is the quota global, regional, or VPC-scoped?Capacity planning must match the LB family's quota scope.

Operations and scenario

Before a large deployment, measure current quota consumption, URL-map complexity, and number of active forwarding paths. Keep generated routing configuration modular and monitor quota during CI/CD rather than discovering the limit in production. Scenario: a team duplicates frontends around one very large URL map. The map itself remains under its single-object limit, but active configuration usage crosses quota because the same complex configuration is activated multiple times.

Takeaway: modern ALB scaling has both object-size limits and active-configuration quota economics. Count references, not just bytes.
