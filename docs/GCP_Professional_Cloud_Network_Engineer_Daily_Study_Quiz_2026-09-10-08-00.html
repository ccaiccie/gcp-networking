1. Resource Manager tags on VPC resources

Domains 1 / 6

Purpose and architecture

Resource Manager tags are centrally governed key-value metadata that can be attached to supported VPC resources including networks, subnetworks, routes, firewall rules, network firewall policies, network attachments, service attachments, Packet Mirroring resources, IP addresses, and BYOIP delegated prefixes. They are different from Compute Engine network tags and from labels. Resource Manager tags can participate in IAM conditions and policy decisions; labels are descriptive metadata, while network tags are instance selectors used by specific networking features.

IAM and lifecycle

A tag binding joins a Resource Manager tag value to a target resource. Administration therefore spans permissions on the tag definition/value and permissions on the VPC resource. Relevant roles include Tag Viewer, Tag Administrator, Tag User, Organization Viewer, and Compute Network Admin for attaching tags to VPC resources. Regional resources require a location when listing bindings, while global resources do not. Tag-binding operations use full numeric resource identifiers, which matters for automation.

Scenario and troubleshooting

An automation service is conditionally granted privileges only when environment=regulated is present. A newly created subnet has correct routes but automation fails. Verify the tag value, direct/inherited binding, Tag User permission, resource permissions, numeric resource ID, and location. The symptom is authorization metadata, not forwarding.

flowchart LR ORG[Org tag key/value] --> B[Tag binding] B --> N[VPC resource] IAM[IAM condition] --> B NT[Network tag] --> VM[VM selector] L[Label] --> META[Metadata only]

Notice that three similarly named metadata systems feed different consumers.

Remember: Resource Manager tags can drive governance; network tags target instances; labels are not an authorization mechanism.

2. Private Service Connect interfaces and network attachments

Domains 1 / 2

Why this exists

PSC interfaces solve producer-initiated private connectivity. The consumer creates a regional network attachment associated with a subnet. A producer VM creates a PSC interface that requests that attachment. If accepted, Google allocates the PSC interface an address from the consumer subnet while the producer VM retains another standard NIC in the producer VPC. The interface logically participates in the consumer network but its VM lifecycle remains producer-managed.

Directionality and transitivity

This is the reverse of a PSC endpoint. An endpoint lets a consumer initiate toward a producer service; a PSC interface lets a producer initiate into the consumer environment. Interface connections are transitive through networks reachable from the consumer VPC, subject to routing and security, which makes them useful for managed services that need callbacks or egress into customer networks.

Controls and limits

Network attachments can automatically or manually accept producer project IDs or service class IDs. If the same identity is on both accept and reject lists, rejection wins. Attachments are regional, support IPv4-only, dual-stack, or IPv6-only subnets, can accept multiple PSC interfaces, and cannot be deleted while open connections remain. PSC interfaces cannot use public external IP addresses.

flowchart LR P[Producer VM] --> PI[PSC interface] PI --> A[Consumer network attachment] A --> S[Consumer subnet] S --> W[Consumer workload / connected network] P --> PN[Producer standard NIC]

The producer controls the VM, while the consumer controls acceptance and the subnet providing the PSC-interface address.

Remember: endpoint = consumer initiates; interface = producer initiates; network attachment = consumer-side trust and addressing object.

Primary: Google Cloud — About network attachments.

3. Cloud Router BGP session construction

Domains 2 / 4

Interface plus peer

A Cloud Router BGP session is built from a Cloud Router interface and a BGP peer. Each interface connects to exactly one supported underlying resource: an HA VPN tunnel, a Cloud Interconnect VLAN attachment, or an NCC Router appliance instance. One Cloud Router can manage multiple interfaces and peers when their requirements are compatible.

ASN design

All BGP sessions on one Cloud Router share the same Google-side ASN. Transport-specific ASN requirements therefore matter. Partner Interconnect cases can require a public ASN while other interface types use private ASNs, so a single Cloud Router is not always an appropriate universal container for mixed hybrid transports.

Troubleshooting sequence

If a session is Idle or Active, check the underlying tunnel/VLAN/appliance, interface binding, reciprocal peer addresses, ASNs, and authentication. If the session is Established but routes are absent, inspect advertisements, route policies, custom learned/advertised routes, quotas, best-path selection, and VPC dynamic-routing mode. An Established peer proves adjacency, not prefix acceptance.

flowchart LR VPN[HA VPN] --> I1[Router interface] VLAN[VLAN attachment] --> I2[Router interface] RA[Router appliance] --> I3[Router interface] I1 --> B[BGP peers: one Router ASN] I2 --> B I3 --> B B --> R[VPC dynamic routes]
Remember: transport → interface → BGP peer → advertisements/policy. Shared Router ASN can force design separation.

Primary: Google Cloud — Establish BGP sessions.

4. NCC Gateway spokes for Security Service Edge

Domains 2 / 6

Architecture

NCC Gateway is a managed regional spoke that connects Network Connectivity Center topologies to supported third-party Security Service Edge services. It removes the need to run a generic VM-based egress appliance merely to reach the SSE provider, while keeping route orchestration inside the NCC hub-and-spoke model.

Topology, capacity, and addressing

Google recommends hybrid inspection topology for greenfield deployments; supported existing star or mesh topologies can be used in brownfield designs. In hybrid inspection topology the NCC Gateway spoke belongs to the gateways group. Gateway creation selects aggregate capacity, with documented tiers of 1, 10, or 100 Gbps depending on region and partner, and reserves a unique non-overlapping /23. The range cannot be from 100.64.0.0/10.

Regional constraints and scenario

NCC Gateway feature availability, partner availability, and capacity are not uniform across regions. Google documents supported SSE partners such as Palo Alto Prisma Access and Symantec Cloud SWG in applicable locations. A dual-region design can fail before routing is relevant if the second region lacks the selected partner or if the same /23 is reused. Validate topology, group, supported region, partner, capacity, and addressing first.

flowchart LR BR[Branch/edge spokes] --> H[NCC hub] VPC[VPC spokes] --> H H --> G[NCC Gateway spoke] G --> SSE[SSE partner] SSE --> NET[Internet/SaaS]
Remember: NCC Gateway design is topology + gateways group + regional partner/capacity + a unique non-overlapping /23.

Primary: Google Cloud — Create an NCC Gateway spoke.

5. Cross-project NCC VPC spokes and export-range filters

Domain 2

Cross-project governance

An NCC VPC spoke can reside in a different project from its hub. The spoke references the full hub URI and follows proposal/acceptance and IAM rules across projects. This supports a central connectivity hub owned by a platform team while application projects retain VPC ownership.

Include and exclude ranges

VPC spokes can filter exported subnet ranges. Include ranges can use explicit CIDRs or keywords such as ALL_PRIVATE_IPV4_RANGES and ALL_IPV6_RANGES. Google documents up to 16 unique non-overlapping CIDRs in each include and exclude list. An excluded range must be contained within admitted include space.

Defaults and prefix semantics

If include is omitted, NCC behaves as though private IPv4 ranges are included; exclude defaults to empty. A subnet must equal or fit inside the include CIDR. Thus 10.1.0.0/16 can include a 10.1.2.0/24 subnet, but 10.1.2.0/25 cannot include that broader /24. These filters govern subnet export, not arbitrary BGP prefix-list logic.

Failure scenario

A new IPv6 subnet is absent from other spokes. The hub attachment is valid, but the default export behavior never admitted IPv6. Update the spoke export range, then verify propagation and topology.

flowchart LR APP[App project VPC] --> P[Propose/accept spoke] P --> H[Central NCC hub] APP --> F[Include/exclude ranges] F --> H H --> O[Other spokes]
Remember: proposal/acceptance controls attachment governance; include/exclude ranges control subnet-route export.

Primary: Google Cloud — Propose a VPC spoke in another project.

6. Internal proxy Network Load Balancer: regional versus cross-region

Domain 3

Two-connection TCP proxy

The internal proxy Network Load Balancer is Envoy-based Layer 4 TCP proxying. Client connection 1 terminates at the internal VIP/proxy. The proxy opens connection 2 to a backend. Backend source addresses therefore come from the proxy infrastructure, not the original client packet.

Regional mode

Regional mode uses regional forwarding rules and addresses, INTERNAL_MANAGED, and a REGIONAL_MANAGED_PROXY proxy-only subnet. Backends are regional. Client access is regional by default but global access can be enabled.

Cross-region mode

Cross-region mode uses global forwarding rules with regional IP addresses, INTERNAL_MANAGED, and GLOBAL_MANAGED_PROXY proxy-only subnets. The backend service is global and can fail traffic to healthy backends in other regions. Mode cannot simply be edited after creation, so regional versus cross-region is a design-time choice.

Failure scenario

Remote-region clients fail to reach a regional proxy NLB: check global access first. Backends remain unhealthy even when clients connect: allow proxy-only subnet and health-check traffic rather than only original client CIDRs.

flowchart LR C[Client] -->|TCP 1| VIP[Internal VIP] VIP --> E[Envoy proxy] E -->|TCP 2| A[Region A backend] E -->|cross-region failover| B[Region B backend]
Remember: regional = regional backends with optional global client access; cross-region = global backend service and multi-region failover.

Primary: Google Cloud — Internal proxy Network Load Balancer.

7. External proxy Network Load Balancer modes and PROXY protocol

Domain 3

Use case

External proxy Network Load Balancers reverse-proxy internet TCP traffic to backends in Google Cloud, on premises, or another cloud. The front connection terminates at the load balancer and a second TCP connection is opened to the backend. Google recommends Application Load Balancers for HTTP(S) because they understand HTTP semantics; proxy NLBs are for generic TCP/SSL workloads.

Modes

Classic proxy NLBs can be global with Premium Tier or regional with Standard Tier. Global external proxy NLBs use EXTERNAL_MANAGED and globally distributed GFEs with Premium Tier. Regional external proxy NLBs are Envoy-based, use regional external IPs and EXTERNAL_MANAGED, and support Premium or Standard Tier. Mode affects ingress location, IP advertisement, and backend scope.

Client identity

Backends do not automatically receive the original client address as their TCP peer. PROXY protocol can relay client IP/port metadata to a backend that understands it, but does not restore original Layer-3 headers. Frontend and backend ports can also differ because proxying permits port remapping.

Failure scenario

An appliance migrated from a passthrough NLB denies sessions because it expects the client source IP in the packet header. PROXY protocol helps only if the appliance parses it. If native L3 source preservation is mandatory, reconsider the load-balancer family.

flowchart LR U[Internet client] -->|TCP/SSL 1| E[GFE or Envoy] E -->|TCP 2| B[Backend] E -. PROXY metadata .-> B
Remember: PROXY protocol transports metadata; it does not turn a reverse proxy into passthrough forwarding.

Primary: Google Cloud — External proxy Network Load Balancer.

8. GKE dual-stack IPv4/IPv6 networking

Domains 1 / 3

Address model

A dual-stack GKE cluster assigns IPv4 and IPv6 addresses to nodes, Pods, and Services. It supports gradual IPv6 adoption while preserving IPv4 compatibility. GKE's VPC-native model uses alias IP ranges, so Pod addressing participates directly in VPC routing. Dual-stack planning therefore starts at VPC/subnet stack type and range allocation, not only at Kubernetes manifests.

End-to-end behavior

Each family has an independent return path. A service can be healthy on IPv4 while IPv6 fails because of an AAAA record, firewall rule, load-balancer capability, VPC route, or hybrid/upstream issue. Publishing an IPv6 address proves only that an address exists; clients, listeners, proxies, load balancers, and upstream networks still need working IPv6.

Migration scenario

After enabling dual stack, IPv4 calls succeed but IPv6 requests time out. Validate node/Pod/Service IPv6 assignment, AAAA resolution, firewall rules, frontend/backend IPv6 support and release stage, and upstream route reachability independently before changing the whole cluster architecture.

flowchart LR C4[IPv4 client] --> S[Dual-stack Service] C6[IPv6 client] --> S S --> P4[Pod IPv4] S --> P6[Pod IPv6] P4 --> V[VPC routing] P6 --> V
Remember: dual stack is end-to-end: addressing, DNS, routing, firewall, load balancing, and hybrid networks must support the chosen family.

Primary: Google Cloud — GKE IP addressing.

9. Performance Dashboard: interpreting loss and latency

Domain 5

Evidence model

Performance Dashboard provides project-scoped and Google-wide packet-loss and latency views. Project packet loss uses active probes among eligible VM paths; latency is based on Layer-4 traffic observations. The data is useful diagnostic evidence, but it is not packet capture or application-transaction telemetry.

Short spikes and missing data

Google notes that short loss spikes of a few minutes can occur and recommends paying closer attention to sustained loss, particularly when it persists beyond roughly five minutes or correlates with application impact. A project with no eligible VMs has no active-probe packet-loss measurements, and latency needs enough real traffic. Shared VPC project views can contain N/A cells based on VM placement.

Aggregation nuance

Latency is stored as a distribution. Samples within the same bucket can render as the same mean, so a flat graph does not prove every RTT was identical. Google-wide metrics aggregate many projects and are usually smoother than project-specific measurements.

Failure scenario

Dashboard reports loss between zones while the application is healthy. The probe mesh may include a path the application does not use or have sparse samples. Correlate placement, application metrics, flow evidence, and Connectivity Tests before declaring an outage.

flowchart LR PD[Performance Dashboard] --> L[Loss probes] PD --> LAT[Latency distribution] L --> C[Correlate] LAT --> C C --> APP[Application telemetry] C --> FLOW[Flow/Connectivity evidence]
Remember: Performance Dashboard narrows scope; correlation establishes whether the signal is relevant to the application path.

Primary: Google Cloud — Troubleshoot Performance Dashboard.

10. GKE NetworkPolicy enforcement and platform exceptions

Domains 5 / 6

Security model

Kubernetes NetworkPolicy can restrict Pod ingress and egress. GKE implements enforcement with mutually exclusive plugins: Dataplane V2 is Cilium-based, recommended, and default for Autopilot; Calico is available for Standard clusters. A NetworkPolicy object is only policy intent—actual enforcement requires a compatible active dataplane plugin.

Operational impact

On Standard clusters, enabling or disabling network-policy enforcement can recreate nodes and follows maintenance policies. Google documents additional resource overhead and minimum sizing considerations. Disabling enforcement can also remove managed ip-masquerade-agent Pods, changing Pod egress NAT behavior.

Metadata and control-plane exceptions

Default-deny egress must preserve documented GKE metadata-server destinations and ports for Workload Identity Federation. PSC-based cluster control planes can also be blocked if egress policy denies the control plane's internal address. A policy that is too broad can therefore appear as IAM or cluster-health failure.

Troubleshooting

Verify Cilium Pods for Dataplane V2 or Calico-ready node state, then inspect Pod labels, NetworkPolicy selectors, namespace, policyTypes, peers, and ports. Confirm a policy actually selects the workload. If an enable/disable operation appears stuck, inspect maintenance windows and node recreation.

flowchart LR P[Pod] --> NP[NetworkPolicy intent] NP --> PL[Dataplane V2/Cilium or Calico] PL --> A[Allowed peers] PL --> M[Required metadata/control-plane] PL -. default deny .-> B[Blocked peers]
Remember: policy object + enforcement plugin + correct selectors + platform exceptions are all required.

Primary: Google Cloud — GKE NetworkPolicy.

11. Dedicated Interconnect MTU and jumbo frames

Domain 4

Supported MTUs

Dedicated Interconnect VLAN attachments support MTU values of 1440, 1460, 1500, and 8896 bytes. The usable payload size is end-to-end: VPC, VLAN attachment, on-premises routers, guest NICs, and any intermediate appliance must support the intended size. High circuit bandwidth does not imply jumbo frames are active.

8896 limitations

The 8896-byte jumbo MTU is supported only on unencrypted IPv4 or IPv6 VLAN attachments. HA VPN over Cloud Interconnect uses encrypted attachments and therefore does not get 8896. Google also notes that API client libraries can use 1440-byte packets even when a larger MTU exists.

Consistency and changes

Google recommends using the same MTU for attachments connected to the same VPC and matching the VPC MTU. Supported attachment MTU changes can rarely cause a brief disruption. Encrypted HA VPN over Interconnect attachments have fixed 1440 MTU.

Failure scenario

An application is tuned for 8896 after an on-prem router upgrade while the VPC and VLAN attachment remain 1460. Small probes pass but bulk transfers fragment or stall. Verify every segment and test packet sizes deliberately.

12. Cloud NGFW URL filtering, TLS inspection, QUIC, and ECH

Domain 6

Purpose and pipeline

Cloud NGFW URL filtering applies Layer-7 egress policy based on URL/domain context rather than only IP addresses and ports. With TLS inspection, supported encrypted sessions can be inspected for richer URL policy. If URL filtering allows the flow, intrusion detection and prevention can still inspect it, so a URL allow is not a threat-prevention bypass.

Protocol visibility limits

Google documents HTTP/1.x and HTTP/2 support but not QUIC. Encrypted SNI and Encrypted Client Hello reduce hostname visibility. With TLS inspection enabled, Cloud NGFW does not pass QUIC, ESNI, or ECH traffic. Without TLS inspection, those protocols can pass only under documented explicit-allow behavior because normal domain/SNI classification is unavailable.

Implicit deny and workload caveats

URL filtering includes implicit-deny behavior where an explicit allow is required but the request cannot be matched. A browser update that enables HTTP/3/QUIC or ECH can therefore change the observed policy outcome even when the website is unchanged. Google also documents that URL-filter inspection of serverless egress is unsupported for Direct VPC egress and Serverless VPC Access connectors.

Failure scenario

An allowed site works in one browser and fails in another after HTTP/3 is enabled. Verify negotiated protocol, ECH/SNI visibility, TLS inspection, and explicit URL rules before adding broad Layer-3 exceptions.

flowchart LR C[Client] --> F[Cloud NGFW endpoint] F --> T{TLS inspection?} T --> U[URL filter] U -->|allow| I[Intrusion prevention] U -->|deny/implicit deny| B[Block] I --> N[Internet] T -. QUIC/ESNI/ECH caveats .-> B
Remember: URL filtering depends on application visibility; TLS inspection improves visibility but changes unsupported-protocol behavior.

Primary: Google Cloud — URL filtering overview.
