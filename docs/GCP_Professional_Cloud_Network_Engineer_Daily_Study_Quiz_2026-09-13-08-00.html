1. Hybrid Subnets for in-place workload migration

Domain 1

Problem and use case

Hybrid Subnets are a Preview VPC capability for phased migrations where workloads must retain their existing IPv4 addresses while some instances remain on-premises and others move to Compute Engine. A VPC subnet and an on-premises segment share the same CIDR, so migration can happen one address at a time rather than forcing an application-wide renumbering event.

Architecture and route ownership

The VPC subnet, Cloud Router, and the HA VPN tunnels or Dedicated/Partner Interconnect VLAN attachments that provide migration connectivity must be in the same Google Cloud region. The subnet range matches the on-premises shared CIDR. Hybrid-subnet routing changes the usual meaning of a subnet route: if an address in the shared range is not represented by an active Google Cloud resource, route evaluation can continue toward the hybrid path instead of treating the local subnet as an unconditional terminal destination.

Cloud Router is prepared with custom route advertisements. During migration, host-specific routes for moved workloads tell the on-premises side that those IPs now live in Google Cloud. Address ownership, BGP advertisements, and migration state therefore have to move together.

Prerequisites, security, and limits

Use supported hybrid connectivity, enable required APIs, and grant network administration permissions. Overlapping addressing is intentional only inside the shared migration construct; unrelated overlap remains dangerous. Firewall policies must allow required traffic from the shared CIDR, and on-premises routing must return traffic over the intended hybrid connection.

Failure scenario

If a migrated VM works from other Google Cloud resources but on-premises clients still reach the old server, verify that the migrated address is being advertised from Cloud Router, that the peer actually learned the host route, and that the hybrid connection is in the same region as the hybrid subnet. A missing advertisement can leave the old on-premises path preferred even after the VM moves.

ApproachTradeoff
Normal subnetOne VPC subnet route owns the whole range.
Hybrid subnetSplit address ownership during migration without renumbering.
Renumber migrationSimpler routing but changes application addresses.

Exam anchor: Hybrid Subnets are for address-preserving migration, not generic overlapping-network design.

2. VPC route evaluation order and special routing paths

Domains 1–2

Distributed routing model

Google Cloud VPC routing is distributed; there is no central router appliance assigned to the VPC. Controllers associated with workloads receive the routes applicable to them. Route changes are eventually propagated, so a route-table change and data-plane convergence are related but not instantaneous events.

Evaluation sequence

Route lookup is not simply “pick the longest prefix first.” Google first checks non-removable special routing paths. Policy-based routes are then evaluated. Ordinary subnet routes normally take precedence over static and dynamic custom routes. Private Service Connect endpoints for global Google APIs have their own routing step. Only after these checks does Google evaluate the most-specific static/dynamic destination, then the route category, preference, priority, and equal-cost possibilities.

Special paths

Important special paths include external passthrough Network Load Balancers and protocol forwarding through Maglev; Google Front End paths to proxy-load-balancer backends; health-check probe paths; IAP TCP forwarding ranges; Cloud DNS and Service Directory traffic using 35.199.192.0/19; and Serverless VPC Access using 35.199.224.0/19. Some of these paths continue to work even if you remove a normal default route.

Troubleshooting workflow

Classify the traffic before inspecting route priority. Ask whether the flow qualifies for a special service path, whether a policy-based route matches, whether the destination belongs to a local/peering/NCC subnet route, and only then compare custom routes. This avoids the common mistake of expecting a more-specific static route to override a regular local subnet route.

flowchart TD PKT[Packet] --> S{Special path?} S -->|yes| SP[Use special path] S -->|no| P{Policy-based route?} P --> SUB{Subnet route match?} SUB --> PSC{PSC Google APIs endpoint?} PSC --> MS[Most-specific static/dynamic] MS --> RC[Route class, priority, ECMP]

The visual matters because “longest prefix” occurs after several higher-order checks.

Exam anchor: route applicability and route selection order are distinct concepts.

Primary: Google Cloud VPC routes.

3. Cloud DNS server policies: inbound, outbound, and DNS64

Domain 3

What a server policy controls

A DNS server policy attaches to a VPC network and can enable inbound forwarding, outbound forwarding to alternative resolvers, or both. It can also configure DNS64. This is broader than creating a forwarding zone because the policy can change the network-wide resolution path for workloads using the metadata resolver.

Inbound forwarding

An inbound policy creates internal IPv4 entry points from eligible subnet primary ranges. On-premises DNS clients reach those addresses through HA VPN, Interconnect, or Router appliance connectivity. The query is associated with the VPC that receives the hybrid packet and with the region where that packet enters Google Cloud, not necessarily with the region containing the selected entry-point address. Entry points are not directly reachable across VPC Network Peering or NCC boundaries, so deploy the inbound policy in the VPC receiving the hybrid query and use DNS peering when records live elsewhere.

Outbound forwarding

An outbound policy configures alternative name servers. Cloud DNS can send queries to those resolvers, which may reside in the VPC or on-premises. Private-routed alternative resolvers see queries sourced from 35.199.192.0/19 and must return responses to the exact source. Firewalls and on-premises routing must permit TCP and UDP 53 in both directions. Alternative servers can change normal Cloud DNS resolution behavior, so understand which private zones and Google-managed names will no longer be resolved locally.

DNS64 and IPv6-only clients

DNS64 synthesizes IPv6 answers from IPv4-only records so IPv6-only workloads can use an appropriate translation path. IPv6-only subnets do not support inbound DNS server policies, but outbound server policies remain possible.

Official figure/reference: DNS server policies overview
flowchart LR ON[On-prem resolver] -->|UDP/TCP 53| IN[Inbound policy entry point] IN --> CDNS[Cloud DNS resolution order] VM[VM via metadata DNS] --> CDNS CDNS -->|outbound policy| ALT[Alternative DNS server] ALT -->|reply to 35.199.192.0/19| CDNS

Hybrid DNS failures often come from the return path to Google's DNS proxy range, not from record content.

Exam anchor: inbound exposes Cloud DNS to hybrid clients; outbound redirects Cloud DNS queries to alternative resolvers.

Primary: Google Cloud DNS server policies.

4. Application Load Balancer advanced traffic management: locality, affinity, and outlier detection

Domain 3

Two independent distribution decisions

Application Load Balancers first select backend capacity according to backend configuration and balancing mode. After a backend group or zone is selected, the locality load-balancing policy decides which endpoint receives the request. Capacity distribution and endpoint selection are therefore separate layers.

Locality policies and session affinity

Policies such as ROUND_ROBIN, LEAST_REQUEST, RING_HASH, and MAGLEV fit different workloads. Consistent-hash session affinity is best-effort and depends on compatible locality policy. Affinity does not override endpoint health or backend capacity, so a client can move when its preferred endpoint becomes unavailable.

Outlier detection

Outlier detection observes production request failures and can temporarily evict a bad endpoint, then later re-admit it. It complements active health checks: a health check validates a known probe endpoint, while outlier detection catches a backend that passes probes but fails real requests.

Failure scenario

If only one backend instance returns intermittent 5xx responses while health checks remain green, outlier detection can reduce user impact. If stickiness is also required, use a supported hash-based affinity mechanism but do not assume it will pin clients to an unhealthy endpoint.

ControlPurpose
Balancing modeHow much traffic a backend group should receive.

Exam anchor: health checks, locality policy, affinity, and outlier detection solve different problems.

5. Media CDN architecture, origin shielding, routing, and signed delivery

Domain 3

Purpose and components

Media CDN is optimized for high-throughput media delivery and large objects, complementing Cloud CDN's web-acceleration use cases. Its conceptual components are the edge router, edge cache, and cache filler. An EdgeCacheService contains routing, cache, TLS, and header behavior and points to one or more EdgeCacheOrigin resources.

Request flow and shielding

The edge router matches host and path. The cache searches by cache key. On a miss, the cache filler creates an origin request and stores the returned object. Origin shielding reduces the number of origin fetches by concentrating miss traffic through shield capacity instead of letting every edge location independently hit the origin.

Security and access

Media CDN integrates with Cloud Armor edge policies, supports signed URLs and signed cookies, and can authenticate to private Cloud Storage origins. Client delivery supports modern protocols such as HTTP/2 and QUIC. Service Extensions plugins can add supported lightweight customization to the request/response path.

Operations

When playback stalls, determine whether the request was an edge hit, an edge miss waiting on origin fill, a routing mismatch, or an authorization failure. Invalidating cache entries can correct stale content but temporarily increases origin demand while caches refill.

Official figure/reference: Media CDN overview and component figure
flowchart LR U[Viewer] --> R[Edge router] R --> C{Edge cache} C -->|HIT| U C -->|MISS| F[Cache filler / shield] F --> O[Origin] O --> F --> C

Notice that the cache filler, not the viewer, owns the origin fetch on a miss.

Exam anchor: route, cache key, cache status, and origin-fill behavior are separate troubleshooting layers.

Primary: Media CDN overview.

6. HA VPN peer-gateway topologies and failure-domain design

Domain 4

Topology choices

Google documents three common peer arrangements: an HA VPN gateway to two separate peer VPN gateways; an HA VPN gateway to one peer gateway with two IP addresses; or an HA VPN gateway to one peer gateway with one IP address. The first design provides the strongest peer-device fault isolation because maintenance or failure on one physical peer does not remove both tunnels.

Tunnels, BGP, and IPv6

HA VPN interfaces establish IPsec tunnels to peer interfaces, and Cloud Router BGP sessions exchange routes. Redundancy depends on genuinely independent tunnel and peer failure domains plus consistent route advertisement. IPv6-capable HA VPN stack types also require IPv6 enabled in the relevant BGP sessions.

Failure analysis

Differentiate tunnel failure, BGP failure, peer-device failure, and upstream LAN failure. An IPsec tunnel and BGP session can remain healthy while the peer loses reachability to an application subnet, so end-to-end probes remain necessary.

Two peer devicesBest device and maintenance isolation.
One device, two IPsInterface/path redundancy but one device failure domain.
One device, one IPLeast peer-side redundancy.

7. Dedicated Interconnect LACP bundles and non-disruptive circuit scaling

Domain 4

Physical connection model

A Dedicated Interconnect connection can aggregate multiple physical circuits using Link Aggregation Control Protocol (LACP). VLAN attachments sit above that logical connection, which allows the physical bundle to change while existing logical attachments continue to operate.

Increasing and decreasing capacity

Increasing the requested circuit count resembles new provisioning: Google issues an updated LOA-CFA, your vendor completes cross-connect work, and new circuits are tested before they become usable. Decreasing capacity removes member ports from the LACP bundle and requires corresponding vendor action. Google documents supported capacity increments according to 10-Gbps and 100-Gbps link types.

Immutable design choices

You cannot change an existing connection from 10-Gbps link type to 100-Gbps in place. Provision a new connection alongside the old one and migrate traffic. Requested features such as MACsec likewise are not generic in-place toggles for an existing connection. Initial physical design therefore still matters even though circuit count is adjustable.

Operational scenario

Before scaling down, review utilization and redundancy. Removing links from an LACP bundle can be technically non-disruptive yet still create congestion or violate an intended availability design if the remaining capacity is insufficient.

flowchart LR R[Customer router] == LACP bundle ==> I[Dedicated Interconnect] I --> V1[VLAN attachment A] I --> V2[VLAN attachment B] R --- C1[Circuit 1] R --- C2[Circuit 2] C1 --> I C2 --> I

LACP decouples member-circuit changes from the VLAN attachments above the bundle.

Exam anchor: circuit count can change without rebuilding VLAN attachments; link type requires a new connection.

Primary: Modify Dedicated Interconnect connections.

8. GKE ClusterNetworkPolicy hierarchy for cluster-wide guardrails

Domain 6

Why a cluster-wide policy layer matters

Standard Kubernetes NetworkPolicy is application and namespace oriented. GKE supports the Kubernetes-native ClusterNetworkPolicy for administrator-wide security. Platform teams can enforce mandatory controls across namespaces while application owners keep namespace-level policies.

Policy evaluation tiers

Admin-tier ClusterNetworkPolicy is highest precedence. Explicit Deny can override lower tiers, while an Accept can terminate policy evaluation for that flow. The middle NetworkPolicy tier contains application-specific policies. Baseline-tier ClusterNetworkPolicy is lowest and can establish defaults that developers may override in the middle tier. If no policy matches, the default remains implicit allow.

Compatibility and verification

Google recommends the standardized ClusterNetworkPolicy for new designs rather than relying on the older proprietary CiliumClusterwideNetworkPolicy. Operators can list and describe cluster network policies with kubectl and inspect status conditions for reconciliation. Dataplane V2 observability and network-policy logging provide evidence of real packet decisions.

Failure scenario

If a namespace owner adds an allow NetworkPolicy but traffic remains denied, inspect the Admin tier first. A higher-tier explicit deny is intentionally non-overridable by namespace policy.

flowchart TD PKT[Packet] --> A{Admin tier} A -->|Deny| DROP[Drop] A -->|Accept| OK[Allow] A -->|No final match| N[NetworkPolicy tier] N --> B[Baseline tier] B --> I[Implicit allow if nothing matches]
Exam anchor: ClusterNetworkPolicy introduces policy hierarchy, not merely cluster-wide scope.

Primary: Configure GKE ClusterNetworkPolicy.

9. GKE network-policy logging for audit and troubleshooting

Domain 5

What the logs prove

Network-policy logging records the allow or deny decision made by the GKE policy engine. This turns policy troubleshooting from YAML inference into evidence. Logs can identify the policy responsible for an administrative deny and are useful for audit trails and zero-trust rollouts.

Selective logging strategy

Logging every allowed connection in a busy cluster can create large volumes. A practical rollout often begins with denied traffic to identify breakage, then adds targeted allow logging for sensitive workloads or high-value policy transitions. Retention and log sinks should match the security requirement.

Troubleshooting workflow

For a failed Pod connection, confirm DNS and destination endpoints, list active policies, then correlate the attempted flow with policy logs. If no policy decision appears, investigate routing, Service/EndpointSlice state, node networking, or the application rather than assuming the policy engine dropped the packet.

flowchart LR A[Pod A] -->|flow| DP[Dataplane policy engine] DP -->|allow/deny| B[Pod or Service B] DP --> L[Policy decision log] L --> CL[Cloud Logging] CL --> Q[Audit and troubleshooting]
Exam anchor: network-policy logs explain policy decisions; they do not replace DNS, routing, or application diagnostics.

Primary: GKE network-policy logging.

10. Cloud NGFW Enterprise TLS inspection

Domain 6

Why decrypt

Layer-7 controls such as threat inspection and detailed URL filtering need visibility that encrypted application data normally hides. Cloud NGFW Enterprise can intercept selected TLS flows, decrypt them, apply security inspection, and establish a separate encrypted connection toward the destination.

Control components

TLS inspection relies on firewall endpoints and associations plus a TLS inspection policy and CA configuration. A matching firewall policy rule must enable TLS inspection when the applied security profile group requires decrypted visibility. Merely creating the inspection policy does not cause every encrypted session to be decrypted.

PKI and trust boundary

Clients must trust the inspection CA or they will reject the substituted certificate. Certificate-pinned applications may fail even when the CA is trusted. Privacy, regulatory, and data-handling implications should determine exclusions and scope.

Troubleshooting

If HTTPS fails only after enabling inspection, validate endpoint association, rule match, CA trust, certificate behavior, SNI, security profile group, and whether the application pins certificates. Without decryption, some URL controls can still use SNI/domain information, but full host/path visibility is more limited.

Official figure/reference: Set up TLS inspection
flowchart LR C[Client] -->|TLS leg 1| FW[Cloud NGFW firewall endpoint] FW -->|decrypt and inspect| SEC[Security profiles] SEC -->|TLS leg 2| S[Server] CA[Inspection CA] -. trust .-> C

Inspection creates two trust relationships: client-to-inspector and inspector-to-server.

Exam anchor: TLS inspection is both a firewall-policy feature and a PKI deployment.

Primary: Cloud NGFW TLS inspection setup.

11. Cloud Armor Adaptive Protection and automatic mitigations

Domain 6

Behavior-based detection

Adaptive Protection learns normal Layer-7 traffic patterns for backend services protected by a Cloud Armor policy. It detects anomalous HTTP-flood behavior, generates a signature describing the suspected attack, and can recommend a custom WAF rule. A training period is required before the baseline becomes reliable.

Visibility and editions

Full Adaptive Protection alerts, signatures, and suggested rules are available with Cloud Armor Enterprise; basic alerting is more limited. Events flow to Cloud Logging and Security Command Center and include confidence and attack characteristics that can drive alert policies.

Granular models and auto-deploy

Granular models can learn host/path-specific baselines so a hot endpoint is not hidden inside an otherwise normal backend average. Automatic mitigation uses a placeholder rule with evaluateAdaptiveProtectionAutoDeploy(); preview mode is useful for validating suggested enforcement before blocking real traffic. If an upstream proxy masks client IPs, trusted user-IP headers must be configured carefully.

Limits and tuning

Requests served directly from Cloud CDN and requests already rejected by Cloud Armor are not counted like ordinary backend traffic for Adaptive Protection learning. Review false positives and report event errors to improve future model behavior.

flowchart LR T[HTTP traffic] --> ARM[Cloud Armor policy] ARM --> BASE[Behavior baseline] BASE --> A{Anomaly?} A -->|yes| SIG[Attack signature + suggested rule] SIG --> PRE[Preview or auto-deploy] PRE --> ARM
Exam anchor: Adaptive Protection is learned L7 DDoS defense; it complements static WAF and rate-limiting policy.

Primary: Adaptive Protection overview.

12. Service Extensions authorization extensions on load-balancing paths

Domain 3

Purpose

Service Extensions adds programmable decisions to supported managed application-delivery paths. An authorization extension inserts custom authorization logic into the request path without replacing the Google-managed load balancer.

Request flow

A request reaches the supported forwarding/load-balancing path, matches an authorization policy, and invokes the configured extension backend. The extension evaluates allowed request context and returns an authorization decision. Approved traffic continues to normal route selection; denied traffic does not reach the application backend.

Design constraints

An authorization policy can have only one authorization extension. A forwarding rule can be associated with multiple authorization policies, but only one can be a custom authorization policy under current documented limits. Timeouts, product support, failure behavior, and extension availability must be designed before putting business-critical traffic behind custom logic.

Security and operations

The extension becomes part of the authorization chain, so its service identity, IAM, latency, availability, and logs become production dependencies. Keep the decision deterministic and fast, and define behavior for extension failure. Avoid exposing secrets through request headers or logging.

flowchart LR C[Client] --> LB[Application Load Balancer] LB --> AP[Authorization policy] AP --> EXT[Authorization extension] EXT -->|allow| R[Normal route] EXT -->|deny| D[Reject] R --> APP[Backend]
Exam anchor: an authorization extension is a programmable policy decision on a managed data path; it does not replace application authorization or IAM.

Primary: Configure a Service Extensions authorization extension.
