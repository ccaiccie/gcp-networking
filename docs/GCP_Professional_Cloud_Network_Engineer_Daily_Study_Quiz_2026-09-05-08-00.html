1. Network Service Tiers: Premium versus Standard is a routing decision, not just a price switch

Domain 1

What problem the feature solves

Network Service Tiers lets you select how internet-facing traffic reaches and leaves a Google Cloud resource. Premium Tier optimizes performance by carrying traffic on Google’s global private backbone for as much of the path as possible; Standard Tier optimizes cost by using ISP and transit networks earlier. Internal VPC traffic is not converted into “Standard Tier” traffic merely because the project default is Standard: traffic between Google Cloud resources continues to use Google’s network.

Ingress and egress path

With Premium Tier, internet ingress enters Google’s network at a point of presence near the user and remains on Google’s backbone toward the workload. Egress similarly stays on Google’s network until a PoP close to the destination. Standard Tier is regional: internet traffic reaches a PoP selected near the workload region and traverses more of the public internet. That changes latency, failure exposure, and the location at which TCP proxying occurs for supported regional/classic load-balancing patterns.

flowchart LR U[Internet user] --> PPOP[Nearest Google PoP] PPOP -->|Premium: Google backbone| PR[Google Cloud region] U --> ISP[Transit / ISP path] ISP --> SPOP[PoP near workload region] SPOP -->|Standard: shorter Google backbone portion| SR[Google Cloud region]

Official figure reference: Network Service Tiers overview contains the Premium and Standard routing-path figures and the decision tree. Notice where the public internet ends and Google’s backbone begins.

Resource support and scope

Global external Application Load Balancers and global external proxy Network Load Balancers require Premium Tier. Standard Tier is built around regional external IP addresses and regional service behavior. Cloud CDN is always Premium Tier. Cloud VPN gateways require Premium Tier. Public Cloud NAT can allocate Premium or Standard regional external addresses. Because tier selection is tied to external IP resources and forwarding rules, changing tiers can require replacement resources rather than an in-place path flip.

Design and migration implications

RequirementPreferReason
Global anycast-style frontend and multi-region backendsPremiumGlobal external IP and global load-balancing capabilities depend on Premium.
Regional internet workload with cost priorityStandardRegional external addresses can use Standard and send traffic through transit networks.
Cloud CDNPremiumCloud CDN does not support Standard Tier.
Predictable performance across distant user populationsPremiumTraffic enters Google’s backbone closer to users.

Separate address pools exist for Premium and Standard. A Standard Tier external IP cannot simply become a Premium Tier IP. For some load-balancer changes you create a new forwarding rule and address and migrate DNS. Google also warns that Premium Tier is not a failover mechanism you can activate during a Standard Tier outage; reclassification during such an outage does not make the traffic Premium for the duration of that event.

Scenario and troubleshooting

If users in Europe see much higher latency to a workload in us-central1 after a cost optimization, verify whether the frontend moved from Premium global service to a Standard regional IP. DNS may still resolve and TCP may still work, but the path can now spend substantially more time on transit networks. Confirm the address tier, forwarding-rule tier, backend region, and actual user-to-PoP path before blaming application processing.

Remember: Premium versus Standard determines internet path and feature availability. It does not change the fact that normal intra-Google VPC traffic uses Google’s network.

Primary: Network Service Tiers overview.

2. IPv6 in Google Cloud VPC: subnet stack type, access type, /64 and /96 behavior

Domain 1

Architecture choices

Google Cloud VPC networks can contain IPv4-only, dual-stack, and IPv6-only subnets in the same global VPC. IPv6-capable subnets require a custom mode VPC. When you add IPv6 to a subnet, you select an access type: internal IPv6 for VPC-scoped routing or external IPv6 for internet-routable addresses. The access type cannot be changed later, so it is a design choice rather than a cosmetic attribute.

Address allocation model

An IPv6 subnet receives a /64. Internal IPv6 uses a VPC-level unique local address allocation, with the VPC assigned a /48 ULA that cannot later be removed or changed. VM interfaces are assigned /96 ranges from the subnet; DHCPv6 provides the first address of that range. Internal forwarding rules for supported services can also consume internal /96 ranges. Google divides the subnet /64 so that one half is used for VM allocations and the other half for Cloud Load Balancing-related allocations.

flowchart TD VPC[VPC - custom mode] --> ULA[VPC internal IPv6 /48 ULA] ULA --> S1[Regional subnet /64] S1 --> VM1[VM NIC /96] S1 --> VM2[VM NIC /96] S1 --> ILB[Internal forwarding rule /96] VPC --> EXT[External IPv6 subnet /64] EXT --> EVM[Internet-routable VM /96]

Official figure/reference: Subnets documentation explains stack types and the IPv6 allocation model.

Transitions and limitations

You can change an IPv4-only subnet to dual-stack. A dual-stack subnet with external IPv6 can be changed back to IPv4-only, but a dual-stack subnet with internal IPv6 cannot be converted that way. IPv6-only subnets are not convertible to IPv4-only or dual-stack, and the reverse conversion to IPv6-only is not supported. External IPv6 addresses are available only with Premium Tier. These constraints mean migration plans should create new subnets when the desired end state is not an allowed in-place transition.

Routing and security

An external IPv6 address is globally routable, but reachability still depends on firewall policy. Because IPv6 removes traditional IPv4 address scarcity, do not infer that NAT is a security boundary. For IPv6-only workloads that must reach IPv4, Google provides NAT64 patterns through Cloud NAT, but product support varies by workload type. Route tables include IPv6 subnet routes and can include a system-generated ::/0 route for external IPv6.

Scenario and verification

A team wants to convert a dual-stack subnet using internal IPv6 back to IPv4-only after a pilot. That conversion is not supported. The safe design is to create an IPv4-only replacement subnet and migrate workloads. Before enabling internal IPv6, verify on-prem and other-cloud ULA planning because the VPC’s internal /48 becomes a durable part of the network design.

gcloud compute networks subnets create SUBNET \
  --network=NETWORK \
  --stack-type=IPV6_ONLY \
  --ipv6-access-type=INTERNAL \
  --region=REGION

The syntax above follows Google’s current VPC create/modify guide; substitute your values and confirm product/workload compatibility.

Remember: stack type and IPv6 access type are separate decisions; internal and external IPv6 have different routing and lifecycle constraints.

Primary: VPC subnets. Supporting configuration: Create and modify VPC networks.

3. Policy-based routing and route evaluation: how to steer selected traffic to inspection

Domain 2

Why policy-based routes exist

Ordinary destination routing answers “where should packets for this prefix go?” Policy-based routes (PBRs) can additionally match source IP, destination IP, protocol, and selected ingress context so that only matching flows are steered. A common use is appliance insertion: traffic matching a security policy is sent to an internal passthrough Network Load Balancer whose backends are network virtual appliances.

Evaluation order matters

Google first considers special routing paths, then policy-based routes, then subnet routes, Private Service Connect routes for global Google APIs, and finally the most-specific static/dynamic route selection. This is why a PBR can override a conventional destination route for matching traffic. PBRs are evaluated by priority. If multiple matching PBRs share the same highest priority, Google can choose one using an internal algorithm; Google recommends unique priorities to avoid ambiguity. A PBR can also be configured to skip remaining PBR evaluation and continue to normal route selection.

flowchart TD PKT[Packet leaves workload] --> SP{Special routing path?} SP -->|yes| DONE[Use special path] SP -->|no| PBR{Matching highest-priority PBR?} PBR -->|next-hop ILB| ILB[Internal passthrough NLB] ILB --> NVA[Inspection appliances] PBR -->|skip PBR| SUB[Evaluate subnet routes] PBR -->|none| SUB SUB --> PSC[PSC global API route check] PSC --> SD[Most-specific static/dynamic route]

Official routing model: Google Cloud routes.

Applicability and propagation

PBRs can target all VMs, selected VMs by network tag, or traffic entering through VLAN attachments in supported regional/all-region scopes. They are not exchanged through VPC Network Peering. This is important in centralized-security designs: creating a PBR in one VPC does not automatically force peer-VPC traffic through the same appliance path.

Static/dynamic routes still matter

After PBR evaluation, subnet routes take precedence over custom static/dynamic routes for destinations they own. For remaining custom routes, Google applies most-specific destination selection before comparing route type/priority according to its routing model. Special service paths, such as those used by external passthrough load balancers or Google Front Ends, can bypass assumptions based solely on visible VPC route tables.

Failure scenario

An inspection design uses two PBRs with the same priority that both match 10.0.0.0/8 egress. Engineers expect the more specific source expression to win, but PBR tie handling is not longest-prefix routing. Give rules unique priorities and explicitly define bypass traffic. If inspection backends fail, verify internal passthrough NLB health, appliance IP forwarding, symmetric return design, PBR priority, and whether a special routing path is taking precedence.

Remember: PBR is evaluated before subnet/static/dynamic routing and is priority-driven. Use unique priorities and design bypass paths deliberately.

Primary: Routes and routing order.

4. Public Cloud NAT: distributed NAT, ports, NAT44/NAT64, and failure modes

Domain 3

What Public NAT actually is

Public NAT lets workloads without external IPv4 addresses initiate connections to IPv4 destinations on the internet. It can perform NAT44 for IPv4 sources and NAT64 for supported IPv6-only Compute Engine VMs. A Cloud NAT gateway is associated with one VPC, one region, and one Cloud Router, but neither the gateway object nor Cloud Router is a packet-forwarding hop. They provide control-plane configuration; translation is implemented in Google’s distributed data plane. Public NAT does not depend on BGP even though it is managed alongside Cloud Router.

Packet and firewall sequence

For an eligible VM, egress firewall policy is evaluated before NAT. The source is then translated to a NAT external IPv4 address and source port. Response traffic is destination-translated back to the original internal tuple and then evaluated by ingress firewall processing. Public NAT allows responses to connections initiated from inside; it does not permit unsolicited inbound internet sessions simply because a firewall rule would allow them.

sequenceDiagram participant VM as Internal-only VM participant FW as VPC firewall participant NAT as Distributed Public NAT participant NET as Internet server VM->>FW: src 10.10.1.5:42000 FW->>NAT: allowed egress NAT->>NET: src NAT_IP:61023 NET-->>NAT: response to NAT_IP:61023 NAT-->>FW: dst 10.10.1.5:42000 FW-->>VM: allowed established response

Official architecture/specification: Public NAT.

Route dependency and eligibility

Public NAT relies on a local static route whose next hop is the default internet gateway; the normal 0.0.0.0/0 route usually provides it. A VM interface with an external IPv4 address uses Google’s one-to-one NAT for its primary internal IPv4 and is therefore not eligible for Public NAT for that primary address, though alias ranges can still be handled by Public NAT when configured.

Ports and scaling

Cloud NAT maps source ports to NAT IPs. You can use static or dynamic port allocation. Exhaustion appears as connection failures even when routing and firewall policy are correct. Endpoint-Independent Mapping (EIM) is supported for Public NAT but is disabled by default for newly created gateways; it affects whether the same internal source tuple is reused as the same external tuple across multiple destinations. Logging and NAT metrics are essential when diagnosing port pressure.

Network tier changes

Automatically allocated NAT IPs can be Premium or Standard Tier. Changing the tier of automatically allocated NAT IPs releases the current addresses and port allocations and immediately closes existing connections. Treat that as a disruptive change.

Scenario

A large proxy fleet can reach the internet but begins dropping only new connections during traffic spikes. Check NAT port allocation and endpoint counts before adding routes. Increasing VM bandwidth will not fix a port-exhaustion problem. If a VM unexpectedly bypasses Cloud NAT, inspect whether it acquired an external IPv4 address.

Remember: Cloud NAT is distributed; Cloud Router does not forward the packets. Diagnose eligibility, default-internet-gateway routing, NAT IP/port capacity, and firewall sequence separately.

Primary: Public NAT specifications.

5. Private NAT: overlapping-address avoidance, NCC/Hybrid NAT, and NAT64

Domain 2

Use case

Private NAT performs private-to-private translation rather than internet egress. It is useful when VPC spokes, on-premises networks, or other-cloud networks have non-overlapping reachability requirements but you want the source represented by addresses from a dedicated NAT pool. Google supports Private NAT for NCC-spoke connectivity and Hybrid NAT through Cloud Interconnect or Cloud VPN. It is also a tool for IPv6-only VM access to IPv4 private destinations through NAT64.

Architecture

A Private NAT gateway is regional, associated with a VPC and Cloud Router control plane, and requires a subnet with purpose PRIVATE_NAT as the translation pool. As with Public NAT, packets do not traverse Cloud Router or a centralized gateway appliance. Private NAT supports outbound sessions and return traffic but not unsolicited inbound requests. It supports TCP and UDP, not ICMP. Endpoint-Independent Mapping is not supported.

flowchart LR VMA[Source VPC VM 10.1.0.10] --> PN[Private NAT distributed translation] POOL[PRIVATE_NAT subnet 172.31.0.0/24] --> PN PN --> NCC[NCC / Hybrid route] NCC --> DEST[Private destination network] DEST --> NCC --> PN --> VMA

Official figure reference: Private NAT contains NAT44 and NAT64 example topologies.

Route interactions

For NCC Private NAT, the gateway uses NCC subnet and dynamic routes. Hybrid NAT relies on local dynamic routes learned through Interconnect or VPN. Private NAT NAT64 has its own route behavior: destination IPv6 addresses in 64:ff9b::/96 are translated and the embedded IPv4 address is looked up in the IPv4 route table. IPv6 policy-based routes do not override this NAT64 process for those destinations. If the embedded address resolves through VPC peering, the packet is dropped; for internet destinations, use Public NAT64 instead.

Capacity and constraints

Private NAT does not support auto mode VPC networks. The purpose-built Private NAT subnet cannot be resized after creation, though multiple Private NAT subnet ranges can be used. Google documents a maximum of 64,000 simultaneous connections per endpoint. Because the gateway translates all IPv4 ranges of an included subnet rather than an arbitrarily selected single primary/secondary range, subnet-scoping must be planned carefully.

NAT64

Private NAT64 is Preview and currently applies to supported IPv6-only Compute Engine VM instances, not every workload type. DNS64 can synthesize addresses by prepending 64:ff9b::/96 to IPv4 destinations. Private NAT then extracts the final 32 bits, rewrites source and destination, and routes the packet using the IPv4 route table.

Scenario

Two business units attach VPCs to a hub and one requires translated source identities before reaching a shared private service. Private NAT can provide a stable translated pool, but it does not make overlapping destination subnets reachable: Google explicitly requires reachable connected destinations to be non-overlapping. If the business units have true overlap, address architecture or additional translation design is required.

Remember: Private NAT is private-to-private source translation, not a magic overlap solver. The PRIVATE_NAT subnet, route family, protocol support, and NAT64 release stage all matter.

Primary: Private NAT.

6. Cloud CDN: cache keys, cache modes, invalidation, and origin protection

Domain 3

Architecture and request flow

Cloud CDN uses Google’s globally distributed edge points of presence to cache content served through supported external Application Load Balancing backends. On a cache hit, the edge responds without contacting the origin. On a miss, Google retrieves the object from a backend service, backend bucket, or supported external origin, returns it to the client, and may store it according to cache policy. This reduces origin load and latency while keeping the load balancer as the control point for host/path routing.

sequenceDiagram participant C as Client participant E as Google edge cache participant LB as External Application LB participant O as Origin C->>E: GET /asset.js alt cache hit E-->>C: cached object else cache miss E->>LB: request LB->>O: fetch object O-->>LB: response + cache headers LB-->>E: response E-->>C: response and cache object end

Official overview: Cloud CDN documentation.

Cacheability and cache keys

Cache policy decides whether a response is stored and how distinct requests map to cache entries. Query strings, hostnames, headers, cookies, and protocol can influence the key depending on configuration. A poorly chosen key can either fragment the cache into low-hit-rate variants or, worse, mix responses that should be isolated. Signed URLs/cookies can protect time-limited private content while still using edge caching.

Origins

Cloud CDN supports managed instance groups, network endpoint groups, Cloud Storage backend buckets, Cloud Run through supported load-balancer integrations, and internet/external backends. With a Cloud Storage backend bucket, enabling Cloud CDN gives you controls such as cache modes, invalidation, signed URLs, and caching of larger objects beyond basic Cloud Storage cache behavior.

Invalidation is exceptional, not routine

Invalidation requests are rate limited to 500 per minute and generally take effect in about 10 seconds. Path patterns must begin with /, cannot contain ? or #, and can use * only as a final character. Invalidating /picture* is a prefix operation and can match more objects than an operator expects. Query-string variants cannot be selectively invalidated using a query in the path matcher. Google recommends versioned URLs or appropriate TTLs for normal releases instead of repeated invalidation.

Cache tags

Cache tags let an origin label cached objects with metadata in the Cache-Tag header. An invalidation can match up to ten tags using OR semantics. This is useful for invalidating a release group or content category without knowing each URL. Invalidating too broadly can create an origin thundering herd.

Scenario

After a bad deployment, operators invalidate /* before fixing the origin. The cache refills with the same broken content. Correct workflow: fix and verify the origin first, then invalidate only affected paths/tags. For a Shared VPC cross-project frontend, remember that invalidation belongs to the frontend project that owns the forwarding rule, target proxy, and URL map; backend-service administrators might not have permission.

Remember: optimize cache keys/TTLs first; use invalidation as an exception. Invalidation does not clear browser or third-party ISP caches.

Primary: Cloud CDN docs. Supporting: Cache invalidation overview; Backend bucket setup.

7. Cross-Cloud Interconnect: dedicated multicloud connectivity and the shared-responsibility boundary

Domain 4

What it solves

Cross-Cloud Interconnect (CCI) creates high-bandwidth dedicated connectivity between Google Cloud and supported cloud providers. Instead of building a router in a colocation facility or stitching multiple third-party contracts, Google provisions a physical connection between Google’s network and the remote cloud provider. Supported providers currently include AWS, Microsoft Azure, OCI, and Alibaba Cloud; Partner Cross-Cloud Interconnect options also exist for certain providers.

Control plane and data plane

On the Google side, a VLAN attachment connects the physical CCI connection to a Cloud Router in a region, and BGP exchanges routes with the remote-cloud routing domain. The attachment is regional and indirectly tied to one VPC through its Cloud Router. Data then crosses the dedicated physical interconnection into the other cloud’s network. The remote provider’s routing constructs and limits remain part of the design.

flowchart LR VPC[Google VPC] --> VA[VLAN attachment] VA --> CR[Cloud Router BGP] VA --> CCI[Cross-Cloud Interconnect physical port] CCI --> RCP[Remote cloud edge] RCP --> RNET[Remote cloud VPC/VNet] CR <-. route exchange .-> RCP

Official figures: CCI overview includes configuration, physical support-boundary, and SLA topology diagrams.

Capacity, MTU, encryption

Google documents 10/100/400-Gbps CCI sizes for AWS and OCI and 10/100-Gbps for Azure and Alibaba Cloud. Jumbo MTUs can be configured, but the remote provider must support the selected MTU as well. MACsec can encrypt supported Cloud Interconnect physical links; application-level or tunnel encryption might still be required depending on trust requirements.

SLA design

CCI follows the Cloud Interconnect SLA for Google’s portion of the service. A production non-critical 99.9% design uses at least primary and redundant connections in different edge availability domains. A 99.99% design requires stronger redundancy; Google documents both multi-region and single-region patterns. Importantly, the SLA and Google support boundary end where traffic is transferred to the remote cloud provider. Google cannot guarantee the remote provider’s uptime.

NCC site-to-site role

CCI can participate in NCC site-to-site data transfer. For example, separate CCI pairs to Azure and AWS can be represented as hybrid connectivity resources and NCC can use Google’s backbone as WAN transit between those external sites, subject to supported locations and topology. That is distinct from simply giving a Google VPC access to both clouds.

Scenario

A company needs 99.99% Google-side CCI connectivity to AWS but buys one physical port in one metro. Route redundancy on the AWS side cannot compensate for the missing Google edge availability-domain redundancy. Validate both providers’ port topology, BGP sessions, VLAN attachment region, MTU, MACsec support, and support ownership before production cutover.

Remember: CCI is a physical multicloud interconnect with a shared support boundary. Redundancy must be engineered on both cloud-provider sides.

Primary: Cross-Cloud Interconnect overview.

8. Cross-Site Interconnect: using Google’s network to connect on-premises sites without a VPC in the data path

Domain 4

Concept

Cross-Site Interconnect is a Cloud Interconnect family service for private connectivity between external sites through Google’s network. Unlike ordinary Dedicated Interconnect, whose central purpose is extending an on-premises network into a Google Cloud VPC region via VLAN attachments, Cross-Site Interconnect creates a cross-site network and wires that connect supported Google edge locations so external sites can exchange traffic.

Provisioning sequence

Provisioning begins by checking bandwidth quotas and per-wire limits, ordering Cross-Site Interconnect connections, receiving LOA-CFAs, and having the colocation provider establish the physical cross-connects to Google. Google tests optical light levels. After the connections are ready, you create a cross-site network and define the wire or wire groups, including bandwidth. You then configure the on-premises routers to establish site-to-site connectivity over that wire.

flowchart LR SITEA[On-prem Site A router] --> COLOA[Colocation / Google Edge PoP A] COLOA -->|Cross-Site network wire| GNET[Google backbone] GNET --> COLOB[Colocation / Google Edge PoP B] COLOB --> SITEB[On-prem Site B router] LOA[LOA-CFA + facility cross-connects] -. provisioning .-> COLOA LOA -. provisioning .-> COLOB

Official references: Provisioning overview and supported locations.

Location constraints

Cross-Site connections must physically meet Google at supported colocation facilities. Google currently lists dozens of locations across APAC, Europe, and North America. A key design constraint is that you cannot create a cross-site network between connections in the same metro; the location metadata identifies which metros can be connected, including supported intercontinental pairs.

Difference from NCC site-to-site data transfer

FeatureCross-Site InterconnectNCC site-to-site data transfer
Primary building blockCross-site connections and wires between Google edge locationsHybrid spokes built from VPN/Interconnect/other supported connectivity
Typical purposePrivate site-to-site transport over Google backboneUse Google as WAN across attached external sites and cloud resources
VPC dependencyNot the same VPC-extension model as VLAN attachment connectivityOrchestrated by an NCC hub and spokes

Operational scenario

A company orders ports in two facilities that are both in the same metro and expects to create a cross-site circuit. The location constraint prevents that design. Verify CrossSiteInterconnectInfos for each candidate location before ordering physical circuits, and validate facility/provider lead times because LOA-CFA provisioning is a real physical dependency.

Remember: Cross-Site Interconnect is physical WAN transport between external sites over Google’s network; location pairing and facility provisioning are first-class design constraints.

9. VPC Flow Logs: sampling, aggregation, metadata, organization scope, and evidence quality

Domain 5

What Flow Logs provide

VPC Flow Logs record sampled network-flow metadata for supported Google Cloud network attachment points. They are useful for traffic baselining, incident investigation, cost analysis, forensics, and troubleshooting, but they are not packet captures. A flow record summarizes observed traffic and can include VM, VPC, geographic, and other metadata; byte and packet counts are estimates based on sampling.

Configuration model

Google now recommends Network Management API VPC Flow Logs configurations. You can scope configurations to subnets, VPC networks, VLAN attachments, Cloud VPN tunnels, or at organization level depending on the workflow. A custom configuration controls aggregation interval, a filter expression, secondary sampling rate, and metadata inclusion. Organization-level logging can add cross-project annotations for Shared VPC, VPC Peering, and NCC flows.

flowchart LR TRAFFIC[Packets / flows] --> PS[Primary sampling - managed by Google] PS --> AGG[Aggregation interval] AGG --> SS[Secondary sampling] SS --> FILT[Filter expression] FILT --> META[Metadata enrichment] META --> LOG[Cloud Logging] LOG --> ANALYSIS[Flow Analyzer / SIEM / BigQuery export]

Official configuration guide: Configure VPC Flow Logs.

Aggregation and sampling

Network Management API configurations support intervals from 5 seconds through 15 minutes. The secondary sampling rate can be greater than 0 through 1.0. Reducing sampling and increasing aggregation lowers log volume and cost but reduces forensic granularity. Because counts are estimated from sampled packets, short-lived flows and low-volume anomalies require careful interpretation; aggregate evidence over longer periods when accuracy matters.

Metadata and filters

Metadata can be included in full, excluded, or selected. Filter expressions can suppress irrelevant records before they are written. This matters economically: logging every flow with full metadata in a high-throughput environment can be expensive. However, aggressive filters can also remove the very evidence needed during an incident. Define security-critical flows separately from cost-optimized operational telemetry.

Validated CLI pattern

gcloud network-management vpc-flow-logs-configs create CONFIG_NAME \
  --location=global \
  --subnet=projects/PROJECT_ID/regions/REGION/subnetworks/SUBNET \
  --aggregation-interval=interval-5-sec \
  --flow-sampling=1.0 \
  --metadata=include-all-metadata

Scenario

An investigator sees 2 GB in a sampled flow record and assumes an exact packet count. That is unsafe: reported bytes and packets can be estimated. Correlate multiple flow records, application logs, load-balancer/NAT logs, and if payload evidence is required use Packet Mirroring or another capture mechanism. For cross-project paths, confirm whether cross-project annotations were enabled at organization scope.

Remember: Flow Logs answer “who talked to whom, approximately how much, and with what metadata?” They do not preserve payloads.

Primary: Configure VPC Flow Logs. Supporting: Flow Log record fields.

10. Packet Mirroring with Network Security Integration: out-of-band full-packet inspection

Domain 5

Why it is different from Flow Logs

Packet Mirroring clones full packets, including headers and payload, and sends the copies to collector appliances for analysis. The original workload traffic continues on its normal path, so the inspection is out-of-band: a collector failure does not inherently block the production flow. This makes mirroring well suited to IDS/NDR, packet forensics, and performance analysis where flow summaries are insufficient.

Modern Network Security Integration architecture

In the Network Security Integration out-of-band model, mirroring rules live in a global network firewall policy. Rules can match source/destination, protocol, ports, direction, and use DO_NOT_MIRROR negative filtering. Matching packets are encapsulated with GENEVE, preserving the original packet and adding metadata including a VPC network identifier so collectors can distinguish overlapping address spaces. Mirroring endpoint groups let a security team centralize collector service deployments for multiple producer networks.

flowchart LR VM[Workload VM / GKE node] -->|original traffic continues| DST[Original destination] VM --> RULE[Mirroring rule in network firewall policy] RULE -->|clone packet| GEN[GENEVE encapsulation UDP 6081] GEN --> MEG[Mirroring endpoint group] MEG --> ILB[Internal passthrough NLB] ILB --> COL[Collector / IDS / NDR appliances]

Official architecture: Out-of-band integration overview.

Collector and firewall requirements

The producer side needs ingress permission for GENEVE UDP 6081 from the producer subnet gateway/local range and health-check probes to the collector internal passthrough Network Load Balancer. The collector load balancer is marked as a mirroring collector; non-mirrored traffic sent to it is dropped. Do not place producer and consumer in the same VPC because that can create a mirroring loop.

Zones, cost, and GKE

Packet Mirroring is zonal with regional deployment patterns. Cross-zone mirroring is supported but incurs cross-zone traffic charges and can add failure dependency; Google recommends same-zone producer deployments when practical. To see traffic between Pods on the same GKE node, enable Intranode Visibility, because such traffic otherwise might never traverse the VPC interface in a way the mirroring service can observe.

Session behavior

Mirroring rules are session-oriented based on the initiator. When a session is selected, both directions of the session are mirrored. Firewall Rules Logging does not log the mirrored copies themselves; it logs the original traffic according to normal firewall behavior.

Scenario

A SOC expects mirrored packets from two VPCs with overlapping 10.0.0.0/8 addresses and cannot tell them apart in the collector. In the NSI architecture, the GENEVE metadata’s VPC identifier solves this ambiguity—provided the collector decodes it. If no packets arrive, check mirroring rule match, endpoint group association, GENEVE UDP 6081 firewall, collector ILB health, and zone placement.

Remember: Flow Logs are metadata; Packet Mirroring is cloned packet content. Modern out-of-band integration uses GENEVE and centralized endpoint groups.

Primary: Out-of-band Packet Mirroring integration. Supporting: Mirroring endpoint groups.

11. VPC Service Controls: service perimeters, ingress/egress rules, dry run, and data-exfiltration defense

Domain 6

Security boundary

VPC Service Controls (VPC SC) protects supported multi-tenant Google services by creating service-level perimeters around projects/resources. It is designed primarily to reduce data-exfiltration risk—for example, a compromised credential attempting to copy protected Cloud Storage or BigQuery data to a resource outside the trusted perimeter. It complements IAM rather than replacing it: IAM answers whether an identity may perform an action; VPC SC additionally evaluates whether the action crosses an allowed perimeter boundary.

Ingress and egress model

An ingress rule permits a client outside a perimeter to access protected resources inside it under defined identity/source/service conditions. An egress rule permits a caller/resource inside the perimeter to access resources outside it. A request that crosses a boundary without a matching rule is denied even if IAM allows the underlying API operation. Access levels can incorporate public source IP, identity, or device trust where supported.

flowchart LR EXT[External client] --> IR{Ingress rule / access level} IR -->|allowed| PER[Service perimeter] IR -->|no match| DENY1[Denied + audit log violation] PER --> DATA[Protected Google service/resource] DATA --> ER{Egress rule} ER -->|allowed| OUT[External resource/service] ER -->|no match| DENY2[Denied + audit log violation]

Official architecture/guides: VPC Service Controls docs.

Dry run before enforcement

Dry-run configuration is a core deployment practice. It lets teams observe which legitimate workflows would violate the proposed perimeter before enforcement blocks production. The output can inform ingress/egress rules and access levels. Do not create broad identity allowlists simply to eliminate every dry-run alert; an identity allowlisted at the perimeter can gain access from any network unless you constrain it appropriately.

Access-level caveats

IP-based access levels use public IP CIDRs. When traffic is routed internally within Google, audit metadata can redact the caller as gce-internal-ip, so internal workflows often need ingress rules based on project/service account or other attributes rather than an external-IP allowlist. Device-based trust depends on supported Chrome Enterprise Premium context.

Troubleshooting

Audit logs identify ingress and egress violations, the perimeter involved, and target/source resource context. An ingress violation means an outside client attempted protected access without a matching ingress path. An egress violation can mean a protected caller reached outside or a single API operation tried to move data between an inside and outside resource. Fix the narrow policy condition rather than disabling the perimeter.

Scenario

A storage copy from a protected bucket to a bucket in an unprotected project fails even though the service account has Storage Admin on both. That is expected if the operation crosses the perimeter without an egress rule. IAM success does not override VPC SC. Use dry run to model the workflow, then add only the necessary egress target/service/method/identity condition.

Remember: VPC SC is a service/API data boundary layered on top of IAM and network controls. Dry run plus audit-log-driven rule design is the safe rollout pattern.

12. Secure Web Proxy: identity-aware egress, TLS inspection, explicit/PSC/next-hop deployment

Domain 6

Purpose and default posture

Secure Web Proxy (SWP) is a managed outbound HTTP/HTTPS security service. It provides a mandatory checkpoint for web egress and starts from a default deny-all posture. Security policy is modular and reusable: administrators can separate gateway instances from policies, URL lists, and identity conditions, allowing central security teams to enforce consistent egress rules without maintaining proxy VMs.

How a request is processed

Clients send web traffic to SWP using the selected deployment mode. The proxy identifies the source using attributes such as secure tags, service accounts, IP addresses, or verified client-certificate identities. It evaluates gateway security and authorization policy. For HTTP—or HTTPS when TLS inspection is enabled—it can evaluate hostname/URL, methods, headers, and other request attributes. If allowed, SWP creates the outbound connection; Google documentation notes that internet egress typically uses Cloud NAT and external name resolution uses Cloud DNS.

TLS inspection and identity

TLS inspection allows SWP to decrypt, inspect, and re-encrypt HTTPS so policies can evaluate URL/request details. Certificate Authority Service participates in issuing the interception certificates; clients must trust the configured CA chain. Frontend mTLS can provide cryptographically verified client identities for authorization policy. Without TLS inspection, encrypted payload and URL-level fields inside TLS cannot be evaluated the same way.

Current limitations and scope

Google currently documents IPv4-only support: IPv6 is not supported. HTTP/0.9, 1.0, 1.1, and 2.0 are supported, but HTTP/3 is not. SWP can be deployed only in a host project, not a Shared VPC service project. Global access can let clients in other Google Cloud regions connect to a proxy instance when enabled.

Scenario

A new IPv6-only workload is routed to SWP and cannot establish egress. The failure is architectural, not a missing allow rule: SWP currently supports IPv4 only. For supported IPv4 clients that are denied, verify source identity resolution, policy priority/match, TLS-inspection trust, DNS resolution, Cloud NAT capacity, and proxy transaction logs.

Remember: SWP is identity-aware managed web egress, not a generic L3/L4 firewall. Deployment mode, TLS inspection, client trust, and IPv4-only support are essential design details.

Expert memory anchors

  • Premium Tier keeps internet traffic on Google’s backbone for more of the path; Standard Tier is regional/cost optimized.
  • IPv6-capable subnets require custom mode VPC; internal versus external IPv6 access type is not freely changeable later.
  • Policy-based routes are evaluated before subnet/static/dynamic route selection and should use unique priorities.
  • Cloud NAT is a distributed data-plane function; Cloud Router is control plane and BGP is not required for NAT itself.
  • Private NAT cannot make overlapping destination subnets magically routable.
  • Cloud CDN invalidation is an exception; fix the origin first and prefer versioning/TTL design.
  • Cross-Cloud Interconnect’s SLA/support boundary covers Google’s side up to the remote cloud handoff.
  • Cross-Site Interconnect is physical site-to-site WAN transport and has metro-pair location constraints.
  • VPC Flow Logs are sampled metadata, not packet captures.
  • Packet Mirroring clones full packets out of band and modern NSI uses GENEVE metadata.
  • VPC Service Controls complements IAM by enforcing service-perimeter boundaries.
  • Secure Web Proxy is default-deny web egress and currently supports IPv4, not IPv6 or HTTP/3.
