1. NCC propagation of global Google APIs

Domain 1 — Design

Problem and architecture

Network Connectivity Center (NCC) announced Preview support on September 10, 2026 for propagation of global Google APIs. This matters when a hub-and-spoke design needs deliberate reachability to Google API endpoints rather than treating API access as an unrelated local-network concern. The NCC hub remains the control-plane coordination point; spokes participate according to supported propagation behavior and quota.

Control plane and data plane

The control plane distributes eligible endpoint reachability. A workload then follows the effective VPC route selected for the resolved Google API destination. DNS selection and route propagation are separate: propagating a route cannot force an application to resolve a different endpoint class.

flowchart LR API[Global Google API endpoint] --> H[NCC hub propagation] H --> S1[Spoke A] H --> S2[Spoke B] S1 --> W[Workload]

Choices, caveats, operations

The feature is Preview and introduces a quota for propagated global Google APIs. Inventory endpoints and quotas before enabling it. Verify effective routes, DNS answers, spoke policy and security controls. A strong failure scenario is correct propagation paired with DNS resolution to an endpoint not covered by the intended path.

Takeaway: API endpoint selection, NCC propagation and packet forwarding are three separate checks.

Primary: https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/release-notes

2. NCC IPv6 include/exclude filters for hybrid spokes

Domain 4 — Hybrid

Architecture and behavior

As of August 31, 2026, IPv6 dynamic routes are supported in Preview for include and exclude spoke filters on hybrid spokes. Export filters govern what a spoke contributes to the hub; import filters govern what a spoke accepts from the hub. This is route-distribution policy, not a replacement for packet security policy.

Design and failure domains

Model IPv4 and IPv6 independently. A dual-stack design can be healthy for IPv4 while IPv6 is asymmetric because one side exports a prefix that the other side excludes. Apply explicit filters close to the propagation boundary and document intent so later prefix additions do not silently widen reachability.

flowchart LR A[Hybrid spoke A] -->|export filter| H[NCC hub] H -->|import filter| B[Hybrid spoke B] B -->|return IPv6 route| H

Operations

Compare advertised, accepted and effective routes on both sides. Check address family, prefix match and filter order before blaming BGP. Preserve a route-policy matrix for each spoke.

Takeaway: route admission must be symmetric enough for the intended flow, and IPv4 success does not validate IPv6.

Primary: https://docs.cloud.google.com/network-connectivity/docs/network-connectivity-center/release-notes

3. Cloud Router BFD on Interconnect

Domain 4 — Hybrid

Problem and packet behavior

Bidirectional Forwarding Detection (BFD) detects forwarding-path failure faster than relying only on BGP hold timers. It is valuable when a path fails while the BGP TCP session would otherwise remain established long enough to delay convergence.

Prerequisites and choices

Google documents BFD for provisioned Interconnect VLAN attachments using Dataplane version 2. Verify dataplaneVersion before designing around BFD. BFD peers exchange rapid control packets; expiration drives routing-session failure and withdrawal, after which alternate-route selection still determines recovery.

sequenceDiagram participant C as Customer router participant G as Cloud Router C->>G: BFD control G->>C: BFD control Note over C,G: forwarding failure G--xC: detection timer expires G->>G: BGP path removed / alternate selected

Operations and caveats

Fast detection is not the same as fast application recovery. Measure alternate-path availability, ECMP behavior, remote convergence and application retries. Confirm BFD state on both peers and avoid aggressive timers unsupported by the peer.

Primary: https://docs.cloud.google.com/network-connectivity/docs/router/how-to/configuring-bfd

4. Partner Interconnect VLAN attachment lifecycle

Domain 4 — Hybrid

Architecture

Partner Interconnect separates Google-side VLAN attachment creation from service-provider provisioning. A pairing key identifies the intended attachment to the provider. Production designs normally use a redundant pair so one attachment can carry traffic when its partner is unavailable.

Control plane and configuration

The attachment is regional and associates with a Cloud Router in the same VPC network and region. Google can create the router interface and BGP peer as part of the workflow. IP stack, BGP addresses, MTU, activation state and provider handoff all affect readiness. Optional MD5 authentication, custom learned routes and BFD are later controls where supported.

flowchart LR V[VPC] --> CR[Cloud Router] CR --> VA[VLAN attachment] VA --> P[Partner network] P --> CE[Customer edge]

Troubleshooting

A pairing key is not proof of service. Check attachment state, provider provisioning, BGP state, learned routes, MTU and then application traffic. Redundancy should span the required failure domains, not merely create two logical objects on one fragile path.

Primary: https://docs.cloud.google.com/network-connectivity/docs/interconnect/how-to/partner/creating-vlan-attachments

5. Cloud VPN MTU and TCP MSS engineering

Domain 4 — Hybrid

Problem

IPsec encapsulation consumes bytes that applications otherwise expect to use for payload. This creates a characteristic failure: BGP and small probes work while large transfers stall, fragment or perform badly. MTU therefore belongs in hybrid design, not only incident response.

Packet flow

An endpoint emits an IP packet; the VPN path adds encapsulation; the resulting outer packet must fit the path. Path MTU Discovery depends on usable ICMP feedback. TCP MSS controls TCP segment sizing, but it does not solve oversized UDP or other non-TCP payloads.

flowchart LR H1[Host packet] --> V[VPN encapsulation adds overhead] V --> P{Fits path MTU?} P -->|yes| H2[Remote host] P -->|no| F[fragment/drop/PMTUD response]

Operations

Test with packet sizes and DF behavior, inspect ICMP filtering, verify endpoint MTU and MSS policy, and compare TCP with UDP. Do not change routing when the symptom is payload-size dependent.

Primary: https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/mtu-considerations

6. Cloud DNS forwarding zones

Domain 3 — Managed services

Problem and architecture

Forwarding zones let Cloud DNS send queries for selected namespaces to alternative DNS servers, commonly authoritative or recursive infrastructure on-premises. This preserves namespace ownership while giving Google Cloud workloads integrated resolution.

Control/data path

DNS resolution selects the forwarding zone, then Cloud DNS reaches the configured forwarding target over a supported network path. The query and response path must both work. A VM being able to query the same server does not prove the Cloud DNS forwarding path is valid because the source and routing context differ.

sequenceDiagram participant VM participant DNS as Cloud DNS participant ON as On-prem DNS VM->>DNS: query corp.example DNS->>ON: forwarded query ON-->>DNS: answer DNS-->>VM: answer

Troubleshooting

Confirm zone selection and suffix, target reachability, return routing and firewall policy. Use query logs and compare expected versus actual response codes. Separate DNS success from transport reachability to the returned address.

Primary: https://docs.cloud.google.com/dns/docs/zones/forwarding-zones

7. Private Service Connect consumer controls

Domain 1 — Design

Architecture

Private Service Connect (PSC) exposes a producer service through a private consumer endpoint without merging VPC routing domains. Because the model is service-oriented rather than peering-oriented, consumer and producer address spaces can overlap in supported designs.

Connection lifecycle and security

The producer publishes through a service attachment; the consumer creates an endpoint represented by a forwarding rule. Producer connection preference and accept/reject controls determine whether a consumer connection becomes usable. Producer-side NAT separates consumer addressing from backend service addressing.

flowchart LR C[Consumer workload] --> E[PSC endpoint] E --> SA[Service attachment] SA --> NAT[Producer NAT] NAT --> B[Producer backend]

Operations

Check endpoint/connection status before routes and firewalls. Verify NAT capacity, acceptance policy, service attachment health and backend reachability. PSC deliberately avoids creating generic transitive connectivity between networks.

Primary: https://docs.cloud.google.com/vpc/docs/private-service-connect

8. VPC dynamic routing mode and regional route visibility

Domain 2 — Implement VPC

Architecture

A VPC network is global, but Cloud Router is regional. Dynamic routing mode controls where learned dynamic routes are applicable. Regional mode keeps dynamic route applicability regional; global mode allows eligible learned routes to be used across regions in the VPC.

Design behavior

This distinction matters when adding a new region to an existing hybrid design. Cloud-local subnet reachability can work while on-premises reachability fails because the dynamic prefixes are not applicable in the new region under the selected mode.

flowchart LR ON[On-prem] --> CR[Cloud Router region A] CR --> RA[Subnet region A] CR -. global dynamic routing .-> RB[Subnet region B]

Operations

Inspect VPC dynamic routing mode and effective routes in the failing region before rebuilding tunnels. Also inspect route priority, advertisements and overlapping prefixes. Global routing expands failure and propagation scope, so choose it intentionally.

Primary: https://docs.cloud.google.com/network-connectivity/docs/router/concepts/overview

9. IPv6 load-balancer frontend design

Domain 3 — Managed services

Architecture

Supported Google Cloud load balancers can present IPv6 frontends while proxy-based products can use a separate backend connection. This makes the load balancer a useful protocol boundary during staged IPv6 adoption.

Packet behavior

For proxy load balancing, the client TCP/TLS connection terminates at Google's proxy and a new connection is made toward the backend. Therefore an IPv6 client does not imply an IPv6 backend flow. Passthrough products have different semantics, so validate the exact load-balancer family.

flowchart LR C[IPv6 client] --> VIP[IPv6 frontend] VIP --> P[Google proxy] P -->|separate backend connection| B[Backend]

Design and troubleshooting

Publish AAAA only after frontend, firewall, health and client path are ready. Test IPv4 and IPv6 independently and avoid assuming DNS preference is identical across clients. Check product-specific scope and backend support.

Primary: https://docs.cloud.google.com/load-balancing/docs/ipv6

10. Cloud Armor rate limiting

Domain 6 — Security

Problem and policy

Cloud Armor rate limiting protects HTTP(S) applications from abusive request volume. It complements backend autoscaling and application authentication; it is not a substitute for either. Rate controls are evaluated as part of security policy processing, so rule priority determines whether the intended limiter is reached.

Design choices

Throttle-style behavior and rate-based bans have different user impact. Choose a key that represents the population you actually want to constrain. Source-IP-only designs can aggregate many legitimate users behind carrier, enterprise or cloud NAT.

flowchart LR R[Requests] --> P[Cloud Armor policy] P --> K[Rate key/counter] K -->|within threshold| A[Allow] K -->|exceeded| L[Throttle or ban action]

Operations

Roll out with observability, inspect matched-rule logs and test realistic shared-source patterns. A sudden rise in blocks can be a policy-key mistake rather than an attack. Keep rate limiting distinct from DDoS infrastructure protection and WAF signatures.

Primary: https://docs.cloud.google.com/armor/docs/rate-limiting-overview

11. Cloud DNS query logging as a troubleshooting instrument

Domain 5 — Operations

Why it matters

DNS failures are often view-dependent: two clients can ask the same name and receive different behavior because of network association, zone type, policy or forwarding. Query logging provides evidence about what was actually requested and answered near the failure timestamp.

Workflow

Start with the application's timestamp and queried name. Confirm the returned response and address, then troubleshoot the transport path to that exact address. This prevents engineers from testing the IP they expected DNS to return rather than the one the client actually used.

flowchart LR APP[Application error] --> LOG[DNS query log] LOG --> ANS[Actual answer] ANS --> ROUTE[Route/firewall test to returned IP] ROUTE --> FIX[Root cause]

Operations and caveats

Logging has cost and data-governance implications, so enable it deliberately and retain only what policy requires. Correlate DNS evidence with VPC Flow Logs, application logs and Connectivity Tests where appropriate. A successful DNS response does not prove the destination is reachable.

Primary: https://docs.cloud.google.com/dns/docs/monitoring

12. Hierarchical firewall policy delegation with goto_next

Domain 6 — Security

Architecture

Hierarchical firewall policies let organization and folder administrators establish controls above project and VPC policy layers. The goto_next action is explicit delegation: it tells evaluation to continue to a lower policy layer instead of making an immediate allow or deny decision.

Evaluation behavior

Rules are evaluated according to hierarchy and priority. A central team can deny prohibited traffic, allow mandatory shared services, and use goto_next where application teams are permitted to decide. Treating goto_next as an allow is a serious mental-model error.

flowchart TD O[Organization policy] -->|goto_next| F[Folder policy] F -->|goto_next| V[VPC policy/rules] V --> D{Final allow/deny}

Operations

When a flow is unexpectedly denied, reconstruct the complete hierarchy and priorities rather than inspecting only the VPC rule list. Logging and policy association are essential. Document which layer owns each decision so delegated rules do not become accidental security gaps.

Primary: https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-details
