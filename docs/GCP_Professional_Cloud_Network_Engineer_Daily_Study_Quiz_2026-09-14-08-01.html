1. VPC firewall statefulness and connection tracking

Domain 6 — network security

What problem this solves

Google Cloud VPC firewall rules provide distributed, stateful packet filtering at VM interfaces. The important word is stateful: after a permitted initiating flow is tracked, matching return traffic is allowed without requiring a separate reverse-direction allow rule. This is different from a purely stateless ACL design and affects how you interpret both ingress and egress policy.

Connection tracking behavior

A tracked response must match the original 5-tuple in reverse: source and destination IPs, source and destination ports, and protocol. Google tracks IPv4 TCP, UDP, SCTP, and ICMP and corresponding IPv6 protocols including ICMPv6. Tracking is maintained even for protocols that are not connection-oriented. The connection state is considered active when traffic continues within the documented activity window; when state expires, later packets are evaluated as new traffic.

Fragmentation is a classic caveat. Firewall processing does not reassemble fragmented TCP packets. A protocol-specific TCP rule can match the first fragment because it contains the transport header, while later fragments lack it. Connection tracking also allows only the first fragment of return fragmented traffic automatically, so additional explicit rules can be required for subsequent fragments.

Scale and limits

Tracked-connection capacity depends on VM machine type. Shared-core machines support 130,000 tracked connections; machines with 1–8 vCPUs support 130,000 per vCPU; machines above 8 vCPUs cap at 1,040,000 tracked connections. When capacity is exceeded, the longest-idle entries are displaced first so newer connections can be tracked. High-connection-rate middleboxes and large proxies therefore need both CPU sizing and connection-table sizing considered together.

Teaching diagram — stateful return path
flowchart LR C[Client 10.1.1.10:50000] -->|TCP SYN to 443| FW[VPC firewall ingress allow] FW --> VM[VM 10.2.0.20:443] VM -->|TCP SYN-ACK reverse 5-tuple| CT[Connection tracking] CT -->|Automatically allowed while state active| C

Notice that the return packet is authorized by connection state, not by requiring a second mirror-image ingress rule.

Failure scenario and troubleshooting

If a long-idle application resumes and packets suddenly fail, do not assume the original allow rule disappeared. Verify whether the connection state expired, whether a new flow now needs policy evaluation, whether fragmentation is present, and whether connection-table pressure is evicting idle entries. For asymmetric appliance designs, remember that firewall state is tied to the VM interface processing path; unusual forwarding can produce behavior that looks like a routing issue but is really state tracking.

Exam memory: VPC firewall rules are distributed and stateful; return traffic for a tracked flow is allowed, but fragmentation and connection-table limits remain material.

2. Private Service Connect service connection policies

Domain 1 — design managed-service connectivity

Purpose and architecture

A service connection policy authorizes a supported managed service to create Private Service Connect endpoints automatically in a consumer VPC. Instead of an application team manually creating an endpoint from a service attachment, the policy defines the service class, consumer VPC, subnet used for endpoint addresses, and the maximum number of service connections. This is particularly useful for services such as AlloyDB that can automate endpoint lifecycle.

Control plane versus data plane

The policy itself is control-plane authorization. It does not forward packets. When the managed producer provisions an endpoint under that authorization, the resulting PSC endpoint is a consumer-side internal forwarding rule and address. Client data-plane traffic then targets that private address and is carried through PSC to the managed producer service. The endpoint subnet therefore needs sufficient usable address capacity for automated growth.

Trust boundary and lifecycle

The policy delegates a constrained action to a service class rather than broadly allowing arbitrary producers to create resources. Capacity limits are a safety control: if the configured connection limit is reached, new automated endpoints cannot be provisioned until capacity is increased or old endpoints are removed. DNS should normally abstract endpoint addresses so clients do not hard-code specific endpoint IPs.

Teaching diagram — automated endpoint creation
flowchart LR ADMIN[Consumer network admin] --> SCP[Service connection policy] SCP -->|authorizes service class + subnet + limit| SVC[Managed service control plane] SVC -->|creates| EP[PSC endpoint in consumer subnet] APP[Consumer workload] -->|private IP / DNS| EP EP --> PSC[PSC data plane] PSC --> PROD[Managed producer service]

The dashed conceptual distinction is authorization first, packet forwarding second: the policy creates permission for endpoint lifecycle; the endpoint carries traffic.

Failure scenario and verification

If a database instance exists but no endpoint is created, check the policy's network, service class, subnet, IAM, and connection limit before troubleshooting application routing. If the endpoint exists but remains unusable, move down the stack: endpoint status, DNS record, client firewall policy, producer acceptance/state, and application health.

Exam memory: a service connection policy is not a route and not a service attachment; it is consumer-side authorization for a supported service class to create PSC connections.

3. Network Connectivity Center producer VPC spokes

Domain 2 — NCC implementation

Why producer spokes exist

Private services access and certain producer-managed VPC peering relationships traditionally expose managed-service routes only to the directly peered consumer VPC. An NCC producer VPC spoke lets supported producer-service subnet routes participate in an NCC hub so other attached VPC spokes can reach those managed services without building pairwise service peering from every VPC.

Architecture and prerequisites

You do not specify the inaccessible Google-owned producer VPC directly. You identify your consumer VPC spoke and the existing peering connection between that consumer VPC and the producer. For most supported services, the peering name is servicenetworking-googleapis-com; Google Cloud NetApp Volumes uses its own sn-netapp-* peering naming. The peering must already be active. The producer spoke resource lives in your project even though the actual producer network is service-owned.

Supported services include several private-services-access products such as AlloyDB, Cloud SQL, Filestore, Memorystore, Apigee, Looker, Cloud Build, Managed Lustre, NetApp Volumes, and Vertex AI. Producer VPC spokes are not a general mechanism for arbitrary third-party peer networks.

Propagation and filtering

The value of a producer spoke is route propagation through the NCC topology. Include and exclude export ranges can control which producer subnet prefixes are shared through the hub. In a star topology, the producer spoke and its corresponding consumer VPC spoke must be placed in the same group. The topology still determines which spoke groups can communicate; adding a producer spoke does not magically make every resource transitive.

Teaching diagram — producer route reachability
flowchart LR P[Google service producer VPC] <-->|existing PSA peering| C[Consumer VPC spoke] C --> H[NCC hub] P -. producer VPC spoke represents peering .-> H H --> A[Application VPC spoke A] H --> B[Application VPC spoke B] A -->|service subnet route| P B -->|service subnet route| P

Notice that the producer VPC remains Google-owned. NCC is given a spoke representation of the existing producer peering, not ownership of that VPC.

Failure scenario

If an application VPC reaches other NCC spokes but not Cloud SQL private IPs, confirm that the service is supported, the original consumer-to-producer peering is active, the producer exports only compatible subnet routes, the producer spoke references the correct peering, and export filters are not hiding the managed-service range.

Exam memory: producer spokes extend supported producer subnet routes into NCC; they depend on an existing supported producer peering and are not for arbitrary third-party services.

Primary: Supported services for producer VPC spokes. CLI: gcloud producer VPC spoke create.

4. Cloud DNS cross-project binding

Domains 1 & 3 — DNS architecture

Problem solved

Shared VPC separates network ownership from workload ownership. Without cross-project binding, DNS administration often collapses back into the host project or requires DNS peering and placeholder networks. Cross-project binding lets a service project own a private DNS zone while binding that zone directly to the Shared VPC network owned by the host project.

Ownership and resolution behavior

The service project owns and administers the zone and records; the host project owns the network. IAM stays at project boundaries, so application teams can receive DNS permissions in their service project without becoming Shared VPC network administrators. Because the zone is directly associated with the Shared VPC network, workloads throughout the shared network can resolve it without traversing a DNS-peering chain.

This simplifies hub-and-spoke DNS governance: there is no transitive peering-hop limit for the bound zone because the association is direct. It also removes the need for a placeholder VPC that exists only to host a service project's zone for peering.

Teaching diagram — ownership split
flowchart TB HOST[Host project: Shared VPC network] --- NET[Shared VPC] SVC1[Service project A: owns zone app-a.internal] -->|cross-project bind| NET SVC2[Service project B: owns zone app-b.internal] -->|cross-project bind| NET VM1[VM in service project A] --> NET VM2[VM in service project B] --> NET NET -->|direct private-zone visibility| SVC1 NET -->|direct private-zone visibility| SVC2

The important separation is administrative: DNS namespace ownership can remain with the service team while the host team keeps network ownership.

Design and troubleshooting

Use cross-project binding when the organization wants decentralized DNS-zone administration inside one Shared VPC. Use DNS peering when the resolver relationship is genuinely between separate VPC networks and you want one network to consult another network's namespace. If records fail to resolve, verify the target network/project association, zone visibility, authoritative suffix overlap, IAM on zone creation, and whether a more-specific private zone shadows the expected answer.

5. Zonal Cloud DNS zones for GKE

Domain 3 — Cloud DNS

What is different about a zonal zone

A zonal Cloud DNS managed zone can be scoped to one or more GKE clusters in a particular location instead of being visible to an entire VPC network. This creates a tighter DNS visibility boundary for cluster-oriented names such as cluster.local patterns when network-wide private-zone visibility would be unnecessarily broad.

Resource scope and creation

The managed zone uses private visibility, a specific location, and GKE cluster bindings. The current gcloud surface supports --gkeclusters together with --location. The scope matters operationally: commands that inspect or manage zonal resources may require the location so the intended zone is unambiguous.

gcloud dns managed-zones create my-zonal-zone \
  --description="GKE-scoped zone" \
  --dns-name=cluster.local. \
  --visibility=private \
  --gkeclusters=cluster1 \
  --location=us-east1-b

Design implications

Zonal visibility reduces accidental namespace exposure across unrelated VPC workloads. It also means troubleshooting must include the querying cluster's identity and location, not just VPC membership. If the same suffix exists in multiple visibility scopes, determine which managed zone is authoritative for the querying context before blaming CoreDNS or application caching.

Teaching diagram — cluster-scoped name visibility
flowchart LR ZA[Zonal Cloud DNS zone
cluster.local] -->|bound| GKEA[GKE cluster A] GKEA --> PODA[Pods resolve records] GKEB[GKE cluster B elsewhere] -. no binding .-> ZA VM[Ordinary VPC VM] -. not automatically network-wide .-> ZA

The visual emphasizes scope: unlike a VPC-wide private zone, a zonal zone's intended visibility is tied to configured GKE cluster bindings.

Failure scenario

If Pods in cluster A resolve the name while Pods in cluster B do not, that can be correct behavior. Check the zone's location and gkeClusters associations before modifying application DNS. If the wrong zone is returned, inspect overlapping suffixes and record sets, then query from an affected Pod to observe actual resolver behavior.

Exam memory: not every private Cloud DNS zone is VPC-wide; zonal zones can scope DNS to GKE cluster bindings and therefore change both design and troubleshooting boundaries.

Primary: gcloud dns managed-zones create.

6. GKE NodeLocal DNSCache

Domain 2 — GKE networking

Why it exists

Kubernetes workloads generate large volumes of DNS queries. Sending every lookup across the node network to a centralized DNS Service adds latency, consumes conntrack entries, and makes DNS more sensitive to packet loss or kube-dns scaling. NodeLocal DNSCache runs a local caching DNS agent on each node so repeated queries can be answered closer to Pods.

Current defaults and lifecycle

For Autopilot, NodeLocal DNSCache is enabled by default and cannot be disabled. For Standard clusters, it is enabled by default beginning with GKE version 1.34.1-gke.3720000 and later. On older Standard clusters it can be enabled with the NodeLocalDNS add-on. Enabling or disabling the feature on an existing Standard cluster requires node recreation; GKE uses the node upgrade strategy and respects maintenance policies.

gcloud container clusters update CLUSTER_NAME \
  --location=COMPUTE_LOCATION \
  --update-addons=NodeLocalDNS=ENABLED

Packet flow and caching

A Pod sends a DNS query to the cluster-configured resolver path; with NodeLocal DNSCache the node-local agent can serve cached responses or forward misses upstream to the cluster DNS provider. Because the request is handled locally first, repeated lookups reduce cross-node DNS traffic and can improve resilience during transient DNS backend stress.

Teaching diagram — local hit versus upstream miss
flowchart LR POD[Pod] --> NLD[NodeLocal DNSCache] NLD -->|cache hit| POD NLD -->|cache miss| DNS[Cloud DNS / kube-dns path] DNS --> AUTH[Authoritative DNS] AUTH --> DNS --> NLD --> POD

The performance gain comes from turning repeated DNS requests into node-local cache hits, not from replacing authoritative DNS.

Operations and failure scenario

After enabling the add-on, expect a node update event; schedule it like an infrastructure change. If only Pods on one node experience DNS latency, inspect the node-local DNS Pod/agent on that node before scaling the cluster-wide DNS service. If all nodes fail equally, move upstream: cluster DNS provider, Cloud DNS zone visibility, forwarding, or authoritative DNS.

Exam memory: NodeLocal DNSCache is a node-local performance/resilience layer, not a replacement for Cloud DNS or kube-dns authority.

Primary: Set up NodeLocal DNSCache.

7. GKE Ingress BackendConfig and FrontendConfig

Domain 3 — managed load balancing for GKE

Control-plane mapping

GKE Ingress is declarative Kubernetes configuration that drives Google Cloud Application Load Balancer resources. A Kubernetes Service maps to a load-balancer backend service; a BackendConfig custom resource modifies backend-service behavior, while FrontendConfig changes selected frontend properties such as SSL policy and HTTP-to-HTTPS redirect.

Backend health-check behavior

Load-balancer health checks are external to the cluster and are not the same object as a Kubernetes readiness or liveness probe. GKE can derive a health check from BackendConfig, from a readiness probe, or from defaults. BackendConfig gives the most deterministic control. With container-native load balancing, its health-check port must match the serving Pod's container port; with instance-group backends, it must match the Service nodePort. Custom GKE Ingress health checks support HTTP, HTTPS, or HTTP2, not gRPC.

Feature composition and limitations

BackendConfig can enable features such as Cloud Armor integration, IAP, Cloud CDN, custom health checks, timeouts, and draining depending on the supported GKE/load-balancer combination. A key limitation is that one Service/port pair consumes one BackendConfig even if multiple Ingress objects reference it; those Ingresses therefore share that backend configuration. IAP and Cloud CDN cannot be enabled together on the same backend service through one BackendConfig.

When removing a feature, deleting the field from YAML is not always enough: the controller only reconciles values that are explicitly configured. Set the relevant field to the documented empty/false state to disable a previously enabled feature.

Teaching diagram — Kubernetes objects to Google load-balancer resources
flowchart LR ING[Ingress] --> ALB[Application Load Balancer] SVC[Service port] --> BS[Backend service] BC[BackendConfig] -->|health check, Armor, IAP/CDN, timeout| BS FC[FrontendConfig] -->|SSL policy / HTTPS redirect| ALB BS --> NEG[NEG or instance-group backends] NEG --> POD[Pods]

Troubleshooting works best when you map each Kubernetes object to the Google Cloud resource it programs.

Failure scenario

If Pods are Ready but the load balancer reports them unhealthy, compare the BackendConfig health-check path, protocol, and port with the actual serving endpoint. Do not treat Kubernetes readiness as proof that the external Google health checker can reach and receive the expected response.

Exam memory: readiness probes and load-balancer health checks are related configuration inputs but distinct checks; BackendConfig controls the backend service, FrontendConfig controls supported frontend settings.

Primary: Ingress configuration. Supporting: Troubleshoot Ingress health checks.

8. Internal passthrough Network Load Balancer global access

Domain 3 — load balancing

Regional frontend, optional global client reach

An internal passthrough Network Load Balancer is still a regional load balancer even when global access is enabled. Its forwarding rule remains regional; global access changes which clients are allowed to reach that regional internal frontend. Without global access, clients generally need to be in the same region as the load balancer, including connected on-premises paths. With global access, clients can originate from any region as long as network connectivity and routing exist.

Data plane and source preservation

This is a passthrough load balancer, not a proxy. The backend receives packets with the original client source IP and the forwarding-rule IP as the destination. Backend guest configuration adds a local route so the OS accepts packets destined to the load-balancer IP. The application must bind to the forwarding-rule IP or an any-address such as 0.0.0.0/::. Responses use direct server return to the client instead of returning through a proxy.

Connected networks

Clients can arrive through VPC Network Peering, Cloud VPN, or Cloud Interconnect when route and firewall prerequisites are satisfied. If global access is disabled, VPN tunnels or VLAN attachments used by on-premises clients must align to the load balancer region. Enabling global access removes that regional-client restriction, but it does not create routes. The peer or on-prem network must still know how to reach the internal frontend and receive return traffic.

Teaching diagram — same regional frontend, wider client geography
flowchart LR EU[Client europe-west1] -->|global access enabled| VIP[Regional ILB VIP us-east1] ONP[On-prem via Interconnect in us-west1] -->|global access enabled + route| VIP VIP --> B1[Backend VM us-east1-b] VIP --> B2[Backend VM us-east1-c] B1 -->|direct server return| EU B2 -->|direct server return| ONP

Global access changes client eligibility, not backend region and not passthrough semantics.

Failure scenario

If a remote-region VM cannot connect after global access is enabled, verify the forwarding rule's allowGlobalAccess, route reachability, client ingress firewall rules on backend VMs, and whether the application is listening on the VIP/any-address. If on-prem fails, also validate learned routes and return path across VPN/Interconnect.

Exam memory: global access does not make the load balancer global; it permits cross-region clients to a regional internal frontend.

Primary: Internal passthrough Network Load Balancer overview.

9. Load-balancer SSL policies and post-quantum key exchange

Domain 6 — TLS security

Where the policy applies

An SSL policy controls TLS negotiation on the frontend connection between a client and a target HTTPS or SSL proxy. It does not configure TLS from the load balancer to the backend. Scope must match the load balancer: some target proxies use global SSL policies and regional Application Load Balancers use regional SSL policies. One target proxy can reference at most one SSL policy, while one policy can be reused by multiple compatible proxies.

Profiles and minimum versions

Google provides COMPATIBLE, MODERN, RESTRICTED, and FIPS_202205 profiles plus CUSTOM for selected TLS 1.2-and-earlier cipher suites. The minimum TLS version further constrains negotiation. FIPS_202205 requires a minimum TLS version of 1.2. Selecting minimum TLS 1.3 requires the RESTRICTED profile. CUSTOM does not control TLS 1.3 cipher selection.

If no SSL policy is attached, the load balancer behaves as though COMPATIBLE with minimum TLS 1.0 is configured. Existing established connections are not interrupted when a policy is changed; the new settings affect new TLS handshakes.

Post-quantum key exchange

SSL policies also carry a post-quantum key-exchange setting for the hybrid X25519MLKEM768 mechanism. ENABLED negotiates it with compatible TLS 1.3 clients. Google's current rollout states that DEFAULT disallows it until October 2026 and will then enable it by default; DEFERRED postpones that default until October 2027. This feature applies to frontend TLS only.

Teaching diagram — two TLS legs
flowchart LR C[Client] -->|TLS connection 1
SSL policy applies| TP[Target HTTPS/SSL proxy] TP -->|TLS/HTTP connection 2
configured separately| BE[Backend] POL[SSL policy
profile + minimum TLS + PQ mode] --> TP

The most common misconception is applying frontend SSL-policy behavior to backend TLS. They are separate connections.

Failure scenario

If older clients suddenly fail after a security hardening change, compare the client's offered protocol/cipher set against the new minimum version and profile. A RESTRICTED or FIPS policy can intentionally remove older cipher overlap. Use staged testing because the load balancer can remain healthy while only a subset of legacy clients loses TLS compatibility.

Exam memory: SSL policies constrain frontend negotiation; scope must match the target proxy, and backend TLS is configured independently.

Primary: SSL policies overview.

10. Dual-stack Cloud Interconnect VLAN attachments

Domain 4 — hybrid connectivity

Stack type and route exchange

A Dedicated or supported Partner Interconnect VLAN attachment can be IPv4-only or dual-stack IPv4/IPv6. The attachment stack type determines the user traffic families the attachment can carry. For dual-stack Dedicated Interconnect, Cloud Router can exchange IPv6 routes through a dedicated IPv6 BGP session or use MP-BGP on a single session depending on the chosen design.

Changing stack type

Changing an IPv4-only attachment to dual stack adds IPv6 addressing and, where applicable, a default-configured IPv6 BGP session that can establish when the peer is ready. Changing dual stack back to IPv4-only removes IPv6 addressing/session state and causes IPv6 packets to drop. If you need to stage the change without accepting IPv6 immediately, disable the attachment or the peer's IPv6 BGP configuration before switching.

For Dedicated Interconnect, newly created dual-stack attachments can be provisioned with --stack-type=IPV4_IPV6. Google automatically allocates an unused /125 for IPv6 peering from its documented link-local-style Interconnect range when using automatic addresses. Partner Interconnect capabilities also depend on provider mode and configuration.

Teaching diagram — dual-stack underlay
flowchart LR VPC[VPC dual-stack subnets] --> CR[Cloud Router] CR <-->|IPv4 BGP and/or MP-BGP| ONP[On-prem router] CR <-->|optional IPv6 BGP| ONP CR --- VA[VLAN attachment IPV4_IPV6] VA --- IC[Cloud Interconnect] IC --- ONP

User traffic families and BGP session families are related but not identical: MP-BGP can advertise IPv6 NLRI over an IPv4 BGP session when supported/configured.

Operational change scenario

When enabling IPv6 on an existing attachment, verify the VPC has suitable internal IPv6 subnet ranges, workloads are configured for IPv6, the attachment is dual stack, the peer router supports the selected BGP design, IPv6 routes are exchanged, and firewall policy permits the traffic. A BGP session can be up while IPv6 application traffic still fails because the VPC or peer has no usable IPv6 routes.

Exam memory: dual-stack attachment state enables IPv6 transport; BGP design then determines how IPv6 prefixes are exchanged. Downgrading to IPv4-only removes IPv6 and is traffic-affecting.

Primary: Dedicated Interconnect overview — IPv6 and stack types. Supporting: Modify VLAN attachments.

11. Internet NEGs for external backends

Domains 3 & 4 — managed and hybrid load balancing

What an internet NEG represents

An internet network endpoint group lets a Google load balancer use an endpoint reachable through the internet rather than a backend hosted in the consumer VPC. Endpoint types include INTERNET_IP_PORT and INTERNET_FQDN_PORT. Global internet NEGs contain a single endpoint; regional internet NEGs can contain many endpoints and are served by Envoy-based regional load balancers with different health-check behavior.

Global versus regional behavior

Global internet NEGs used by GFE-based external Application Load Balancers do not use centralized Google health checks in the same way as VM backends. Regional internet NEGs can use distributed Envoy health checks sourced from proxy-only-subnet addresses. This means an origin firewall that allows only traditional Google health-check ranges can still fail for regional internet NEG health probes.

Internet NEGs are useful for CDN/external-origin designs, incremental migration, or fronting a third-party service with Google load balancing. They are distinct from hybrid connectivity NEGs, which represent non-Google private IP:port endpoints reachable through Cloud VPN, Cloud Interconnect, or router appliances.

Security and origin authentication

Because the external origin is internet reachable, protect it against direct bypass. For Application Load Balancers, a custom request header with a high-entropy shared value can help the origin distinguish traffic that came through the Google load balancer, combined with appropriate origin firewall/access controls. Cloud Armor can inspect Layer 7 requests at the Google edge before they are forwarded to a supported internet-NEG backend.

Teaching diagram — edge frontend to external origin
flowchart LR U[Internet client] --> GFE[External Application Load Balancer] ARM[Cloud Armor policy] --> GFE GFE --> BS[Backend service] BS --> INEG[Internet NEG FQDN:port] INEG -->|public internet to origin| ORG[External / third-party origin] GFE -. custom origin-auth header .-> ORG

The Google edge remains the client-facing control point, while the backend endpoint is outside the VPC.

Failure scenario

If a regional external origin is marked unhealthy, check which proxy-only-subnet addresses the distributed Envoy health checks use and whether the origin permits them. If users can bypass the load balancer by contacting the origin directly, treat that as an architecture/security problem, not just an application issue.

12. Cloud Armor edge policies and network-edge protection

Domain 6 — Cloud Armor

Policy types and enforcement point

Cloud Armor distinguishes backend security policies from edge security policies. Backend policies are commonly attached to supported backend services for application-aware filtering and WAF features. Edge security policies execute earlier in the edge path for supported resources and can also be attached to backend buckets. The correct policy type matters because not every match attribute, action, or protected resource is supported by every type.

Attachment and IAM

Creating or editing security policy rules requires Compute Security Admin permissions, while attaching a policy to a backend service is a network-administration action requiring the relevant policy-use and backend-service permissions. A backend service can have one policy of each supported type attached. Policy rules are priority ordered; the highest-priority matching rule determines the action before the default rule.

Network-edge DDoS protection

Cloud Armor Enterprise extends protection beyond HTTP applications with advanced network DDoS capabilities for network load balancers, protocol forwarding, and public-IP VMs. This provides attack monitoring, mitigations, and telemetry for L3/L4 scenarios that are different from the WAF-oriented HTTP request inspection used with Application Load Balancers.

Teaching diagram — choose enforcement by traffic type
flowchart LR ATT[Attacker / client] --> EDGE[Google edge] EDGE --> EP[Edge security policy / network DDoS controls] EP --> LB[Supported load balancer] LB --> BP[Backend security policy where supported] BP --> APP[Backend application] EDGE --> NLB[Network LB / protocol forwarding / public-IP protection path]

Do not collapse all Cloud Armor features into “WAF.” Network-edge DDoS and edge-policy controls protect different layers and resource types.

Operational workflow

Roll restrictive rules in preview where supported, inspect logs, then enforce. If a legitimate request is denied, identify the exact policy type, target, priority, matching expression, and default action. For path rules, normalize case and URL encoding to reduce bypass opportunities. On GKE Ingress, remember that BackendConfig is the controller-owned integration surface; out-of-band edits can be overwritten by reconciliation.

Exam memory: Cloud Armor has distinct policy types and enforcement points. Match the policy to the protected load-balancer/resource layer and understand who owns attachment/reconciliation.

Primary: Create and manage security policies. Supporting: Advanced network DDoS protection.
