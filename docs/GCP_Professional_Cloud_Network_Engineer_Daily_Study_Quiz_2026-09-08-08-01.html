1. Shared VPC IAM: separate network ownership, security control, and workload administration

Domain 1

Problem and architecture

Shared VPC is an organizational control model, not simply subnet reuse. The host project owns the VPC network and shared subnets; attached service projects own workload lifecycles. This permits centralized networking without forcing application teams into one project.

IAM control plane

Google’s networking IAM guidance separates duties by resource scope. A central network team can receive Shared VPC Admin and Network Admin, while a separate security team can receive Security Admin. Developers need Compute Network User to consume shared subnets plus workload roles such as Instance Admin in their service projects. Workload creation permission does not automatically grant subnet-use permission.

Governance caveat

Instance administration can allow creation of resources with external IPs. If external addresses are prohibited, use organization policy in addition to IAM. Google also recommends groups for principals so staffing changes are handled by group membership rather than repeated policy edits.

Failure scenario

A developer can create a VM object but cannot select the Shared VPC subnet. Check that the service project is attached to the host, then validate Network User on the host subnet or host project and the workload role in the service project. Routing and firewall troubleshooting is premature until the attachment authorization succeeds.

2. GKE Multus + IPVLAN + Whereabouts: multiple Pod interfaces with Layer-2 adjacency

Domain 1

Use case

Some network functions and data-plane workloads need a second Pod network for traffic isolation, control/data separation, or Layer-2 adjacency. Multus is a CNI meta-plugin; it invokes IPVLAN to create secondary interfaces and Whereabouts to allocate addresses.

Interface and packet model

The normal Pod interface remains under GKE Dataplane V2. A NetworkAttachmentDefinition describes the extra network. Multus creates an interface such as net1; IPVLAN provides Layer-2 connectivity and Whereabouts allocates an address from the configured pool.

Limits and dependencies

Google documents that Pods using this Multus design cannot simultaneously use GKE built-in multi-networking. The design requires intra-Pod Layer-2 ARP resolution. By default, VPC subnets do not provide the needed ARP behavior on secondary Compute Engine interfaces; Google documents a Private Preview resolve-subnet-mask capability that requires support enrollment.

Troubleshooting

A Pod can be Running and reachable on eth0 while net1 is broken. Check the NetworkAttachmentDefinition, IPVLAN creation, Whereabouts allocation, node secondary interface, and ARP behavior. Kubernetes health over the primary interface does not prove the secondary data plane.

flowchart LR P[Pod] -->|eth0| G[GKE Dataplane V2] P -->|net1| M[Multus] M --> I[IPVLAN L2] M --> W[Whereabouts IPAM] W --> I I --> S[Secondary network]

Official documentation includes a Multus/IPVLAN/Whereabouts architecture figure; the diagram above reconstructs the same roles for study.

Remember: Multus is a dispatcher, IPVLAN is the interface mechanism, and Whereabouts is IPAM.

3. GKE multi-subnet clusters: expand future node and Pod IPv4 capacity

Domain 1

Why use it

A VPC-native cluster can outgrow its initial subnet and Pod ranges. Multi-subnet support lets the cluster attach additional VPC subnets so new node pools can consume fresh node and Pod IPv4 space without rebuilding the entire cluster.

Requirements

Google documents VPC-native GKE and version 1.30.3-gke.1211000 or later as requirements. A cluster can use up to eight additional subnets. Those subnets provide IPv4 addresses for nodes and Pods.

Important caveats

Existing node pools do not migrate when an additional subnet is added; only new node pools can use the new subnet. Added subnets cannot provide IPv6 node or Pod addresses. A secondary IPv4 range in a non-default subnet can be used by only one cluster, and ranges must not overlap any multi-network CIDRs.

Operational scenario

An operator adds a subnet but sees all current nodes remain in the original range. That is expected. Create a new node pool on the added subnet, then migrate workloads using normal draining and disruption controls.

4. Static routes: next-hop VMs, internal passthrough NLBs, tags, and failure behavior

Domain 2

Next-hop choices

Static routes can use the default internet gateway, VM instances, internal passthrough Network Load Balancers, or Classic VPN tunnels. Appliance insertion typically uses a VM or an internal passthrough NLB as next hop.

VM next hops

A forwarding VM must have IP forwarding enabled. A next-hop VM can be referenced by name/zone or a valid primary internal IPv4 or supported VM IPv6 address. Alias IP addresses are not valid next-hop VM addresses. Google does not health-check the guest forwarding function, so a route can remain selected even when the appliance is broken.

Internal passthrough NLB next hop

An internal passthrough NLB fronting gateway VMs provides health-checked distribution and supports symmetric hashing for multi-NIC appliance designs. Global access determines whether a regional NLB next hop is usable from other regions. Even if all backends are unhealthy, the static route itself remains in effect, so the operator must understand both route state and load-balancer backend state.

Failure scenario

A high-priority static route points to a stopped VM and a lower-priority route exists. Do not assume the guest failure removes the higher-priority route. Verify route selection and next-hop viability. For HA service insertion, a health-checked load-balanced next hop is generally stronger than a single VM next hop.

flowchart LR C[Client] --> R[Static route] R -->|VM next hop| V[NVA VM] R -->|ILB next hop| L[Internal passthrough NLB] L --> A1[Appliance 1] L --> A2[Appliance 2] V --> D[Destination] A1 --> D A2 --> D
Remember: Route existence is not appliance-health proof.

Primary: Static routes.

5. Cloud Router BGP timers and graceful restart

Domain 2

Why timers matter

BGP convergence is controlled by different timers for different events. The hold timer detects ordinary session failure. Graceful restart preserves learned state while a peer restarts. The stalepath timer cleans up routes that were preserved but not refreshed after the session returns.

Cloud Router maintenance

Cloud Router supports graceful restart and uses a 120-second graceful restart timer. During maintenance, a capable peer can retain learned routes while a new Cloud Router BGP task re-establishes the session. This helps separate control-plane maintenance from data-plane forwarding.

Stale route handling

After BGP returns and an End-of-RIB marker is received, stale paths that are not refreshed cannot remain forever. The stalepath behavior governs their removal.

Failure scenario

A peer logs a BGP reset during Cloud Router maintenance but applications remain healthy. That can be correct behavior when graceful restart preserves forwarding. If a peer does not support graceful restart, route withdrawal can be more disruptive. Correlate peer capabilities, BGP logs, route continuity, and application reachability.

sequenceDiagram participant P as Peer participant O as Old Cloud Router task participant N as New Cloud Router task O->>P: Graceful restart notification Note over P: Preserve learned routes N->>P: BGP re-establishes P-->>N: UPDATE / End-of-RIB Note over P: Refresh or remove stale paths
Remember: A BGP reset and a forwarding outage are not synonymous.

Primary: Manage BGP timers.

6. Cloud DNS DNSSEC: chain of trust and operational safety

Domain 3

Security property

DNSSEC authenticates DNS responses so validating resolvers can detect forged or poisoned data. It does not encrypt DNS queries.

Chain of trust

Cloud DNS signs the zone and manages DNSKEY material and rotation. The parent registry must contain a DS record authenticating the child key, normally published through the registrar. A validating resolver then verifies signatures through the chain. Enabling signing in Cloud DNS without the registrar DS does not create a complete public trust chain.

Records

DNSKEY publishes key material, RRSIG carries signatures for RRsets, and DS links the parent to the child. The operational responsibility is split: Cloud DNS handles zone signing, but the domain owner still controls registrar-side delegation.

Migration and failure

When disabling DNSSEC for a zone that remains active, remove/deactivate the registrar DS before disabling signing. Otherwise validating resolvers can mark responses bogus and return SERVFAIL. When troubleshooting, inspect the chain from root/TLD to DNSKEY/RRSIG rather than relying on a non-validating resolver.

flowchart TD R[Root trust anchor] --> T[TLD] T -->|DS| Z[Cloud DNS zone] Z --> K[DNSKEY] Z --> S[RRSIG] V[Validating resolver] --> R V --> T V --> Z V --> C[Validated answer]
Remember: DNSSEC authenticates data; registrar DS publication completes the public chain.

Primary: DNSSEC overview.

7. Service Extensions traffic extensions: programmable Application Load Balancer processing

Domain 3

Purpose

Service Extensions adds custom processing to supported Application Load Balancers. A traffic extension can use a Google-managed Wasm plugin or a user-managed callout backend implementing the ext_proc gRPC API.

Processing order

Traffic extensions run after backend service selection on the request path, so they can modify headers and payloads without normally changing which backend service was selected. For response events, extension execution is reversed.

Chains and matching

Chains use CEL expressions to select traffic. Chains are evaluated sequentially; only one chain matches a request. All extensions in the chosen chain can execute, and mutations made by one extension are visible to later extensions.

Plugins versus callouts

Plugins are Wasm modules hosted on Google-managed sandbox infrastructure near the data plane. Callouts are general-purpose gRPC services on user-managed or partner compute, providing flexibility but making the customer responsible for capacity and availability. Only one traffic extension can be attached to a forwarding rule.

Troubleshooting

If a header mutation is absent, validate the forwarding-rule attachment, CEL match, event configuration, and extension health. For callouts, also test gRPC reachability and scaling. Do not start with URL-map backend selection if the extension is correctly designed to run after service selection.

flowchart LR C[Client] --> LB[Application LB] LB --> S[Backend selection] S --> E1[Extension 1] E1 --> E2[Extension 2] E2 --> B[Backend] B --> E2 E2 --> E1 E1 --> C
Remember: Extensions are programmable hooks in the LB processing path, not a replacement for the URL map.

Primary: Configure a traffic extension.

8. Dedicated Interconnect redundancy: edge availability domains and full-stack HA

Domain 4

Physical redundancy

A redundant Dedicated Interconnect pair must be in the same metropolitan area but different edge availability domains. Two connections in the same edge domain do not provide the documented redundancy boundary.

Logical and routing redundancy

Physical diversity must be paired with redundant VLAN attachments and BGP sessions. Cloud Router provides route exchange across those attachments; route preference determines how traffic shifts after failure.

Capacity and validation

The surviving path must carry failover load. Connection groups can help verify redundancy status, but operational testing should also confirm attachment/BGP health and capacity.

Failure scenario

An enterprise buys two circuits in the same edge domain and loses both during an edge event. The lesson is that circuit count is not the same as failure-domain diversity. Validate metro, edge availability domain, VLAN attachments, Cloud Router sessions, and surviving-path throughput.

flowchart LR ON[On-prem] --> C1[Interconnect A - EAD1] ON --> C2[Interconnect B - EAD2] C1 --> V1[VLAN attachment A] C2 --> V2[VLAN attachment B] V1 --> CR[Cloud Router] V2 --> CR CR --> VPC[VPC]
Remember: HA is physical + logical + routing + capacity.

Primary: Duplicate a connection for redundancy.

9. Hybrid Application Load Balancing: Google edge to external backends

Domain 4

Use case

A global external Application Load Balancer can front workloads that remain on-premises or in another cloud. This is useful for staged migrations, active-active designs, and centralized global ingress.

Data path

The Google frontend accepts the client connection. The backend service references network endpoints representing the application backends. Private hybrid connectivity—typically Interconnect or VPN with Cloud Router—must provide reachability from Google Cloud to those endpoints.

Health and routing

Load-balancer health checks need end-to-end reachability to the external endpoints. A healthy frontend VIP and certificate prove the edge plane only. They do not prove the NEG endpoint, hybrid route, firewall, or application listener is healthy.

Failure scenario

On-prem users reach the app directly, but the global load balancer returns backend errors. Validate NEG membership, backend health, hybrid routes, Cloud Router advertisements, firewall allowances, and the health-check path from Google infrastructure to the endpoint.

flowchart LR U[Internet client] --> G[Google Front End] G --> LB[Global external ALB] LB --> N[NEG backend] N --> H[Interconnect / VPN] H --> A[On-prem or other-cloud app] HC[Health check] --> N
Remember: Frontend health and hybrid backend health are separate failure domains.

Primary: Set up a global external ALB with hybrid connectivity.

10. Cloud Interconnect observability: attachment, bundle, circuit, and optics

Domain 5

Layered monitoring

Dedicated Interconnect exposes metrics at multiple layers. VLAN attachment metrics show logical capacity and traffic. Aggregate Interconnect metrics show bundle health, traffic, errors, and congestion. Per-link metrics expose individual circuit state and optical receive/transmit power.

Why per-link metrics matter

An LACP bundle can remain UP while one member is degraded or failed. That can reduce capacity and create packet loss before the aggregate status goes down. Optical power is especially useful for identifying marginal physical-layer conditions.

Sampling caveat

Many metrics are sampled on minute-scale intervals and may not become visible immediately. Correlate metrics with Cloud Router BGP state, provider/on-prem counters, and application symptoms rather than treating one delayed sample as definitive evidence.

Failure workflow

For intermittent loss with an apparently healthy Interconnect, check VLAN attachment utilization/capacity, aggregate operational state, per-link operational state, optical levels, send/receive errors, congestion drops, and BGP stability.

11. Cloud NGFW address groups: reusable IP objects and policy propagation

Domain 6

Purpose

Address groups centralize lists of IP addresses and CIDRs so multiple firewall rules can reference one object. Membership updates propagate to referencing policies, reducing duplicated rule maintenance.

Scope and type

Address groups can be project-scoped or organization-scoped and can be global or regional. Organization-scoped groups can be used in hierarchical and network firewall policies; project-scoped groups are used by global/regional network firewall policies. Each group is IPv4 or IPv6, never both, and that type cannot be changed later.

Capacity and IAM

Capacity is selected at creation and cannot be changed later. For non-Cloud-Armor purposes, Google documents a maximum capacity of 1,000 items. The configured capacity contributes to firewall policy attribute count. Compute Network Admin can manage address groups, while Network User includes permissions to discover and use them.

Dangerous failure behavior

If a referenced address group does not exist, Google documents that the address-group filter is removed from the firewall rule. Deleting an object can therefore alter effective policy rather than simply failing closed. Treat object deletion as a security-impacting change and review effective rules immediately.

flowchart LR A[Address Group] --> R1[Rule 1] A --> R2[Rule 2] A --> R3[Rule 3] U[Membership update] --> A A -->|propagates| R1 A -->|propagates| R2 A -->|propagates| R3
Remember: Scope, immutable type/capacity, and deletion behavior matter as much as convenience.

Primary: Address groups for firewall policies.

12. DNS Armor Advanced Threat Detection: DNS telemetry as a security signal

Domain 6

Purpose

DNS Armor Advanced Threat Detection analyzes internet-bound DNS query telemetry for malicious patterns and signs of compromise. It adds detection without placing a user-managed DNS inspection appliance inline with production traffic.

Scope

A DNS threat detector can monitor VPC networks in a project and can be configured to exclude selected networks. With broad project scope, newly added VPC networks can be brought under monitoring automatically.

Detection versus enforcement

DNS Armor is observational. It analyzes DNS telemetry and surfaces threat logs. It is different from DNSSEC, which authenticates DNS answers, and different from firewall policy, which enforces allow/deny decisions on network traffic.

Failure scenario

A workload makes suspicious lookups but no finding appears. Verify that the workload VPC is within detector scope and that its queries use the monitored internet-bound DNS path. Alternative or encrypted resolver paths can change what telemetry is visible.

flowchart LR W[Workload] --> D[DNS query] D --> I[Internet-bound DNS] I --> T[DNS telemetry] T --> A[DNS Armor detector] A --> F[Threat logs] F --> S[SOC investigation]
Remember: DNS Armor detects; DNSSEC authenticates; firewall policy enforces.

Primary: Create a DNS threat detector.
