1. Network Connectivity internal ranges as an IPAM reservation primitive

Domain 1 — Designing and planning a VPC
Primary: Internal ranges · Implementation: Create and use internal ranges

Architecture and behavior

An internal range is a Network Connectivity resource that reserves an IPv4 or IPv6 CIDR in the context of a VPC before a subnet or other consumer owns that space. It is control-plane IPAM state, not a routed subnet. Usage intent communicates whether space is for VPC use, external-to-VPC use, or migration; peering behavior communicates whether the reservation is relevant to self, peer, or neither. This lets a central network team protect future address blocks and surface conflicts before deployment.

flowchart LR
A[Enterprise IP plan]-->B[Internal range]
B-->C{Usage intent}
C-->D[FOR_VPC]
C-->E[EXTERNAL_TO_VPC]
C-->F[FOR_MIGRATION]
B-->G[Overlap governance]
G-->H[Future consuming resource]

Design choices and caveats

Prefer an explicit CIDR when enterprise IPAM has already assigned space; automatic allocation is useful when Google can select from a target pool while honoring exclusions. Treat the reservation as durable architecture: properties are intentionally constrained after creation and narrowing is not a casual rollback. Current documentation also defines specific supported usage/peering combinations for IPv6 internal ranges. A reservation does not override all other overlap rules; consuming resources still have their own validation.

UseValue
Future subnet/servicePrevents accidental allocation of planned space.
MigrationProtects address ownership while resources are moved.
Peer-aware planningMakes overlap intent explicit before peering-related deployment.

Operations and scenario

Inventory reservations with gcloud network-connectivity internal-ranges list and compare them with subnets and hybrid prefixes. If an application team tries to create a subnet inside a centrally reserved migration block, the conflict is discovered before routes, firewall objects, and DNS dependencies are built around duplicate address space.

Memory anchor: internal range = reservation and overlap governance; subnet = allocated/routed address space.

2. Expanding a subnet's primary IPv4 range safely

Domain 2 — Implementing a VPC network
Primary: Create and modify VPC networks · Supporting: Subnets

Control and data plane

Primary IPv4 range expansion changes the prefix to a shorter prefix length, for example /24 to /23. Existing VM addresses are retained; the subnet route and allocatable pool become larger. This is designed to avoid renumbering existing workloads, but the architectural change is one-way: you cannot shrink the primary range back to the old prefix as a routine rollback.

flowchart LR
A[/24 subnet]-->B[Check adjacent space]
B-->C[Expand to /23]
C-->D[Larger subnet route]
D-->E[Existing IPs retained]
D-->F[New allocatable IPs]
F-->G[Update CIDR-dependent controls]

Prerequisites, dependencies, limits

Check the enlarged block against subnets, static and dynamic routes, peered networks, internal ranges, and on-premises prefixes. Proxy-only subnets have special behavior and should not be treated as ordinary workload subnets. Auto-mode networks also have documented range constraints. Expansion can be nondisruptive to established traffic while still breaking dependent controls that remain scoped to the old CIDR.

DependencyPost-change risk
Firewall/security policyOld CIDR remains narrower than the new subnet.
Hybrid route filtersLarger prefix might be rejected or overlap on-prem.
GKE authorized networksNew source IPs might not be permitted to the control plane.

Implementation and troubleshooting

Verified CLI pattern: gcloud compute networks subnets expand-ip-range SUBNET --region=REGION --prefix-length=PREFIX_LENGTH. After expansion, inspect subnet properties, effective routes, firewalls, advertisements, and any source allowlists. If old hosts work but newly allocated addresses fail, investigate dependent CIDR policy before blaming the subnet operation.

Memory anchor: expansion preserves current addresses but permanently changes the address-plan boundary.

3. GKE authorized networks for IP-based control-plane endpoints

Domain 2 — Implementing a VPC network
Primary: Network isolation · Configuration: Configure network isolation

Trust boundary and request flow

GKE can expose the Kubernetes API through DNS-based and IP-based endpoints. For IP endpoints, authorized networks create a source-CIDR reachability gate in front of API authentication and authorization. Google recommends the DNS-based endpoint for many modern deployments, but when IP access is needed, the engineer must decide public/internal endpoint exposure, authorized CIDRs, and global access behavior.

flowchart LR
A[Administrator]-->B{Endpoint choice}
B-->C[DNS endpoint]
B-->D[IP endpoint]
D-->E[Authorized CIDR check]
E--allowed-->F[API authentication / authorization]
E--denied-->G[Blocked]

Design and caveats

An internal IP endpoint reduces internet exposure but still requires correct VPC/hybrid routing. Public IP access with a narrow allowlist is workable for controlled external administration but enlarges the reachable attack surface. Authorized-network limits and exact endpoint behavior depend on current GKE versions; do not clone an old cluster's assumptions. A subnet expansion or NAT change can alter the source address seen by the API without changing the user's identity.

PatternUse
DNS endpointIdentity-centric modern access where supported.
Internal IP + authorized rangesPrivate routed operations from known source networks.
Public IP + narrow allowlistControlled external operations with higher exposure.

Verification

Documented cluster creation supports flags including --enable-dns-access, --enable-ip-access, --enable-master-authorized-networks, and --master-authorized-networks. Troubleshoot path first, then observed source IP, then CIDR match, then IAM/Kubernetes credentials. A VPN user can fail even with valid credentials if NAT translates the source outside the authorized set.

Memory anchor: authorized networks are an IP gate, not an identity system.

4. GKE Dataplane V2: eBPF service forwarding, policy, and scale

Domain 2 — Implementing a VPC network
Primary: GKE Dataplane V2

Architecture

Dataplane V2 uses eBPF with Cilium technology for Kubernetes service forwarding and NetworkPolicy enforcement. The anetd DaemonSet programs node dataplane state. Network policy is integrated and always on in this dataplane, with policy logging support. Customers do not gain permission to install arbitrary eBPF programs into Google's managed networking stack.

flowchart LR
A[Pod packet]-->B[eBPF node hooks]
B-->C{NetworkPolicy}
C--deny-->D[Drop / log]
C--allow-->E[Service endpoint map]
E-->F[Backend pod]
G[anetd]-.programs state.->B

Scale and compatibility

eBPF service maps have finite scale; current documentation calls out approximately 260,000 service endpoints across services. High endpoint churn can increase anetd CPU. Dataplane V2 is selected when creating the cluster rather than being a generic in-place toggle. Some manually assembled load-balancing patterns, fragmented traffic cases, and custom eBPF expectations are unsupported or behave differently from legacy iptables networking.

SymptomFirst investigation
anetd CPU risesEndpoint churn, service-map scale, policy updates.
Policy deny logSelector/direction logic rather than route creation.
Only fragmented flows failDocumented fragmentation/MTU constraints.

Operations

Correlate anetd health, policy logs, service endpoints, node networking, and cluster release level. Newer releases support hashing choices such as Maglev in supported service paths; evaluate memory/update tradeoffs rather than treating a hashing algorithm as a free performance switch.

Memory anchor: Dataplane V2 is a managed eBPF dataplane; troubleshoot programmed node state and policy together.

5. Application Load Balancer timeouts: request deadline, keepalive, and WebSocket behavior

Domain 3 — Configuring managed network services
Primary: Backend services · External ALB: Request distribution, timeouts and retries · Internal ALB: Internal Application Load Balancer

Timeout semantics

For HTTP/HTTPS/HTTP2 Application Load Balancers, the backend service timeout is a request/response deadline: it measures how long the load balancer allows the backend to produce the complete response after the request is sent. The common default for non-serverless backends is 30 seconds; serverless backends can have different defaults. This is different from a TCP idle timeout and different again from connection draining.

sequenceDiagram
participant C as Client
participant LB as Application LB
participant B as Backend
C->>LB: HTTP request
LB->>B: first request byte
Note over LB,B: backend-service request/response timer
B-->>LB: headers + body
LB-->>C: response

Keepalive, retries, and WebSockets

Internal ALBs distinguish client HTTP keepalive from backend HTTP keepalive; current documentation gives a 610-second default client keepalive and fixed 600-second backend keepalive. Backend server keepalive should exceed the load balancer's backend keepalive to avoid the backend winning the race with an RST. External ALB retry behavior is also method/state dependent rather than a guarantee that every failed request is retried. WebSocket connections have load-balancer-specific behavior: active WebSockets can be governed differently from ordinary backend request deadlines, while idle WebSockets can still be closed by timeout behavior.

FailureThink about
Large response truncated near a fixed intervalBackend request/response timeout.
Intermittent backend RST after idle reuseBackend server keepalive shorter than LB keepalive.
Long-lived WebSocket ends unexpectedlyMode-specific WebSocket lifetime, idle timeout, proxy maintenance.

Configuration and scenario

Use gcloud compute backend-services update ... --timeout=VALUE for supported backend services. A regional external ALB route action can override backend service timeout, so inspect URL-map policy before changing the backend service. Scenario: a report download takes 90 seconds but the backend timeout remains 30 seconds; health checks stay green while users receive partial/failed responses. Increase the request deadline only after confirming application behavior and retry semantics.

Memory anchor: request timeout, TCP keepalive, WebSocket lifetime, and connection draining are four different timers.

6. Application Load Balancer LONG traffic duration and IN_FLIGHT balancing

Domain 3 — Configuring managed network services
Primary: Backend services

Why concurrency can be the right signal

For fast homogeneous requests, arrival rate can approximate backend load. Streams, uploads, long RPCs, and other long-lived transactions consume resources for longer, so concurrency is often the better pressure signal. Supported modern Application Load Balancers can describe backend traffic duration as SHORT or LONG and use IN_FLIGHT balancing so active requests—not just requests per second—drive distribution.

flowchart LR
A[Requests]-->B[Application LB]
B-->C{Balancing signal}
C-->D[RATE: arrivals/sec]
C-->E[IN_FLIGHT: active work]
E-->F[Backend with concurrency headroom]

Backend support and capacity

Balancing mode and target-capacity controls apply only to supported backend types such as instance groups and appropriate zonal NEGs. Serverless, internet, and PSC NEGs follow different backend models. Target capacity is a distribution input, not a strict circuit breaker: if every backend is beyond target, the system can still distribute requests rather than simply refusing all traffic.

WorkloadSignal
Short similar HTTP callsRATE can approximate pressure.
Long streams/RPCsIN_FLIGHT models occupancy.
Serverless NEGUse controls supported by that backend model.

Operations and scenario

A documented backend-add workflow supports --traffic-duration=LONG where compatible. Observe in-flight requests together with latency, utilization, queue depth, and health. If two zones receive equal RPS but one carries many long streams, RATE says “balanced” while concurrency says “saturated.”

Memory anchor: select the load-balancing signal that represents the resource being exhausted.

7. Carrier Peering: what it does, and why it is not Cloud Interconnect

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Carrier Peering overview

Purpose and architecture

Carrier Peering lets an enterprise use a service provider to reach Google applications—classically Google Workspace—over provider connectivity to Google's edge. It is not a private VPC attachment and does not create custom routes inside a VPC. If Google Cloud workloads use Carrier Peering, traffic still exits the VPC through ordinary next hops such as the default internet gateway or another routed construct; Carrier Peering exists outside the VPC control plane.

flowchart LR
A[Enterprise]-->B[Service provider]
B-->C[Carrier Peering]
C-->D[Google edge / Google applications]
E[GCP VPC]-.no Carrier-Peering VPC custom routes.->F[Default internet gateway or other VPC next hop]

Decision criteria

Carrier Peering fits enterprises that primarily need service-provider-assisted, higher-quality access to Google applications without operating their own direct peering edge. For private connectivity to Google Cloud VPC workloads through a provider, Partner Interconnect is generally the relevant product. Dedicated Interconnect is the direct physical Cloud Interconnect model. Direct Peering is a separate direct relationship with Google's edge and was covered in an earlier daily report, so today's lesson focuses on the carrier-mediated Google-application use case.

NeedTypical fit
Google applications through a providerCarrier Peering.
Private VPC connectivity through a providerPartner Interconnect.
Direct private VPC circuitDedicated Interconnect.

Security, HA, troubleshooting

Work with the provider on redundancy, routing policy, edge location, and SLA characteristics. Do not troubleshoot Carrier Peering by searching a VPC routing table for a magically injected carrier route; the service does not create one. Scenario: an engineer expects a private RFC1918 path from on-premises to a VPC because Carrier Peering is active. That requirement is a product-selection error—use an Interconnect/VPN design for VPC private routing.

Memory anchor: Carrier Peering improves access to Google applications; Cloud Interconnect attaches private networks to VPC routing.

8. Cloud VPN MTU, IPsec overhead, prefragmentation, and TCP MSS

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Cloud VPN MTU considerations · Supporting: Advanced Cloud VPN configuration

Packet transformation

Cloud VPN documents a 1460-byte MTU for the inner path. IPsec adds outer IP/ESP overhead, so a packet that is too large must be reduced or fragmented before encryption as supported by the peer path. Cloud VPN is not designed around fragmenting an already encapsulated ESP packet as the normal recovery mechanism. Path MTU Discovery and TCP MSS therefore directly affect whether applications generate packets that fit.

flowchart LR
A[Inner packet]-->B{Fits effective tunnel payload?}
B--yes-->C[IPsec encapsulation]
B--no-->D[Endpoint reduces size / peer prefragments]
D-->C
C-->E[Encrypted underlay]
E-->F[Decrypt / deliver]

Design interactions

PMTUD requires useful ICMP behavior. MSS clamping can help TCP endpoints negotiate a smaller segment size, but it does not solve large UDP datagrams. Jumbo-capable underlays do not automatically turn HA VPN payloads into jumbo paths; encrypted-path constraints still apply.

SymptomDirection
Small ping works, large payload failsMTU/PMTUD/ICMP.
TCP fixed by MSS clampOriginal TCP payload exceeded effective path size.
UDP still failsMSS is TCP-only; fix packet sizing/fragmentation.

Troubleshooting

Compare host MTU, peer/tunnel settings, DF behavior, ICMP filtering, and packet captures on both sides. A tunnel can be UP and BGP can be stable while large application payloads black-hole. Distinguish route adjacency from packet-size viability.

Memory anchor: tunnel health proves adjacency; MTU proves whether real payloads fit.

9. Modern Load Balancing operations: resource topology plus audit history

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Cloud Load Balancing release notes · Architecture: Load balancing overview

Operational model

The modern load-balancing console exposes a component-oriented inventory and interactive topology so operators can trace a frontend through forwarding rules, proxies/routing configuration, backend services, and backends. Audit-log integration answers a separate control-plane question: who changed the resource graph and when? This is especially useful when healthy backends are attached to the wrong routing component.

flowchart LR
A[Forwarding rule]-->B[Target proxy]
B-->C[URL map / route selection]
C-->D[Backend service]
D-->E[Backends]
F[Audit logs]-.change history.->A
F-.change history.->C

Evidence separation

EvidenceQuestion
Resource topologyAre control-plane components connected as intended?
Health/traffic metricsIs the serving path healthy and receiving traffic?
Audit logsWho changed configuration and when?

Do not use one evidence type to answer every problem. Backend health cannot explain a host rule that points at the wrong matcher, and audit history cannot prove current latency.

Scenario

After maintenance, clients receive 404s while every backend reports healthy. Topology confirms the forwarding rule and proxy, then reveals the host/path mapping points to the wrong backend service. Audit history identifies the configuration edit. Recreating VMs would have added risk without touching the root cause.

Memory anchor: proxy load balancers are resource graphs; troubleshoot graph linkage, runtime health, and change history separately.

10. Cloud Router route-scale troubleshooting: quotas, dropped prefixes, and max-prefix resets

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Cloud Router quotas and limits · Routes: Troubleshoot BGP routes · Sessions: Troubleshoot BGP sessions

Two different scale failure modes

Cloud Router has quota on assured unique learned destinations applied per region/VPC context. In global dynamic routing mode, from-own-region and from-other-regions usage can be distinct. When learned-route quota is exhausted, routes can be dropped and connectivity can become intermittent even though the BGP session itself remains established. Separately, if an on-premises peer sends more than 5,000 prefixes to a BGP session, Cloud Router can close the session with a max-prefix notification and require corrective action before peering is re-enabled.

flowchart TD
A[BGP advertisements]-->B{Per-session prefixes > 5000?}
B--yes-->C[Session CEASE / MAX_PREFIXES_REACHED]
B--no-->D[Learned routes]
D-->E{Unique-destination quota exceeded?}
E--yes-->F[Some routes DROPPED / quota events]
E--no-->G[Routes ACTIVE]

Metrics, logs, and route status

Use Cloud Router status to inspect peer state, learned routes, and routeStatus such as ACTIVE or DROPPED. Current documentation describes quota metrics including used unique destinations, unique-destination limit, and whether destinations were dropped. Route quota events are logged, with warnings beginning before hard exhaustion. The important diagnostic split is “session down” versus “session up but route rejected/dropped.”

SymptomLikely scale cause
BGP peer shuts and log says MAX_PREFIXES_REACHEDPer-session advertisement exceeded 5,000 prefixes.
BGP remains UP, selected destinations vanishLearned unique-destination quota may be exhausted.
Quota rising toward limitSummarize prefixes and/or plan quota increase before impact.

Remediation

Aggregate routes at the source when architecture allows, remove accidental deaggregation, monitor quota metrics, and request quota increases early. For a max-prefix shutdown, reduce received advertisements and then disable/re-enable the peer as documented. Do not treat “BGP Established” as proof that every intended route is installed.

Memory anchor: peer state, received-prefix count, and installed-route quota are separate gates.

11. Migrating classic VPC firewall rules to global network firewall policies

Domain 6 — Cloud network security
Primary: Migration overview · Workflow: Without dependencies · Dependencies: With dependencies

Staged control-plane migration

The migration tool creates a global network firewall policy and translated rules; it does not silently attach the policy and erase the legacy rules. That separation is the rollback boundary. Review translated priority, direction, action, target identity, logging, and dependency semantics before association.

flowchart LR
A[VPC firewall rules]-->B[Migration conversion]
B-->C[Global network firewall policy]
C-->D[Review priorities / targets / logging]
D-->E[Associate + choose enforcement order]
E-->F[Test effective firewalls + logs]
F-->G[Disable legacy rules]
G-->H[Delete after rollback window]

Priority and identity translation

When source rules share priority, migration creates deterministic policy ordering while preserving intended behavior; documented handling gives deny precedence when same-priority allow/deny rules must be disambiguated. Service-account and network-tag targets can require secure-tag/IAM-aware dependency handling. Administrator-owned VPC rules and GKE-created rules should not be assumed to share the same migration lifecycle.

PhaseValidation
ConvertRules, priorities, targets, logging.
AssociatePolicy attachment and enforcement order.
Cut overEffective rules, logs, real traffic, rollback.

Verified commands and scenario

Documented patterns include gcloud beta compute firewall-rules migrate --source-network=NETWORK_NAME --target-firewall-policy=POLICY_NAME, gcloud compute network-firewall-policies associations create, optional network enforcement-order updates, and gcloud compute networks get-effective-firewalls NETWORK_NAME. If a workload breaks because a secure-tag target was not bound as expected, roll back association/order and fix the identity dependency rather than broadening CIDRs.

Memory anchor: successful object conversion is not successful security migration; validate effective behavior.

12. Application Load Balancer configuration-size quota and URL map quota units

Domain 3 — Configuring managed network services
Primary: Load Balancing quotas and limits · Change history: Release notes

Object size versus active configuration

Modern Application Load Balancers can use a newer configuration-size quota model. For projects using it, applicable modern URL maps can reach the documented 1 MB class while classic ALB limits remain smaller; projects without the newer model retain the documented legacy limits. More importantly, active quota consumption is not simply “bytes in one URL map.” Rule complexity and active references through proxies/forwarding rules contribute to configuration quota.

flowchart LR
A[Forwarding rules]-->B[Target proxy]
B-->C[URL map]
C-->D[Hosts / paths / route rules]
D-->E[Backends]
A-.active references.->F[Configuration quota]
C-.complexity.->F

Scope and planning

Quota scope varies with load-balancer family: a global external design is accounted differently from regional or VPC-scoped internal designs. Platform teams that centralize many frontends on reusable routing configuration should therefore track both per-object size and active configuration usage.

QuestionWhy it matters
Classic or modern ALB?Different limits/models apply.
How many frontends activate the map?References can multiply active usage.
What quota scope applies?Capacity planning must match global/regional/VPC scope.

Operations and scenario

Make quota checks part of CI/CD for generated URL maps. A map can remain below its individual size limit while deployment fails because multiple active frontends push aggregate configuration usage over quota. Monitor usage before a routing expansion, and modularize policies where that improves operational scale.

Memory anchor: count configuration activation, not only file size.
