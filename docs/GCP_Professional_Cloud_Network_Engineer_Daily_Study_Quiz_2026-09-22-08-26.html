1. Network Connectivity internal ranges as an IPAM reservation primitive

Domain 1 — Designing and planning a VPC
Primary: Internal ranges · Implementation: Create and use internal ranges

Architecture and behavior

An internal range reserves an IPv4 or IPv6 CIDR in the context of a VPC before a subnet or another consuming resource owns that space. It is control-plane IPAM state, not a routed subnet. Usage intent communicates whether space is for VPC use, external-to-VPC use, or migration; peering disposition communicates whether the reservation is relevant to self, peer, or neither. Central network teams can therefore protect future blocks and surface overlap before application resources exist.

flowchart LR
A[Enterprise IP plan]-->B[Internal range]
B-->C{Usage intent}
C-->D[FOR_VPC]
C-->E[EXTERNAL_TO_VPC]
C-->F[FOR_MIGRATION]
B-->G[Overlap governance]
G-->H[Future consuming resource]

Design choices, caveats, security

Use an explicit CIDR when enterprise IPAM already assigns deterministic space; automatic allocation is useful when Google can choose from a target pool while honoring exclusions. Treat reservations as durable architecture: mutation is intentionally constrained and narrowing is not a casual rollback. Current documentation defines supported usage/peering combinations for IPv6 internal ranges. A reservation does not override the consuming resource's own overlap and permission checks.

UseWhy it helps
Future subnet/servicePrevents accidental allocation of planned address space.
MigrationProtects ownership while resources move.
Peer-aware planningMakes overlap intent explicit before connectivity is built.

Operations and failure scenario

Inventory with gcloud network-connectivity internal-ranges list and reconcile against subnet and hybrid-prefix inventories. If an application team tries to create a subnet inside a centrally reserved migration block, the conflict is discovered before routes, firewall objects, and DNS dependencies are built around duplicate space.

Exam anchor: internal range = reservation/overlap governance; subnet = allocated and routed address space.

2. Expanding a subnet primary IPv4 range safely

Domain 2 — Implementing a VPC network
Primary command reference: gcloud compute networks subnets expand-ip-range

Control-plane and packet impact

Primary IPv4 range expansion moves to a shorter prefix length, such as /24 to /23. Existing interface addresses remain; the subnet route and allocatable pool become larger. This avoids workload renumbering, but the address-plan change is effectively one-way: primary ranges cannot be casually shrunk back after expansion.

flowchart LR
A[/24 subnet]-->B[Check adjacent space]
B-->C[Expand to /23]
C-->D[Larger subnet route]
D-->E[Existing IPs retained]
D-->F[New IP capacity]
F-->G[Update CIDR-dependent controls]

Dependencies and caveats

Before executing, compare the enlarged block with subnets, static/dynamic routes, peered networks, internal ranges, and on-premises prefixes. Auto-mode networks and proxy-only subnets have specific constraints. A control-plane expansion can be nondisruptive to current flows while security and hybrid controls remain scoped to the old range.

DependencyRisk
Firewall/policy CIDRNew source addresses are outside old rule scope.
Hybrid route filtersLarger prefix can be rejected or overlap.
GKE authorized networksNew IPs might not reach an IP-based control plane.

Configuration and troubleshooting

Verified command pattern: gcloud compute networks subnets expand-ip-range SUBNET --region=REGION --prefix-length=PREFIX_LENGTH. Verify the new prefix, effective routes, policy CIDRs, advertisements, and source allowlists. If old addresses work and new ones fail, look for stale dependent CIDRs before blaming VPC forwarding.

Exam anchor: expansion preserves existing IPs but permanently moves the address-plan boundary.

3. GKE authorized networks for IP-based control-plane endpoints

Domain 2 — Implementing a VPC network
Primary: Customize network isolation in GKE

Trust boundary and request flow

GKE supports DNS-based and IP-based control-plane endpoints. For IP-based access, authorized networks create a source-CIDR gate before Kubernetes API authentication and authorization. Current guidance favors DNS-based access for many modern deployments, but when IP access is required the design must choose public/internal exposure, authorized CIDRs, Google Cloud public-IP access, and global private-endpoint reachability.

flowchart LR
A[Admin source]-->B{Endpoint}
B-->C[DNS endpoint]
B-->D[IP endpoint]
D-->E[Authorized CIDR check]
E--allow-->F[API authn/authz]
E--deny-->G[Blocked]

Configuration choices and limits

--enable-master-authorized-networks restricts the public IP endpoint to listed CIDRs; --enable-authorized-networks-on-private-endpoint can enforce the same concept on the internal endpoint. --enable-private-endpoint disables external IP endpoint access, while --enable-master-global-access controls private endpoint access from other regions. Current documentation allows up to 100 authorized ranges in the modern model. Be careful with dynamic client IPs and NAT because the API evaluates the observed source address.

PatternUse
DNS endpoint onlyStrong identity-centric control and simpler IP operations.
Internal IP + authorized CIDRsPrivate routed operators from known ranges.
Public IP + narrow CIDRsControlled external access with higher exposure.

Verification and scenario

Use gcloud container clusters describe CLUSTER_NAME and inspect controlPlaneEndpointsConfig. Scenario: a VPN user has valid IAM but access fails after a NAT change; the translated IP no longer matches the allowlist. Fix source-policy alignment rather than changing Kubernetes RBAC.

Exam anchor: authorized networks are an IP reachability gate, not an identity system.

4. GKE Dataplane V2: eBPF forwarding, NetworkPolicy, and scale

Domain 2 — Implementing a VPC network
Primary: GKE Dataplane V2

Architecture

Dataplane V2 uses eBPF with Cilium technology for Kubernetes service forwarding and NetworkPolicy enforcement. The anetd DaemonSet programs node dataplane state. Network policy is integrated and enabled as part of the dataplane, with policy logging support. This is managed eBPF; it does not imply that customers can load arbitrary eBPF programs into the GKE network stack.

flowchart LR
A[Pod packet]-->B[eBPF node hooks]
B-->C{NetworkPolicy}
C--deny-->D[Drop / log]
C--allow-->E[Service endpoint map]
E-->F[Backend pod]
G[anetd]-.programs state.->B

Scale and compatibility

Service maps are finite; current documentation calls out roughly 260,000 service endpoints across services. Very high endpoint churn can drive anetd CPU. Dataplane V2 is a cluster-creation choice rather than a generic in-place toggle. Some manually assembled load-balancing patterns, fragmented traffic cases, and custom eBPF expectations are unsupported or differ from legacy iptables networking.

SignalInvestigate
anetd CPU spikeEndpoint churn, service-map scale, policy updates.
Policy deny logSelectors and direction before routes.
Fragment-only failureDocumented fragmentation/MTU behavior.

Operations

Correlate anetd health, policy logs, endpoint count, node networking, and release version. Newer supported service paths can use consistent hashing such as Maglev; evaluate its memory/update tradeoffs rather than treating it as a free optimization.

Exam anchor: troubleshoot the programmed node dataplane and policy layer together.

5. Application Load Balancer backend timeout, keepalive, retry, and WebSocket semantics

Domain 3 — Configuring managed network services
Primary: External ALB request distribution, timeouts and retries · CLI: backend-services update

Four timers that engineers confuse

For HTTP/HTTPS/HTTP2 Application Load Balancers, backend service timeout is a request/response deadline: the backend must return the complete HTTP response in the allowed time. The common default for non-serverless backends is 30 seconds. This is not the same as connection draining, HTTP keepalive, or a WebSocket's active/idle lifetime.

sequenceDiagram
participant C as Client
participant LB as ALB proxy
participant B as Backend
C->>LB: request
LB->>B: first request byte
Note over LB,B: request/response deadline
B-->>LB: headers + body
LB-->>C: response

Retry and long-connection behavior

Retry behavior is conditional: an HTTP GET can be retried in specific cases before response headers arrive, but not every failed request is safely retried. Regional external ALB route actions can override backend service timeout. Active WebSockets on modern global/regional ALBs are not always governed like ordinary request deadlines; idle WebSockets can still be closed by timeout behavior and proxy maintenance creates practical lifetime limits.

SymptomCheck
Response truncates near fixed timeRequest/response timeout.
Idle reused connections resetProxy/backend keepalive ordering.
WebSocket endsALB mode, active/idle semantics, maintenance.

Configuration scenario

Use gcloud compute backend-services update ... --timeout=VALUE where supported. If a report takes 90 seconds but timeout is 30 seconds, health checks can remain green while requests fail. Increase the request deadline only after confirming application behavior, route-action overrides, and retry expectations.

Exam anchor: request deadline, keepalive, WebSocket lifetime, and connection draining are distinct.

6. LONG traffic duration and IN_FLIGHT balancing for long-running requests

Domain 3 — Configuring managed network services
Primary command reference: backend-services add-backend

Why arrival rate is not always load

Short homogeneous calls often correlate well with requests per second. Streams, uploads, and long RPCs consume backend capacity for much longer, so active concurrency is the more meaningful pressure signal. For supported managed HTTP(S) backend services, IN_FLIGHT spreads load according to in-progress requests and requires --traffic-duration=LONG together with a maximum in-flight target.

flowchart LR
A[Requests]-->B[Managed LB]
B-->C{Signal}
C-->D[RATE: requests/sec]
C-->E[IN_FLIGHT: active work]
E-->F[Backend with concurrency headroom]

Compatibility and capacity

Current CLI documentation limits IN_FLIGHT to managed load-balancing schemes and HTTP/HTTPS/HTTP2. It is not available for internet or serverless NEG endpoint types. Target capacity is an allocation signal rather than a universal circuit breaker; when all eligible backends are pressured, traffic can still be distributed according to the product's serving logic.

WorkloadSignal
Short similar requestsRATE can model pressure.
Long streams/RPCsIN_FLIGHT models occupancy.
Serverless/internet NEGUse controls supported by that backend model.

Operations

Monitor in-flight count with latency, utilization, health, and application queues. If two zones have equal RPS but one carries many long streams, a rate metric can call them balanced while concurrency shows one is saturated.

Exam anchor: choose a balancing signal that represents the scarce backend resource.

7. Carrier Peering: provider-mediated access to Google applications, not VPC routing

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Carrier Peering overview

Architecture and intended use

Carrier Peering lets an enterprise use a service provider for enterprise-grade connectivity to Google applications such as Google Workspace. It exists outside the Google Cloud VPC routing control plane. When Google Cloud resources are involved, Carrier Peering does not create custom VPC routes; VPC packets still use their actual VPC next hops such as the default internet gateway or another connectivity service.

flowchart LR
A[Enterprise]-->B[Service provider]
B-->C[Carrier Peering]
C-->D[Google edge / applications]
E[GCP VPC]-.no Carrier-Peering custom VPC routes.->F[Normal VPC next hop]

Product selection

Use Carrier Peering when the requirement is improved provider-based access to Google applications without operating your own direct peering edge. If the requirement is private routed connectivity to VPC workloads through a service provider, Partner Interconnect is the normal fit. Dedicated Interconnect supplies a direct physical private connection, while Direct Peering is a separate direct relationship to Google's edge.

RequirementTypical product
Google apps via providerCarrier Peering.
Private VPC via providerPartner Interconnect.
Direct private VPC circuitsDedicated Interconnect.

HA, security, troubleshooting

Redundancy, provider edge design, route policy, and service SLA are coordinated with the provider. If an engineer expects RFC1918 VPC routes to appear because Carrier Peering is active, the root problem is product selection, not Cloud Router convergence.

Exam anchor: Carrier Peering is for Google applications; Cloud Interconnect/VPN solve private VPC routing.

8. Cloud VPN MTU, IPsec overhead, prefragmentation, and TCP MSS

Domain 4 — Hybrid and multi-cloud interconnectivity
Primary: Cloud VPN MTU considerations · Supporting: Advanced Cloud VPN configuration

Packet transformation

Cloud VPN documents a 1460-byte inner-path MTU. IPsec adds outer IP and ESP overhead, so an oversized packet must be reduced or fragmented before encryption according to supported peer behavior. Cloud VPN is not designed around fragmenting an already encapsulated ESP packet as the normal recovery method. PMTUD and TCP MSS directly affect whether workloads generate packets that fit.

flowchart LR
A[Inner packet]-->B{Fits effective payload?}
B--yes-->C[IPsec encapsulation]
B--no-->D[Endpoint reduces / peer prefragments]
D-->C
C-->E[Encrypted underlay]
E-->F[Decrypt + deliver]

Protocol interactions

PMTUD needs useful ICMP signaling. MSS clamping can keep TCP segments small enough but does not control all UDP datagrams. A jumbo-capable Interconnect underlay does not automatically make an encrypted VPN payload a jumbo path; encryption retains its own overhead and limits.

SymptomDirection
Small packets work, large failMTU/PMTUD/ICMP.
TCP fixed by MSS clampOriginal TCP payload too large.
UDP still failsMSS is TCP-only.

Troubleshooting

Compare endpoint MTU, peer/tunnel settings, DF behavior, ICMP filtering, and captures on both sides. An UP tunnel with stable BGP proves adjacency, not payload viability.

Exam anchor: tunnel state and packet-size viability are separate dimensions.

9. External Application Load Balancer statusDetails: finding the real owner of a 5xx

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Global external ALB logging and monitoring · Metrics: Load balancing metrics

Why HTTP status alone is insufficient

An external Application Load Balancer log includes statusDetails, which explains why the proxy emitted or relayed an HTTP response. A 502/503 can mean backend timeout, backend connection closure, corrupt response headers/body, policy enforcement, or another proxy-path condition. response_sent_by_backend is a strong clue that the backend application itself supplied the response.

flowchart LR
A[Client request]-->B[External ALB]
B-->C[Backend]
C-->B
B-->D[Request log]
D-->E[HTTP status]
D-->F[statusDetails]
F-->G[Proxy / backend / policy root-cause branch]

Metrics and optional fields

Cloud Monitoring exposes request counts and latency distributions with labels such as response code/class, protocol, matcher, and load-balancing scheme depending on load-balancer type. Optional log fields can expose forwarding rule, target proxy, and URL map names. Correlating statusDetails with backend latency and routing labels helps distinguish “backend slow,” “backend returned error,” and “proxy never got a valid response.”

EvidenceUse
response_sent_by_backendBackend generated the response.
backend_timeoutBackend missed the proxy deadline.
Backend latency metricQuantifies proxy-to-backend response time.

Scenario

Users report 503s. Health checks are green. Logs show backend_timeout and latency rising toward the configured request deadline. The correct investigation is backend processing and timeout sizing—not firewall policy, because the load balancer reached the backend and waited.

Exam anchor: HTTP code tells you what the client saw; statusDetails tells you why the load balancer produced it.

10. Cloud Router route-scale troubleshooting: quota drops versus max-prefix session shutdown

Domain 5 — Managing, monitoring, and troubleshooting
Primary: Cloud Router quotas and limits · Routes: Troubleshoot BGP routes · Sessions: Troubleshoot BGP sessions

Two independent scale gates

Cloud Router has limits on assured unique learned destinations applied in a regional VPC context; in global dynamic routing mode, own-region and other-region usage can be distinct. When unique-destination quota is exhausted, routes can be DROPPED while the BGP session stays Established. Separately, if an on-premises peer advertises more than 5,000 prefixes on a session, Cloud Router can send a CEASE/MAX_PREFIXES_REACHED notification and close that session until the source advertisements are reduced and the peer is reset.

flowchart TD
A[BGP advertisements]-->B{Session prefixes > 5000?}
B--yes-->C[Session shutdown: MAX_PREFIXES_REACHED]
B--no-->D[Learned routes]
D-->E{Unique-destination quota exceeded?}
E--yes-->F[Some routeStatus = DROPPED]
E--no-->G[ACTIVE routes]

Logs and metrics

Inspect Cloud Router status for peer state, learned-route count, and routeStatus. Current docs describe unique-destination usage/limit metrics and route-quota event logs, including warnings before hard exhaustion. Diagnose “session down” separately from “session up, route missing.”

SymptomLikely cause
MAX_PREFIXES_REACHED and peer downPer-session >5,000 received prefixes.
Peer UP, some routes DROPPEDUnique-destination route quota.
Usage nearing limitSummarize or raise quota before impact.

Remediation

Aggregate routes at the source where architecture permits, remove accidental deaggregation, monitor quota, and request increases early. For a max-prefix shutdown, reduce advertisements then disable/re-enable the peer as documented.

Exam anchor: BGP state, received-prefix ceiling, and installed-route quota are separate gates.

11. Migrating classic VPC firewall rules to global network firewall policies

Domain 6 — Cloud network security
Primary: Migration overview · Workflow: Rules without dependencies · Dependencies: Rules with dependencies

Staged migration model

The migration workflow creates translated rules in a global network firewall policy; it does not silently attach the policy and delete the legacy rules. That separation is a rollback boundary. Review priority, direction, action, logging, target identity, and dependencies before enforcement changes.

flowchart LR
A[VPC firewall rules]-->B[Migration conversion]
B-->C[Global network firewall policy]
C-->D[Review priority / targets / logs]
D-->E[Associate + enforcement order]
E-->F[Test effective firewalls]
F-->G[Disable legacy]
G-->H[Delete after rollback window]

Priority and identity dependencies

When source rules share a priority, conversion must create deterministic policy ordering while preserving intended behavior; documented handling gives deny precedence where same-priority allow/deny rules need disambiguation. Service-account and network-tag rules can require secure-tag/IAM-aware handling. GKE-managed rules have their own lifecycle and should not be treated like ordinary administrator rules.

PhaseValidate
ConvertRule semantics, priorities, targets, logging.
AssociatePolicy attachment and enforcement order.
Cut overEffective rules, logs, traffic, rollback.

Verified commands and failure scenario

Use the documented migration pattern gcloud beta compute firewall-rules migrate --source-network=NETWORK_NAME --target-firewall-policy=POLICY_NAME, policy association commands, and gcloud compute networks get-effective-firewalls NETWORK_NAME. If a secure-tag target is missing after association, roll back association/order and fix the identity dependency rather than broadening network ranges.

Exam anchor: successful object conversion is not successful security migration; prove effective behavior.

12. Application Load Balancer configuration-size quota and active URL-map usage

Domain 3 — Configuring managed network services
Primary: Load Balancing quotas and limits

Individual object size versus active configuration

Applicable modern Application Load Balancers can use a newer configuration-size quota model. Under that model, modern URL maps can reach the documented 1 MB class while classic ALB limits remain smaller; projects without the newer model retain the documented legacy constraints. Active quota usage is not merely “bytes in a URL map”: rule complexity and active references through target proxies and forwarding rules can increase consumption.

flowchart LR
A[Forwarding rules]-->B[Target proxy]
B-->C[URL map]
C-->D[Hosts / paths / route rules]
D-->E[Backends]
A-.active references.->F[Configuration quota]
C-.complexity.->F

Scope and planning

Quota scope varies with load-balancer family. Global external, regional external, cross-region internal, and regional internal designs are accounted at their documented project/region/VPC scopes. A platform with many frontends reusing one large map must therefore track individual map size and active configuration quota.

QuestionWhy it matters
Classic or modern ALB?Different configuration limits can apply.
How many active frontend references?References can multiply active usage.
What quota scope?Capacity planning must match product scope.

Operations and scenario

Include quota checks in CI/CD for generated URL maps. A map can remain below its individual limit while a deployment fails because multiple active frontends push aggregate configuration usage beyond quota. Modularize route configuration and request quota changes before rollout where appropriate.

Exam anchor: count active configuration, not only raw object bytes.
